# dsh-eval

English | [中文](README.md)

**The web-eval orchestrator: the dataseek contract schemas, plan/condition validation, deterministic condition & scoped-home hashing, run-template generation from a dataset-suite manifest, and the stage-one/two run loop (per-cell materialization, byte-exact delegation, submit/transition, the archive gate, bundle export).** Starting a run is a human action (`/eval run` — the invoking session is the parent of every delegation); the two MECHANICAL verdict sources (probes writing `script`, blind LLM judging writing `llm-draft`) land with T9, while `human-final` stays a person's act. No sibling-plugin dependencies: the four upstream services (`datasets` / `mission` / `localAgent` / `lab`) are probed per run via `ctx.get`, and a missing one is a refusal naming it — never a boot failure. The first three are needed by every run; `lab` is needed only when the plan carries a `unit` segment (the container path) — without one the run works in host directories, and the refusal says so ("mount the dsh-lab plugin, or drop the unit segment").

The model-facing surface is five read tools, one draft verb and one analysis door (see "Model tools"); run, finalize, and annotation are never offered to the model.

`report` turns a mission export bundle into results.jsonl + summary.md (see "The report"); it only reads the bundle and consumes no host capability.

## What it owns

Three contract schemas plus one lock record (full text in [dataset-authoring-protocol §6](../../docs/dataset-authoring-protocol.md); in code they live in the single `src/schema.ts` module, and tests pin doc and code against drift):

| Schema | What it is |
|---|---|
| `dataseek.condition/1` | The subject under test: harness, model declaration, permissions (per-harness vocabulary), scoped-home hash, env key names |
| `dataseek.plan/1` | All inputs of one run: items × conditions × reps × stages × order × budget × judge × expected verdict sources |
| `dataseek.verdict/1` | Verdict output: the format both probes and judges emit |
| `dataseek.condition-lock/1` | The material record of a condition hash and its scoped home; a plan's shas resolve from here |

The validator follows the field decisions I1 froze: null in a condition's nullable fields (`harness.version`, `model.declared`, `model.endpoint`, `home.sha`) means "unresolved", listed as a warning; `plan.conditions` carries condition IDs, shas resolve from `conditions/<id>.lock.json`, a missing lock means "not ready" (also a warning — blocking belongs to the pre-run readiness gate); `judge` may be absent, and when it is, `expectedNs` must not contain `llm-draft`; a plan carries no template field.

## Template generation: manifest → run template

The run template is never hand-written by a person or an agent: it is a deterministic function of the dataset-set `manifest.yml` (`generateTemplate`), and tests pin it item-for-item equivalent to the I1 hand-written `templates/bench-v1.json`:

```text
pending → ws-ready → stage-1 → … → judged → archived → releasable → released
                          └→ halted (halt_on fired) → archived
```

- The earliest transition carries the run-meta schema-check (`schemas/run-meta.json`: `datasetId` + `commit`), pinning the snapshot into the state machine;
- every stage's OUTGOING edge carries a schema-check on that stage's structured schema (the `schemas/<stage>.json` file the manifest's `output_schema.<stage>.structured` references; the retired inline draft notation is refused on sight);
- a stage declaring `halt_on` gains a `→ halted` edge whose guard points at the conventional `schemas/<stageId>-halted.json` file (the const check lives in the schema file);
- entering `releasable` carries the file-check (`archive/workspace/`, `archive/verdicts/` — directories must be non-empty).

Stage states are named by manifest position (`stage1` → `stage-1`); cell outputs are `<stageId>.json` / `<stageId>.md` (the prompt names the stage). Schema paths are emitted relative to the template's own location — the orchestrator writes the template beside the plan (`plans/<plan>.template.json`), resolving `../schemas/…` exactly like the hand-written template does.

## The run loop v0 (stages one and two; host directories or container units)

`ctx.eval.run(planPath, options)` is the body; `/eval run` is the human act of starting it. The flow:

1. **Validation first**: a plan with errors is refused before anything executes; a condition lock that disagrees with the fresh hash is refused (a missing lock is a warning and the fresh hash is used — the full readiness gate lands with I4 provision).
2. **Readiness (T23)**: before the run is created, every condition is probed with ONE minimal delegation through the same facade, provider and cwd rule the cells use — see [Readiness](#readiness-one-real-delegation-per-condition). Any condition that fails refuses the whole run; `--ignore-readiness` starts anyway and records every cell of that condition as `cell-skipped` with the reason.
3. **Subset (T23)**: `--only <missionId,…>` and `--max-cells N` select part of the seeded order. The selection lands in `run.meta.subset` (`{only, maxCells, totalCells, selectedCells}`) and the generated template carries exactly the selected missions, so the ledger holds no cell the run will never drive. The plan contract gains no field: a subset belongs to ONE execution, not to the reviewed program.
4. **Snapshot**: `datasets.snapshot` pins the commit into run.meta.
5. **Template + matrix**: the template is generated beside the plan; `expandMatrix` expands (items × conditions × reps) and `orderCells` shuffles by `plan.order.seed`, preferring same-condition non-adjacency when interleaving; order and concurrency are written into run.meta.
6. **Per cell** (concurrency default 1): an isolated directory `$DSH_HOME/state/eval/cells/<runId>/<missionId>/attempt-<N>/` receives the item's visible-layer content plus a `materialization.json` (sorted per-file sha256 + overall sha, addArtifact kind `materialization`); each stage's prompt = the dataset-level `prompts/<stage>.md` bytes + one newline + the item's `task.md` bytes, sha256 recorded into the orchestrator ns; the orchestrator calls `ctx.localAgent.start` (first round) / `resume` (later rounds) directly, passing the cell directory as the delegation `cwd` (the local-agent family's cwd support, T11).
7. **Advancing**: after each delegation the stage outputs are collected from the cell directory and `submit({to, json, files})` (intended-edge pre-validation) + `transition(to)` run; a fired `halt_on` diverts to `halted`. Schema violations are never retried: `{kind: 'submission-rejected', violations}` is recorded and the cell stops in its current state.
8. **Failure policy**: delegation start failures, facade errors, and timeout cancels → `retry(reason, 'infrastructure')` and the cell is redone, budget default 1 (adjustable via `--retries`); past the budget `{kind: 'cell-skipped'}` is recorded and the cell skipped. Timeout = the per-cell cumulative delegation time against `plan.budget.activeMinutes`; on expiry `cancel(childSessionId)` fires.
9. **Judge, then archive, then pass the gate**: once the cell parks in its terminal stage state it is judged (next section), the verdicts land in `archive/verdicts/`, the cell directory is copied into `archive/workspace/`, and `transition(archived)` runs. The run then pushes `releasable → released` — **by default, cell by cell, since T57** — and the file-check requires a non-empty verdicts/: either source having produced something is enough; with neither, `finalize-refused` is recorded honestly and the cell stays at archived. `--keep-units` is the debugging opt-out: every cell then stops at archived and keeps its container.
10. **Export**: at the end the bundle is exported to the experiment's `exports/` (a run started from an old plan path still uses `<dataset repo>/exports/`; override with `--out`), visible layer only (modelFacing:true — no leak-gate confirmation needed).

Before any work, the run writes one anchor per cell: `{kind: 'cell', task, condition, conditionSha, rep}` — so even a cell that never runs stays attributable, and the report reads cell identity from this anchor alone (a bundle carries no labels, and the mission id is lossy).

Every delegation records one orchestrator-ns annotation `{kind: 'delegation', stage, round, childSessionId, promptSha, startedAt, durationMs, usage, toolCalls?, cliVersion?, model: {declared, observed}}` (`toolCalls` and `cliVersion` are written only when this round's settled event carried them; absence means the round reported none); `observed` comes from T11's read-back — this round's settled event first, then the `delegationOf(childSessionId)` record. Reading the record means WAITING: a provider merges its observation in a settle pass chained after the result resolves, while the facade clears the tracked run (and with it the `onProgress` the options carried) at that same moment — so on a real facade the settled event never reaches the orchestrator and the record gains its value a beat late; reading it the instant the run returns reads nothing (what the first real two-cell run showed). The loop therefore polls the record for a bounded moment after settle (10s by default, `readbackWaitMs` to tune), taking an observation that differs from the one held before the round began; when the wait expires it still returns the record's current value (a resumed round that ran the same model is indistinguishable anyway, and the record means "this delegation's latest observation"), and null only when neither channel ever carried one. `usage` rides the settled event alone: a facade that clears the tracked run first records none here, and null is the honest answer. A model read back that contradicts the condition's `model.declared` fails the run on the spot (frozen decision 5: the run is misattributed), never as a retryable infrastructure failure.

**The declared model is now REQUESTED before it is compared (T30b).** `model.declared` used to be a claim checked against the read-back, while what actually ran was whatever the harness's own configuration said — which is how a judge condition declaring dsh v4-pro ran the host default v4-flash and failed the readiness check (T22 step 5). The player rounds, the judge delegations and the readiness probe now all pass a non-null `model.declared` to local-agent as the delegation's `model`, which lands as each CLI's own model flag; a null declaration passes nothing, as before. The delegation annotation and `run.meta.readiness` each carry a `requestedModel` beside the observed one — what this round ASKED the harness for, next to what came back. The comparison itself is unchanged: request one model, read back another, and it is still a MisattributedRun. Resume rounds carry no model — local-agent records the first round's request and re-issues it.

## The container path (I3·T20)

A plan that declares a `unit` segment takes the container path; one that does not takes the host path, **byte for byte** what it was before this section existed (pilot A's bundle recomputed on this branch produces a byte-identical `results.jsonl`). The container path needs `ctx.lab`; credentials need nothing extra — it mounts this instance's own scoped homes (below).

**One unit per cell, in a fixed order** (architecture trajectory steps 11–17):

1. **`acquire`**: image, network, `user` and ceilings come from the plan's `unit` segment; **exactly one mount** — this condition's credential directory, `bind` and writable (a credential refresh has to land back on the host — T17's decision); **exactly one environment entry**, the condition's `unit.scopedHome.var` = its in-container path, plus `NODE_OPTIONS=--use-env-proxy` for dsh; `missionId` and `runId` both ride along. `workdir` is `/workspace`, and lab is asked to hand it to the unit's own user (`ownWorkdir`) — docker creates a missing workdir as root, which a non-root unit cannot write.
2. **The egress self-check (T29d; only when the plan declares `unit.egressCheck`)**: after `acquire` and before `populate`, the plan's own command runs inside the unit through `lab.verify`, and only exit 0 continues. Asking BEFORE using is a measured decision: `eval-net` is an `--internal` network whose only way out is a sidecar proxy, and with that sidecar stopped codex came up inside the unit, read its model and its sandbox policy, ran for 230 seconds, and returned `task_complete` with `last_agent_message: null` — an EMPTY answer and not one word about the network. Every layer above reads that as "the probe failed", and the same four minutes would burn on every cell. The readiness probe's unit is asked the same question BEFORE its delegation, so a dead proxy is one `EGRESS_UNAVAILABLE` refusal that spends no delegation at all. The command and its target live in the plan, beside the network they belong to — the orchestrator holds no address of its own; a declaration that is empty or carries an empty word is refused as `EGRESS_CHECK_MALFORMED`. A plan with a `network` and no check says so once in the log: it runs, but that run cannot tell an unreachable network from a model that said nothing.
3. **`setRefs({resource, fingerprint})`**: written by the orchestrator itself, the moment the unit exists. lab writes the same two refs, but that write is warn-and-skip by design, and an invariant may not rest on a write that is allowed to skip — pilot A's fingerprint column was empty for a whole run and the report read `unverifiable` for the whole iteration.
4. **`populate`**: the host materialization directory → `/workspace`, with `manifestPath` pointing at the attempt's `materialization.json`; lab hashes, writes it, and registers the artifact. The orchestrator does not compute a second one: two files called `materialization.json` carrying two different hashes is worse than either alone. The workspace therefore holds **only the item's bytes** — no manifest, and so no host path, inside the unit.
5. **One delegation round per stage**: `exec = {container, workdir: '/workspace', env: {<VAR>: <in-container path>}}`, and **no `cwd`** (inside a unit the host cwd means nothing; a target that fails to name the scoped-home variable is refused outright by T17).
6. **A `checkpoint({name: <stage id>})` at the end of each stage** (its ref reaches mission through lab), then `collect('/workspace' → the cell directory)`. On the container path the cell directory is the **host mirror of the workspace**: collecting outputs, contract-checking, `submit`, and the judge's material all read it, which is why steps 7 and 9 of the run loop are shared code between the two paths.
7. **Judging happens inside the unit**: the probes run through `lab.verify`, their material riding verify's own scratch directory (`/run/dsh-lab/verify`, removed after every call); `--out` is written to `/run/dsh-lab/verdicts/<probe>/`, **not** into `/workspace` — the archive is the player's work and must not carry judging output. After the last probe, one `collect` brings the whole verdict tree back into the attempt's `probe-verdicts/`, where it is read and judged on the host; then the in-unit directory is removed. The three exit states and the backfill-before-validation order are identical to the host path's, verbatim.
8. **`archive`**: lab exports `workspace/` plus `manifest.json` into the attempt's `archive/`; `verdicts/` is already beside it (judging runs before archiving, because the gate refuses an empty one).

### «环境一致» compares the environment CLASS

`refs.fingerprint` does not carry the unit's full fingerprint. It carries the **environment class**: the unit's composite components minus the ones **that condition itself contributed** — its own scoped-home mount target, the variable naming it, that harness's extras (dsh's `NODE_OPTIONS`), and the keys the condition declares in `env.keys`. What is left is what the plan declared: image, ceilings, network, user, plan-level mounts and env keys.

Without that, the invariant fails on exactly the comparison this profile exists to run. Four harnesses mount four credential directories under four variables (`CODEX_HOME` / `CLAUDE_CONFIG_DIR` / `KIMI_CODE_HOME` / `DSH_HOME`), so one run yields four fingerprints and the report reads `violated` and refuses to compare — of four environments that are, in every sense the comparison cares about, one.

The subtraction is read back off the code that BUILT the spec, not guessed from the components: whatever `acquireSpecFor` put in, `conditionOwnedComponents` takes back out. The hashing rule is not re-implemented — the class is hashed by `lab.fingerprintOf(components)`, the same function `acquire` uses, which is what makes a derived class and a unit's own fingerprint comparable at all. The label stays `lab-env:<sha256>` and the component `version` does not move: it is one algorithm over a smaller component set.

The unit's own fingerprint is not lost: it is recorded on the cell's `unit` annotation in the orchestrator ns (with the excluded components) and in lab's archive `manifest.json`. It does **not** go into refs — mission's refs carry `resource` / `fingerprint` / `sessions`, and a fourth key is a mission change this package does not own. Under the invariant line the report lists every cell's unit fingerprint and what its class left out, so a reader can see where the difference is instead of trusting that there is one.

### The judging directory reproduces the repository's real relative paths

A dataset-level verify layer is a real directory (`datasets/<id>/verify/`), so it lands at `<judging>/verify/…`. An ITEM's layer is where the two dataset layouts diverge, and getting it wrong costs exactly one directory level:

- convention: the files live in `items/<id>/verify/` and their display paths are relative to it (`probes/x.mjs`);
- register: the descriptor re-homes free files from the item directory into a layer role, and their display paths are **item-relative** (`checks/probes/x.mjs`) — the file really is at `items/<id>/checks/probes/x.mjs`.

Materializing both as `items/<id>/verify/<display>` puts the register item one level too deep, so `../../../../verify/helpers/lib` resolves above the judging root and the item can only carry a copy of the shared library. Every file now lands at the path it really occupies; which displays were re-homed is read from the `register` entries of the descriptor `datasets.show` already returns (optional on the face — a facade that does not report one degrades to the convention layout, which is what every caller got before). A probe's `by` stays the display path: that names the verdict's origin, not a location on disk.

A probe's cwd is **the directory holding that item's checklist** — `items/<id>/verify` by convention, `items/<id>/checks` once re-homed — so a shared probe reads this item's own `./checklist.yml` under either layout. An item with no checklist falls back to the convention root.

### One materialization hash, both paths

`materialization.json` is computed by the orchestrator on both paths, by one algorithm (sorted per-file sha256, then an overall sha256), so the same item at the same commit hashes to **the same number** on the host and inside a unit. The container path used to record lab's populate manifest instead, which left «题面一致» answerable only within a path. lab's own hash is not lost — it moved to `populate-manifest.json` beside it, under its own name, because it makes a different claim ("what went into the unit is this") rather than being a second spelling of the same one.

### Directory and credential conventions

- The container path mounts **the evaluation instance's own scoped home**: `<homesRoot>/<harness>`, the directory `local-agent` provisions for that harness, `bind`-mounted writable at the in-container path the condition's `unit.scopedHome.container` declares. Credentials get there from `/<harness> login` ON THIS INSTANCE; nothing is staged or copied. If a refresh fails or the directory is emptied, log in again here.
- It has to be the SAME directory, not a copy: a containerized round's CLI writes its rollout / session log into whatever was bound, and the delegation read-back looks under `homeDir(<harness>)`. Pointing them at two places raises no error at all — the read-back is simply empty forever, every round's `model.observed` is null, readiness reports `ready, model —`, and the report's «受试对象一致» never leaves ⚠️. That is precisely what T20's separate credential tree did, and pilot B paid for it.
- **One scoped home per condition**: a condition's optional top-level `scope` field (a `[a-z0-9-]` NAME, never a path) switches both its mount source and its delegations to `<homesRoot>/<harness>@<scope>` — a sibling of the default directory with its own login. Omitted, everything is byte for byte what it was before the field existed. `scope` enters the condition hash: two conditions differing only in it are two subjects, because they log in as two accounts, which is how one run compares two accounts of one harness. The readiness probe probes each condition's own scope, each container cell mounts its own directory, and `run.meta.unit.scopedHomes` records the `scope` per condition (the host path stays out of the bundle, as before — it is an operator fact).
- The orchestrator checks that the directory **exists, is non-empty, and has a plausible owner**, and never reads its contents. An empty one means "nobody has logged in on this instance for that harness" — refused before the run, which is cheaper than twenty-four cells discovering it one 401 at a time.
- The attempt's run-data directory gains two things: `materialization.json` (the orchestrator's manifest) and `probe-verdicts/` (the raw verdicts the probes wrote inside the unit). The host mirror of the workspace does not live there; where it lives is recorded in `workspace-mirror.json`.

### One destroy path

`run.ts` holds a single `destroyUnit`, and `lab.release` appears nowhere else:

- **Pass the gate, then destroy.** The unit is destroyed as soon as `archived → releasable` succeeds, and only then does the cell move `→ released`. The placement is deliberate: `isReleasable` reads the CURRENT state and the template's releasableStates is `['releasable']` alone — destroying after `released` asks the gate a question it answers no to, and every container would survive. `finalize` takes the same three steps in the same order, which is what makes reclaiming a container after the fact possible at all.
- **Walking the gate is the default (T57).** It was opt-in while v0 had no judge and could not fill the `verdicts/` the gate requires. Since every cell is judged before it archives, the old default meant one thing in practice: every container survived its run, and the fourth cell of a plan met lab's `maxConcurrentUnits` and could not start — so the loop's default silently decided how large a matrix was runnable. `--keep-units` (the CLI flag, and the approve dialog's 保留单元 box) asks for the old behavior when a container is wanted for debugging.
- **Refused gate, kept container.** With `--keep-units`, or when an empty `verdicts/` blocks `releasable`, the destroy is still attempted, still refused, and the **container stays**, with `{kind: 'unit-retained', reason}` recorded on the cell. For a cell nobody has looked at, the scene is worth more than the container.
- **The failure path archives first.** When a cell throws (infrastructure failure, schema refusal, misattribution) the loop does `collect` → `archive` → the same gate: releasing without archiving destroys the evidence (lab README, «失败恢复循环»). No force there either, so a failed cell keeps its container.
- **`force` appears exactly once in this file**: the readiness probe unit. It is bound to no mission and therefore has no gate; lab requires an explicit `force` for such a destroy precisely so that a gate-less destroy is a sentence rather than a default.

### Known trade-offs

- **Serial.** The container path pins `concurrency: 1` (an explicit `>1` is refused); parallel units are I4. An `acquire` that hits `maxConcurrentUnits` is reported as a defect, not queued — and the refusal **names the holders**: lab says "release a unit first" and nothing about which, so the orchestrator adds the run id, unit id, container name and cell of every unit holding a slot, plus the two commands that end them. The list is added here rather than in lab because lab does not know what a run is.
- **The multi-harness fingerprint problem is what the environment class solves** (above): `refs.fingerprint` carries the class, and the unit's own fingerprint lives on the `unit` annotation and in the archive manifest.
- **Both paths hash their materialization the same way** (above): `materialization.json` is the orchestrator's, by one algorithm; lab's own hash lives beside it as `populate-manifest.json`. The report still reads an older bundle's `sha` field.

## Readiness: one real delegation per condition

`/<harness> status` answers a SHAPE question — is there a credential record here? An expired, unrefreshable grant reads exactly like a working one. Pilot A took that answer at face value: `claude-code status` said `authenticated: yes` while every delegation returned 401, six of twenty-four cells were doomed before the run began, and the first evidence arrived at the first delegation.

The JUDGE conditions are probed too. A judge is the same kind of thing — a real delegation that can fail on a credential that reads authenticated — and its failure is dearer: a player that cannot be delegated to loses its own cells, a judge that cannot be delegated to loses the whole round's llm-draft verdicts. Pilot B lost both of its judge samples while the run walked on to `released` with an empty llm-draft namespace. So a judge is probed on the same rule, refuses the run on the same rule, and is recorded in `run.meta.readiness` with `role: 'judge'`. Judging delegates from the orchestrator rather than from a cell, so even on the container path the judge is probed on the HOST — probing it in a unit would test an environment it never meets.

So the pre-run check does not ask; it spends one delegation. Before `runCreate`, every plan condition is probed with the byte-exact one-sentence prompt `READINESS_PROMPT` (reply `READY`, no tools, no files) through the SAME facade, provider and per-directory `cwd` rule the cells use — there is no back door, so what the probe proves is what the cells will meet. A condition is ready only when the delegation both started AND returned `stopReason: 'completed'`; the probe REQUESTS the model the condition declares (the same one the cells will request) and reads the model back and fails the condition when it contradicts `model.declared` (frozen decision 5, caught before the run instead of at its first stage round).

Each verdict is a `{kind: 'readiness', condition, harness, provider, ok, startedAt, durationMs, childSessionId, declaredModel, requestedModel, observedModel, reason?}` record. It lands in `run.meta.readiness` AND as an orchestrator-ns annotation on every cell of that condition, so a reader asking why a cell produced nothing finds the answer on the cell. A failed condition refuses the whole run and prints the reason (the 401, not "a condition failed"); `--ignore-readiness` starts anyway, and then every cell of that condition is recorded `cell-skipped` with the reason and is never delegated to.

## The capability face: `preset` becomes a fact

`preset` in a condition document was always a sentence with **no counterpart**. It enters the condition hash, so two conditions differing only in preset are two subjects on paper — but nothing ever wrote a preset anywhere, so nothing could disagree with the claim. T32 gives it one:

- **Who may declare it.** `dsh` alone. The sub-profile inside its scoped home is written by the evaluation instance, and the preset roster is a layer of that patch. The three external CLIs run their vendor's own composition, which this family cannot compose — a preset for one of them is a validate error (`PRESET_NOT_FOR_HARNESS`) and the only legal value is `null`. Their equivalent is `skills.pack`, which does not exist yet either (I6).
- **Provision composes the preset into the scope first.** For a condition that declares one, `conditions provision` calls `localAgent.provisionScope(harness, scope, { preset })` BEFORE it hashes the scoped home: a preset is a property of the SUBJECT, so the condition document is what decides it, not a plugin setting with one answer per instance (before pilot D the roster layer had to be hand-appended to each scope's patch — and that layer is silently erased by the next restart). The order is not incidental: the scope's own copy of the preset lives inside the scoped home, so composing it after the hash would lock a `home.sha` describing a directory that no longer exists. A facade without the verb degrades to what it always did — read back whatever is there.
- **Provision writes down what it built.** `conditions provision` (T31) records two more things in `provisioned`: `preset`, read back from the sub-profile that was written, and `capabilities.sha`, the CAPABILITY HASH capability-catalog computed over the provisioned environment (the canonical form keeps each skill's name/source/body-sha and each tool's name/channel/parameters — descriptions stay out, because rewording one must not mint a new subject). The measurement is done by an **in-instance probe** (T32b, below); in a composition with no catalog there is no probe, and the condition is still locked but without a capability record, `CAPABILITIES_UNMEASURED` saying so by name — the readiness gate then refuses it.
- **Readiness also checks freshness.** The lock records the hash as of provision time; at run start the readiness gate MEASURES IT AGAIN, and a disagreement fails the condition naming "the preset changed after provision". Without that step a lock reads as verified forever while the preset it measured is edited underneath it — and editing a skill BODY moves no other recorded hash (`home.sha` hashes config files, not SKILL.md), so this is the only thing that sees it. When nothing can be measured (no catalog, a preset that will not mount) the locked record stands: an absent measurement is evidence about the catalog, not about the subject. When the edit is to the scope's OWN copy there is a second check that needs no catalog at all: `capabilities.snapshot.sha` is recomputed and a disagreement refuses. **`validate` and `conditions list` check that one too** (when they run inside an instance and can resolve the scoped home), which closes T32b's "reads ready offline, refused at run start" for that case; the capability face itself still needs a live catalog, so the pure-CLI `validate` still cannot see it.
- **Readiness checks it.** A declared preset with no capability record in the lock, or a record taken under a different preset, fails the condition BEFORE any delegation is spent. A factor that enters the hash and that nobody measured leaves two subjects on paper and one in fact.

The orchestrating instance's own capability hash is a different thing: it is recorded in `run.meta.orchestrator.capabilities` as PROVENANCE. The report's 程序一致 invariant lists it and compares nothing against it — the orchestrator answers none of the dataset's questions, and making its capabilities a pass/fail input would turn "we upgraded the planning agent" into a violated invariant. A composition without the catalog records no such line.

## `finalize`: the re-entry point after `archived`

A run's own gate walk happens at the moment each cell finishes, and judging-then-final-review is work that happens after archiving. Pilot A therefore pushed twelve cells through `dsh-mission transition` by hand. `/eval finalize <runId>` is that walk, mechanized: for every `archived` cell of a run it takes the same gate (`archived → releasable → released`, the archive gate's non-empty `verdicts/` file-check included), and for every cell that is not `archived` it reports the state and moves on. It is the re-entry point after `--keep-units`, after a cancel, and after a gate refusal somebody has since fixed.

It never forces. A gate refusal is recorded as `{kind: 'finalize-refused', from, error}` in the orchestrator ns and the cell stays where the gate stopped it — the gate is the reason an archive means anything. And it never touches a cell that has not reached `archived`: a pending or mid-stage cell is unfinished work, not un-released work. Skips are classified `already-released` / `interrupted` / `not-started` so a whole run summarizes in one line.

**It reclaims the containers too (T57).** Each cell that passes the gate has its unit destroyed between the two transitions — the same place, the same order, the same no-force rule as the run loop. Before that the walk moved the ledger and nothing else, so a container run finalized after the fact reached `released` with every container still up and no gate left that could release them (T39 · G18). The report says what it destroyed and what is still up, each with the reason: the gate refused its cell; the cell is past the gate and only `dsh-lab release <unit> --force` can end it, which is a human's call; or the cell never finished. The unit face is **optional** — a composition without lab reports the list **unknown**, never `0`.

Outside a host there is no mission service, so `dsh-eval finalize` drives the `dsh-mission` CLI in a child process (`--data-dir`, `--mission-cli`, `$DSH_MISSION_CLI`) — the same seam a person uses by hand. eval still imports nothing from the mission package. That child process is a ledger and not a lab, so the CLI face releases no container and says so every time.

## Condition provisioning: declaration → reality → lock (I4·T31)

A condition is a **declaration**; `conditions/<id>.lock.json` is the anchor saying "this declaration was checked against reality once". T8b built the anchor and both of its readers — validate reports `LOCK_STALE` / `HOME_NOT_PROVISIONED` / `HOME_MISMATCH`, and the run loop refuses a stale lock outright — but until T31 **nothing wrote one**. `dsh-eval conditions provision` is that writer, and deliberately the only one: a hand-written lock claims the scoped home was checked when nobody checked it.

Five steps, each of which can stop:

1. **Resolve the scoped home** — ask local-agent for the `homeDir` of the condition's `(harness, scope)`; reading it materializes it.
2. **Grade the credential** — anything but a present one (`present-unverified` / `verified`) stops here and prints the login command, `/<harness> login [--scope <name>]`. **Provision never logs in and never copies a credential from another scope** — the login is the human's.
3. **Check the declaration field by field** — read that scope's effective settings and compare:

   | Condition field | Compared against | On disagreement |
   |---|---|---|
   | `harness.version` | the CLI's self-reported version | warning (a `null` declaration is **back-filled into the lock**, never into the condition document) |
   | `model.declared` | the harness's default model | warning — since T30b the declaration is the value **requested per delegation**, so differing from the default is normal; running the wrong one is still caught by the read-back |
   | `reasoning.effort` | `reasoningEffort` | warning (a harness with no such knob is an honest absence) |
   | `permissions` | codex `sandbox` / claude-code `permissionMode` / kimi `autoApprove` (dsh has no knob) | **error, no lock written** |
   | `model.endpoint` | `"default"` when no base URL is in force, else the endpoint hostname (a declared URL is reduced to its host first) | **error, no lock written** |

   The two errors are not an arbitrary pick: `permissions` is the approval boundary (frozen decision 3) and `model.endpoint` is the upstream route (frozen decision 5). Those two ARE the subject under test, so a disagreement means the condition describes an experiment nobody ran.
4. **Hash the scoped home, and write it back** — the config-content hash of that directory (see [Hash rules](#hash-rules); credential-shaped files are excluded by name and by directory). When the declaration's `home.sha` is `null` or no longer matches, **provision writes the measured value into the condition document and re-hashes the condition**, so the lock written in step 5 anchors the document as it now reads — which is what makes "the condition becomes ready" ONE action. `--no-write-back` restores the old behavior: the disagreement is a warning, the document is untouched, and a person copies the digest in by hand and provisions a second time (the only path before T58, and the source of half the avoidable human actions in the walkthrough's step 4). The write-back touches `home.sha` and nothing else, only when it disagrees, and only inside the deployment's condition library (before T73: the dataset working copy `--repo` named).
5. **Write the lock** — `{schema, condition, sha, home:{sha}, provisioned:{at, cliVersion, effective:{model, reasoningEffort, permissions, endpoint}}}`. `provisioned` is **additive** in `dataseek.condition-lock/1`: a lock without it was written before provision existed, and validate reads that as "nobody ever checked" rather than as a violation.

validate re-checks the lock's `provisioned.effective` with **the same function**: when either error-grade field disagrees, the condition is "not ready" and the field is named. With the sha still matching, that can only mean the lock was not written by provision — which is exactly the forgery worth seeing.

### The capability probe (T32b)

One more step runs before step 5, and only for a condition whose `preset` is non-null:

1. **Read the roster back.** Every `profiles/*/cordis.patch.yml` under the scoped home is scanned for an insert row mounting `@deepseek-ai/dsh-agent-presets`, and its `default` is the answer. What is keyed on is the PACKAGE — not the generated comment banner, not the profile's directory name — so a deployment that renamed its sub-profile still reads correctly. Unreadable means no measurement: copying the declaration into `provisioned.preset` is the one thing that would make that field meaningless.
2. **Confirm both sides read the same preset directory.** The catalog resolves a preset id through the EVALUATION INSTANCE's roster roots; the sub-dsh resolves it through the scoped home's. Two arrangements:
   - The scope keeps **no** copy (`source: "instance-root"`): both read the deployment's preset root, and it is measured. But a unit bind-mounts the scoped home and nothing else, so such a condition **resolves its preset only on the host path** — the probe logs exactly that.
   - The scope keeps **its own** `<scope>/.agent-presets/<id>` (`source: "scope-snapshot"`, the only arrangement a container round can use): measured only when the provisioning that MADE that copy (`localAgent.provisionScope`) reports it byte-identical to the deployment's. Why the measurement transfers: the canonical capability face carries **no filesystem path** (a skill enters as name/source/body-sha, a tool as name/channel/parameters), so two byte-identical directories hash alike — which T32's own machine run measured from the other side (the same content under a different preset id produced the same digest). Nothing vouching for it, an **absolute path** in the copy's composition, or a tree that is not plain files (a symlink, which does not survive the bind mount) are each refused by name.
3. **Measure.** `ctx.capabilityCatalog.snapshotFor(<the id read back>)`, taking the `sha` the snapshot stamps. A preset that will not mount makes the catalog THROW rather than degrade to the global layer (T32's decision), and that refusal is the answer here too.

The probe also hashes that copy WHOLE (every file, `SKILL.md` included) into `capabilities.snapshot.sha`. That is not a second opinion about the capability face; it is the only evidence an OFFLINE reader has that the subject is still the one that was measured — `home.sha` hashes config-suffixed files by design and never moves when a skill body is edited, and the face needs a live catalog. The readiness gate and `validate` both check it, which **closes the gap T32b recorded** ("validate reports a stale lock as ready"), at least for a body edit; `validate` does it only when it is given a scoped-home resolver (it has one inside an instance, and none in the pure CLI), and behaves byte-identically to before without one.

**What it measures**: that preset's capability face *as the evaluation instance composes it*, not as the sub-dsh does (dsh-base plus the headless patch plus the roster). As a factor it is real — two presets, two hashes, and editing a skill body moves one — but it is not the sub-dsh's whole face. Measuring that means booting the sub-profile and asking a catalog mounted inside it, which is left for later; every lock written until then reads stale against the new measurement, which is exactly what the freshness check above says ("re-provision"), rather than a silently wrong comparison.

Provision needs the local-agent service (the scoped home, the credential grade and the effective settings all live there) and — for the probe — the capability-catalog service, so like `/eval run` it starts from a live session: `/eval conditions provision <condition id> [--no-write-back]`. A CLI process has no service plane and is refused as before. The deployment's condition library (`$DSH_HOME/state/eval/conditions`) is the only place it may write; a dataset repository is never written.

The same act on the interface is the **Provision button on every row of 实验室 › Conditions** (T58): the same service verb, writing into the deployment's condition library, and the same flat `ok / warn / error` list the plan-review page renders. That page also edits exactly ONE field of an existing declaration — `model.endpoint`, the readiness-gate field that until then had no input anywhere. Editing it edits a FACTOR: the condition re-hashes and the lock beside it goes stale, which the page says out loud while leaving "provision again" as the person's click rather than silently re-anchoring a subject. Neither action has a model-tool twin (R1).

## Judging: probes (`script`) and blind LLM judging (`llm-draft`)

Once the cell has finished its stages and parked in its terminal state, the orchestrator runs the two mechanical sources before archiving. The full contract is [protocol §6.7 / §6.8](../../docs/dataset-authoring-protocol.en.md); this is the implementation-side reading.

**Probes (`script`)** — any `.mjs` / `.sh` under a `probes/` segment, from either of two sources: **the item's own** (its verify layer, judging that item alone) and **the dataset's shared** (the dataset-level verify layer, run once for every item — this is where "every item is measured with the same ruler" criteria like `shared/no-patch.sh` live). The invocation is `<probe> --cell <cell dir> --rubric <rubric path> --out <verdicts.json>`.

**The exit code carries three states**: `0` = judged (including `pass: false`), recorded `judged`; `3` = **not applicable this round** (the probe is fine and the criterion is not false — the input it needs is not in place: stage three never ran, the harness worktree is not in the cell), recorded `probe-skipped` with the first stderr line and **not counted a failure**; any other non-zero = the probe failed, recorded `probe-failed`. Exiting 0 without a readable `--out` counts as a failure. `3` rather than `2`, because `2` is the getopt-conventional "usage error" code and reading it as "cannot judge" would swallow every mis-invocation.

**The execution environment**: **both verify layers are materialized whole** into a host-side temporary directory, in the dataset's own relative layout (`<tmp>/verify/…` and `<tmp>/items/<item id>/verify/…`), so an item probe imports the dataset's shared library through the same relative path that resolves in the repository (`../../../../verify/helpers/lib/x.mjs`). The cwd is always the item's verify root, shared probes included. The whole directory is removed afterwards (from I3 `lab.verify` runs it inside the container; the contract is unchanged).

**`task` / `by` are backfilled BEFORE validation** — both are `required` under `additionalProperties: false`, so the other order would void a complete verdict for omitting exactly the two fields the orchestrator supplies. `by`: an item probe's display path in that item's verify layer; a shared probe's is `shared/` plus its display path in the dataset-level verify layer. A value the probe wrote that disagrees loses, and `overwritten` is recorded in the orchestrator ns. A verdict carrying `ratio` is checked at the source against the two numeric facts (`total > 0` with `0 <= passed <= total`, and `pass === (passed === total)`); a failure counts as off-contract output — the report's fallback to the boolean is a backstop, not the only gate.

Output goes to the `script` ns and `archive/verdicts/script.json`; when neither layer ships a probe, nothing at all is written. Every probe run is recorded in the orchestrator ns under `kind: 'probes'` as `{probe, origin, exitCode, outcome, ok, verdicts, durationMs, error?, reason?, overwritten?, dropped?}`.

**Blind LLM judging (`llm-draft`)** — the judge is itself a condition, named by `plan.judge.conditions` (which may name **several** — a judge panel), with `plan.judge.samples` (default 2) samples per judge condition. The constraints are enforced by the orchestrator (decision 9, relaxed 2026-09-10):

- **A judge pins its model explicitly**: a judge condition with `model.declared: null` is a validate error and a run refusal. When the judge runs whatever its harness happens to default to, "was this cell self-judged" is undecidable, and the report would be quietly wrong rather than loudly incomplete.
- **A judge MAY share a model with a player, and who judged what goes into the report**: two different ids naming the same `(harness, model)` are no longer refused. Every `llm-draft` verdict carries `judge` (the judge condition id, its model, `selfJudged`, the sample number), summary.md lists per cell who judged it, and a cell whose judge model is the model that cell ran is marked **self-judged**. Exactly two things are still refused: the same id on both `conditions` and `judge.conditions` (that is a bookkeeping mistake, not a panel), and one judge id listed twice.
  - Why not exclude globally: when the thing being evaluated IS every model, the judge necessarily overlaps one of the players. The public leaderboards that judge with models (MT-Bench, AlpacaEval, Arena-Hard) all let contestants judge and record the self-preference; the remedy there is a **panel plus disclosure**, not exclusion, and a benchmark that wants neither uses deterministic graders (SWE-bench). The old rule's cost was measured: at T22 step 5 the judge declared one model and ran another, and re-declaring it collided with a player — neither declaration could be run.
- **De-fingerprint first**: harness names, CLI names and self-reported names in `stage1.json` / `stage1.md` / `stage2.json` / `stage2.md` become `<harness>`, and the plan's declared model identifiers become `<model>`; the replacement table and counts are recorded as `{kind: 'deidentify', files, table, total}`, the **originals are untouched**, and the judge only ever sees the copy.
- **Two samples**: each sample is a **fresh delegation** (a resumed judge would see its own previous answer), in its own cwd — the judge material directory.

The judge prompt = the `kind: llm-draft` criteria of the item's grading-layer rubric (`objective` rows go to the probes, `human` rows to the judge bench; neither is shown) + the de-identified material + the output contract. The judge writes a `dataseek.verdict/1` array into `verdicts.json` in its cwd; an unreadable answer records `{kind: 'judge-parse-failed'}` and is **retried once**, and a second failure drops that sample honestly. One `llm-draft` annotation per sample, `{sample, judgeCondition, judgeSha, judgeModel, selfJudged, promptSha, verdicts}`, plus `archive/verdicts/llm-draft-<judge condition>-<sample>.json`; `task` and `by` are backfilled by the orchestrator (the judging side only echoes them, and getting them wrong would corrupt every join the report performs).

The judge's cost is recorded as `{kind: 'judge', judgeCondition, judgeSha, judgeModel, selfJudged, sample, attempt, childSessionId, promptSha, startedAt, durationMs, usage, model}` — the kind is not `delegation`, so it **stays out of the report's contestant efficiency table**. The judge material directory (`$DSH_HOME/state/eval/judge/<runId>/…`: prompt + de-identified material + the judge's answer) is retained after the run for review; the probe directory is removed as soon as its probes have run.

The grading and verify layers are read through the datasets service face with an explicit single-layer scope (`layers: ['grading']` / `['verify']`) and materialized into host-side directories — **never into a player's cell**.

## Experiments: a deployment-level object (T73)

Before T73 an experiment was `datasets/<set>/plans/<name>.json` inside the dataset repository, its conditions lived beside it, and which repository the evaluation read was decided by the **session binding**. So everything the evaluation itself recorded — plans, conditions, locks, analysis drafts, exports — was written into a checkout several agents share. T73 separates the two: **the dataset repository is read-only input pinned to one commit; an experiment is the deployment's own object**.

```
$DSH_HOME/state/eval/
├── experiments/<experimentId>/
│   ├── plan.json        # the plan, byte for byte (serialized when drafted, verbatim when imported)
│   ├── meta.json        # name, originSession, createdAt, dataset {registry, set, commit}, experimentId
│   ├── analysis/        # analysis drafts (the only place eval_analysis_write writes)
│   └── exports/         # the default export directory; plan.exports and --out / exportsDir still win
└── conditions/<id>.json + <id>.lock.json   # the condition library every experiment shares; hash and lock semantics unchanged
```

- **The id rule**: `<slug>-<yyyymmdd>-<4hex>`. The slug is the name's `[a-z0-9-]`, at most 40 characters; the date is UTC (one instant is one date on every machine); the tail is random and re-minted on a collision. The directory is written into a hidden temp directory, moved into place by one rename, and `plan.json` is read back and compared byte for byte — a listing never sees a half-written experiment, and a crash leaves only a dot-directory the lister skips.
- **The version pin**: `eval_plan_draft` and the 新建实验 form take `dataset: "<registration id>/<set>"` and an optional `commit`. The candidates are the registration's tracked-branch latest plus the commits pinned by existing experiments on **the same set sharing a condition**. When every candidate holds identical `items/` and `schemas/` trees it is not ambiguous and the latest is pinned silently; otherwise the draft is refused with the candidates listed, telling the agent to ask the person with `ask_user_question` and stop if they skip. A `commit` that is no candidate is refused the same way. Verbatim:

```
version is ambiguous for <registration id>/<set>: these commits hold different items/ or schemas/, and results pinned to different ones do not compare:
  …the candidates (one commit per line, with why it is one)…
Ask the person which version this experiment should pin with ask_user_question, then draft again with that `commit`. If they skip the question, stop — do not pick one yourself.
```

- **validate reads the materialized view**: an experiment materializes its set at `meta.dataset`'s commit through the datasets registry as a read-only view; contract files (stage schemas, items, probes) are read from there and conditions from the library. The plan's own `dataset` segment no longer locates anything. The "walk up from the plan's sibling `plans/`" fallback survives only on the **legacy path** (an old plan file never imported).
- **Pairing**: a new run's `run.meta` carries `experimentId`, which is how the list files it under an experiment. Old runs have no such field and pair by planSha (which is why import keeps plan bytes verbatim), then by planPath (against an imported experiment's source path); a run nobody claims is still listed, labelled 「旧运行（未关联实验）」.
- **Import**: `dsh-eval import --from <registration id>@<ref> [--plan NAME] --instance URL` (Remote `importExperiments`). It reads `datasets/<set>/plans/*.json` with `git show` only and keeps plan bytes verbatim; the experiment pins the plan's own `dataset.commit`, else the commit the ref resolves to. The conditions a plan names go into the library: an identical hash is the same condition and is left alone; **the same id with different content refuses the whole import** with the differences listed field by field, and not a byte is written. Importing the same plan at the same commit again is a no-op the report names.
- **Starting**: `/eval run <experimentId>`, `dsh-eval run --experiment <id> --instance URL`, or the design page's 批准并启动. The plan-path door is still there, for old plans never imported; its results belong to no experiment.
- **The binding tail is gone**: eval reads no binding any more (`DatasetsBindingFace`, `resolveRepoScope`'s binding branch and the repo-config fallback are deleted), and 「未绑定」 is gone from the interface. Old binding files are **never deleted automatically**; they live at `$DSH_HOME/state/datasets/bindings/<session>.json` (see the datasets README) and may be removed by hand once the migration is confirmed.
- An instance without `DSH_HOME` has no state root: the experiment and library verbs refuse, the error seat says 「这台实例没有评测状态目录」, and the list degrades to runs only (all legacy) with a note saying so.

## Service face `ctx.dshEval`

The cordis service name is `dshEval`, deliberately NOT `eval`: the loader evaluates `!!js` config expressions with `with (ctx) { return eval(expr) }`, so a ctx property named `eval` shadows the global `eval` and crashes any composition mounting this plugin the moment a `!!js` expression is interpolated (found live on the 3171 instance). The package name, the loader entry id (`eval`), and the `/eval` slash name are unaffected.

## The report (`report`)

Input: a mission export bundle (manifest.json, run.json, missions/<id>/attempt-N/{meta,annotations,artifacts}, dataset/<layer>/). Output: three files.

- **results.jsonl** — one verdict per line: `{task, condition, conditionSha, rep, attempt, stage, ns, criterion, pass, ratio?, weight?, negative?, toolCalls?, evidence, by}` (`toolCalls` is the CELL's rounds summed; a cell no round reported an accounting for carries no key at all — which is why a report recomputed over an older bundle is byte-identical). `ratio` appears only when the verdict declared a usable `{passed, total}`; `weight` / `negative` appear only when that criterion's polarity is known (below); `stage` comes from the annotation record's stage field (the verdict contract itself has no stage — null when unrecorded).
- **summary.md** — opens with the five validity checks. The first four are invariants (same materialization / same environment fingerprint / same subject / same procedure): **if any one fails or cannot be established, the report prints fact tables only — no comparison.** The fifth, verdict coverage, is checked per pair and failing it only degrades that pair to description (see T71 below). When comparison is allowed: factors are derived by pairwise-diffing the condition documents recorded in run.meta.conditions (exactly one differing field names the factor; several degrade to 多因子, descriptive only); pairing blocks on tasks and resamples reps for a deterministic seeded bootstrap 95% CI (hand-written statistics, no dependency; withheld when fewer than 3 items carry a difference), reporting per-task deltas (scored criteria and weighted score), n, and refusing to rank when verdict coverage differs, n < 3, the factor is unknown/multi, or there is no interval. Judge consistency reports per-criterion agreement and Cohen's κ across **one judge's** repeated samples (each panel member counted separately, so two judges disagreeing is never charged to either one as noise), plus a cross-judge line when the plan named several (each judge reduced to its own majority first, then compared judge against judge), llm-draft vs human-final agreement when the final pass exists, and a line counting the self-judged criteria so they can be read apart. The "who judged each cell" table goes into the comparison section when comparison is allowed and under judge consistency when it is not — who judged is a fact, and it does not stop being one because an invariant refused the comparison. Efficiency metrics stay parallel, never summed, and every one of them counts **completed cells only** (`judged` / `archived` / `releasable` / `released`): active time (summed delegation durationMs), tool calls (the rounds' `toolCalls.count` summed; a dash rather than a 0 when no round reported an accounting — "nobody reported it" is not "it used none"), listed price (only when run.meta.pricing records one), delegation rounds (compared only on tasks both sides completed), tokens only within the same model. An unfinished cell's delegation time buys an unknown fraction of the work, so pooling it produces a number that means nothing — pilot A's two harnesses both read 21.0 min of active time, and the tie was one dsh cell that had only ever run stage one. What was excluded is printed on its own line under the table, by condition and state; `results.jsonl` is unaffected. The procedure invariant also prints `run.meta.subset` when the run recorded one, so a run that covered part of its plan cannot be read as a complete one. An expectedNs namespace whose verdicts were all written by `tool:` origins raises a red flag at the top of the summary.

- **usage.jsonl** — the spend ledger, **one line per delegation round**: `{run, cell, attempt, condition, task, stage, round, counted, observedModel?, cliVersion?, durationMs?, usage?, toolCalls?}`. Nothing is aggregated here and nothing is priced — the efficiency table is summed from it, and an outside pricing step reads only this file. `counted` says whether the round is inside the table's scope (current attempt, finished stages — T23's rule): summing a condition's `counted: true` rows reproduces its table row item for item, while the `counted: false` rows are the spend the table deliberately excludes, kept here rather than dropped so an outside reader can choose its own scope. Every unreported field is absent, never zero-filled — "nobody reported it" and "it spent nothing" are different facts.

The authoritative verdict source is picked PER CRITERION, in order (human-final > llm-draft > script, majority across that layer's samples), so one cell's score may come from several layers and the report names the mix; reps are independent samples and attempts are infrastructure retries — every attempt's verdicts land in results.jsonl, aggregation uses each cell's latest attempt.

### Criterion polarity and the weight table (protocol §6.5)

`pass` always means "the criterion holds". A negative criterion words a DEFECT, so its holding means the defect is present — which is why the report's main axis is the **scored-criterion count**: a positive criterion scores 1 when it holds, a negative one scores 0 when it holds and 1 when it does not. The weighted score is Σ `weight` × the fraction that criterion earned, so a negative weight subtracts on its own. The summary also carries a separate «negative criteria that held» table (which cell, which criterion, what proportion, what evidence) — the defect list.

Criteria scored proportionally (F2 / F3's C1 and C2) carry an optional `ratio: {passed, total}` on the verdict (protocol §6.5): the report scores `passed / total` instead of the boolean (a negative criterion scores the remainder, `1 − passed/total`), averaging the proportions across samples of the same criterion. `pass` remains the boolean fact (the criterion **fully** holds) and `ratio` only refines it — a consumer that does not understand `ratio` degrades to the strict boolean and can only under-count. The proportion travels in the field alone: the report **never** parses a `通过 6/9` prefix out of `evidence`, and a ratio with `total ≤ 0` or a `passed` out of range is treated as absent and named in the notes.

Polarity comes from the rubric, never from the verdict. The rubric lives in the grading layer and never enters a bundle, so after exporting, the run DERIVES a weight table from that layer into `<bundle>/report/rubric-weights.json` (`dataseek.rubric-weights/1`: `{task, id, weight, negative, kind, axis}` — identifiers and numbers only, **no criterion text and no evidence**, which is why it needs no leak gate). The report prefers that table and falls back to a rubric inside the bundle's dataset layers (a deliberately guarded export). With neither, it prints counts only and says plainly that the polarity is unknown and the counting assumes every criterion positive, reporting the negative-criterion count as unknown — "cannot tell" is never rendered as "no defects". `report` only reads this file; it never rewrites it.

### No `repo` parameter

T58 narrowed the tools' `repo` parameter to "may only restate this session's datasets binding", because an agent told there was no binding searched the disk with glob and edited a pilot plan somebody else was running inside a checkout several agents share (walkthrough gap G1). T73 removes the road altogether: the tools have no `repo` parameter and the evaluation reads no binding — a dataset is read only as `<registration id>/<set> @ commit` (`git show` / the materialized view), and what the evaluation writes goes into the deployment's state directory. An agent has no path to point anywhere, so there is no way around.

Configuration is `tools: 'all' | 'none'` (default `all`) and it MOVED to the **companion row**; this row no longer has that key. There is no finer grouping because there is nothing to group: the model-tool face registers no tool that can start, advance, or finally judge anything. Under `none` (or with no row named at all) the model simply does not see these seven tools; this package's service face and CLI stay mounted, while the `/eval` slash command follows the companion row's preset grant (`tools: none` gates only the model face — the human face is not tiered: a named row means a visible command).

Tools join through **deferred injection** (`ctx.inject(['tools'], …)`), not an apply-time `ctx.get('tools')` probe: the probe races the tool registry's own mount order and loses, so the tools silently never register and nothing says so (room and worktrees each shipped this same fix). Deferred injection fires when the registry appears and never fires in a composition without one — such a composition keeps the slash, CLI, and service faces and never fails boot. The `tool:eval` prompt section rides through the same deferred door on `systemPrompt`.

## Starting a run: three doors, one cancel path

A run is a BACKGROUND JOB, not a reply. `/eval run` registers it as an
`eval-run` job and answers IMMEDIATELY with a job id and a run id: the turn
ends, the session closes, the browser tab closes — the run keeps going. It
used to live inside the turn that started it, so the initiating surface going
away took the whole run with it (I3·T22 step 5).

| Door | For | Shape |
|---|---|---|
| `/eval run <experimentId>` | a person, in the instance (the default) | starts the job and replies `job <id> · run <id>`; read the log with `job_output` |
| `/eval run <experimentId> --wait` | short interactive runs (`--dry-run`, a one-cell plan) | the old shape: the reply comes when the run finishes, byte for byte what it was before this change |
| `dsh-eval run --experiment <id> --instance <url>` | CI (no browser) | starts the same job through the instance's Remote face, follows the log to the end, exits with the job's verdict |

- **There is exactly one cancel path**: `job_kill <jobId>`. It calls the job's
  cancel → the run's `AbortSignal` → the same lever the per-cell budget timer
  pulls (`localAgent.cancel` on every in-flight delegation). A cell the cancel
  caught is NOT retried and NOT forced anywhere: it stays in the state it was
  in, which is what makes `finalize` count it `interrupted` (T23's category);
  a cell that never started stays `pending`, which is `not-started` — a
  different fact. The run records `run.meta.cancelled`, and the bundle is
  still exported (a cancelled run's cells are evidence).
- **The parent session**: a delegation needs a LIVE AGENT, not merely a
  session record (the family facade's `requireLiveParent`). A job started by
  `/eval run` parents to the calling session — its agent outlives the tab —
  and a run started without one (the Remote/CI door has no calling session)
  opens its own session for the delegations and closes it when the run ends.
  The reply says which of the two happened. **The session it opens carries a
  working directory** (T29d): the run's own cell root,
  `<stateRoot>/cells/<runId>`, created before the session claims it. A
  container round passes no per-round cwd (inside a unit a host path means
  nothing), so the provider falls back to the parent session's — and a parent
  with none made every container condition refuse with «the parent session has
  no working directory to run the CLI in», a sentence about the orchestrator's
  own plumbing delivered as though the harness were at fault (I4·T29c). The
  readiness text of the two start paths is therefore identical, and a test
  pins it.
- **A composition without a jobs service** is not refused: the run is waited
  on in the turn, and the FIRST line of the reply says what that means.

```sh
/eval run <experimentId> [--wait] [--concurrency N] [--dry-run] [--keep-units] [--out DIR] [--retries N]
                         [--only id,id] [--max-cells N] [--ignore-readiness]
/eval finalize <runId>
```

Starting a run is still a human action, and no run-class model tool is
registered — the write verbs belong to the orchestrator's service face and to
people. What the model can see is the JOB: `job_list` / `job_output` /
`job_kill`, all three already in the evaluation preset.

## slash and CLI

Reached through a symlink — a `PATH` entry, pnpm's `.bin/<name>` — the bin behaves exactly as `node lib/cli.js` does: the entry guard resolves `argv[1]` to its real path before comparing, so a symlinked path can never make it exit 0 doing nothing.

```sh
dsh-eval validate <plan.json>             # validate a plan; JSON report on stdout
dsh-eval run <plan.json> --dry-run        # offline rehearsal: validate + template + matrix + order
                                          #   [--only id,id] [--max-cells N] rehearse a subset
dsh-eval run --experiment <id> --instance URL  # start an experiment's run ON a running instance and follow its log (the CI door)
                                          #   [--token T] (or $DSH_TOKEN) carries the instance's launch token
                                          #   [--no-follow] prints the job and run ids and returns
                                          #   [--keep-units] stops every cell at archived and keeps its container; stop it with job_kill there
                                          #   an old plan never imported: run <plan.json> --instance URL (path resolved on the instance), results pair to no experiment
dsh-eval import --from <id>@<ref> --instance URL [--plan NAME]
                                          # bring old plans over from a registered repository as experiments (git show, byte for byte, conditions into the library; a conflict refuses all)
dsh-eval finalize <runId>                 # walk the archived cells through the release gate
                                          #   [--data-dir DIR] [--mission-cli PATH]; drives the dsh-mission CLI
                                          #   a ledger, not a lab: this face releases no container
dsh-eval template <manifest.yml> [--stages a,b]  # print the generated run template
dsh-eval conditions hash <condition.json> # prints { id, sha, warnings }
dsh-eval conditions list                  # the library, per condition: hash, lock state, home verified, provisioned snapshot
dsh-eval conditions diff <a> <b>          # field-by-field diff (each side a library id or a path)
dsh-eval conditions provision <id>        # needs the local-agent service, which no CLI process has —
                                          #   it refuses and points at /eval conditions provision
dsh-eval report <bundleDir> [--out DIR]   # emit results.jsonl + summary.md; JSON summary on stdout
```

Plan paths and `--out` (and `report`'s bundle path) expand `~` at the service
boundary, so all three faces get one rule: a slash argument never saw a shell,
and a CLI argument quoted to survive one did not either.

Data goes to stdout as JSON, diagnostics to stderr; exit codes 0 ok / 1 failure / 2 usage (matching `dsh-lab`). The CLI builds the kernel directly and needs no host — scripts and mounted plugins behave identically. Outside an instance there is no live parent agent and none of the three upstream services, so `run` WITHOUT `--instance` is `--dry-run` only; with it the CLI stops pretending to be an orchestrator and becomes what a pipeline needs — a caller. The transport is the instance's ordinary Remote RPC (`POST <base>/api/dshEval/<method>`, `{args:{…}}` in, `{ok,value}` out, token as `?token=`), and its four verbs are the same job layer the slash face uses. `finalize` needs no parent agent — only the ledger — so it works outside a host by driving the `dsh-mission` CLI in a child process, and exits 1 when any cell's gate refused.

## The Experiments tab (the browser half, I5 · T35a and T36)

This package now has a client half: a **实验室 / Experiments** entry (order 40) in the session's `conversation.view` tab ring. The plugin id stays `eval` — `lab` in this repository is the container-unit plugin, and the two names must not be confused (UI spec R5).

- **Self-hide**: the tab registers exactly while the current session's preset composition names the `@khorsheed/dsh-eval-tool` row, and otherwise does **not register at all** — the tab strip's buttons enumerate registrations, so a component returning null would leave an empty-bodied button on the strip. The criterion reads the official `pluginInventory` Remote and **fails OPEN (visible) on every unreadable path**: a host without that namespace, a pending or failed RPC, a missing or `broken` preset group, and sessions with no preset. The criterion is PRESENCE of that row and nothing else — hiding a read-only viewer breaks no existing run, so no second escape hatch is invented. **"The current session's preset" means the nearest one in its PARENT chain since I5 · T60** (I5 · T39 · G13): a member sub-session — the session a player's delegation ran in — declares no preset of its own (`"preset": null` is the usual condition), so read alone it took the fail-open arm and every gated tab appeared inside a player's transcript while the parent session correctly hid them. Walking to the parent is the honest reading of the criterion, not a special case: a sub-session inherits its parent's composition, so it inherits the answer. A session with neither a preset nor a parent still fails open.
- **The list**: one row per experiment, **drafts and runs in one table** — to the person planning the next comparison they are the same kind of thing (UI spec §五). Columns: name, dataset snapshot, condition count (+ judges), items, reps, factors, status, progress, start time. The only action is 新建实验 / New experiment, a placeholder in this slice (it belongs to T36).
- **Status words**, derived by the pure function `deriveExperimentStatus` from four sources — the plan's validate outcome, each cell's stage in the ledger, the background job's fate, and the **closure mark** a human leaves (T72): draft → awaiting approval → running → judging (every cell reached `judged` or beyond) → done (a human took one of the first three of human review's four exits); plus refused (the job settled as failed), cancelled (the job was killed), **evaluation void** (the fourth exit, grey) and **stalled** (orange). **Only a human makes a run done**: a run whose every cell was `released` but that nobody closed is still judging — "the judge is done" and "a person has said what the result is" are different facts. **Stalled is computed and never written to the ledger**: non-terminal, no live job on this instance, and the ledger (cells' entered-current-stage times, annotations) has not moved for longer than `STALL_THRESHOLD_MS` (`src/experiments.ts`, 10 minutes); a fully judged run is waiting on a person, and waiting on a person is not stalling. The coarse edges are documented on the function rather than smoothed over: the job layer records a readiness refusal and a mid-run throw as the same `failed`; a run with no cells reads as running (stalled once past the threshold); after an instance restart the job record is gone and refused / cancelled are unreachable; a healthy CLI run in another process whose one cell spends over 10 minutes in a single stage reads stalled too — the ledger records transitions, not heartbeats.
- **The detail** is the **four-stage** shell (Design · Run records · Results · Human review, per UI spec §五 v2; v1's seven sub-pages are in git history and T67 is the pass that replaced them). Every stage carries one line at the top: **the status, and ONE primary action**, chosen by a state machine — draft → *Validate it*, awaiting approval → *Approve and start*, running → *See run records*, judging → *Go to human review*, done → *See results*, refused → *Check again*. The reason for the rewrite was a SPEC gap rather than an execution one: §五 v1 fixed what each page held and never what a person does on it, so the seven grew into seven correctly-labelled piles of fields (the overview and the plan review were very nearly the same definition list, and neither had an action). **Approve and start** moved onto that bar in this pass: it is a human act (R1) and it belongs where the person is standing, not behind a sub-page they have to find. After approving the page **stays on Design** — a readiness refusal is written only in the run log below it, and walking the reader to an empty grid would leave behind the reason they are about to look for; the bar turns into *See run records* the moment the status does.
- **Design** (T67; it absorbed the old overview, plan review and conditions pages): ① **Scale and variables** — "4 items × 2 groups × 2 reps", the comparison variables in words (key names only on hover), the dataset version, the judges and their sample count. Four lines. ② **Comparison groups and readiness** — the **readiness badge** (one `✓ 环境就绪` chip when every group passed, otherwise one red cross per group and a *Check again*, with the records folded under Details), the validate lines that need **reading** (the passing ones fold away — a clean check is not news), the group table (only the groups THIS experiment uses; the repository's other declarations are not what this page is about, and the judge's row carries a 判官 chip), and the **planned grid** — items down, groups across, `计划 n 次` in every seat. The grid is **one component used twice**, before the run and during it: v1 had nothing here at all, so the shape of an experiment stayed an arithmetic expression until the run made it a picture, which is too late to change it. ③ **Advanced settings**, folded — order seed, stages, per-cell budget, verdict sources, retries, the item list, the export directory, the environment, the plan path, the readiness records, the job log, the run.meta receipt, and the **author's note** (line breaks kept; in v1 it was a paragraph smeared across the page).
- **New experiment is a four-step wizard** (T67, UI spec §五 v2): ① dataset and items ② comparison groups (existing ones, or a copy of one with named fields changed) ③ judges, reps, stages and the per-cell budget ④ environment and confirm, every field defaulted. It was one bare form asking twenty questions at once with no order and no sense of how far along you were — and the first two of them decide what the rest can even OFFER. Every step goes back and back discards nothing (the answers live outside the steps); only the last step's action is 保存草稿并 validate, and **starting is not on the wizard** (R1). The wizard is only a way of COLLECTING: the same `draftExperiment` verb receives the same document at the end, so a plan a person fills in and a plan an agent drafts in one sentence are still the same file in the same list.
- **A plan document that is gone** gets the three-part error seat instead of `cannot read plan file: /Users/…` rendered onto the page; **a comparison group the plan names and the repository does not declare** is a 「缺失」 ROW rather than a silent omission, and the readiness badge counts the plan's OWN subject list — so a group nothing knows about can no longer drop out of the denominator and leave a 「✓ 环境就绪」 behind. Each red cross carries its reason, read from the review's STRUCTURE (status, whether a lock is there, whether it still matches, whether a scoped home was ever hashed); only the unresolved endpoint has no structural field, and that one is found through the `condition <id>: ` prefix validate itself writes. Nothing parses a sentence for its meaning.
- **The dataset-version row** reads `<registration id>/<set> @ short hash` (T73), and the list's dataset-version column reads the same; the page shows no 「未绑定」 and no path. Before T73 this page had a *Bind a dataset* button and a sentence about binding in the datasets tab; both went with the binding — an experiment carries its own pin, and there is nothing to bind.
- **Run records** (T67; it absorbed the old matrix and cells pages): the **same grid** at the top, filled in by the ledger this time — rep dots, run state, the **verdict** where there is one, and the warnings; under it one row per run record: item × comparison group × rep · run state · score · elapsed · attempts. The filter is §五 v2's five (All / Running / Done / Failed / Blocked), applied **in the browser** over one read of the run: "failed" is not a bucket at all (`halted` is projected into `done` — it IS finished), so a server-side bucket filter could answer three of the five and would have to fetch everything for the other two anyway, and the counts beside the chips would then be counting two different populations. The grid's verdicts are joined out of that same list payload by missionId, so no projection field had to be added for them.
- **The walkthrough's presentation pass** (T67 fixups, 2026-09-18): the five tones actually reach the TOKENS — `ok` had the brand blue and `busy` the body label colour, so 「已完成」 rendered blue and 「运行中」 grey; they are `state-success-primary` and `state-business-primary` now, the datasets tab's hand-kept copy took the same correction, and `tests/tones.spec.ts` reads the stylesheets to hold it (a chip's colour is a token and jsdom computes neither, so no client spec could catch it). 「在态时长」 prints an em dash on a TERMINAL state: the ledger measures from the last transition to now, which on a finished cell is just how long ago the run ended. The timeline's grey bars were the chip being stretched by its grid track; they are real bars now, each scaled against the longest segment of that record, and a segment nobody timed draws none. The bench's two columns are no longer clipped (the third column of the old three-column template survived the criteria moving inside each answer and squeezed them into 509 px), and each column's material is FOLDED with the criteria on top — thousands of lines of stage json above them meant two columns never showed their scoring boxes at one scroll position.
- **The score column currently shows the verdict's SOURCE** (final verdict / judge draft / script / not judged), not a number. The cell projection carries no score, and the score is `report.ts`'s, computed from the **exported bundle** — polarity per criterion from the rubric, the most authoritative layer **per criterion**, majority across samples, and a second weighted pass where the rubric carries weights. Recomputing that against the live ledger would let the run records and the results page report two different numbers for the same cell; no number beats a second scoring rule. The numbers — and which layer each criterion took its value from — are on the results page.
- **After the conditions page merged into Design** (nothing T36 and T58 gave it was lost): **Provision** on every row turns the declaration into a real scoped home, writes `home.sha` back and writes the lock in one press, answering with the same `ok / warn / error` component; the **endpoint cell edits in place**, an empty value declaring "not resolved yet", and the answer names the lock it made stale. Picking two rows diffs them and lists **only the differing fields**. The old 新建条件 placeholder is gone — **choosing a model IS minting a comparison group**, so a single-group experiment gets an *Add a comparison group* invitation above its grid, and pressing it opens the new-experiment wizard (the same `draftExperiment` write, which mints the group and the plan that uses it in one call).
- **What to look at after approving**: the ledger holds no run until `runCreate`, and a readiness refusal happens exactly BEFORE that — a refused run never gets a single ledger row. So the job and run ids the approval answered with stay on the page, and one `runOutput` read by that job id puts the **run log up verbatim**: `readiness <condition>: NOT READY — <reason>` is written there and nowhere else. That block now lives on the Design stage only, which is where approving leaves the reader.
- **An instance with no state root** (no `DSH_HOME`): the list shows runs only with a note; the experiment actions land on the error seat 「这台实例没有评测状态目录」, whose fix is to start the instance with `DSH_HOME` set.
- **The three-part error seat** (UI spec §九): every page's failure site shares one `ErrorState` — a human sentence on the cause (the registered path is not a git repository / not a dataset repository / the path is not there / no state directory / a service is absent), a second on the fix, and the raw exception plus the path folded under Details; `error.message` and absolute paths are off the page. The cause is recovered from the message text (a domain code does not survive the Remote wire), so `tests/error-state.client.spec.tsx` feeds the real service's real sentences to the real classifier — reword a host message and the test goes red first. The datasets tab uses a copy of the same implementation (a client bundle never imports a sibling plugin, UI spec §八). A cell's **readiness refusal** and the run log are not in this: they are evidence, and stay verbatim.
- **No sibling package in the browser bundle**: the mission and datasets projections are computed host-side and sent down, and the tab reads eval's own Remote only (UI spec R2 and §八). The browser verbs carry the session only for the default "started in this session" filter and for the approving parent; since T73 a session no longer decides which repository the browser may see — experiments and the library belong to the deployment. The writes are `approve`, `draftExperiment`, `importExperiments`, the conditions page's provision and endpoint edit, and the three closing actions. The four CI verbs `runStart` / `runStatus` / `runOutput` / `runCancel` are untouched: they take no agent precisely because CI has none, and `runOutput` is now also how the browser reads a run log — one verb, no second implementation. **There is no approve-class model tool and there will not be one** (UI spec R1): the starting verb belongs to the interface.

## The matrix page, the cells page and the cell drawer (I5 · T35b)

The second of the four stages, on the same registration and the same Remote as T35a's shell.

- **The matrix page**: rows are always the item. A comparison is "the same question, asked of different subjects"; letting a reader put items on the columns would line up two different questions and invite reading the difference as a result. The columns are the one factor the reader picked; the remaining factors either band the rows or are pinned to one value by the filter. A factor that is neither **rides along inside the cell**, whose condition list then names more than one id — visible rather than hidden. Every cell carries the same four things: the rep dots, the stage, the stuck warning, and whether its item material agrees with the rest of its row (the odd one out gets a red edge; an unread hash is *unknown*, not a mismatch). Underneath, the run-level summary: item material and environment fingerprint (in the four invariants' own words), unreleased units, judge consistency (`待报告` until a report exists — never computed here), and the stuck count.
- **The run-record list and detail** (T35b, detail rebuilt in T67): the list is the old missions queue filtered to this run, and beside it is **one record in full**. The detail answers three questions in ui-spec §五 v2's order. **The head**: the verdict this cell carries (its SOURCE, not a number) and 成功 / 异常, which is the ledger's — `halted` is the one state that says it stopped rather than finished. **The stage timeline**: how long each state lasted, from the ledger's own transition times — the transition that entered a state is its start and the one that left is its end, so the last state has no duration (running it to «now» would make the panel report a number the ledger never recorded), and one untimed transition breaks the chain on both sides rather than measuring across the hole. **A parameter table**: item / comparison group / rep / attempt / verdict source / item material / environment fingerprint / unit, plus whatever else the ledger labelled the cell with — no JSON. **Attachments**: artifacts named in words (item material / archived workspace / verdicts / stage submission / run log) with the path on the hover, and **each row IS the control that opens it** (I5·T69): one click reads the whole file in place (verbatim in a `<pre>`, NOT rendered as markdown — `stage1.md` is evidence on this page rather than a document, and a renderer would quietly swallow an unclosed fence, which here is a finding); a second click closes it. A directory (the archive, the verdicts) lists its entries and an entry opens through the same door; a refused binary says what it is and how big. One attachment is expanded at a time, and changing records collapses it — another record's output must not stay on screen under this one's header. The receipts (attempts, checkpoints, annotation namespaces) fold away; verify output stays verbatim. The three gestures are unchanged: **re-run with a reason** (required; the category is mission's own infrastructure / operator / outcome), **release check**, and **export bundle** — plus 打开子会话, which hands the player's child session to the host's own child-session view to READ that delegation's transcript (the member composer and dock there are local-agent's), disabled with its reason on a cell that recorded none. **Every judge round has one too** (I5·T69): a judge is a delegation like any other and its transcript is the same kind of thing as the player's — this page simply never had a door on it, so «why did it judge that way» could only be guessed from a verdict's one-line evidence. A round that never started a session is kept as a row with its button dead and its error beside it: «this judge round did not run» is an answer, and dropping the row would read as the judge never having judged at all.

  This page renders **no transcript of its own**. A container round's player is the sub-dsh inside the unit, and local-agent-dsh's session mirror folds its session into the **host-side child session** round by round (`persistChildSession` puts it on disk), so it is a host session from the start — it is in `session/list` (`origin: subagent`) and the host's own child-session view serves every message and tool call of it under the subagent address. Copying the session directory, or drawing a second timeline, would both be solving a problem that does not exist.

  **The address needs the parent** (found in I5·T69's live acceptance): `sessions.open(childSessionId)` selects the row and then fails to load its history — *subagent Sessions require their durable parent address (session/agent-busy)* — which is what this button had been doing on both paths since it shipped. The cell detail therefore carries the run's `originSession` (decision 1: a run's parent is the parent of every delegation it made) and the client refreshes that parent's catalog before handing the host `{parentSessionId, childSessionId, mode: 'one-shot'}`; no parent recorded, a rejected refresh, or a child the catalog does not call healthy all fall back to selecting by id.
- **The verify output, verbatim**: there is **no `lab` annotation namespace** on this line. The probes (through `lab.verify` on the container path, directly on the host path) are recorded by the orchestrator as a `kind: 'probes'` annotation, and that is what the drawer shows — whole. The exit codes and the "not applicable this round" reasons are exactly what a person opens this drawer for, and a summary would drop them. Calling it "lab's" would name a source that does not exist.
- **The export gate is not eval's**: `exportPlan` / `exportRun` forward to mission's own Remote, where the guarded-layer decision and the fail-closed re-check (every guarded layer confirmed against a FRESH plan) live. The dialog's whole job is to make a person tick each guarded layer on purpose; editing any field voids the confirmations already ticked, because those belonged to the layer set that was on screen.
- **Still no sibling package in the browser**: reads and writes alike go through eval's own Remote (`matrix` / `cells` / `cell` / `cellArtifact` / `retry` / `releaseCheck` / `exportPlan` / `exportRun`, all session-scoped), and the browser half never names mission.

## The report page (I5 · T38)

The third of the four stages, and where step 7 of the eight-step flow (finalize · judging · report) lands in the interface.

T67 added two things to it. Each of the four validity checks carries a **hover saying why that check affects the COMPARISON**: the sentence is constant per invariant id, so it is COPY and lives in the dictionary (a host-composed Chinese string could not exist in both languages), while the `details` beside it are this run's own facts and still come from the bundle. And the efficiency table gained **bars** — active time, output tokens, cache read — each group scaled **within its own metric**, because the three have no common unit and one shared scale would be a lie with a picture attached. The number stays beside the bar (the bar carries the ratio, the number carries the fact); no charting library, just CSS over the host's tokens; a metric nobody measured says so rather than drawing empty tracks.

T71 calibrates the conclusions to what the data can carry (proposal D7). The checks go from four to **five**: the fifth, 「判定覆盖一致」 (verdict coverage), is checked pair by pair — for two cells of the same item and rep, each criterion must have a judge or human verdict (human-final or llm-draft) on both sides or on neither; a side left with only the script's verdict, or nothing, fails it (pilot-d's dsh-full cell lost both judge calls while the other side had the judge's draft, and subtracting across the two sources printed "Δ = 4"). Its scope differs from the first four: those are preconditions of the whole run and any one failing still closes the section; coverage is a property of **that pair**, so failing it only degrades that pair to description — per-item scores and per-rep deltas stay, the interval and the rank go, and `rankReason` reads 「判定覆盖不一致：<item> 的 <criteria…> 在 <group> 没有判官 / 人的判定（判官缺席 / 仅脚本）」; `comparisonAllowed` and the criteria-table gate still look at the first four only. "Judge absent" is read from the `judge-parse-failed` annotations already in the bundle, and the failure text goes into the details verbatim. A person changing one criterion does not trigger it — a human verdict counts as judged. **The confidence interval is given by item count**: with k < 3 items carrying a difference there is no interval (`ciWithheld: {tasksWithDelta}`; the page and summary say 「只有 k 道题有差值，给不出区间」); from k ≥ 3 it is computed as before, but with n < 3 it is marked `ciAdvisory` and the page says 「仅供参考，未达排名条件（每题需跑满 3 次）」. The ranking gate is unchanged: n ≥ 3 and an interval excluding 0.

- **It reads a BUNDLE, not the ledger**: a report is a projection of an EXPORT. So the page looks for one first — the directory you just typed into the export dialog, **the directory the run's own export note recorded** (T60), the plan's own `exports`, then `<dataset repo>/exports`, trying `<runId>-bundle` under each — and when there is none it shows "no bundle yet" plus **which directories it looked in**, and offers an export button and a box to name another directory (a run started with `--out` records nothing in `run.meta` about where its export went, and without the box the only way out is to export it again). "Not exported yet" and "no report" are different facts, and showing the first as the second sends a person to investigate a run that is not broken. Export from the page and it re-reads against the directory just written (the dialog takes a free-text path; not remembering it would leave the page calling a freshly written bundle 未导出).
- **The comparison gate shuts host-side, and the browser cannot open it**: when any of the first four invariants is violated or unverifiable, the paired data **does not cross the wire at all** — `pairs` is empty, so there is nothing for the page to render even if it tried, only the line the UI spec asks for: 比较节未开, naming which invariants did not pass. An "allowed" boolean beside the data it gates would hand that rule to the front end to remember to check.
- **Five checks, five rows**: `ok / violated / unverifiable` each keep their own word (never collapsed into pass/fail), and every row lists its `details` verbatim underneath — a status word with no facts under it is just an opinion.
- **The paired difference table**: one row per item — both sides' scores, Δ, the per-rep deltas, n, and **who judged this row**. The judge conditions and models come from the judge assignments of that item's cells on both sides; if ANY of those cells was self-judged (the judge's model is that cell's own player model), the whole row is marked 自评 — decision 9 relaxed the exclusion and made the report disclose it per cell instead, and a warning shown on only some of the cells behind one number warns about nothing. Two weighted columns appear when the rubric carried weights; the confidence interval and the **ranking verdict verbatim** (including the refusals, such as "n = 2 < 3，不排名") are copied from the report.
- **The criteria × comparison-group table** (T54 follow-up, 2026-09-18): the pair table answers «which side won» and nothing else — the user's words after reading the results page were «I cannot see the per-dimension scores, nor what the judges based their verdicts on». The data was always there (every line of `results.jsonl` IS one verdict); the projection was not. There is now one table per item: rows are criteria (id, dimension = the rubric's `axis`, weight, polarity), columns are the comparison groups, and each cell is what that criterion concluded in that group — `✓` / `✗` (a negative criterion that holds is a defect and wears the ✗ colour), the proportion for a proportionally scored one, and how many reps it held in when there are several. The small print under it is where the **score came from**: `人 1 / 判官 3` is exactly which layer each criterion took after the per-criterion merge. **Opening a cell** gives the verdicts verbatim: the evidence (folded to one line), the judge's condition and model (the report is where the blind comes off), every sample listed; a criterion a person re-judged is marked «人已改判» and **the judge's original verdict stays underneath**. The bottom row is the item's total, taken from `scoreOf` itself rather than summed from this table's own column — one computation, so the two tables cannot disagree. **The comparison gate is unchanged**: when the invariants did not all hold this section does not cross the wire, exactly as `pairs` does not. **A single-group run gets the table too** (one column): the grounds a judge gave do not depend on there being something to compare against. `summary.md` carries the same table, with the evidence folded into a `<details>`. Each cell takes the SAME road to the records as the pair table's numbers (T69): a cell carries the `missionId` of every verdict behind it, so one record behind it opens that record and several leave the record list standing under its chip — no third jump.
- **The efficiency table stays parallel**: active time, delegation rounds, tool calls, output / input / cacheRead tokens — one row per condition, never summed into a score. **A dash is not a zero**: a condition no round reported a tool-call accounting for prints `—`, because "nobody counted" is not "it used none". Two lines under the table: the cross-model caveat when more than one model is present (frozen decision 10), and the unfinished cells the efficiency scope excluded (T23).
- **Judge consistency** splits one judge resampled (multi-sampled criteria, agreement, Cohen κ) from the panel across judges (cross-judged criteria, all-agreed, κ) — reading two judges' disagreement as one judge's noise conflates two things. κ is NaN in the degenerate case and crosses as `null`: JSON has no NaN, and rather than let it become a quiet null on the way, it is converted where the reason can be written down.
- **Two actions**: **finalize** calls the `finalize` verb, walking every `archived` cell of this run through the release gate. It is a run-wide write from a reading page, so it **asks once** before it walks, and the outcome is shown cell by cell — which cell the gate refused, in the gate's own words, what became of each container, plus the walk's log verbatim. **Export** reuses the run-record dialog (the gate still lives on mission's side).
- **One export writes two things** (I5 · T60 · G15): mission writes the bundle, and eval writes `report/summary.md` (with `results.jsonl` / `usage.jsonl`) INTO it, by the same function `dsh-eval report` calls — the receipt names the files that landed. Before this the page exported and then printed a command line for the reader to go and run in a terminal, which is how a walkthrough with **every surface on screen** still ended at a shell. The run's own export at the end of a run writes the report too. The CLI verb stays: a bundle from anywhere can still be given a report. A report that cannot be rendered does not unexport a bundle — the receipt says so and prints the command.
- **Where the bundle went is recorded on the run** (I5 · T60 · T53): every export writes one run-level note (`orchestrator` ns, on the run's first cell; read by scanning every cell for the newest) carrying the export directory, the bundle directory, the time, the layers included and the snapshot reference. A run started with `--out` is no longer untraceable — the report page tries the noted directory first, and the "look in another directory" box becomes a fallback rather than the only way back.
- **A bundle older than the final verdicts says so** (I5 · T60 · G17): the page shows the bundle's own `manifest.json` `exportedAt` and compares it with the run's newest `human-final`; when the bundle is older it prints one plain sentence and an **Export again** button — the final verdicts are written after the bundle and do not travel into a directory already on disk, while everything downstream is read from that directory. The repeat REPEATS the recorded export (same layers, same snapshot reference) into a NEW directory, `<original>/re-<timestamp>/`, writes the report with it, and leaves the old one byte for byte. It repeats and never widens: nothing guarded is re-confirmed, mission still re-checks against a fresh plan, and a layer that became guarded refuses the whole call and sends the reader back to the dialog to tick it on purpose. The judge bench carries the same sentence and the same button — the page that writes the verdicts is where this belongs.
- **Unreclaimed units** (T57 · G18): the top of the page counts the containers this run has not let go, read from `runUnits` — lab's own list, not the ledger's. Above zero it offers **回收**, which is the `finalize` call again rather than a second path: reclaiming a container *is* its cell passing the gate, and a verb that skipped the ledger would be the force this seam refuses. The section under it lists each container with its cell's state, because that state is what says whether 回收 can still take it (`archived`) or only `--force` can (`released`). An instance with no lab renders **未知**, never `0`: a confident zero from something that never looked is how a held container stays invisible.

## Human review (I5 · T37, T67)

The fourth of the four stages, where **step 8** of the eight-step flow (the final verdict and the first draft of the analysis) lands in the interface — and the **only write entry the `human-final` namespace has anywhere in this family** (UI spec R1: approving, logging in and the final verdict are always a person's act).

- **The queue is by ITEM, and one item's answers come up side by side** (T67, UI spec §五 v2): one row per question on the left, carrying how many answers it has and how many are graded; opening it lays those answers out **beside each other**, one column each — de-identified, numbered in the run's own seeded order, and each carrying a full criteria form and its own button. The reason is the standard: a person reading four answers to one question applies one yardstick to all four, and reading them a page at a time is how a yardstick bends between the first answer and the last. **It is not a choice between them** — the verdict contract is untouched, one score per cell written against that cell's own criteria; side by side changes what a grader can SEE, not what the ledger receives. In-flight answers are therefore keyed by ticket (several are being written at once, and one submission clears only its own column), and the evidence inputs carry the answer's number in their label (four boxes named «evidence H1» are four boxes a screen reader cannot tell apart).

- **Blind is a property of the PAYLOAD, not of the page's self-restraint**: what `judgeQueue` sends contains no condition id, no harness, no model — **and no missionId either**. The orchestrator names cells `<item>-<conditionId>-rep<N>`, and a condition id names a harness as often as not, so sending it to the browser would put the subject in the DOM. Each cell therefore arrives as an **ordinal plus an opaque ticket** (`sha256(runId\0missionId)` truncated to 16 hex, resolved back host-side on write), and the panel reads **Judge A / Judge B** (by the run's own sorted judge order — stable, and nameless). The numbering follows the run's own seeded order, which is itself part of the blind: consecutive numbers say nothing about which cells share a condition. **Unblinding happens on the report page** — after the verdict is recorded, where it cannot change it.
- **One de-identifier, not two**: the middle column's artifacts come out of the SAME `deidentify` the run loop feeds the LLM judge, over rules rebuilt from the same `run.meta.conditions` (each condition's `model.declared` and `harness.name`). A second scrubber would be a second place for the same red line to be wrong, and the two would drift the first time a harness alias was added to one of them. The text is read from the **archive** (`archive/workspace/`, written by the host path's directory copy and the container path's `lab.archive` alike), so the bench keeps working after the per-cell scratch directory is gone. Each file reports **how many fingerprints were replaced** — the one number that tells a grader the scrub actually ran.
- **Three things side by side on the right**: the rubric's `kind: human` criteria (`objective` belongs to the probes and `llm-draft` to the LLM judge, and neither is asked here — a criterion the author marked `human` is one they decided no model should settle), every llm-draft value and its evidence **per judge per sample** (self-judged samples carry the mark), and the person's own input. Polarity comes from the RUBRIC: `pass` always means the criterion HOLDS, and a negative criterion holding means the defect is present — which is why 负向 / veto / weight are printed at the head of the row. It is the only thing standing between a grader and an inverted answer.
- **One layer scores a CRITERION, not a cell** (I5 · T54, the user's call of 2026-09-18): the report takes, for each criterion independently, the most authoritative layer that judged IT (`primaryPass`, `human-final` > `llm-draft` > `script`) — a criterion a person re-judged scores on their word, one they did not still scores on the judge's, one no judge touched on the script's. A single cell may therefore mix layers, and the report must SAY which. **The old rule took the best layer for the whole cell**, so the first human-final verdict on a cell — even one answering a single `kind: human` criterion — dropped every llm-draft-only criterion from its score (measured on T37: the judge answered 4 criteria, a person re-judged 1, the score fell to 1 and the other 3 vanished with nothing on any page saying so; on a synthetic bundle the paired mean falls from 4 to 1). A rule whose cost is invisible at the moment it is paid is the wrong rule. With the merge in place the bench's sentence changed too — from «it drops your other criteria» to «it covers only what you answer; the rest stays the judge's» — and it still names them (`draftOnlyCriteria`), no longer as a cost but as the fact that this record's score now has two authors. **Historical reports move when recomputed**: old bundles are not migrated, and re-exporting one is what puts it on the new rule.
- **Append-only**: `humanFinal` forwards to mission's `annotate(ns: human-final)` and does nothing else. Grading the same cell again **appends** an annotation; the report reads the latest value per criterion, and the earlier one stays in the ledger — so the page tells a grader plainly that recording again appends. An identical repeat is a no-op by mission's own rule, and the page says nothing was written rather than claiming a write.
- **`by` is the SESSION**: the annotation's `by` is `tab:<sessionId>`, the same tag the drawer's retry and the report page's finalize use; the verdict document's own `by` is `judge-bench`, the protocol's word for this origin. The red flag at the top of the report watches for the `tool:` prefix — a final verdict written from here **cannot** raise it, because there is no model anywhere on this path.
- **Every verdict needs evidence**: `dataseek.verdict/1`'s `evidence` is "a checkable fact, not an opinion"; a blank one is refused host-side and the button will not send it either — once a grader's reasoning is gone, the verdict can never be reviewed. Unanswered criteria are **not sent**: a criterion nobody touched is not a verdict of "does not hold".
- **The agreement header is computed live, off the ledger**: same-judge κ, cross-judge, and llm-draft against human-final, all through the report page's own `judgeConsistencyOf` (widened to a structural input for this, not copied). Only the source differs: the report reads a bundle, the bench reads the **live ledger** — the verdict a grader just recorded has to move the numbers they can see, not wait for a re-export.
- **No model tool, and there will not be one**: `@khorsheed/dsh-eval-tool` registers no twin of `humanFinal`. R1's 终评是人的 holds here because the toolset has **no path to this code at all**, not because a check turns a model away.

## The four-stage journey and conclusion-first results (I5·T72)

T67 folded the detail into four stages with one "status + one primary action" bar per page; T72 carries the same idea to the list, the readiness check, the close-out and the results page, so that everywhere a person only has to answer "what is mine to do now".

- **The list is grouped by whose move it is**: **Needs you** (draft, awaiting approval, stalled, refused, judging — the judge is done and it is a person's turn), **Running**, **Finished** (including evaluation void and cancelled), **Archived** (collapsed, last). Columns: name, dataset version, groups (+ judge), items, reps, compared variables, status, progress, started — plus one column of row actions: **Rerun** on a stalled row, **Archive / Unarchive** on any row with a run. Prototype v5 put stalled under Running; here it is under Needs you, because nothing is driving a stalled run and it stays stalled until someone acts.
- **Default: only this session's experiments**: a run whose `originSession` is the current session counts as mine, and so does every draft (it has no run yet). The header says "n more not from this session", and clicking it switches to All; the toggle lives in `localStorage` (every read and write in try/catch, falling back to the default in a private window) — a per-browser preference, nothing more.
- **Rerun is approving again**: there is no "resume from where it stopped" verb for a stalled run (resuming means knowing each cell's step and whether its unit still exists — the orchestrator's business, not this page's), so Rerun starts a **new run** from the same plan; the old row stays, and the receipt suggests archiving it.
- **Archive changes grouping only**: ns `eval-archive`, written the export note's way (on the run's first cell, read by scanning every cell for the newest); the status rule never looks at it.
- **The readiness checklist**: the awaiting-approval page splits readiness into **Blockers** and **Reminders**, one human sentence per line (dictionary `readiness.<CODE>`, zh and en, raw code and message on hover), with a fix at the end of the line: **Provision** / **Edit endpoint** / **Let the agent handle it** (before T73 there was also **Register repository**, opening the bind explanation; it went with the binding). Blockers are validate's errors plus the warnings about a subject that is not ready; other warnings are reminders. The status bar's primary action is **the first blocker's fix**, and only an all-green list offers Approve and start.
- **Let the agent handle it fills, never sends**: it writes "Experiment <name>, readiness item k: <message>" into **this session's composer draft** (the host's conversation input face, `ctx.sessions.scope(sid).get('conversation').input.for(scope).setDraft`) and does not send — whether to send, or to edit it first, is the person's call. When the input face is unavailable it falls back to the clipboard and says "Copied — paste it into the composer".
- **Human review's four exits**, written in ns `eval-closure`: ① **Submit final review**; ② **Submit with a flag** (a reason is required, e.g. "judge absent, this pair should not be compared"); ③ **Close without final review** (judge's draft only); ④ **Abandon final review** (a reason is required; the run is "evaluation void" from then on). The newest exit wins; after ④ every further exit is refused — voiding says the evaluation cannot stand, and a later "final" quietly turning the withdrawn result back into one is what this seam refuses. The queue names the **judge-absent** cells (every judge call failed, only the script verdict remains) and offers an optional **Re-judge**, which goes through "let the agent handle it" because re-judging is a delegation and a delegation's parent should be a session.
- **Results lead with the conclusion**: the order is **conclusion card → criteria table → efficiency → audit (collapsed)**. The card's first line names the source: final or flagged → "Source: judge's draft + human final review" (flagged puts the reason on top); not closed, or exit ③ → "Judge's draft, not confirmed by a person". The second line is **Validity checks 5/5 ✓ / 4/5 ⚠**, and clicking it opens the audit section. After ④ the whole page is "Evaluation void: <reason>" plus a link to the run records — a withdrawn result has no "but the numbers are still worth a look".
- **`eval_run_status` speaks the same words**: the tool's `status` / `stalledMinutes` / `closure` / `archived` come from the same `experimentDetail` as the list row, so when an agent tells a person "this run is stalled" it uses the word the person sees on the page.
- **Every word is in the dictionary**: status words, buttons, readiness sentences, close-out receipts, group names, in zh and en; the server sends structured fields (code, condition, exit, minutes), never sentences. Colours come from host tokens only.

## Session face: the experiment card on the tool row (I5·T76 · D3)

Once an agent had drafted an experiment in a session, all the session showed of it was a generic tool row: the tool name, a JSON blob, two absolute paths. To learn what was drafted, where it stands and where to look, the person had to switch to the Experiments tab and search.

- **The `eval_plan_draft` tool row mounts the host's `tool.call.toolview`** (key `eval_plan_draft`) and renders an experiment card: the name, the person's question verbatim (protocol v1-rev14's `question`, shown only when present), the scale (tasks × groups × reps = cells), the dataset version (`<registration>/<set> @ short hash`), and the status. The card reads **the call's own block** — the arguments and the `EvalDraftResult` — so a call from days ago still points at the experiment it made; only the status is live (the lab list's row, read once on mount). The result's `planPath` / `conditionPaths` never enter the card's model, so no page can show them.
- **One action, 打开实验 (Open experiment), and no approve button** (UI spec R1): starting spends compute and is a person's decision, taken on the design page beside the readiness checklist. The host gives a plugin no way to switch the conversation's tab (`dsh.conversation`'s `openView` is injected into the conversation frame and the tab header only), so the action falls back: it **marks the row** in the Experiments tab's list (back to the list, 全部 when the row is outside this session's scope without writing the preference, scrolled into view, framed by a primary-colour hairline) and the card says "switch to that tab to see it". When the Experiments tab is not mounted the request waits and is taken on its next mount.
- **No dependency on `@deepseek-ai/dsh-client-ui-tool`**: that package declares the slot; this one registers structurally (`slots.inject` waits for the declaration). In a composition without it the row stays the host's generic one. The card does not self-hide on the preset — the row exists only because the session was granted `eval_plan_draft`.
- **No count on the tab label**: a "running n" on the 实验室 label was considered, but the host re-reads a label only when the slot is subscribed or the locale changes (ui-conversation's `refreshViews`), so a label cannot redraw with state, and rewriting it through a DOM anchor breaks the convention. So there is none.
- **Progress does not flow back into the session** (the S18 fallback): no chip, no notification; an agent that needs progress reads `eval_run_status` / `eval_experiment_get`. The rc.1 candidates examined all fall short; they are recorded in the Agent Note and not wired.

## Visual and copy pass (I5·T63)

The six sub-pages had each grown their own look. The matrix treated **every**
differing key of a condition document as an equal factor — `unit.scopedHome.var`
and a 64-hex `home.sha` sat in the filter row — its column headings were arrays
like `["DEEPSEEK_API_KEY","DSH_HOME"]`, a cell's stage read `mixed (archived /
ws-ready)`, and the report page printed English exceptions and absolute paths
straight onto the page. ui-spec §九 fixed the rules; this pass took both tabs
through them end to end. **Nothing functional and nothing on the data plane
changed**: the host-side projections, the pivot and the report computation are
byte-identical (bar two digest widths, 16 → 12). Everything that changed is
presentation and copy.

- **One word table** (`src/client/vocab.ts`): ledger stages, mission's five
  buckets, retry categories and every leaf of the condition document resolve to
  one dictionary key each, in both locales. Every lookup is TOTAL — a token the
  table has never seen still gets a word, and the token itself survives in the
  `title` beside it, for whoever greps the ledger with it. Stage names are
  generated by manifest position (`stage-<n>`), so they are not a closed enum:
  the first six have their own words and anything past them takes the
  parameterized key rather than a fabricated numeral.
- **«Mixed» is no longer parsed out of a host string.** `mixed (archived /
  ws-ready)` is English tokens in English punctuation; a page that took it apart
  to translate it would break the first time the host reworded it. A cell's
  stage is computed from `cell.reps[].state` instead.
- **A matrix column is headed by its condition id**, with the factor value as
  its subtitle (§九). The pivot is unchanged — a column already WAS a factor
  value and `column.conditions` already said which conditions carry it; only the
  heading and the subtitle swapped sides.
- **Designed factors are separated from the ones that follow from them.**
  `conditionFactors` honestly reports every differing key, so a run that varies
  only the model also "varies" `home.sha`, `env.keys` and `unit.scopedHome.var`
  — all of which are DICTATED by another field (a harness decides its credential
  variable; a provisioned home is what it hashes to). A reader cannot hold one
  of those fixed while varying another, so only the fields §九 names may be a
  column, a band or a pin; the rest are reported in one folded line at the foot
  of the matrix and are never controls. The default column is chosen on this
  side too: given no `column`, the pivot takes the ALPHABETICALLY first
  differing key, which is exactly how `env.keys` became a heading. The browser
  half knows which field is the designed factor, so it corrects the arrangement
  once, on the first answer (naming the column puts `matrixColumn` past null, so
  the branch cannot run twice).
- **A single-factor matrix has no filter row at all**, and with more than one
  factor the column / band / pin controls sit in one disclosure, closed by
  default: the matrix is what the page is for.
- **One set of components.** The status chip, the empty seat, the section box,
  the rep dots, the tables and the drawer are one implementation across both
  tabs (`Chip` / `EmptyState` / `Section` / `Detail`; the 题集 tab carries a
  verbatim copy, because a client bundle never imports a sibling plugin — §八).
  A chip's fill is `currentColor` at 12%, so it follows its tone and light and
  dark have one source of truth: the host's tokens.
- **An empty page says what to do next.** "Not exported yet" is one sentence and
  an Export button, not a paragraph of English. The toolbar's own actions stay
  permanent, and the seat's call to action has its own wording ("Create the
  first experiment"), so the two never read as one button duplicated.
- **No absolute path, JSON document or full digest on a page.** The plan file,
  the bundle directory and the repository root show their last segment, with the
  whole path on the `title` and under «详情»; `run.meta` and the readiness
  records fold away (they are evidence, so they are kept — they just do not take
  the page); digests are twelve characters everywhere.
- **Host-written sentences are still kept verbatim**, folded rather than
  printed: the readiness gate's refusal, finalize's walk log and per-cell
  refusals, the report's explanation of where it looked for a bundle. A refused
  run has no row in the ledger at all, so those sentences are the only record of
  why.
- **Known gap (data plane; recorded, not widened).** `pivotMatrix`'s summary
  sentences and `report`'s invariant details and `rankReason` are assembled
  host-side IN CHINESE, so an English UI mixes the two. Fixing that means
  sending structured fields and composing the sentence in the browser half —
  a data-plane change, recorded here rather than taken on in a copy pass.

### Terminology v2 and number formatting (I5·T63, second pass)

After the walkthrough the UI spec §九 gained three rules (a glossary, colour
semantics, numbers and sentences). This pass took both tabs through them —
**copy, colour and formatting only**; everything structural belongs to T67.

- **Glossary v2** (Chinese UI): condition → 对比组 (arm), factor → 对比变量
  (variable), cell → 运行记录 (run record), snapshot → 题库版本 (dataset
  version), matrix shape → 实验规模 (experiment size), the four invariants →
  实验有效性校验 (validity checks), the judge bench → 人工评估 (human review);
  the grid page is 网格, as §九 writes it. English terms in column headers went
  too: canary, validate, attempt and rep all have words now; `harness` stays.
  The conditions page's key-name headers (`model.declared`, `model.endpoint`,

  `provision` is defined once in the dictionary as 准备环境 so both its sites

  over a sentence saying «condition» is the inconsistency §九's word table
  exists to prevent.
- **Bucket and stage merged into one 运行状态 column.** The stage is the
  specific fact and always shows; the bucket only appears when it says
  something the stage cannot — «blocked» (an unmet dependency) and «scheduled»
  (waiting on a clock). The other three are implied by the stage, and two chips
  saying one thing is the noise this pass removes.
- **Five tones, and one counter-intuitive rule §九 names**: archived /
  releasable / released are GREY, not green. Reaching the end of the pipeline
  is «finished», not «succeeded»; green is kept for `judged`, the state that
  actually carries a verdict. The `blocked` bucket moved from amber to red.
- **Numbers and sentences**: counts compact to `31.5k` (nothing under a
  thousand is rounded — those digits each mean something); durations are
  composed through the dictionary (「4 分 48 秒」 is not `4m 48s` with the
  numbers swapped); judge agreement collapses from three numbers to the word a
  reader acts on — «high (κ 0.85)», κ on the hover, plus one line of advice
  when κ < 0.6, because that is the only number on the page anyone can act on.
  Host verdict sentences became prompts: one arm reads «no comparison data;
  what follows is the baseline», and a closed comparison section moved from an

The new pure helpers (`compactCount`, `durationParts`, `agreementBand`) are

## Hash rules

- **Condition hash**: sha256 hex (lowercase) of the canonical JSON (keys fully sorted, no whitespace); `notes` excluded.
- **planSha**: sha256 of the canonical JSON of the whole plan document (notes included — an edited comment IS a new plan, which is exactly the "same plan, same program" reading).
- **home.sha**: hash config-suffixed files only (`.json .jsonc .yml .yaml .toml .ini .cfg .conf .xml .properties`), fed to sha256 as `<relPath>\0<content>\0` in sorted relative-path order. Deny list: `auth.json`, `.env*`; file names containing `token` / `key` / `credential` / `secret` / `password` / `auth` (case-insensitive); the `credentials/`, `oauth/`, `sessions/`, `keys/`, `secrets/` directories whole; symlinks and oversize files (>1 MiB). File content is never logged or printed.
- **materialization.json**: the item's visible-layer files, path-sorted, each with its sha256; the overall sha folds `<path>\0<fileSha>\0` in sorted order — same-task cells can PROVE identical materialization.
- **Capability hash** (`provisioned.capabilities.sha`, `run.meta.orchestrator.capabilities.sha`): computed by capability-catalog; this package records it and never recomputes it — the canonical form is that package's contract, and eval depends on no sibling. The two byte-identical `canonicalJson` copies are pinned by each side's own tests.
