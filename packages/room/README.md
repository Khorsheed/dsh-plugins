# @khorsheed/dsh-room

English | [中文](README.zh.md)

A room is a normal dsh session marked as a multi-agent group conversation: the standard chat UI hosts several peer agents addressed by @-mention, and the human is the hub. The room's entire state — identity, roster, dispatch records, notification relays, the task board, run states — is a journal of custom session events (`room/*`) on the room session, folded by a pure replay; the host half is the `room` Typert Remote service (`isRoom` / `getState` / `invite` / `updateMember` / `removeMember` / `postMessage` / `confirmRelay` / `dismissRelay` / `addTask` / `closeTask` / `cancel` / `listProviders`), and the client half mounts its generated Remote contribution through `ctx.remote.$mount` and registers only official slot/Definition entries, so the plugin installs into any profile with no edits to core packages. A room is never created apart from a session: the「邀请 agent」action in every session's header (and the members tab's guide state) invites an agent INTO the current session, which promotes it into a room — `ensureRoom` appends the `room/created` marker and seats the main agent, idempotently.

Dispatch: leading `@name` tokens in the room composer address members (multiple @ fan out); a bare message (no leading @) is released to the official submit path — an ordinary turn of the room's own main agent (host-side, a bare `postMessage` is a structured `no-targets` rejection, pure defense). The @-message itself is host-appended as a standard `user/message` event (source kind `user`): the official user bubble renders it and the main agent's next turn reads it — appended, never woken. The @-completion lists only existing members — pure addressing, never invitation — and triggers on a whitespace-or-line-start-preceded `@` anywhere in the draft (a glued `a@b` stays prose; CJK names match); a menu pick is explicit addressing wherever the `@name` sits: picks ride postMessage's `targets` and union host-side with the leading tokens, the text dispatched verbatim, while a hand-typed mid-sentence mention without a pick addresses nobody. There is NO blackboard: every member dispatch carries a uniform prompt of exactly five parts — the member's role instructions (on the first dispatch; an edit rides the next dispatch as an update notice), the room goal (one line on every dispatch, when set), the roster (who exists, with the notification protocol — the member's first dispatch, and later only when it changed since their last dispatch: a member add/remove or a role/rename update; the childSessionId handle journaling does not re-trigger it), the member's confirmed-undelivered notifications, and the dispatch text. Members never see the room's running log; their own CLI sessions (the resume chain) hold their working memory. Same-member dispatches serialize (the family resume lock allows one in-flight resume per child session anyway); different members run in parallel.

Members: the session's own main agent is seated at room creation as an equal member (`main`) — bare human messages reach it through the official submit path, and member activity stays model-invisible to it (custom events never enter `deriveMessages()`). CLI members are local-agent family delegations: the first dispatch starts a fresh child session (`parentSession` = room session), later dispatches resume the same CLI conversation, and the delegation handle is journaled (`room/member-updated` with `childSessionId`) so a reload reattaches the member. The members tab (`成员` view) owns the roster — per-row name/provider/role-instructions/status + elapsed, trajectory jump, interrupt, member edit (rename — the journal fold migrates every name-keyed projection; the main agent itself cannot be renamed — the cwd override, and role instructions, both clearable), remove — and the invite dialog (provider picker reflects the local-agent roster's login state, logged-out providers greyed; a member-level **cwd** field — a read-only display plus a 浏览… button driving the official `workspaces.pickDirectory` wire primitive — empty = inherit the room session's cwd, recorded on the roster, not yet passed to the facade, pending the family's per-call cwd override; role instructions are optional, honestly described as "prepended to the first task message", and omitted when blank; the advanced drawer also carries an optional invite-time **model** field — a text input whose datalist rides the localAgentGateway `harnessModel` read when the family's client half is around, a plain input otherwise; blank = follow the provider default — recorded on the roster and handed to the facade as the `start` call's `model` option on the first dispatch, bound at spawn for exec and live alike, switchable later in the member session). The main agent can also invite: the model-facing `room_invite` tool lands in the same invite path with `invitedBy: 'agent'`. And it can write the shared task board: the model-facing `room_task` tool (add/close/update) goes through the very host functions the capsule UI uses — a task it opens is a public commitment every member and the human sees, distinct from its private todo draft. Its dispatch channel is the third tool, `room_message({ member, text })` — the model-facing equivalent of the human's `@member text` minus the user bubble: the same dispatch internals (journal record, auto-opened task, engine run), with an unknown member rejected against the live roster.

Member-to-member notifications: the family bridge calls room's gate entry `receiveMemberMessage({ from, to, content, parentSessionId, provenance })` (the verbatim-frozen contract); without the bridge, a reply whose trailing own line is `@name <content>` (the roster-taught format) is detected as the same pending relay. Phase 1's gate is always human confirmation: the relay journals as a pending row in the chat flow (`⇢ ada → bill: …` with [确认派发] [忽略]), the sender's receipt is honestly `pending-confirm` (never `sent`); confirming dispatches the notification to the recipient as a continuation (`{from} 给你的通知: …`) and the relay folds to `sent` once the recipient's own session receives the prompt — a relay whose delivery failed rides the recipient's next dispatch in its notifications section.

Task board: the human's management view, journal-driven (`room/task-*`) like everything else. An @-dispatch auto-opens an in_progress task under the target (title = the truncated dispatch text); a member's speech settle closes it (done on completion, cancelled on abort; a failed run leaves it to the human). The strip above the composer card — rendered by the composer takeover itself, since its `conversation.input.dock` seat hides with the official fallback the takeover replaces — groups tasks by member and offers add/close. A fresh room (no goal, no tasks) hides the dual capsules and renders a single 「＋ 邀请成员」 capsule that opens the invite dialog straight from the dock; the pair returns as soon as a goal or a task exists. The board never enters any member's prompt. The composer takeover likewise re-renders the session stats row (turns/steps, wall times, TTFT/tok·s, cache hit, input/output tokens) below the card from the `sessionStats`/`tokenUsage` projections — the room session's own main-agent figures, not a whole-room aggregate. The send row also re-homes the main agent's model seat: the official `conversation.input.model` seat hides with the fallback and cannot be re-hosted (slots are single-owner), so the composer carries its own trigger over the official per-session ModelDirectory (`ctx.modelDirectories.directoryFor(sessionId)` — the same directory the official seat and the /model popup share): a pick writes the durable per-session selection through the session controller's selectModel, exactly what the official seat switches, effort levels included when the model exposes them; it touches the session selection only — @-addressed member dispatches ride room's own submit remote and are unaffected — and a host without ui-model-selection renders no picker. The dock stays live without a reload: the client store subscribes the current session's host-pushed session-event feed and refreshes (300ms debounce) on any journal nudge, so tasks or relays the main agent's tools or the member bridge write land on the capsules within a beat (own mutations refresh eagerly; a 2s poll still covers running-member turns).

Chat flow: a member's reply renders as a member-color-railed block (a 2px identity band down the left of the whole speech) holding the identity row (member-color dot + name capsule + provider), unframed markdown (a body past 600 chars starts collapsed to ~10 lines under a bg-base fade, with an expand/collapse toggle), and an action row replicating the official IconActions chrome (copy, child-session jump, honest duration, hover-revealed clock — deliberately no branch, no TPS); a running member is a ToolRow-isomorphic 24px line (StateDot +「ada 正在工作… · 12s」+ sweep with a `prefers-reduced-motion` fallback), the whole row a jump link into the child session, with a trailing stop button wired to `cancel`; joins/leaves and resolved relays render as compaction-marker-style dim lines; the human's own @-messages render as official user bubbles (postMessage appends a standard `user/message` alongside the `room/dispatch` bookkeeping record, which drives no chat node).

## Install

```sh
dsh plugin add @khorsheed/dsh-room
```

The package is self-mounting: `dsh.bundle.patch` inserts the `room` loader row, and the browser half is discovered through the `dsh.client` block. Removing the plugin removes every surface it adds.

> **The model tools split out (BREAKING)**: the core no longer registers the model-facing `room_invite` / `room_task` / `room_message` tools at the profile root — they now ride the companion `@khorsheed/dsh-room-tool`, **granted per session** through agent-preset compositions (migration: install the companion and add `- id: room-tool / name: '@khorsheed/dsh-room-tool'` to the target preset's `agent.cordis.yml`; the web-dev dev preset already carries it). The room service, members UI, and every Remote are unchanged.
>
> **Session chrome self-hides by preset (M3')**: the「invite agent」header chip and the 成员 tab show exactly when the current session's preset composition names the `@khorsheed/dsh-room-tool` row (the official `pluginInventory` data — no hand-maintained list); every unreadable path fails open, and an actual room always keeps its chrome whatever its preset granted. The members tab hides at the REGISTRATION level: the tab strip's buttons come from the slot registry, so the entry unregisters rather than rendering an empty body.

## Compatibility

- npm release line (`@deepseek-ai/dsh@0.1.5-rc.1`): ⚠️ degraded — **CLI members are unavailable**: they require the local-agent family's public delegation facade (`start`/`resume`/`cancel`, the M1 of `proposals/active/2026-08-18-local-agent-delegation-api.md`, merged on this repo's main), which no published `@khorsheed/dsh-local-agent` carries yet. Invite answers `local-agent-unavailable`; the main-agent member and every other surface work. The 0.1.5 cold-read path rides the handle-based sessionPersistence (`open(id, 'read')` → `read` → `close`; the one-shot `inspect` is gone). minHost moves up to 0.1.5-rc.1 — older hosts stay on the previous release line.
- source line (deepseek-harness master): ✅ full — with the local-agent family (M1 or later) mounted for CLI members (verifiedHost: 0.1.5-rc.1). Structured member-to-member notifications additionally need the family's member-channel bridge (`proposals/active/2026-08-19-local-agent-member-channel.md`); without it the fallback channel (reply's trailing own-line `@name <content>`) carries notifications.

**Persistence**: room registers its `room/*` event types into the harness's `KNOWN_SESSION_EVENT_TYPES` catalog at apply time (a one-cast `Set.add`; the catalog's own header defers a registration surface for out-of-repo plugins "until such a consumer exists" — room is that consumer, and this is the surface's temporary form, to be migrated when the official one lands). A persisted room session reloads on any build with room mounted, and stays refused — safely, by design — on builds without it.

## Known Limitations and Deferred Work

- **The notification gate is manual**: phase 1 always shows the human a confirm/dismiss card; the auto gate with a cascade budget (phase 2) is deferred. The fallback channel's format can drift (a "mentioned, not notified" line is correctly ignored; an in-prose notification is missed — the human's own @ covers it).
- **Member-level cwd is roster-only**: invite records it, but the delegation facade's per-call cwd override (family need R2) has not landed, so members still run in the room session's cwd.
- **Cross-restart CLI continuation** needs the family facade's M4 (delegation-mapping persistence): after a host restart the room session itself reloads, but `resolveDelegation` misses the in-memory mapping, so a member's next dispatch fails its run until M4 lands.
- **Member visual identity is replicated chrome**: `.refChip`, the IconActions row, and the ToolRow sweep are not exported plugin API; room replicates their styles. Upstream visual drift is a maintenance tax — cosmetic, acceptable.
