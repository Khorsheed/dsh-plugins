# Agent Note: 画布卡片类型——参考稿、Agent 设计、确认生效

Status: proposed

## Problem

0.4.14 让 Agent 看得见每块画布自建的分类（`canvas_read_board`，开放的 `kind`），但分类仍然只是一个名字：「人物」卡和「灵感」卡长得一样，没有字段，后来的 Agent 也不知道一张人物卡该写什么。用户想要的是：

- **不同类型长得不一样。** 人物有姓名、身份、性格、关系；世界观条目有名称、所属、描述。复杂一点的，像人物仪表盘那样，把角色的几项状态做成可视的样式。
- **Agent 能给类型提建议并直接生成**，定下来之后，其他 Agent 照这个格式落卡。
- **用户也能自己表达想要什么样子**：手画一张草图、写一段话、贴一张参考截图，用的是跟卡片编辑器同款的编辑器。
- **流程要直观。** 上一轮给的方向（手动建类型 + 让 Agent 设计 + 提议经确认）用户认可，但没说清一个人从哪里点进去、看到什么、点完之后发生什么。

同类产品调研（Sudowrite Story Bible、Novelcrafter Codex、Campfire、World Anvil、Tana）的共同点是：类型的定义权在人手里，AI 负责起草和填写，改动都要确认。Novelcrafter 把字段做成少数几种类型（单行、多行、下拉、引用），每个字段可设 AI 可见性；Tana 给每个字段写一句「AI 怎么填」。没有一家让 AI 静默发明或改写类型。

## Proposal

### 三个名词

- **类型**：就是现在分类面板里的一行（`BoardCategory`），不另起一个概念。一个分类有了**定义**，就是一个「有样子的类型」；没有定义的分类照旧是便签卡。
- **参考稿**：用户写给 Agent 看的「我想要什么样」。它就是一段卡片正文，用同一个块编辑器写：文字、手绘、图片、以后的表格都能用。参考稿不约束卡片，只给 Agent 看。
- **定义**：Agent 起草、用户采用的结构化契约，包括字段表（每个字段有类型和一句「怎么填」）、版式、一张示例卡。采用之后，所有 Agent 都按它落卡；它也是卡片渲染的依据。

### 类型页：一切都在这一页发生

类型页是画布详情里的第三种页面（卡片页、成稿页之外），面包屑是 `画布 › 分类 › 人物`。进入方式：

1. 分类面板每一行加一个「设计」按钮；
2. 筛选条上分类 chip 的 ⋯ 菜单里的「设计这个类型」；
3. 新建分类时，名字输入框下方一行小字「想让这类卡长得不一样？建好后点『设计』」。

类型页从上到下分三段，**始终是这个顺序**，状态不同只是各段内容不同：

```
┌─ 画布 › 分类 › 人物 ────────────────────────── ⋯ ┐
│                                                  │
│  ① 参考稿                                  [编辑] │
│  ┌────────────────────────────────────────────┐  │
│  │ 每个人物一张卡：名字、身份、性格三个词，     │  │
│  │ 和谁有关系。卡面上要能一眼看到身份。         │  │
│  │ ┌──────────┐  ┌──────────────────┐          │  │
│  │ │ 手绘草图 │  │ 贴的参考截图     │          │  │
│  │ └──────────┘  └──────────────────┘          │  │
│  └────────────────────────────────────────────┘  │
│                                                  │
│  ② 定义                                          │
│     （还没有定义：这类卡现在是普通便签）          │
│                                                  │
│  ③ [ 交给 Agent 设计 ]                           │
│     把参考稿和这类卡现有的几张带进对话，         │
│     你可以再补一句要求。                         │
└──────────────────────────────────────────────────┘
```

- **参考稿**用块编辑器写，保存方式和卡片一样（⌘⏎ / 保存）。参考稿是空的，也可以直接交给 Agent，它会根据名字和现有的卡来设计。
- **「交给 Agent 设计」**的做法和成稿的「让 Agent 改」一样：往主会话输入框里追加一段引用，内容是「为画布《X》的分类「人物」（cat_…）设计卡片类型」，不自动发送，用户补一句要求再发。Agent 用新工具 `canvas_read_type` 读参考稿、现有定义和几张样本卡，然后用 `canvas_propose_type` 落一份**提议**。

### 提议：在类型页里看效果，再决定

提议到达后，类型页第 ② 段变成对比视图：

```
┌─ 画布 › 分类 › 人物 ────────────────────────── ⋯ ┐
│  ① 参考稿（折叠）                          [展开] │
│                                                  │
│  ② Agent 的提议 · 待确认                         │
│  ┌────────── 预览 ──────────┐  字段              │
│  │ ┌──────────────────────┐ │  名字   单行  必填 │
│  │ │ 林默         退役刑警│ │  身份   单行  卡面 │
│  │ │ 冷静 · 固执 · 愧疚   │ │  性格   标签  卡面 │
│  │ │ ─────────────────── │ │  关系   引用→人物  │
│  │ │ 关系：苏晴、老周     │ │  备注   多行       │
│  │ └──────────────────────┘ │                    │
│  │ 用示例卡 ▾ / 用「林默」  │  版式：档案         │
│  └──────────────────────────┘                    │
│  Agent：身份放卡面是因为你说要一眼看到……         │
│                                                  │
│  [ 采用 ]  [ 不采用 ]   想改？在对话里接着说     │
└──────────────────────────────────────────────────┘
```

- **左边是预览**：默认用提议里的示例卡渲染；下拉可以换成这类已有的某张卡，看它套上新样子的效果（没对应上的字段显示「待填」）。
- **右边是字段表**：只读，每行是名称、字段类型、「必填」「卡面」这类标记；悬停显示这个字段「怎么填」的说明。
- **想改就在对话里说**。Agent 再提一版，会**替换**当前提议（同一时间只有一份待确认的提议），不会叠出多份。
- **采用**：定义生效。这类已有的卡如果还没填字段，会接着问一次：

```
┌──────────────────────────────────────────┐
│ 已采用「人物」的定义。                    │
│ 这类已有 6 张卡，字段还空着。             │
│ [ 让 Agent 回填 ]   [ 先不用 ]            │
└──────────────────────────────────────────┘
```

  「让 Agent 回填」同样往输入框追加一段引用。Agent 对每张卡调用 `canvas_propose_fields`，卡上出现「字段待确认」的标记，卡片页里逐张 ✓/✗。板上的批量选择加一个「全部采纳字段」。卡片正文**原样保留**，字段是加上去的，不是从正文里挖走。
- **不采用**：提议丢弃，参考稿和已有定义都不变。

### Agent 主动发起

用户在对话里说「帮我把人物做成卡」，这时画布上还没有「人物」分类：

```
用户：帮我给这些角色做人物卡
  │
  ▼
Agent：canvas_read_board → 没有「人物」分类
  │
  ▼
Agent：canvas_propose_type（label: 人物，没有 kind）
  │    → 新建一个 enabled=false 的分类，带一份提议
  ▼
画布上：筛选条末尾出现一个虚线 chip「人物 · 待确认」
  │    点开就是上面那张类型页（参考稿为空，提议在）
  ▼
采用 → 分类启用 + 定义生效 → 回填的问题同上
不采用 → 这个待确认分类连同提议一起删除
```

对话里的回复只说「我在画布上提议了一个『人物』类型，点筛选条上的虚线标签看效果」，不在回复里贴字段表。

### 采用之后：卡长什么样，后来的 Agent 怎么用

```
板上（档案版式）              卡片页
┌──────────────────┐         ┌─ 画布 › 人物 › 林默 ──────┐
│ 林默   退役刑警  │         │ 名字  林默                │
│ 冷静·固执·愧疚  │         │ 身份  退役刑警            │
└──────────────────┘         │ 性格  冷静 · 固执 · 愧疚  │
  名字 + 标记「卡面」的字段    │ 关系  [苏晴] [老周]       │
                             │ 备注  ……                  │
                             │ ───────── 正文 ────────── │
                             │ （原来的卡片正文，块编辑器）│
                             └────────────────────────────┘
```

- **板上**：标题取第一个必填的单行字段，下面最多放 3 个标「卡面」的字段；
- **卡片页**：字段表单在上，正文在下。字段是就地编辑的表单项（单行、多行、下拉、标签、引用选择器）；正文仍用块编辑器。
- **后来的 Agent**：`canvas_read_board` 在每个有定义的分类后面列出字段表和每个字段的说明。`canvas_propose_card` 多一个 `fields` 参数。缺了必填字段或写了未知字段时，会把问题列出来退回，不会静默吞掉。

### 数据形状

```ts
interface BoardCategory {
  id; label; order; enabled
  brief?: string              // 参考稿，和卡片正文同一种 markdown（draw:// 与 attachment:// 行）
  definition?: TypeDefinition // 采用中的定义
  proposal?: {                // 同一时间最多一份
    definition: TypeDefinition
    rationale: string
    renames?: Record<string, string> // 改版时的旧字段名 → 新字段名
    createdAt: number
  }
}

interface TypeDefinition {
  version: number             // 每次采用 +1
  fields: FieldDef[]
  layout: 'note' | 'profile' | 'entry'  // 便签 / 档案 / 词条；自定义 HTML 模板留给后续
  guide?: string              // 这类卡整体怎么写（给 Agent 看）
  example: Record<string, FieldValue>
}

interface FieldDef {
  key: string                 // 稳定 id，改名不换 key
  label: string
  type: 'line' | 'text' | 'select' | 'tags' | 'ref' | 'number'
  options?: string[]          // select
  refKind?: string            // ref：只能引用哪个分类的卡
  hint: string                // 「怎么填」，给 Agent 和人看
  required?: boolean
  face?: boolean              // 在卡面上显示
}

interface BoardCard { /* … */ fields?: Record<string, FieldValue>; fieldProposal?: Record<string, FieldValue> }
```

- 都写在 `canvas.json` 里。没有这些字段的旧文件照常读取，不需要迁移。
- 定义改版时，按 `renames` 搬值。新定义里没有的字段，**值保留**在卡上，卡片页底部显示「已移除的字段」，可以复制出来，不会静默删掉。

### 新工具

| 工具 | 作用 |
|---|---|
| `canvas_read_type(kind)` | 返回名称、参考稿文字、现有定义、待确认提议、最多 3 张样本卡；参考稿里的**图片和手绘作为图片**带给模型（见「风险」） |
| `canvas_propose_type({kind?, label?, definition, rationale, renames?})` | 落一份提议；没有 `kind` 就新建一个待确认分类 |
| `canvas_propose_fields(cardId, fields)` | 给一张卡提议字段值（回填用），等用户确认 |
| `canvas_propose_card` + `fields` | 按定义落卡；缺了或写错字段会列出问题退回 |

### 分期

- **P1a**：类型页（参考稿 + 定义 + 提议预览 + 采用/不采用）、`canvas_read_type` / `canvas_propose_type`、三种版式、卡片页字段表单、`propose_card` 的 `fields` 参数。
- **P1b**：回填（`canvas_propose_fields`、「字段待确认」标记、批量采纳），以及 Agent 主动发起时的虚线 chip。
- **P1c**：自定义 HTML 版式，用字段填模板、在沙箱里渲染（人物仪表盘那种）。
- **之后**：引用字段的反向链接（P2），字段按章节演化和 Agent 提议更新（P3）。数据形状里 `FieldValue` 先只存当前值，以后再扩成带「从哪一章起」的历史。

## Alternatives considered

**只能找 Agent 建类型。** 名字这一层用户随手就能建，Agent 不在或离线时也不该被卡住。调研里没有一家产品把类型的创建权交给 AI，被交出去的只有起草和填写。

**让用户自己拖字段、搭版式（表单设计器）。** 这是 Campfire / World Anvil 的做法，能力完整，但界面很重，而且用户要的是「说出想要什么」，不是「学会一个设计器」。参考稿加 Agent 起草覆盖了这个需求。字段的小修改（改名、删除）以后可以在字段表上直接开放，不影响这套流程。

**把类型页做成弹窗，或塞在分类面板里。** 预览需要宽度，参考稿要用完整的块编辑器，提议也需要一个能来回看的位置；弹窗装不下，也没法在对话进行时一直开着。用详情页的第三种形态，面包屑和返回都是现成的。

**让 Agent 的提议直接生效，出错再撤销。** 定义改变的是这一类所有卡的样子，也是后来所有 Agent 遵守的契约。先预览、再确认的成本很低，静默生效的代价很高。

**字段从卡片正文里解析（正文就是 `名字：林默` 这样的行）。** 不用改数据形状，但格式一变就解析失败，Agent 写正文时也得小心别破坏格式。字段单独存、正文保持自由，两边互不干扰。

**同时保留多份提议并排比较。** 会有状态管理和「采用哪一份」的困惑。一次一份、在对话里改，版本来回靠对话记录。

## Acceptance criteria

- 在分类面板新建「人物」，点「设计」进入类型页；在参考稿里写一段话、手画一个框、贴一张图，保存后刷新还在。
- 点「交给 Agent 设计」，输入框出现引用，发送后 Agent 调用 `canvas_read_type`，**描述出参考稿里的手绘和图片内容**，再调用 `canvas_propose_type`；类型页出现提议，预览能在示例卡和已有卡之间切换。
- 在对话里说「身份改成下拉」，提议被替换，页面上只有一份提议。
- 采用后：已有卡片正文不变；回填提议逐张确认后，板上卡面显示身份和性格；卡片页字段可以直接编辑。
- 新开一个会话，让 Agent「加一个人物：苏晴」。它不需要提示就读到定义，按字段落卡；故意漏掉必填字段时收到列出问题的回答。
- Agent 主动发起时，筛选条出现虚线 chip；不采用后 chip 和分类都消失。
- 旧 `canvas.json` 不迁移也能读，没有定义的分类渲染和现在完全一样。

## Risks

- **Agent 能不能看见手绘。** 手绘现在存成笔迹，给 Agent 的引用里只有「附手绘 N 笔」。宿主的 llm 层支持工具结果里的图片块（按附件引用），但还要确认 `defineTool` 的输出能不能发出这种块。如果不能，就要走宿主改动流程；在那之前，退路是保存参考稿时把手绘栅格化成附件，由 Agent 用读附件的方式看。这一点要在 P1a 开工前先验证。
- **模型对字段契约的遵守程度。** 缺字段时退回会增加一轮调用。`hint` 写得太长又会挤占工具说明的上下文，所以 `canvas_read_board` 只列字段名和类型，完整的 `hint` 放在 `canvas_read_type` 里。
- **定义改版和已有卡。** 字段改名靠 `renames`，模型可能漏给。旧值会保留并显示在「已移除的字段」里，最坏的结果是要手动搬，不会丢数据。
- **放弃的东西**：P1 里用户不能直接增删字段、不能自己调版式细节，都要经过 Agent；三种固定版式也画不出仪表盘，要等 P1c。
