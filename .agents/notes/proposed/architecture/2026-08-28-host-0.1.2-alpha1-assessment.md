# Agent Note: Host 0.1.2-alpha.1 adaptation assessment

Status: proposed

## Problem

Upstream released `dsh-v0.1.2-alpha.1` (GitHub tag `cd5ef814`, full changelog `dsh-v0.1.1-rc.2...dsh-v0.1.2-alpha.1`). We needed to know — before it reaches npm — which plugins must adapt, which self-built mechanisms the host now provides natively, and how the new subagent model configuration compares to the local-agent family. The audit below was done read-only against the tag (two explorer passes: host API surface diff + subagent model-config mechanism), cross-checked against a full-repo grep of this monorepo.

## Key findings

**Not on npm yet.** No `@deepseek-ai/*` package has a 0.1.2 version on the registry (latest is 0.1.1-rc.2). Our peer range `^0.1.0-rc.6` does not match the prerelease `0.1.2-alpha.1` anyway — it will match the eventual stable 0.1.2. Nothing can or should be validated through the normal consumer path until then.

**The one big breaking change: `@deepseek-ai/dsh-client-runtime` was removed** (`be531688f3`). This repo references it 157 times across 107 files (sources, tests, package.json peers). Symbol migration map (verified against the tag):

- `ClientContext` → cordis `Context`
- `createSnapshotStore`, `defineStore`, `SnapshotStore`, `shallowEqual` → `@deepseek-ai/dsh-client-store`
- `ISessions`, `SessionListState`, `SessionSummary` → `@deepseek-ai/dsh-api-session-controller/client`
- `IWorkspaces` → `@deepseek-ai/dsh-api-workspace-controller/client`
- chat node/contract types (`UserMessageNode`, `ConversationNodeDefinition`, …) → `@deepseek-ai/dsh-client-ui-chat` (slots `conversation.chat.node`/`turnTail` moved there with identical keys and owner props, commit `c7d8e32aec`)
- `TypertRemoteNamespaceMap`, `RemoteResult` → typert-protocol (re-exports remain; switch to direct imports)

**Smaller breaking / behavioral items:**

- `SubagentCapabilities` gained a **required** `agentOptions: boolean`; only `local-agent-tool-subagent/tests/scripted-provider.ts:36` (inline literal) breaks at compile time once `@deepseek-ai/dsh-subagent` types bump — production providers use the `NO_START_CAPABILITIES` constant and are unaffected at runtime.
- systemPrompt first-party `order` anchors were re-spread (identity -100→-1000, tool guidance 100–199 → 1000–2900, `TOOLS_SDK: 5000`) and equal orders now sort by name. Plugins that picked `order` to slot between persona and tool guidance (mission 113, datasets 150, local-agent-dsh-headless persona override) land in a different relative position — must eyeball the rendered prompt.
- ui-input-trigger `icon?: string` narrowed to a union; `@`-menu DOM changed (`role="listbox"` moved inside the viewport, new `data-trigger-menu`). Only matters for trigger-source authors; ui-file-preview's mention interceptor needs a re-smoke.

**Verified compatible, no action:** every slot key we use (incl. `settings.plugin.item` — it existed since rc.2, the release-note "plugin configuration slots" is not new), settings registration API, skills registry, `remote.commands.execute` signature (incl. the rc.8 `images` param), `contextPressure` projection schema, chat DOM anchors (`data-chat-anchor-key`, `data-conversation-scroll`, plus new `data-chat-turn`), Remote mounting (browser plugins ride the new one-time-token cookie auth transparently). No plugin ever touched ApiProxy — its removal is a non-event for us.

**Host now ships things we built ourselves:**

- `TurnNavigator` rail (`d38ff54150`) — turn navigation with hover preview, overlapping message-timeline's core. Ours still differs (user-message-only ticks, reading-position highlight, paging); keep-or-retire is a product decision, not a compatibility one.
- `deriveTurnTokenUsage` in `@deepseek-ai/dsh-token-meter/client` + exact per-turn usage in turn tail (`b565df3442`) — adjacent to context-guard's surface; taskpilot's token rollup could optionally consume the official derivation.
- Subagent task-level model config — see below.

**Subagent model configuration vs local-agent family.** `SubagentStartRequest` gained optional `agentOptions: {provider, model, reasoningEffort, maxTokens}`; `tool-subagent` (spawn tool only, web presets) exposes `provider`/`model`/`reasoning_effort` params plus a `list_subagent_models` tool, gated by a user allowlist (`subagent-model-selection` settings namespace, default off). Crucially this covers **only in-process spawn/fork and dsh-sdk children** — the official claude-code/codex/ACP providers are explicitly `agentOptions: false` (`out-of-process.ts`); those two instead got a deployment-level `model?: string` plugin config pinning the CLI's native model for the whole instance. So: official is **not** ahead of us on per-task model selection for external CLIs — parity there. Official *is* ahead in shipping maintained `dsh-subagent-claude-code`/`dsh-subagent-codex` one-shot providers, which overlap our claude-local/codex-local exec path. Our distinctives remain: kimi-cli provider, live resident mode, member-channel, session-mirror, command family, taskpilot.

## Proposal

1. **Do not adapt to the alpha.** Keep the CI harness seed pinned at `dsh-v0.1.1-rc.2`; prod 3080 stays on rc.2. Revisit when 0.1.2 rc lands on npm.
2. When adapting (one focused wave): redirect all `dsh-client-runtime` imports per the map above and drop the peer; fix the `scripted-provider.ts` capabilities literal (`agentOptions: false`); re-smoke mission/datasets prompt ordering, ui-file-preview mention interception, and every Remote consumer against the new token-auth transport; refresh `dsh.compat` + README Compatibility sections.
3. Product decisions to make before that wave: message-timeline vs official TurnNavigator (differentiate or retire); whether the three CLI providers grow an instance-level `model` config (parity with official) and/or declare `agentOptions: true` and pass `request.agentOptions.model` through to CLI model flags (enhancement; our own delegation tool defines the semantics).
4. Track official `subagent-claude-code`/`subagent-codex` maturity; long-term the family may cede the one-shot exec path and focus on live/member-channel/mirror.

## Alternatives considered

- **Adapt now against the source tag** — rejected: nothing installable exists on npm, prerelease API may still churn, and the client-runtime migration is large enough to want a stable target.
- **Retire message-timeline immediately** — rejected: the official rail differs in content (all turns vs user messages) and behavior; the overlap deserves a deliberate product call with screenshots, not a panic deletion.
- **Rush `agentOptions: true` into the CLI providers** — rejected: official itself excludes external CLIs from task-level model routing, so there is no parity gap to close under time pressure; the enhancement can ride the normal adaptation wave.

## Acceptance criteria

- This note exists and the assessment is reproducible from the cited commits.
- The adaptation wave PR builds and tests green against a 0.1.2 (rc or stable) harness seed, with `dsh.compat.verifiedHost` bumped per package.

## Risks

- Alpha → rc may move more API (the chat package split was still settling); the import map may need a second pass.
- message-timeline's overlap with TurnNavigator unresolved: shipping both could confuse users; retiring ours strands its distinct features.
- The 0.1.2 client-runtime migration touches nearly every package — schedule it when no large feature worktrees (room, composition-rollback) are mid-flight, or sequence the merges explicitly.
