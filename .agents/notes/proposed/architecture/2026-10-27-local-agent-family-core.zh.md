# Agent Note: consolidating the local-agent provider family into its core

Status: proposed

## Problem

四个 CLI 提供方（`local-agent-claude-code`、`-codex`、`-kimi`、`-dsh`）加起来约 1.5 万行，旁边的 core 约 8 千行。每个提供方都各自重写了同样的三层：

- **镜像用语。** 同一段 `*_INTERRUPTED_TOOL_RESULT` 文本出现了四次。每个提供方都有自己的 `append*RequestHeader`、助手事件构造、对话记录行追加、`textTask`、`toolCallsOf`、`register*MemberRun` 和 CLI 版本探测。
- **日志结构。** 每个提供方各自给轮次和步骤编号、负责收尾、配对工具调用的生命周期、归属用量。10-24 到 10-27 之间，这一层产生了七种日志无法读取的情况，还有两次「回复被折叠进过程」的回归（见[写入关卡](../../implemented/feature/2026-10-27-member-child-log-guard.md)）。
- **常驻进程生命周期。** 每个实时驱动（1.0k–1.7k 行）都有自己的运行时类、空闲回收、崩溃后带恢复的重启、通道断路器、按成员串行的轮次链、取消处理、流台账和收尾顺序。四份实现之间的差异大多是偶然形成的。

修好一层，只能一个提供方一个提供方地推过去；每次行为变更都要推导四遍。

## Proposal

把每一层共享逻辑分阶段移进 `@khorsheed/dsh-local-agent`，提供方只通过一个小接口接入。每个阶段都单独合入，合入时测试全绿。

1. **写入关卡（已完成）。** core 守住每个成员子会话。提供方仍然自己编号，但日志是否合法由关卡负责。
2. **镜像用语。** core 导出：一份中断结果文本；一个请求头追加函数（只在变化时写入）；一个助手事件和工具生命周期写入函数（一个原子步骤：消息、调用、结果、结束）；一份用量映射约定，各提供方各写适配器；`textTask`、`toolCallsOf` 和版本探测。提供方删掉各自的副本。
3. **步骤写入器。** core 提供 `childLog.step(turn, { blocks, tools, usage })` 和 `childLog.turn()`，在写入时编号（Claude 和 Codex 一直是这样，Kimi 从 59c2cbb24 起也是），并在收尾时关闭轮次。提供方不再处理编号；预留编号只作为预览的标识。
4. **常驻运行时基类。** core 提供一个 `ResidentRuntime` 基类，负责启动和恢复、空闲回收、断路器、轮次串行、取消处理以及「先收尾、后关闭」的顺序，其中包括 Claude 的「收尾后不再写入」规则。提供方只提供协议适配器：stream-json、app-server、ACP 或 dsh `--serve`。

## Constraints

- 每个阶段开始前先协调。实时驱动正在被多个分支修改（`codex/room-local-agent-main-integration` 同时动了三个），所以每个阶段都等这些分支合入后再从 main 开始。
- 阶段内不改变行为。每个阶段只是在接口不变的前提下删掉重复代码，提供方现有的测试不改动、保持全绿。
- core 与配套包之间的方向规则不变：提供方注入 `localAgent`，core 从不导入任何提供方。

## Acceptance criteria

- 每个阶段单独合入，合入时每个提供方现有的测试套件不做修改、保持全绿。
- 第 2 阶段完成后，任何提供方包都不再自己定义中断结果文本、请求头追加函数、助手事件或工具生命周期写入函数。
- 第 3 阶段完成后，任何提供方都不再为持久化步骤编号。生产环境连续使用一周，`pnpm repair:member-logs` 报告的不可读日志始终为零，隔离记录中没有回复内容。
- 第 4 阶段完成后，每个实时驱动只保留自己的协议适配器，四个驱动共用同一套生命周期实现。

## Risks

- 四种协议在一些地方存在差异，共享基类可能会把差异抹平：kimi 的 wire 与 ACP 分离、codex 按条目发送的 app-server、claude 按内容块发送的事件。每个适配器都必须保留自己的顺序规则。
- 如果在进行中的驱动修改分支合入之前就开始某个阶段，会与这些修改冲突。
- 共享生命周期里的一个 bug 会同时影响全部四个提供方，所以第 4 阶段需要把各提供方的实时驱动测试套件放在基类上运行。

## Alternatives considered

- **保持现状，只靠写入关卡。** 关卡能防止日志无法读取，但防不住内容错误（调用被拆开、用量不对、回复顺序），生命周期方面的修复也仍然要重复四遍。
- **一次性大重构。** 范围太大，没法对照四种实时协议逐一审查，也会和正在进行的驱动修改冲突。

## Consequences

- 如果采纳，提供方包会缩减为协议适配器、解析器，以及各自的设置和登录界面。
- Context Lens 和房间读取的日志约定由一处统一维护。
