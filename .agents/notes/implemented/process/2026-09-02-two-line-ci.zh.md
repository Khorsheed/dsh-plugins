# Agent Note: CI 对将要适配的线做报告，对将要交付的线设门禁

Status: implemented

## Problem

`ci.yml` 只钉一个 harness ref（`dsh-v0.1.1-rc.2`），全部门禁都对着它跑。对"我们交付什么"而言这是对的——社区用户 `npm install @deepseek-ai/dsh` 拿到的仍然是稳定线——但它让适配工作处在无人验证的状态。一旦适配 alpha 的代码进了 main，CI 会继续拿一条它不是为之而写的宿主线去检验它并报绿，而它真正针对的那条线，什么都没检验过。

这个缺口有期限。上游 alpha 线一周之内从 `alpha.1` 走到 `alpha.4`，而 `latest` 一直停在 `0.1.1-rc.2`；ankh-guard 的适配即刻就要合并——这个插件在稳定线上的失败形态不是"少个功能"，而是"重启门禁坏了"，因为 3080 跑的正是稳定线，而守着它重启的正是 ankh-guard。

## Decision

两个 job，权限不同：

- **`gates`** —— 稳定线，钉版本，**阻断**，十四步全跑。
- **`alpha-compat`** —— 正在适配的线，**不阻断**，只跑 install + build + test。

`alpha-compat` 的 ref 从 npm 的 `alpha` 分发标签解析（`dsh-v<版本>`，harness 的发布 tag 惯例），而不是在 workflow 里钉死一个版本。

alpha job 只跑与 harness 相关的步骤。hygiene、插件独立性、文档门禁与镜像检查都不读 harness，重复跑它们只会让开销翻倍而不产生任何新信号。

## Alternatives considered

**让 alpha job 阻断。** 否决，而且这是最可能被重新提起的一条。alpha 线按上游的节奏发布——一周四个版本——所以一道必需检查会在不属于我们的原因下、在我们没得选的时刻变红。**一道别人能随手弄红的门禁，大家会学会绕过它**，而被绕过的门禁保护不了任何东西。同一条理由此前否决了慢档测试 project（见[子进程超时那条](../testing/2026-09-01-subprocess-test-timeout.md)）：被默认路径排除的档会漂向从来没人跑，而总在狼来了的档会漂向从来没人读。

**像稳定线那样把 alpha ref 钉死。** 否决：钉住的 alpha 几天就腐烂，一个测试着没人再适配的宿主的 job 会一直通过、同时毫无意义。跟随分发标签的代价是牺牲可复现性——同一个提交在不同日子可能得到不同的 alpha 结果——而这恰恰可以接受，因为该 job 是报告性质的。阻断的那个 job 仍然钉版本、仍然可复现。

**在整个 `gates` job 上开矩阵。** 最直观的形态，代价是每一步都跑两遍。把步骤分类之后即被否决：只有 install/build/test 读 `DSH_HARNESS`，其余与 harness 无关，翻倍只买到时间开销。

**等 alpha 线稳定成 rc 再说。** 否决，因为适配就发生在现在——ankh-guard 今天就要合——而未经目标线验证就合入的代码会一直累积到基线迁移那天，那正是最不希望发现问题的时刻。

## Consequences

- 只在一条线上能跑的包，在基线迁移**之前**就看得见，而不是迁移当天。
- alpha job 可能连续几天是红的，而且不是我们的错。这是跟踪移动靶的代价，也正是它不能阻断任何东西的原因。把它当报告读；红了就看**是哪个包**红。
- `pnpm gate` 在本地仍然对着 `DSH_HARNESS` 指向的那棵树跑，所以适配 alpha 的开发者在本地得到 alpha 的结果、在 CI 得到稳定线的结果。gate 的 harness-ref 提醒会说清本地那个绿是哪条线给的。
- 发布不受影响：适配更新的线不会移动 `minHost` 地板（docs/ops.md），所以适配 alpha 永远不会抬高社区用户的门槛。
