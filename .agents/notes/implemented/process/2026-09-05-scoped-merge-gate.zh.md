# Agent Note: 合并门禁默认按变更分片，并说明自己跳过了什么

Status: implemented

## Problem

`pnpm gate` 每次都跑全仓：26 个包构建、25 套测试、26 个 tarball 打包——在 8 核 / 16GB 的机器上约九分钟，期间机器饱和，开发者不能碰工作区（有一次运行中改了 README，文档门禁撞上那次运行早已读过的 sidecar 而失败）。

测量曾提示开销高度集中：某个会派生进程的套件，在 409 秒的累加测试时间里占了 250 秒。**这个论证在两处都是错的，而更正比原来那个数字更值得记。**

那次读数发生在该包给自己的套件分片**之前**；此后它把慢 spec 拆成四个并发 shard 并注入了测试专用的 sleep 缩放，包自己的测量数字远低于此。而统计口径本身也不成立：把每个子 vitest 报告的 `Duration` 相加，等于把并发工作当成串行计。后来一次运行让这个错误无所遁形——测试阶段墙钟 240 秒，而报告出的"串行总和"是 1085 秒，虚报 4.5 倍。

**经得起更正的是结构性论点，而它从来不依赖那个数字：一个没碰任何包源码的改动不该构建 26 个包。** 开销的分布决定分片值多少，不决定分片对不对。

## Decision

gate 默认按变更分片。build、test、pack 走 `pnpm --filter "...[<base>]"`——自 base ref 以来有改动的包**加上所有依赖它们的包**，依赖闭包由 pnpm 自己算，不由我们算。`--all` 恢复全仓；`--since <ref>` 换基准（默认 `origin/main`，退回本地 `main`）。

**只要改动碰到"会改变所有包如何构建或测试"的路径，就拒绝分片**——`build/`、`scripts/`、`tsconfig.base.json`、`pnpm-workspace.yaml`、`pnpm-lock.yaml`、根 `package.json`、`.github/`。这些路径不构成 pnpm 眼中的"包变更"，所以改一次共享 vitest 预设本会被分片成零个包、跳过全部测试并报绿。**这是分片唯一不能有的失败模式**，因此这道守卫是一份在咨询 pnpm 之前就先检查的路径清单。

另外三项小改动同源于这一次运行：

- **分步计时，以及最慢的五个套件**及其占比。本文里每个数字都是从过往运行的子命令输出里挖出来的，因为 gate 当时只报总时长。**看不见的开销会被算到"gate 头上"，而不是算到真正拥有它的那个套件头上。**
- **声明依赖检查,置于最前且致命。** 一次加了依赖的合并会让热检出的 `node_modules` 落后,构建随后在几分钟后死于一个既不说原因也不说修法的无法解析 import——就发生在这次运行里:197 秒才走到一个 `TS2307`,而 `pnpm install --frozen-lockfile` 五秒就清掉了。pnpm 自己的 `verify-deps-before-run` 覆盖不到:它比对的是各 manifest 与 lockfile,而当时 lockfile 本就是对的,短缺的只有 `node_modules`。因此这道检查直接查构建真正需要的东西——每个声明的 `dependencies`/`devDependencies` 都有目录可解析。peer 跳过,因为本仓对官方包的惯例就是宽松的可选 peer。**只报告、绝不自动修复**:并发 agent 下的仓库根 `pnpm install` 会解析出多个 peer 变体(冲突规则 3),所以只说清修法,交给知道此刻还有谁在构建的人去执行。
- **工作区指纹**（HEAD 加 `git status --porcelain`），开始时记录、结束时复查。树动过就明确失败：这次结论既不属于它开始时的状态，也不属于结束时的状态。

## Alternatives considered

**改为限制并发。** 仍然值得单独做，但目的是**内存稳定性**——16GB 对上 4 路 workspace 并发、每路各起一个 vitest 池——不是速度，而且数字必须在空载与并发两种条件下量出来，不能拍。第一次试图从单次读数推理，产生的正是上面那个误测；**争用机器上的单次墙钟就是噪声**，而一次失败源自"另一个 gate 正在并行跑"的运行，不构成任何证据。

**修那个慢套件，gate 保持全仓。** 论杠杆这是最大的一条，而且正在做——但它归 ankh-guard 的 owner（包级测试归 owner，见 docs/development.md），而且它消除不掉结构性问题：**一个没碰任何包源码的改动不该构建 26 个包**。两个修法互相独立，都值得做。

**按显式包清单分片。** 否决：那把依赖闭包放进开发者脑子里，而第一次有人漏掉一个下游包时，gate 会报一个 CI 随后打脸的绿。`...[ref]` 让 pnpm 拥有这个推理。

**保持全仓为默认，另提供 `--scoped`。** 按"默认值实际上如何被使用"否决：**昂贵的那个默认值，会在赶时间的时候被整个跳过**——而被跳过的门禁保护不了任何东西。把便宜的路径设为默认、把全量扫描设为显式，摩擦就落在伤害最小的地方：mainline 在推送前跑一次 `--all`，而 CI 无论如何都跑全部。

## Consequences

- 一次典型的包改动现在只为自己和下游付费，而不是全部 26 个。
- **分片通过在构造上就是比全量通过更弱的证据。** 这一点写在 gate 自己的输出里（`scoped; pnpm gate --all before pushing`），并且与既有的分工一致：owner 分片迭代，mainline 推送前全扫，CI 无条件全跑。
- **scope 解析的每一个不确定，都解析为全仓**：base ref 查不到、diff 或 status 读不到，以及最关键的那个——包过滤器**报错**。报错与"什么都没匹配到"在输出上完全一样，除非把失败与空值分开，否则它就是一条静默假绿。
- 基准是本地 `main` 而非 `origin/main`。推送是批量的，origin 会落后几十个提交，其中累积的共享层改动会把每个 owner 的运行推回全仓——**永远不分片的分片**。`--since origin/main` 才是 mainline 自己推送前那次全扫的正确基准，也正是那次全扫的表达方式。
- rename 取两端判定。`R  old -> new` 当成一整串做前缀匹配只测到旧路径，一个被移动**进**共享层的文件不会触发回退。
- 工作区指纹哈希的是内容而非 status 列表：一个已被报成 ` M path` 的文件，内容持续变化时那一行完全不变。
- `scripts/gate.spec.ts` 用可注入的 runner 驱动 scope 解析，因此命令失败、rename、未跟踪、非法 `--since`、空 scope 与 `--all` 全部可达，且不需要真实仓库。
- `GLOBAL_PATHS` 那份清单是承重的，一旦出现清单之外的新共享层路径就会无声腐烂。它很短，且紧挨着理由；将来新增共享层目录必须在创建它的同一次改动里加进去。
- `pack-all-dist` 为分片路径加了 `--only` 过滤。CI 与发布波次不传过滤，两者的全仓打包保证不变。
