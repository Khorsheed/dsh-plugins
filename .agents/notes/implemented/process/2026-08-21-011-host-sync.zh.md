# Agent Note: 0.1.1 宿主同步——API 纯增量，pnpm 预发布合并之战

Status: implemented

[English](2026-08-21-011-host-sync.md) | 中文

## Problem

`deepseek-harness` 发布了 `0.1.1-rc.1`(2026-08-21，发布合并 `528c682e06`，现为 `latest` 标签）。rc.8 适配刚落地，问题是这条 minor 线是否又要改源码，以及——事实证明更尖锐的是——仓库对着它能不能装上依赖。

## Decision

- **API 审计：对本仓库纯增量。** 0.1.1-rc.1 的三个破坏性变更（`ProjectionDefinition` 重构为 `stateSchema`/`wire`、`cacheHitPercent` 改返回 `string | null`、转发事件 `credentials/updated` 改名 `credentials/reference-updated`）在我们的源码里零命中：没有包注册宿主侧 projection,local-agent 用的是自己的本地 `cacheHitPercent` 实现，也没有任何代码监听 credentials 事件。零源码改动。`composeProfile` 仍未导出（ankh-guard 降级项维持）。
- **真正的仗在安装上。** devDependencies 提到 `^0.1.1-rc.1` 后，预发布线上的两个 pnpm 解析疾病爆发：
  1. **幻影 `>=0.1.1` 范围**——同一棵树里一个包要 `^0.1.0-rc.6`/`^0.1.0-rc.8`、另一个要 `^0.1.1-rc.1` 时，pnpm 的范围合并会把下界的预发布标记剥掉，产出 `>=0.1.1 <0.2.0-0`，而任何已发布的预发布版都不满足它（`No matching version`)。受害包的 `latest` 都停在 `0.0.1-rc.1`;`latest` 已在 0.1.x 线上的包合并正常。最小复现：`{ dsh-client-connection@^0.1.0-rc.6, dsh-client-locale@^0.1.1-rc.1 }` 在 `dsh-invariants@>=0.1.1` 上失败。解法（保留）:`overrides` 把所有有 0.1.1-rc.1 的 `@deepseek-ai/*` 钉到该版本（75 条，由 lockfile 生成）。
  2. **peer 变体双实例**——混合 peer 范围（`^0.1.0-rc.6` 对 `^0.1.1-rc.1`）把 `dsh-session` 同时解析出 rc.8 和 0.1.1-rc.1(`dsh-subagent` 多达四个同版本变体）。`Session` 类带 `private` 字段，类身份是名义性的，双实例互相不可赋值——local-agent provider 报 `KimiCliProvider is not assignable to SubagentProvider`，错误链末尾是 `Types have separate declarations of a private property 'log'`。75 条 overrides 把全部包收敛到单实例；`dsh-session@rc.8` 数量归零，每包恰好一个变体。
- **供应链排除列表**按 lockfile 里实际的 75 条 `@deepseek-ai/*@0.1.1-rc.1` 记录重写（rc.8 的教训：列表必须随宿主线换，否则所有安装撞发布窗口）。
- **标注**:`dsh.compat.minHost` 保持各包已验证地板（rc.6/rc.8——地板不追线）；新增 `dsh.compat.verifiedHost` 标记审计针对线（全部 `0.1.1-rc.1`),`scripts/compat-report.ts` 改为按 `verifiedHost`（回退 `minHost`）判定，使 `pnpm compat:report` 正确回答"落后还是当前"。
- **部署检出**(`~/code/deepseek-harness`)：沿用 rc.8 程序——备份分支 `deploy-pre-0.1.1`、硬重置到 `528c682e06`、幻影目录清扫、重建。**纯净实例** toolchain 升到 `@deepseek-ai/dsh@0.1.1-rc.1`。
- **后续（2026-08-22,rc.2）**：官方发布 `0.1.1-rc.2`;增量集中在 attachment 图像管线重构 + deepseek LLM 修复 + 一处权限改动回退——本仓消费的面零变更（ui-conversation 仅增 locale 文案）。基线已跟进：overrides 与 `minimumReleaseAgeExclude` 按 75 条 rc.2 记录重写,CI 种子标签 `dsh-v0.1.1-rc.2`,部署检出已重置（备份分支 `deploy-pre-0.1.1-rc2`;prod 在下一次门禁重启时跟进）,全量构建测试绿,19 个包的 `verifiedHost` 扫到 rc.2 并在 README 兼容条目追加复核记录。
- **后续（2026-08-22）**:`local-agent-claude-code` 此前把 `@deepseek-ai/dsh-commands` 放在 `dependencies`，而 kimi/codex 都是 peer——普通依赖会给消费者多装一份私有副本。已挪到 `peerDependencies`(`^0.1.0-rc.8`，与兄弟包一致）；该导入仅用于类型，运行时解析不变。

## Alternatives considered

- **peer 范围提到 `^0.1.1-rc.1`**——否决（依 rc.7/rc.8 笔记）:peer 范围是面向消费者的兼容包络，不是当前线；双实例问题由 overrides 解决，而不是收窄消费者可搭配的范围。
- **overrides 只钉幻影受害包**——先试（14 条），不够：只要 peer 范围混合 rc.6/rc.8/rc.1，任何包都可能撞合并 bug。全量钉官方集合是唯一"每包单实例"的状态。
- **等 pnpm 修合并 bug**——最小复现已留存，可能提上游 issue;overrides 今天保证正确，且可随时移除（它只是重述范围本来就会解析到的结果）。

## Consequences

- 仓库开发基线为 0.1.1-rc.1：全新安装每个官方包单实例；全量构建绿，测试套件是重启的验收闸。
- `pnpm-workspace.yaml` 现在带一个很大但纯机械的 `overrides` 块——每次宿主线变动都必须**重新生成**（不是手改），与供应链排除列表一样是一行脚本的产物。
- 合并 bug 的复现案例留在本 note 里，可能用于 pnpm issue；在此之前，预发布线上见到 `No matching version` 就等于"去 overrides 里钉它"。
- README Compatibility 段增加 0.1.1 行（纯增量审计，✅ full);ankh-guard 的降级 preflight 项维持降级。
