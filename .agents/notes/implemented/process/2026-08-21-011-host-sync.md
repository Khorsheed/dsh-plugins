# Agent Note: 0.1.1 host sync — additive API, pnpm prerelease-merge battles

Status: implemented

English | [中文](2026-08-21-011-host-sync.zh.md)

## Problem

`deepseek-harness` released `0.1.1-rc.1` (2026-08-21, release merge `528c682e06`, now the `latest` tag). The rc.8 adaptation had just landed, so the question was whether this minor line forced another source-level adaptation, and — as it turned out — whether the repo could even install against it.

## Decision

- **API audit: additive for this repo.** Three breaking changes in 0.1.1-rc.1 (the `ProjectionDefinition` restructure to `stateSchema`/`wire`, `cacheHitPercent` returning `string | null`, and the `credentials/updated` → `credentials/reference-updated` forwarded-event rename) have zero hits in our sources: no package registers a host-side projection, `local-agent` uses its own local `cacheHitPercent` copy, and nothing listens to the credentials event. No source change was made. `composeProfile` is still not exported (ankh-guard's degraded item persists).
- **The install was the real battle.** Moving devDependencies to `^0.1.1-rc.1` surfaced two pnpm resolution diseases on a prerelease line:
  1. **Phantom `>=0.1.1` ranges** — when one tree wants a package at `^0.1.0-rc.6`/`^0.1.0-rc.8` and another at `^0.1.1-rc.1`, pnpm's range merge strips the prerelease tag off the lower bound, yielding `>=0.1.1 <0.2.0-0`, which no published prerelease satisfies (`No matching version`). Every affected package had `latest` still on `0.0.1-rc.1`; packages already carrying `latest` on the 0.1.x line merged fine. Minimal repro: `{ dsh-client-connection@^0.1.0-rc.6, dsh-client-locale@^0.1.1-rc.1 }` fails on `dsh-invariants@>=0.1.1`. Workaround (kept): `overrides` pinning every `@deepseek-ai/*` that has a 0.1.1-rc.1 to exactly it (75 entries, generated from the lockfile).
  2. **Peer-variant twins** — mixed peer ranges (`^0.1.0-rc.6` vs `^0.1.1-rc.1`) resolved `dsh-session` to BOTH rc.8 and 0.1.1-rc.1 (and `dsh-subagent` to four same-version peer variants). `Session` has a `private` field, so class identity is nominal and twin instances are mutually unassignable — local-agent providers failed with `KimiCliProvider is not assignable to SubagentProvider` chains ending in `Types have separate declarations of a private property 'log'`. The 75-entry overrides collapse everything to one instance; `dsh-session@rc.8` count is now 0 and each package resolves to exactly one variant.
- **Supply-chain exclusion list** regenerated from the lockfile's actual 75 `@deepseek-ai/*@0.1.1-rc.1` records (the rc.8 lesson: the list must move with the host line or every install hits the publish-age window).
- **Labeling**: `dsh.compat.minHost` stays as each package's verified floor (rc.6/rc.8 — floors don't track the host line); a new `dsh.compat.verifiedHost` field marks the line the package was audited against (`0.1.1-rc.1` everywhere), and `scripts/compat-report.ts` now reports on `verifiedHost` (falling back to `minHost`), so `pnpm compat:report` answers "behind or current" correctly.
- **Deployment checkout** (`~/code/deepseek-harness`): same procedure as rc.8 — backup branch `deploy-pre-0.1.1`, hard-reset to `528c682e06`, phantom-dir sweep, rebuild. **Vanilla instance** toolchain moved to `@deepseek-ai/dsh@0.1.1-rc.1`.
- **Follow-up (2026-08-22)**: `local-agent-claude-code` declared `@deepseek-ai/dsh-commands` in `dependencies` while kimi/codex carry it as a peer — a regular dependency would install a second private copy into consumers. Moved to `peerDependencies` (`^0.1.0-rc.8`, matching its siblings); the import is type-only, so no runtime resolution change.

## Alternatives considered

- **Bump peer ranges to `^0.1.1-rc.1`** — rejected (rc.7/rc.8 notes): peer ranges are a consumer-facing compatibility envelope, not the current line; the twin-instance problem is solved by overrides, not by narrowing what consumers may pair us with.
- **Pin only the phantom-affected packages in overrides** — tried first (14 entries); insufficient, because any package can hit the merge bug once its peers mix rc.6/rc.8/rc.1 ranges. Pinning the whole official set is the only state with a single instance per package.
- **Wait for pnpm to fix the merge bug** — a minimal repro exists and may become an upstream issue; the overrides keep us correct today and are removable later (they only restate what the ranges already resolve to).

## Consequences

- The repo's dev baseline is 0.1.1-rc.1: fresh installs resolve one instance per official package; full build is green and the test suite is the acceptance gate for the restart.
- `pnpm-workspace.yaml` now carries a large but mechanical `overrides` block — it must be regenerated (not hand-edited) on every host-line move, same as the supply-chain exclusion list. Both are one-liner scripts' output.
- The merge bug's repro is preserved in this note for a possible pnpm issue report; until then, any "No matching version" on a prerelease line means "pin it in overrides".
- README Compatibility sections gain the 0.1.1 line as verified-full (additive audit); ankh-guard's degraded preflight item stays degraded.
