# Agent Note: A member's mode tools are never silently empty

Status: implemented

## Problem

An external-CLI room member reaches its mode's plugin tools (for example `game_publish`) through the member bridge: on `tools/list` the bridge asks the host over the loopback socket and appends the mode tools to the room tools. On any failure — socket error, the host answering `ok: false` ("unknown or expired member token"), the host's own listing throwing — the bridge returned an empty mode list, indistinguishable from "this member has no mode". The resident live drivers keep one CLI process per member, and the CLI lists tools once per process, so one failed list removed the mode tools for the rest of that process's life without a trace: the host diagnostics (`mode-tools.jsonl`) log only successful lists.

A prod incident on 2026-11-02: a Kimi member's process spawned at 22:36 (the first round after the host restart at 21:22) got only the 7 room tools. The model, wanting `game_publish`, kept calling `room_read`, the closest name in its list. The host restarts at 22:51 and 23:06 replaced the process; Kimi's own log shows the 38-tool list from 22:54 on. But the wire log shows no `mcp.tools_discovered` / `llm.tools_snapshot` at 22:54 or 23:07, because Kimi records those events only for a tool hash it has not seen before (the full list's hash was already seen). After 22:54 the model still called `room_read` in place of `game_publish`, apparently copying its own failed attempts in context. Host logs from 22:36 are gone, so why that list failed remains unknown.

## Decision

- **The bridge tells "no mode" from "could not ask".** The host answers an empty list for a member with no mode, and the bridge lists nothing extra. Any failure is retried briefly (3 retries, 250/750/1500 ms, each request bounded at 5 s). If the fetch still fails, `tools/list` carries one placeholder, `mode_tools_unavailable`. Its description says the mode tools are absent from this process, that calling them will not work until the member is reloaded (automatically, when its next round starts), and that the model should tell the user which step it could not do instead of retrying or substituting another tool. The incident model's failure mode was imitation, so the description aims to end the retry loop, not explain the outage. Calling it reports the problem to the host again and returns a tool error the room shows. The error never suggests calling the recovered tools by name: a CLI rejects a tool name missing from its list. The failure reason goes to the bridge's stderr. A host-side listing exception now answers `ok: false` (not `ok: true` with an empty list), so it also counts as "could not ask".
- **Background recovery and `list_changed`.** The bridge declares `capabilities.tools.listChanged: true`. After it serves a placeholder, it keeps probing with backoff (2, 5, 15, 30, then every 60 s; timers are unref'd and stop when stdin closes). When the host answers, the bridge sends `notifications/tools/list_changed`. Probes carry `probe: true`, so the host does not mistake them for a served list.
- **The host records what each process was served.** `MemberChannel` keeps, per bridge token (one token per member process), a `ServedModeTools`: `complete` with the mode-tool count, or `placeholder` with the reason. A non-probe list records `complete`. The new `modeTools: { report: { served: 'placeholder', reason } }` request, or a probe, records `placeholder`. The host logs a warn and a `mode-tools.jsonl` line (`placeholder`). Entries are pruned when their token no longer resolves.
- **Self-heal at round start (provider-generic).** `LocalAgentRegistry.memberToolsStale(token)` delegates to the channel's `staleModeTools` and returns a reason in three cases: the process was served the placeholder; it was served an empty list but the room now gives the member a mode whose host list has tools; or the token no longer resolves. Otherwise it returns undefined. The Kimi, Claude Code and Codex live drivers call it at the start of a normal round's accept, which runs after the member's previous round settled because rounds are chained per member. On a reason they retire the resident runtime (`retireRuntime`) and log a warn. `ensureRuntime` then spawns a fresh process that resumes the same CLI session and lists again. A compaction round is not checked. A missing method on an older core keeps the process.
- **"Never listed" is kept.** A token with no record is not respawned. That covers a bridge from before this change (it never reports), and a CLI that lists lazily at its first prompt: Kimi lists at the first `session/prompt`, so at round start a fresh process has no list yet. Respawning on "no record" would replace every resident process at every round start without telling a broken process from a not-yet-listed one. A deploy restarts the host, and the host restart already replaced every resident process (evidence: the 22:51 and 23:06 restarts each produced a fresh Kimi process). So no pre-change bridge survives a deploy, and the conservative rule costs nothing.

## Alternatives considered

**Rely on `notifications/tools/list_changed` alone.** Rejected. On the installed CLIs, Kimi constructs its MCP `Client` without the SDK's `listChanged` option and registers no handler, so it ignores the notification. Codex 0.163's rmcp `LoggingClientHandler::on_tool_list_changed` only logs "MCP server tool list changed". Only Claude Code registers a `ToolListChangedNotificationSchema` handler. The notification is kept as a cheap extra; the round-start respawn is the recovery that works for every provider.

**Respawn mid-round when the placeholder is served.** Rejected: it would kill a running turn. The member works one round without its mode tools, with the placeholder saying so, and the next round heals.

**Detect the imitation loop on the host.** Not built. After the tools came back, the incident model kept emitting `room_read {}` while its reasoning named `game_publish`. A cheap host-side signal exists: in the room command path, a member whose current process was served a non-empty mode list calls `room_read` several times in one round, back to back. A check that also reads the reasoning text would be more precise, but it means parsing the transcript. Either signal could only tell the human or append a corrective note; neither can repair the model's context.

**Respawn on "no report since spawn".** Rejected for the reasons above: it cannot tell a broken process from one that has not listed yet, and old bridges never report.

**Ask the room for a notice event.** Deferred. `packages/room` is being edited concurrently, so this change surfaces the failure through the host log warn, the bridge's stderr, the `mode-tools.jsonl` line and the placeholder's tool error, which shows in the member's run card in the room. A room-side notice can reuse the channel's report once room has a generic member-notice event. It was built on 2026-11-03 as the `room/member-tools` event, together with a status line and reload in the edit dialog; see [the feature note](../feature/2026-11-03-member-mode-tools-status.md).

## Consequences

A member whose mode-tool list fails works that round with a visible placeholder instead of a silently shorter tool list. Its next round runs on a fresh process with the full list, with no user action. The dsh live driver (`local-agent-dsh`) does not get the check: its sub-dsh reaches the bridge through `local-agent-dsh-headless`, which this change does not touch. A mode change on a member whose process already holds a non-empty list is not detected either: the count is non-zero, so the process is kept. The model may keep imitating earlier failed calls already in its context; a fresh tool list does not erase that history.

## Testing

- `packages/local-agent/tests/member-bridge.spec.ts`: `listChanged` advertised; no mode → no placeholder, no report, no probing; failure → 3 attempts → placeholder + stderr + report; calling the placeholder reports again; unreachable socket → placeholder; recovery → `notifications/tools/list_changed`, a placeholder call still points to the reload, re-list drops the placeholder, probing stops.
- `packages/local-agent/tests/mode-tools.spec.ts`: a host listing exception answers `ok: false`; served-state recording (complete, report, probe) and `staleModeTools` for a placeholder, a re-list, a never-listed token, a gone token, and an empty list before and after the mode gains tools.
- `packages/local-agent/tests/member-channel.spec.ts`: the registry's `memberToolsStale` delegates to the channel and answers nothing after dispose.
- `packages/local-agent-kimi/tests/live-driver.spec.ts`: the first round makes no check, a healthy process is kept, a stale one is retired between rounds and the round resumes on a new process (`session/load`) with its token released; a round in flight is not interrupted.
- `packages/local-agent-claude-code/tests/live-driver.spec.ts` and `packages/local-agent-codex/tests/live-driver.spec.ts`: a stale process is respawned before the next round.
