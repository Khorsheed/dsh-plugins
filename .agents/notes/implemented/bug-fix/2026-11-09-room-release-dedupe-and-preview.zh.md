# Agent Note: 协作间暂存回报的补交去重，并显示补交的内容

Status: implemented

## Problem

收件人在忙时，回报门会把回报暂存起来，之后用一轮补交把收件人叫起来。这一轮是带 `releases`（被暂存的派活 seq）的 `room/dispatch`。`releaseHeld` 每运行一次就追加一条补交。`recover()` 每次进房都会运行；只要某个成员有暂存，而本进程没有替它挂计时器，就会调用 `releaseHeld`。暂存只在收件人真正开始一轮时才关闭。所以收件人忙着或被挡着的时候，每进一次房（人发消息、停任务、目标命令……）都会多排一条一模一样的补交。真实房间里，同一条回报被补交了 6 次，每一次都花掉协调者一轮模型调用。

补交在日志里的 `text` 只是给模型看的结尾那句（「以上 N 条回报一直等着交给你：#m…」），回报正文要等拼提示词时才放进去。所以成员页的排队行（核心账本的 `preview`，「来自协作间：…」）、回复的来由行和团队视图都只显示这句结尾，看不出交的是什么。

## Decision

**补交幂等，依据只有日志。** `releaseHeld` 在追加之前先读 `pendingReleaseSeqs`：这位收件人那些仍处于 `queued` / `running` 的补交所列的 `releases`。它只补交这些补交还没覆盖到的暂存；如果一条都不剩，就什么也不追加，返回 `false`。因此超时、重启或人按「现在交给」时，新追加的补交只列新的暂存。这个判断不需要新字段，也不依赖进程状态，所以跨重启、对旧日志同样成立。

**旧日志里堆着的重复补交，进房时就关掉。** `recoverOnce` 一开始、还没重新提交任何东西之前，由 `redundantReleases` 找出这位收件人那些交不出东西的排队补交。一条排队补交如果列出的每个 seq 要么已经关闭（被某一轮带走了），要么已由正在运行的补交或更早一条被保留的排队补交覆盖，它就是多余的。多余的补交写一条 `cancelled` 边，文字为 `重复的提醒`（即 `delivery-notes.ts` 里的 `DUPLICATE_RELEASE_TEXT`）；如果本进程已经把它提交给核心，就同时从核心队列里撤回。团队视图不列出这类行。房间时间线本来就不渲染补交派活，所以别处不需要再隐藏。

**凡是预览补交的地方，都显示它带的内容。** 新增纯模块 `src/release-preview.ts`，客户端打包时也引用它。它先根据补交的 `releases` 找到房间状态里被暂存的回报，再给出回报人（`reportSource`，从 `client/speech-cause.ts` 挪到这里）和每条回报的开头（80 字，压成一行）。用到它的地方如下：

- `previewOf` → 核心行的 `preview` → 成员页「来自协作间：补交回报：招摇构筑师 · 四地区交付…」；一次补交带多条时为「补交 2 条回报：A、B」。
- 回复的来由行 → 「回应 招摇构筑师 的汇报：四地区交付…」；多条时各条开头用 ` / ` 连接。
- 团队视图的派活列表和「正在做」行 → 「招摇构筑师 · 四地区交付…」。

没有新增事件类型，没有新增字段，也没有加提示小字。

## Alternatives considered

**保留重启路径，只要已经有过补交就跳过。** 不采用。已经结束的补交可能什么都没交：它可能在开始之前就被取消或失败了。只有还在路上的补交（排队中或运行中）才保证会把暂存交出去。

**只去掉完全相同的重复（提案字面规则）。** 我们把范围放宽为：凡是暂存全部已关闭或已被覆盖的排队补交都关掉。事故里的那些副本排在一条后来真的执行、带走了暂存的补交后面。按字面规则，最早那条副本仍会执行，白白花掉一轮。

**把预览文字写进补交派活。** 不采用。日志里已经有补交的 seq 和被暂存的回报，再抄一份预览字段是重复数据，旧日志也没有这个字段。

**在房间输入框上方的排队条里显示排队中的补交。** 没有做。按房间时间线 D 的决定，排队条只放成员级胶囊和还没有气泡的人类消息；房间里那份成员收件箱也按设计排除了房间行。补交在成员页的排队列表里可以看到，执行时则显示在它那条回复的来由行上。

## Consequences

重复进房时，每组未关闭的暂存最多只排一条补交，旧日志里堆着的副本也不会再执行。不过，如果前一条补交还在排队时又有新回报被暂存，新加的第二条补交仍会在第一条把暂存全部带走之后执行，这时它只带着结尾那句。要在准入时丢掉它，需要在核心准入时再检查一次，留作后续。宿主一侧（核心 `preview`）的预览和房间的其他提示文字一样是中文；客户端那几处只显示名字和开头，没有新增文案。

## Testing

- `packages/room/tests/release-dedupe.host.spec.ts`：事故形状（一条已执行、五条排队副本全部多余）；保留最早一条；暂存已被后来一轮带走的补交；已结束的补交不覆盖任何暂存；单条和多条的预览文字，以及 80 字截断。
- `packages/room/tests/dispatch.host.spec.ts`（「held-report releases on room entry」）：CLI 收件人忙时连续调用五次 `recover()` 只排一条补交，且它的核心 `preview` 显示带的回报；之后新增一条暂存，只追加一条只列这条的补交。旧日志里五条排队副本在进房时关掉，只有最早一条提交给核心。
- `nodes.client.spec.tsx` 和 `team.client.spec.tsx` 覆盖来由行文字和团队视图的行。
