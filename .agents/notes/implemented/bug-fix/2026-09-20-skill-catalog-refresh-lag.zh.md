# Agent Note: 技能列表刷新到宿主 watcher 发布改动为止

Status: implemented

## 问题

在「工具与技能」面板里安装技能时提示成功，但新卡片始终不出现；网格一直显示安装前的行，直到重开面板。面板列的是 preset standing scope 下的 `ctx.skills.snapshot()`，而该注册表是通过 skill-filesystem watcher 得知新技能包的。我们写技能用的是 `node:fs`，而宿主唯一的同步失效路径是 `fs/observed` 事件——它由面向模型的文件工具触发，插件直写不会触发。于是注册表要等 chokidar（200ms 稳定阈值）在操作返回之后才跟上，而 `AddSkillModal` 只**立刻刷新了一次**，面板之后再没查询过：那次刷新读到的必然是改动前的快照。删除技能是同样的形状。

## 决策

`refreshUntilSettled(read, refresh, settled)` 取代两处技能变更路径上的裸刷新。它先立即刷新一次——对注册表已知的改动保持原有行为，同时让覆盖安装走真实读取而不是提前返回——然后按有界退避（250/500/1000/1500ms）重查，一旦谓词接受快照就停止。新增等待结果里报告的**每一个**名字（`installedNames` 会拆开宿主用 `', '` 连接的多技能列表，因此 `--skill '*'` 也被覆盖）；删除等待该名字消失。store 以 `refreshSettled` 暴露在注入面上。MCP 路径保留原来的单次刷新：它们的状态从宿主的 MCP store 读取，不来自被监听目录。

## 考虑过的替代方案

**固定延时后再刷新一次。** 不采用：这个猜测要么太短（仍然过期），要么太长（成功提示挂着而卡片缺失）。按实际状态收敛在常见情况下更快，watcher 慢时也依然正确。

**让插件同步使宿主注册表失效。** 暂不采用：`observeHostMutation()` 只存在于具体的 `FileSystemSkillProvider` 上，**没有**进共享的 `SkillProvider` 接口，插件只能靠鸭子类型去够一个私有类。这属于上游接口改动；本仓库跟踪宿主，不修改宿主。

**无上限轮询直到技能出现。** 不采用：真正被拒绝的写入会让界面空转。调度有界，且以最后一次结果为准。

**用定时器整体刷新面板。** 不采用：为了掩盖一个亚秒级竞态，持续轮询会为每个打开的面板按间隔消耗一次 Remote 往返。

## 影响

安装或删除现在会自己更新网格，通常第二次查询（约 250ms）就到位。最坏约 3.25s，之后维持过期读取——与改动前完全一致。每次变更客户端最多发出五次快照查询，而不是一次。`tests/settle.spec.ts` 覆盖：立即尝试、重试到可见的序列、有界放弃、快照未落地、以及多名字解析。
