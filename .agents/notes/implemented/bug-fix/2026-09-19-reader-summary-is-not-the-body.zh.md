# Agent Note: feed 的摘要不是文章，搜索也要说清自己做了什么

Status: implemented

## Problem

同一个面上的两次反馈，第一条是真缺陷、而且尾巴很长。

**文章从来没被取回来。** 从站点自己的 feed 点开 `https://transformer-circuits.pub/2026/workspace/index.html`，只显示标题加一段话——feed 的 167 字符 `<summary>`——再没有别的：没有报错、没有抓取、也没有任何可以要求更多的入口。根因是解析器里一行"提升"：`bestBody()` 先找 `content:encoded`/`content`，没有再回落到 `description`/`summary`，于是只发布摘要的 feed 产出的条目 `contentHtml` 是有值的。下游全部据此认为"这条已经有正文"：自动补齐的候选条件（`contentHtml === undefined`）、上一批刚加的"点开即抓"（同一个条件）、以及详情页那个"显示正文"的分支。也正因为如此，这条摘要从未进入补齐的工作清单。而 `detail.summaryOnly` 这条文案从重写那天起就存在，**没有任何组件渲染过它**——为这个场景写的话是一句死文本。

**搜索不说明自己做了什么。** 搜一个精确的论文标题，结果出现在最后，上面压着六篇更新的文章，屏幕上没有任何东西能区分"这六篇也匹配"和"列表根本没被筛过"。匹配器本身是对的——用读者真实的 state 文档实测，`"Verbalizable Representations"` 在 215 条里只命中 1 条——但一个和未筛选的墙长得一模一样的结果列表本身就是缺陷，读者由此得出"搜索返回了另外六篇"这个结论完全合理。

## Decision

**feed 自己的摘要是摘要，不是正文。**

- `parse-rss` 给这种条目打上 `summaryOnly: true`（`ReaderEntry` 的新字段），这才是对 `contentHtml` 里到底装着什么的诚实描述。
- 两个"这条还欠不欠一次抓取"的消费者现在都把 `summaryOnly` 当作缺正文：自动补齐的候选清单把它算进去，打开它则就地抓一次——用的是卡片「抓取正文」那个同一个 `fetchBody`。
- 详情页先把摘要渲染出来（比空白页好），上面一行是那句终于被用上的 `detail.summaryOnly`；抓到文章后摘要被替换、这句话自动消失——判定条件是"当前正文是否就是 feed 自己的文本"，所以不需要额外存状态。
- 抓取失败不再清空正文：`fetchBody` 保留屏幕上已有的内容（摘要，或此前抓到的文章），把原因加在旁边。此前"第二次请求失败就把读者仅有的一段文字收走"是错的。

**文字搜索按相关性排序，并报出条数。**

- 排序依据是标题有多直接地回答这个 query（标题完全命中 → 标题包含 → 其它字段命中），你选的排序只在**同一档内部**生效。`#源id` / `@标签id` 选择器不参与排序——它们对每一行的匹配方式是一样的。
- 只要有 query，底部就显示 `匹配「X」N 条`，被筛过的墙再也不会被误认成整个墙。

**搜索框独占一行。** 墙上的筛选、排序、翻译三个控件移进表头那一行（和刷新、设置、加号在一起），搜索框留在一整行、占满宽度。反馈里的形态——窄侧栏里被三个按钮夹住的输入框——会让读者看不见自己在打什么。每个弹层仍然挂在打开它的那个按钮的 wrapper 上。清空按钮也不再是一个文字 `×`：它现在是工具条自己的描边字形、同样的 15px、22px 的盒子，读起来像一个控件而不是标点。

## Alternatives considered

**靠长度推断"正文只是摘要"**（比如少于 320 字符）。不采纳：按长度做的启发式会误判短的真文章和长的摘要，而解析器本来就知道是哪个元素提供了这段文字。把这个知识用字段带出去才是对的。

**需要时重新读一遍 feed 来判断。** 不采纳：解析每次加载在浏览器半做一次；宿主从不解析，为了回答"这是不是摘要"而让宿主去解析，等于把这个包刻意留在浏览器半的事搬过边界。

**干脆去掉 description 回落**（没有真 content 元素就不给 `contentHtml`）。不采纳：那会让所有把正文放在 `<description>` 里的 feed 详情页全空，而这类 feed 占比很大。回落是对的，只是必须被标注出来。

**用打分而不是分档排序**（字段权重、词频）。不采纳：在这里既不可度量、对读者也不可见。三档表达了读者唯一拥有的那个区分（"标题里有没有？"），而一个隐式分数只会比计算更难解释。

**只在零结果时显示条数。** 不采纳：反馈讲的正是**非空**列表看起来没被筛过，而这恰恰是"只在零结果时提示"覆盖不到的情况。

**把搜索框放到最后、按钮放前面。** 不采纳：输入框才是读者来这里要用的东西，它保持在最前面并拿到整行宽度，是控件让路。

## Consequences

- 只给摘要的 feed 的条目，现在打开时付一次请求，自动补齐每次墙加载最多付 8 条。这是"显示文章而不是预告片"应付的代价；补齐既有的失败 6 小时退避与并发 2 把它限制住了，而且宿主会记下失败，所以一个解析不出来的页面不会被循环重试。
- `ReaderEntry.summaryOnly` 是会话状态（在浏览器半解析、从不落盘），因此不需要 state 文档迁移；哪天 feed 开始给全文，它自然就不产生了。
- 相关性分档改变了搜索生效时"最新在前"的含义：同一档内仍然是你选的顺序，但档位优先。想要纯时间顺序的读者清掉搜索即可。
- 墙的工具条又变回两行（表头放控件、下一行放输入框）而不是一行；输入框变宽了，表头从三个控件变成四个。侧栏极窄时，标题会比任何控件更早被截断。
- `detail.summaryOnly` 这句文案终于可达，而且它（"全文在原文页面上"）现在坐在一段正在被抓取的正文上方，而不是取代文章。

## Testing

`packages/dsh-reader` 现在跑 208 个测试（新增 7 个）：

- `parse-rss.spec.ts`：唯一文本来自 `<description>` 的 feed 条目是 `summaryOnly`；带 `<content:encoded>` 的不是。
- `selectors.spec.ts`：标题命中排在更新的摘要命中之前；`#源id` 选择器不参与排序。
- `ReaderPane.client.spec.tsx`：打开 summary-only 条目会先显示摘要、显示 `detail.summaryOnly`、恰好抓一次、抓到后这句话消失；summary-only 条目会被交给自动补齐；墙上的输入框独占一行（里面没有按钮），而表头带着筛选与排序的 wrapper；筛选面板仍然锚在自己的 wrapper 里。
- 测试台架的 `feed()` fixture 现在会发布 `content:encoded`，因为它是"发布正文的 feed"这个 fixture——只给摘要的场景有自己的 fixture，这也正是好几个既有 spec 的预期随之变化的原因。
