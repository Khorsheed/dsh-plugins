# Agent Note: the entry guard resolves argv[1] to its real path (T33d)

Status: implemented

English | [中文](2026-09-17-cli-entry-guard-realpath.zh.md)

## Problem

Four bins — `dsh-eval`, `dsh-mission`, `dsh-datasets`, `dsh-lab` — asked the same question the same way: *was this module run, or imported?*

```js
const entry = process.argv[1]
if (entry !== undefined && import.meta.url === pathToFileURL(entry).href) { /* run */ }
```

Node resolves an ESM main module to its **real** path before giving it an `import.meta.url`. `process.argv[1]` keeps the path as it was typed. Where those two differ the comparison is false and the body never runs — and the body is the whole CLI, so the process exits 0 having written nothing. There is no error, no warning, and no exit code to distinguish "the CLI ran and succeeded" from "the CLI was never here".

A symlink anywhere in the path makes them differ, and the package manager puts one there. pnpm's `.bin/<name>` shim spells the entry as `.bin/../@khorsheed/dsh-eval/lib/cli.js`, where `@khorsheed/dsh-eval` is a link to the workspace package. Every one of these bins was dead from `PATH`. T33a measured it on 3171: `dsh-eval` and `dsh-mission` both silently no-op'd, and the workaround in play was to spell out `node …/lib/cli.js` by hand.

The cost is not only inconvenience. lab's release gate reads `dsh-mission is-releasable`'s exit code as `0` = releasable, `1` = not, anything else fails closed. That contract is sound, and a silent no-op defeats it precisely: exit 0 is the one answer the gate treats as permission, so a bin that never ran reads as a green gate on a mission nobody checked.

This is the second mechanism to kill the same line. The first was tsdown moving a shared module into a chunk, which stranded the guard where its `import.meta.url` was the chunk's — pinned since by `packages/mission/tests/bin.spec.ts`. The guard's *question* is right; both bugs were in how it was answered.

## Decision

**Resolve `argv[1]` the same way Node resolved the module, then compare.** One `realpathSync` before the URL conversion, in all four entries, each with a comment saying why:

```js
let entryPath = process.argv[1]
if (entryPath !== undefined) {
  try { entryPath = realpathSync(entryPath) } catch { /* unresolvable — compare the literal path */ }
}
if (entryPath !== undefined && import.meta.url === pathToFileURL(entryPath).href) { /* run */ }
```

The `import.meta.url` side is untouched: it is already the resolved file, which is the entire reason the two drifted apart.

**A path that cannot be resolved keeps its literal form.** `realpathSync` throws on a path that no longer exists; falling back to the string that was passed in reproduces exactly the comparison this code did before, so the failure mode of the fix is the behavior it replaced rather than a CLI that refuses to start.

**lab's gate semantics are unchanged.** `0` / `1` / fail-closed was never the defect — the defect was that the bin it asked never answered. Nothing in `packages/lab/src/cli-core.ts` moved.

## Why the guard stays

The obvious repair is to delete the question: a bin entry that nothing imports can simply run. That holds for `eval`, `mission` and `lab`, whose `src/cli.ts` is a thin entry no module imports. It does not hold for `datasets`, where `src/cli.ts` **is** the implementation — `parse` and `runCli` live there and three test files import them. Unconditional execution would run the CLI on import and break those tests.

Four identical guards are worth more than three deletions and one exception. The next person to read any of these files finds the same shape, and the comment that explains it.

## Alternatives considered

**Compare `fileURLToPath(import.meta.url)` against `argv[1]` as strings.** Drops one conversion and fixes nothing: the two paths still differ by the unresolved symlink, which is the actual defect. Comparing URLs also keeps the encoding rules in one place (spaces, non-ASCII), which the string form would have to restate.

**Use `import.meta.main`.** Node exposes exactly this boolean, and it answers the question with no path handling at all. It works: measured on this machine (v22.21.1) it is `true` for `node cli.js`, for `tsx cli.ts`, and through a symlinked package directory — the case this whole note is about. Two things kept it out. It was added in 22.18.0 and 24.2.0, and this repo's `engines` is `^22.19 || >=24`, whose `>=24` admits 24.0 and 24.1 — versions where the property is `undefined` and the guard would silently never fire again, the exact failure being fixed. It is also still Stability 1.0, early development. `realpathSync` behaves identically on every version the repo admits. This is the simplification to come back to once the floor rules out 24.0/24.1: the guard collapses to `if (import.meta.main)`.

**Fix it in the shim instead — have the bin resolve itself before exec.** The shim is generated by pnpm on install. Patching generated files is not a fix that survives the next install, and the bug reaches any symlinked path, not only the one pnpm makes.

**`realpath` the whole thing at module load and cache it.** The guard runs once per process, at startup. There is nothing to cache.

## Consequences

**Every bin is reachable from `PATH` again, and behaves there exactly as `node lib/cli.js` does.** `dsh-eval --help` through pnpm's `.bin` prints usage; before this change it printed nothing and exited 0.

**lab's release gate now measures what it believes it measures.** A `0` from `dsh-mission is-releasable` means a mission was checked and passed. It could previously also mean the bin was reached through a link and never ran.

**One `realpathSync` per process start.** A single stat before any work — below noise against module loading, and synchronous on purpose: the guard's answer is needed before the body can be entered.

**The fix's own failure mode is the old behavior.** An unresolvable `argv[1]` falls back to the literal path, which is what the comparison used before. It cannot make a working invocation stop working.

**The source-plane tests do not exercise the built artifact.** They spawn `src/cli.ts` through tsx, where the guard is the same source the build emits. `mission` additionally has `tests/bin.spec.ts` over `lib/cli.js`; the other three do not, and the gate's pack step packs and verifies tarballs without running a bin. A regression that reached only the built entry in eval, datasets or lab would therefore be caught by neither — the same blind spot the tsdown-chunk bug fell into, narrowed but not closed.

## Testing

- Four packages, one spec each: `packages/{eval,mission,datasets,lab}/tests/cli-entry.spec.ts`.
- Each spawns the entry through a **symlinked package directory** (`<tmp>/pkg -> packages/<name>`, the same shape pnpm's shim produces) with no arguments. No arguments is the sharp probe: the body answers usage on stderr and exit **2**, so the bug's signature — exit 0, empty output — cannot pass. A second case spawns the real path and asserts the same answer, pinning that the resolution changed nothing for a direct call.
- Verified to fail without the fix: with the guard reverted, the symlink case reports `expected +0 to be 2` with empty output; the direct case stays green.
- `pnpm gate`: 14 steps, 284s, PASSED. Package suites green — eval, datasets, lab, mission.
- On this machine, through pnpm's `.bin` shim: `dsh-eval --help` and `dsh-mission --help` each print usage (6429 and 1649 bytes); the same two commands against the pre-fix build print nothing and exit 0.
