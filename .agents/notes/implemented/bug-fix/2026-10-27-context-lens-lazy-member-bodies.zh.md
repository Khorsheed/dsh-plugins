# Agent Note: member request bodies are rebuilt on read

Status: implemented

## Problem

10-27，在房间 2e44ba43 里，面板把主会话第 1 轮显示为「未载入」，地图上没有任何请求，还有一轮一直停在「加载中」。原因是子会话日志通道会把每个成员请求连同它复制的完整上下文全部展开，没有任何窗口限制。这个房间的两个成员（kimi 成员的上下文有 10 万到 40 万字符）一共存了 391 个请求、1.39 亿字符，占了 store 全局 1.5 亿预算的 93%。只要再读任何一个别的会话，总量就会超出预算，而按「最久未读先清」的淘汰顺序，房间自己存放成员请求的那个隐藏轮次和它的主会话轮次就被清空了。一个全新进程列出这个房间要 7.2 秒，几乎全部时间都花在展开上下文上。

## Decision

- 成员子会话日志改为**不带正文**地折叠。子会话游标的展开判断始终返回 false，所以每个请求只保留结构、用量、耗时、回复和工具执行，不保留复制的上下文。外部 agent 自己的会话（只看日志的会话）回填时也一样处理。
- 日志通道构建的每个请求都记下 `logIndex`，即它在该日志所有请求中的位置；不带正文的请求会打上标记。
- 调用 `getRequest` 时，服务端重建正文：把这个请求所在的日志再折叠一遍，只展开被读取的请求和同一视图里它的前一个请求（前缀对比的基准），然后把它们补进 store。最近重建的 8 个正文会保留，更早的会再次被收回。

## Alternatives considered

- **给每个房间的成员请求加一个窗口。** kimi 成员 30 轮的请求仍然会有几千万字符。
- **调高预算。** 只是把超限的临界点往后推，并没有消除它，而且真正的限制是堆内存。

## Consequences

- 在真实数据上，房间 2e44 列出之后只占 106 万字符，而不是 1.4 亿。列表从 7.2 秒降到 56 毫秒；读取一个成员请求只要 44 毫秒，完整的历史和前缀对比都在。
- 成员请求在列表里的 `totalChars`（上下文大小）在被读取前是 0。列表和地图用的是用量 token，所以显示不受影响。

## Testing

`context-lens`（228）。新的 child-log 用例断言：列出时 store 里没有复制的上下文；读取时正文被重建；收回后再读，内容完全一致。原有那些逐个读取请求内容的 child-log 用例不做修改，在重建的正文上照样通过。
