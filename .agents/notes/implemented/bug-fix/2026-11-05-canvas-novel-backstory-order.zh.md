# Agent Note: 往事导入进入故事时间，事件可以向前移动

Status: implemented

## Problem

章节对账把没有有效 `after` 的事件当作本章下一个事件。第 1 章回忆的童年往事因此即使标了 `backstory=true`，也会落到开场之后；这个标记只改变显示分组。写入 API 只能追加或排到另一个事件之后，无法把错位事件向前修正。显式移入当前事件区的往事还会成为后续无锚往事的隐式锚点，界面也仍把它显示在“故事开始前”，与存储顺序矛盾。

## Decision

- 没有 `after` 的导入往事按 payload 顺序加入开篇前的正常往事区。已显式移入当前事件区的往事不参与这个默认定位。当前事件保持本章顺序，不把往事当作本章隐式锚点。
- 有效的显式 `after` 始终优先。未知导入锚点会以 `id-not-in-ledger` 丢弃该事件，不再静默排到末尾。
- `novel_write(what=event)` 新增与 `after` 互斥的 `before`，可指定已有事件或 `first`。两个入口都会拒绝未知或冲突的位置。手动新建且未指定位置的往事使用同样的默认规则；编辑已有事件而未指定位置时保留原顺序。
- `orderBefore`、`orderBackstory` 与 `orderAfter` 一起放在纯时间轴模块中。已有作品不需要迁移。
- 显式位置同时决定存储和界面展示。移入当前事件区的往事保留事实上的往事标签，但按 order 显示在正文区；只有开篇前的正常往事区显示在“故事开始前”。Remote 视图携带 `order`，客户端无需猜测时间即可保持分组一致。

## Alternatives considered

- **继续把 backstory 只当显示元数据。** 否决：持久化的故事时间仍然错误，每增加一段倒叙都会多一处需要手工修正的数据。
- **根据 `when` 或章号推断先后。** 否决：`when` 是标签而不是日历，讲述往事的章号也不是它发生的时间。默认规则只保证确定性；已知先后由显式位置表达。
- **往事进入正文区时清除 backstory 标记。** 否决：位置是用户的排序选择，并不能证明它不再早于开篇。由 order 决定分组，标记保留事实。
- **未知锚点仍沿用旧回退。** 否决：静默追加模型的错误输出会掩盖问题并破坏故事时间。现在导入报告会明确列出被拒绝的锚点。

## Consequences

- 混合章节保留两种独立顺序：当前事件按正文出现顺序排列，未指定位置的往事按 payload 顺序进入正常往事区。重新对账仍会替换该章提取的事件；后续无锚往事应在后续章节导入，而不是把同章重写当作追加。
- 默认规则不声称知道新发现的往事是否早于已有往事；正文提供明确先后时由 `after`、`before` 表达。
- 已有手工修正的事件位置不变，不执行数据迁移。
- 测试覆盖第 1 章当前事件与多段往事交错、定点往事后在另一章导入无锚往事、存储与界面分组一致、移到开头或任意事件前，以及无效锚点。
