# Agent Note：迟到的结算报告归它观测的那一轮，不归之后开始的那一轮

Status: implemented

## 问题

provider 要等 `run.result` 结束之后才算出一轮的结算观测（模型、用量），所以 facade 会把这次调用的进度通道保留 `RUN_PROGRESS_SETTLE_GRACE_MS`。可是同一子会话一开新轮，`trackRun` 就把这条保留的通道关掉了。房间成员如果有排队的消息，上一轮结果一出来，下一轮立刻开始。于是上一轮的结算报告被送进了**新一轮**的 `onProgress`，房间也就把 `room/execution-metadata` 记在了新的 run id 下。房间 5d4f0d41 里，run 414 的回复没有用量，414 的用量记在了 421 上；14:56 那次失败的 388，用量记到了 394 上。以前的记录里，只要有排队消息，都是同样的情况。

## 决定

- 新一轮开始时，不再关闭上一轮保留的通道；这条通道仍受它自己的宽限计时器限制。
- `reportRunProgress` 收到 `settled` 时，先交给保留着的那条（较早一轮的）通道，交完即关闭。其他类型的进度照旧交给正在运行的那一轮。

## 考虑过的其他方案

- **给 `recordRoundSettled` 带上轮次标识。** 这样最精确，但要改动每个 provider，还要改共享通道的签名。各轮本来就按顺序结算，按顺序归属就够了。

## 影响

即使下一轮紧接着开始，成员的回复也能保住自己那一轮的用量。还剩一个边界情况：如果某个 provider 有一轮始终没有报结算，而下一轮又在 60 秒宽限期内结算，那么下一轮的结算会被交给较早的那一轮。目前没有 provider 会在正常路径上漏报结算。已经记错的历史记录不会被改写。

## 测试

`local-agent`（422）：新增一个 facade 测试。续接一个子会话，结果结束后、观测还没到时再续接一次：迟到的结算交给了第一次调用；实时进度和第二轮自己的结算交给了第二次调用。
