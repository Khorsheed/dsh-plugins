# Agent Note: 看门狗的端口归属——原子 pidfile 声明、绑错端口诊断、有界 EADDRINUSE 重试

Status: implemented

[English](2026-08-18-watchdog-port-ownership-and-atomic-claim.md) | 中文

## Problem

三处缺陷，都能被"启动命令没有绑到被监督端口"这一个失误触发——干净环境装插件时，它让三次重启尝试里的两次落空（实例绑了应用默认的 3080，而监督盯着 8766）。

1. **单例声明是 TOCTOU 窗口。** `[ -f "$PIDFILE" ] && kill -0` 之后再 `echo $$ > "$PIDFILE"` 是先检查后写入：同时启动的看门狗都在任何一个写入之前通过存活检测，于是全部继续执行。八个竞争者对同一个 `WD_HOME`，一个端口上留下了两个 supervisor。
2. **启动窗口超时无法区分"根本没起来"和"起在了错误端口上"。** 看门狗轮询 `:$PORT` 60 秒，报告 `instance failed to come up`，并在第 2 次失败时把仓库回滚到最后已知可用版本。启动命令漏了端口标志属于命令行参数问题，不是代码回归，于是回滚为一个 reset 根本够不着的笔误丢弃了正确的提交。
3. **尝试日志里任何位置出现 `EADDRINUSE` 都会走端口竞态的逃生口。** 该分支只匹配字符串、不检查它指的是哪个端口，然后宣称是被监督端口、对被监督端口调用 `free_port`、并在不递增 `failures` 的情况下 `continue`。因此一条指向被占用的**外部**端口的启动命令会让实例陷入紧密循环重启：没有退避、没有放弃、没有崩溃页——实测 25 秒内重启 24 次而失败计数仍为 0。

## Decision

1. **原子声明。** `(set -C; echo $$ > "$PIDFILE")`——noclobber 让重定向本身在文件已存在时失败，因此恰好一个竞争者创建它。失败者读取持有者：存活就退出；死 pid 就删除 pidfile 再竞争一次。**空文件**则是对手的声明正在写入途中——noclobber 的创建和 echo 的写入是两次磁盘操作，被抢占的赢家就卡在这两者之间——所以读到空先等一拍再重读，而不是删除；只有连续多次读到空（写入途中被放弃的声明）才删除。首次读到空就删会重新打开竞态，并能级联到所有竞争者烧光尝试次数（2026-08-29 在 deploy 门禁负载下实测：8 个竞争者，0 个存活）。最多五次真实尝试。声明发生在安装 cleanup trap 之前，所以失败者不会在退出路上删掉胜者的 pidfile。
2. **点名端口不一致。** 启动窗口超时时，看门狗在回收子进程**之前**读取其进程树的监听端口（`pid_tree` + `lsof`）——回收之后证据就没了。监听在 `:$PORT` 以外的端口时，打印实际绑定端口与被监督端口，并置 `reset_done`：这正是"失败主体在仓库之外"已经在用的逃生口——回滚被标记为已消耗，而 `failures` 继续累加直到崩溃页，把这处配置错误摆到明面上。
3. **端口感知且有界的 EADDRINUSE。** 逃生口现在只在冲突指向 `:$PORT` 时适用，且只适用五次——超过之后说明端口的持有者是这个看门狗释放不了的，那是启动失败而非竞态。冲突发生在其他端口时，作为启动命令错误报告并计入失败。

`WD_BOOT_TIMEOUT`（默认 60）加入已文档化的 `WD_*` 环境契约，使这些路径无需每次尝试都消耗一整个启动窗口即可测试。

## Verification

- `bash -n` 通过。竞态用例，八个看门狗并发争抢同一个 `WD_HOME`：修复前存活两个 supervisor，修复后一个。
- 针对绑错端口的启动命令做新旧脚本端到端对比。目标端口空闲时：18 次重启 / 只计 1 次失败 / 无诊断 → 3 次重启 / 3 次失败 / 输出诊断。目标端口被占用时：24 次重启 / **0** 次失败计数（无界空转）→ 3 次重启 / 3 次失败 / 输出诊断。两次新脚本运行均未触发回滚。
- `tests/self-restart-guard.spec.ts` 新增两个用例，均已确认对修复前脚本失败、对修复后脚本通过：`claims the pidfile atomically`（断言八个竞争者只剩一个存活，且 pidfile 指向它）与 `counts an EADDRINUSE on a foreign port as a boot failure instead of retrying forever`（断言输出诊断、失败被计数、尝试次数停留在个位数、回滚未被消耗）。竞态用例的第一版对新旧脚本都通过——从 node 逐个派生竞争者会把它们错开到窗口之外——因此改为从单个 shell 一次性拉起，并且等待存活数**稳定**而不是首次读到 1（launcher 自身的 fork 窗口就能产生那个读数）。
- 既有用例 `treats EADDRINUSE as a port race` 在等待一个 20 秒死线的同时没有声明超时，于是被 vitest 的 5 秒默认值卡住；六轮"派生并失败"放不进去。它对修复前脚本同样失败（3/3），现在与同组用例一致声明 30 秒。
- 全量连续两轮 68/68；`typecheck` 通过。
- 2026-08-29 跟进：八竞争者用例在四包 deploy 门禁负载下抖动（0 个存活），即上面已封死的空读级联；reclaim 用例的 10 秒窗口又低于负载下一轮监督循环的时长（假实例模式空载约 6 秒：拉起 + 健康轮询 + 两段 sleep)，于是 reclaim/yield 窗口放宽到 25 秒。级联在本地 60 轮压力中未复现（空载、`yes` 满载、套件并发三种跑法都干净）——窗口是靠构造封死的，不是靠测量。

## Alternatives considered

**用锁目录（`mkdir`）替代 noclobber。** `mkdir` 同样原子，但会把持有者 pid 拆到第二个文件里，等于重新引入"锁"与"它本应标识的 pid"之间的窗口。pidfile 本来就是对外接口（CLI、安装器、测试清理都会读它），让它的创建变成原子的可以只保留一件产物。

**当 `--start` 漏掉端口时拒绝启动。** 看门狗无法从任意 shell 命令里解析出一个可能通过环境变量、配置文件或默认值传递的端口。观察实例实际绑定了什么，是唯一对所有启动命令都成立的读法。

**把端口不一致当作硬退出。** 退出会让端口失去监督，而这正是整套设计要消除的形态。继续累加到崩溃页既让看门狗活着，又把诊断放在运维人员正在看的那个端口上。

## Consequences

漏掉被监督端口的启动命令，现在会给出点名的诊断并在四次失败内出现崩溃页，而不是先静默超时 60 秒再回滚仓库；指向被占用外部端口的启动命令会终止而不是空转。针对同一个 `WD_HOME` 的并发 `supervise` 不可能再双双获胜。回滚重新只保留给"重置检出确实能修好"的失败。
