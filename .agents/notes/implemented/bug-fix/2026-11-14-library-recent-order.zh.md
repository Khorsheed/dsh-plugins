# Agent Note: 图书馆最近动态在同时间戳下保持写入顺序

Status: implemented

## Problem

`recentChanges` 和 `recentRecords` 都应该按最新事件在前展示。事件文件按写入先后保存，但这两个视图只比较 `at` 时间戳。同一毫秒内发生多个事件时，原始顺序会保留下来，于是旧的对话记录可能排在新的批阅记录前。

forward-compat CI 的断言期望新的 quiz 记录，却读到了更早的 chat 记录。其他运行时因为事件时间戳不同而通过，因此展示顺序取决于调度时序，而不是实际写入顺序。

## Decision

两个视图都先把收集到的事件倒序，再按时间戳降序稳定排序。时间戳不同的事件仍按 `at` 排序；同时间戳的事件则保持事件日志中较新的写入在前。存储日志、时间戳精度和文件格式都不变。

## Alternatives considered

- **增加序号或提高时间戳精度。** 否决：持久化事件日志本身已有顺序，读取侧修复不需要修改结构，也不需要迁移。
- **让 quiz 优先于 chat。** 否决：按来源类型决定优先级不是时间顺序，而且会掩盖其他场景里更新的对话记录。
- **把 CI 失败当作无关抖动。** 否决：同时间戳时代码确实把旧事件放在前面。虽然只在某个任务中暴露，它仍是真实的顺序缺陷。

## Consequences

首页动态和最近记录视图在同一毫秒内也有确定顺序。新的批阅不会仅因为与旧对话共享一个 `at` 值就落到旧对话后面。不需要迁移数据、提高宿主版本要求或增加配置。

## Testing

`packages/library/tests/service.spec.ts` 的批阅级联场景把所有事件固定在同一毫秒，覆盖先写 chat、再写 quiz 的过程，并断言 `recentRecords()[0].source === 'quiz'`；该文件的 65 项服务测试通过。每个测试结束后恢复计时器。library 全包构建及全部 221 项测试也已通过。
