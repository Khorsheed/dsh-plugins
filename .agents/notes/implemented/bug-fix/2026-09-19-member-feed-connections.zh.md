# Agent Note: 共享浏览器成员订阅

Status: implemented

## Problem

隔离 Room 验收页和成员页分别为配置、模型目录和实时输出打开独立的持续 Remote 订阅。多个页面耗尽浏览器 HTTP/1 同源连接池，历史、Room 刷新和消息提交等待，而已有输出连接仍在接收内容。关闭重复页面后，请求立即恢复。仅在组件内部共享订阅无法限制整页连接数量，Room 同时运行多个成员还会放大这个问题。

## Decision

Core 通过一个 `followMembers` 流订阅当前成员/通道集合。客户端在插件实例内用这一条连接复用所有配置、目录和输出订阅。集合变更通过微任务合并，替换连接并接收新的原生基线。同一通道的重复消费者共享订阅，最后一个消费者释放时关闭该通道。

服务端每个数据源只保留一个待完成读取。安静或失败的目录/控制源不会阻塞其他成员输出。客户端合并配置快照和输出后缀，不保留 token 事件队列。新加入的本地输出消费者收到完整活跃基线，不会只收到孤立后缀。原有单通道 Remote 方法继续保留兼容性。

## Alternatives considered

**规定只能打开一个标签页。** 不采用，因为打开成员自己的会话是已有的受支持工作流程。

**每个成员一条连接。** 不采用，因为 Room 可以同时展示多个运行成员，仍会耗尽连接池。

**要求 HTTP/2 或重写宿主传输。** 这可能改善宿主的通用限制，但限制本插件的订阅数量不需要它，也不属于本次不修改宿主源码的开发范围。

## Consequences

每个浏览器页面仅使用一条持续成员订阅，不随成员数量增加。宿主的其他传输仍占连接，所以这不是无限标签页保证。可见集合变化会重新连接并接收基线，可能短暂重复当前快照；消费者已经使用版本和原生身份避免重复内容。

测试覆盖八名成员的三个通道共享连接、慢消费者后缀合并、后加入消费者的基线、集合变更取消、整体释放、数据源错误隔离，以及安静数据源与活跃输出并存。真实多页面和延迟仍单独验收。
