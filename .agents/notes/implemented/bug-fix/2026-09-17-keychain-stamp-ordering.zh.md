# Agent Note: keychain 印记的解析从来没对上 security 真正打印的格式

Status: implemented

[English](2026-09-17-keychain-stamp-ordering.md) | 中文

## Problem

macOS 允许同一个 keychain service 下挂多条条目，而 claude 的作用域凭据 service 正是会攒起来的：每次登录该配置目录一条，外加历史残留。`readKeychainCredential` 本应枚举该 service、按**最新写入优先**排序、返回第一条**可用**的 blob——这条规则是此前一次修复（pilot 日志里的 G10）定下的，起因是一条 token 全空的空壳被镜像进凭据文件，让每一次委派都报一个并没有发生的过期。

而枚举根本没排序。`keychainTimestamp` 只认带空格的写法 `2026-09-01 02:03:04 +0000`。`security dump-keychain` 真正打印的是紧凑 Zulu 形式，属性末尾那个 NUL 被渲染在结尾数字之后：

```
    "mdat"<timedate>=0x32303236303931363034303835355A00  "20260916040855Z\000"
```

没有观察到哪个构建会吐带空格的那种。于是每条的印记都解析失败、落到 `?? 0` 默认值，`items.sort((a, b) => b.mdat - a.mdat)` 在全相等的键上变成空操作——`Array#sort` 是稳定排序，dump 自身的顺序原样留存。`readKeychainCredential` 于是返回 dump 里恰好排在最前的那条可用条目。**「最新写入优先」在生产里从来没生效过**；G10 的另一条保证（跳过空壳）不受影响、一直正常，所以表面上看不出任何异常。

它是在一个登录过两次的作用域目录上暴露的。该 service 下两条都可用，而 dump 把最差的那条排在了前面：

| acct | mdat | 排位 |
|---|---|---|
| `unknown` | `20260916040855Z` | 第一——被取代的世代 |
| 账号本人 | `20260917053120Z` | 第二——当天那次全新登录 |

每一次协调都把 9/16 那一代镜像进 `.credentials.json`；全新登录始终躺在 keychain 里没被读过。实例全程报 `authenticated: yes`，因为那份陈旧凭证的 refresh 过期时间还有好几周，而它跑在一个 refresh token 十有八九已被用掉的世代上。**再登一次也救不了**：那只是重写账号本人那条，它在 dump 顺序里仍排在 `unknown` 之后。

**为什么测试没抓到**：套件里的 `dumpKeychainOutput` 夹具合成的是带空格那种形状——`security` 从不吐它——于是那条名为「prefers the newest write among several usable entries」的用例一直在针对一个不可能出现的输入做断言。把夹具改成真实形状之后，那条既有用例**在源码一个字没改之前**就当场变红。

## Decision

`keychainTimestamp` 先解析紧凑 Zulu 形式，并保留带空格那种作为兜底。

```
/^(\d{4})(\d{2})(\d{2})(\d{2})(\d{2})(\d{2})Z/
```

不加尾锚：渲染出来的 NUL 跟在 `Z` 后面，加了尾锚就会为了一种换不来任何好处的严格而否掉每一条真实的行。紧凑形式不带偏移量——`Z` 就是偏移量——所以直接过 `Date.UTC`。带空格那条分支保留，以防某个构建确实会吐它，并且由它自己的测试来跑，而不是留成一段没人验证过的死代码。

夹具现在渲染的就是工具渲染的东西，连末尾那个 `\000` 也一并照抄；另有一条测试逐字转录了一整段真实的 dump 区块，而不是合成一段。这才是真正修的东西：一个形状是工具从不吐出的夹具，什么都证明不了，而这个解析器身上挂了两个这样的夹具。

## Consequences

- 登录过不止一次的作用域目录现在会取到它最新的那份凭证。与[凭据同步那份记录](2026-09-17-claude-credential-sync-newer-wins.md)里的新者胜协调合起来，keychain 与凭据文件从两个方向都会收敛到活着的那一代：文件不会被更旧的 keychain 条目盖掉，而被选中的 keychain 条目现在确实是最新的那条。
- 印记解析不出来的条目仍然排在最旧，并且有测试钉住这一点，于是一条解析不了的印记再也不可能靠「被打印在最前面」取胜。
- 一个卡在被取代世代上的 scope，会在下一次协调时自动愈合，不需要重登。

## Alternatives considered

**改按 `cdat` 排序。** 创建印记在多次续期之间是不变的，而这恰恰是反的：要问的是哪一条**最近被写入**，而被全新登录重写过的槽位，其 `cdat` 保持原样。

**把印记丢给 `Date.parse`。** 紧凑形式不是 ISO 8601（没有分隔符），而 `Date.parse` 处理非 ISO 字符串的行为是实现自定义的。用一条明写两种可接受形状的正则，既正确，又可以当作「工具会吐什么」的规格来读。

**放弃排序，改按凭证内容挑**——比如取 `expiresAt` 最晚的那份。这行得通，但它为了做决定要读**每一条的密文**，而元数据 dump 不碰任何一条密文就能回答同一个问题。按元数据排序、只读赢家那一条，暴露面更小。

**不修，一律重登。** 实测行不通：再登一次只是重写账号本人那条，它在 dump 顺序里仍然输给历史遗留的 `unknown` 条目。排序是唯一的杠杆。

## Testing

`records.spec.ts` 里三条用例，对修复前的源码三条全红、修复后全绿：

- 一段逐字转录自真实 `security dump-keychain` 的 dump 区块，两条都可用、被取代的那条排在前面，断言被镜像的是新的那条；
- 把带空格形式的那条列为更新的一条，断言旧分支仍然解析得动，且两种形式落在同一把尺子上比较；
- 把一条解析不了的印记排在最前，断言它按最旧排序，而不是靠位置取胜。

既有那条「prefers the newest write among several usable entries」在夹具改成真实形状之后也会变红——缺陷正是这样被找出来的——它原地保留，作为第四道守卫。
