# Agent Note: 超大文章，以及跟着一起被抽进来的页面装修

Status: implemented

## Problem

同一个研究站点（`transformer-circuits.pub`）的三次反馈，各有各的成因。

**41.8 MB 的文章根本抓不下来。** `https://transformer-circuits.pub/2026/emotions/index.html` 返回 `response exceeds the maximum of 5000000 bytes`。宿主出网缝有**两个**上限：`maxResponseBytes`（默认 5,000,000，就是这次失败的那道字节墙）与 `maxBodyChars`（默认 100,000）。验收实例的 patch 覆盖层只抬了后者——也就是说，这个部署被配置成"愿意读 2,000,000 字符的响应，但拒绝下载超过 5 MB 的它"。实测那一页 41,842,174 字节，其中 60 张插图是内联的 `data:image` base64，体积就来自这里。

**正文开头是重复的页面装修。** 抽出来的正文以「空的 logo 链接、站名、文章标题**两遍**（那个页面里有两个 `<h1>`）、四个 `<br>`」开头，之后才是作者信息——而详情页本来就已经在正文上方渲染了条目标题。读者反馈为"为什么前面会抓取到重复的内容"。

**脚本绘制的插图。** 由上一批的 Agent Note 记录（不执行页面脚本就抓不到）；这一批的调查额外确定了一件事：**同一个出版方的另一篇文章**（emotions）插图是内联 base64，因此**是可以抓到的**；而 workspace 那篇的 84 张是运行时绘制的，抓不到。

## Decision

- **在部署的 patch 覆盖层里把两个上限一起抬高。** `$DSH_HOME/profiles/web/cordis.patch.yml` 把 `web-fetch-http` 那一行设为 `maxBodyChars: 64000000` **和** `maxResponseBytes: 64000000`。原覆盖层自己的注释已经写明它抬高的是**全机**所有网页抓取的上限；字节上限现在加入它，注释也更新了。页面大小是发布站点的性质，而粘进这样一条链接的读者就是在要它。
- **超过 4 MiB 的正文只提供、不缓存。** `MAX_CACHED_BODY_CHARS` 限定一条条目的抽取正文最多能给 `state.json` 增加多少；超限时 `storeEntryBody` 返回带 `tooLarge: true` 的视图且**什么都不提交**，详情页写明「这一篇太大，没有缓存 —— 下次打开这一条会重新抓取」。理由写在常量自己的注释里：state 文档是一份整体读写的 JSON，几篇 base64 内联插图的论文就会让之后每一次读者操作都付出几 MB 的往返。
- **抽取时去掉页面自己的标题块。** `trimLeadingChrome` 先删掉文本等于文档标题（或正文自身第一个标题）的一二级标题，然后沿着开头逐个丢弃站头——无文本节点、`<br>`、很短的纯链接节点——直到遇到第一个停止标签（`p`、任意标题、`table`、`blockquote`、`pre`、`ul`/`ol`）、第一个画面元素、或第一个有 40+ 字符正文的节点。实测那个页面的标题块是 `<d-title>`，一个不在白名单里的自定义元素，所以规范化时会被**拆壳**，它的 `<br>` 就落到正文最前面；因此最后还会把规范化字符串开头的空白与 `<br>` 一并剥掉。

## Alternatives considered

**只抬 `maxBodyChars`（README 里写的那个）。** 不采纳：对这个失败它根本不是正确的旋钮，而错误消息点名的是字节上限。那样会继续让一个部署"愿意截断一份它拒绝下载的文档"。

**改成流式读取、增量抽取，而不是抬上限。** 本包不采纳：出网缝要么交回解码后的整体、要么什么也不给，没有流式面；而抽取是基于 DOM 的，需要整份文档。（真正同时解决体积与脚本问题的答案是 browser pane 渲染器，而它仍在本包范围之外。）

**照旧缓存大正文，靠既有淘汰机制兜底。** 不采纳：`boundAnnotations` 对缓存正文是按**条数**（500）而不是按体积淘汰的，于是一篇 40 MB 的文章会一直留在文档里，直到 500 篇更新的正文把它挤出去——而在此期间的每一次变更都要重写它。

**截断到预算再缓存头部。** 不采纳：在元素中间切断规范化后的 HTML，只会让 React 去猜着修补，而"正文悄悄停住"正是这个包一直在消灭的失败形态。整份提供、并说明没有留存，才是诚实的。

**只按第一个标题去重。** 不采纳：实测页在标题之前还有站名和一个空 logo 链接，标题本身还有两个 `<h1>`；只处理第一个标题的规则一个都留不下。

**删掉正文里所有 `<br>`。** 不采纳：正文中的 `<br>` 可能有意义（地址、诗句）。只剥开头那一段。

## Consequences

- 验收实例现在能抓取并阅读几十 MB 的文章。全机每一次网页抓取都继承更高的天花板：峰值内存与传输量随之上升，一个恶意或单纯巨大的页面在被任何策略挡住之前能消耗更多两者。
- 41 MB 的页面仍然要跨过 RPC 边界到浏览器、并在那边解析（在面板进程里做 DOM 工作）。这是"把这篇给我看"的代价；另一种选择是直接拒绝。
- 缓存守卫意味着重新打开一篇超大文章每次都会重新抓取。详情页的提示把这件事说清楚了，读者不会对延迟感到意外；这个取舍是刻意的（文档保持小）。
- 正文不再重复条目标题，也不再以站头开头。如果某个页面的作者有意让一个章节标题与文档标题完全相同，那个标题会从正文里消失——接受，它仍然出现在页面标题和面板头部。
- 抽取结果因为丢掉脚本插图的图注、标题块与站头而变小：那篇论文的正文从 321,868 字符降到 286,162。
- `ReaderEntryBodyView.tooLarge` 是新的 wire 字段；两半同时发布，旧客户端会忽略它（照常渲染交给它的正文）。

## Testing

`packages/dsh-reader` 现在跑 217 个测试（新增 5 个）：

- `extract-article.spec.ts`：带两个标题 `<h1>`、一个站头与开头 `<br>` 的页面，抽出的正文从 `<h3>Authors</h3>` 开始，不含 `<h1>`、不含站名；开头的 `<figure><img>` 被保留（画面就是内容）。
- `boot.spec.ts`：`storeEntryBody` 超过预算时返回 `tooLarge: true`、把 html 交回、什么都不提交（之后 `getEntryBody` 报告没有缓存）；预算内的正文照旧缓存并可读。
- `ReaderPane.client.spec.tsx`：抓取结果带 `tooLarge` 时渲染"没有缓存"的提示。
