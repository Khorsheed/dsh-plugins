# Agent Note: Context Lens 将房间轮次归属到完整协作树

Status: implemented

## Problem

一个真实房间会话的第 114 轮只显示了直接被点名的成员，尽管该成员随后把任务派给另一个 agent，并在收到回报后继续执行。房间日志已经记录三次执行及其关系。Context Lens 只从人工 dispatch 建轮，并且只挂载 dispatch seq 等于人工根 seq 的运行。嵌套的协调与回报 dispatch 既不并入根轮，也不单独形成编号轮次，因此它们的请求和决策都从房间维度视图消失。简单把这些运行加入现有 scope map 还会覆盖同一成员此前的执行，并可能重复计算请求。

## Decision

- 人工 dispatch 仍定义一个编号房间轮。非人工 dispatch 只提供拓扑，不增加轮号：`parent` 和能解析到运行的 `reportFor` 连接派生工作；`releases` 经由被释放 dispatch 的 `reportFor` 连接。遍历完全按记录进行，可防环，不退回时间推断。跨房间 help 等无法解析的外部标识不强行挂入。
- 轮次构建与决策归属共用同一次协作树遍历。没有链接的旧日志退化为现有直接运行行为；无记录轮继续使用 fallback，不虚构请求归属。
- 同一 child 的多次执行按 scope 合并：请求按时间排列并去重，压缩只认领一次，用量只汇总一次。多次执行事实通过增量 `executions` 字段完整保留；单执行仍使用原有 `execution` 字段保持兼容。
- UI 保持每个成员一个标签，并展示每条执行记录。普通工具调用子 agent 的归属不变。

## Alternatives considered

**给每个协调或回报 dispatch 单独编号。** 虽然能显示部分遗漏工作，但会把一次用户可见协作拆成实现细节、重排后续所有人工轮次，也不符合根轮展示全部参与者的预期。

**只挂直接下一级委派。** 能修出两个标签，却会漏掉回报触发的继续执行及其请求。协作树必须同时包含 `parent`、`reportFor`，并由 `releases` 保留暂存回报的路径。

**每次执行保留一个 scope。** 重复的成员标签会让汇总和请求导航更复杂。按 child scope 合并才能保持一个参与者视图，但请求与执行事实必须同时去重且不丢失。

**按耗时推断派生运行。** 与此前执行记录的决策理由相同：成员可以并发、长时间运行，不沿日志明确链接就无法诚实归属。

## Consequences

根轮现在包含完整的有记录协作，包括嵌套决策与压缩；后续人工轮次编号不变，token 不重复计算。同一成员的多次执行不再互相覆盖。旧日志和没有明确链接的运行保持原行为；无法解析到运行树的工作继续不归属，而不是猜进某一轮。

## Testing

回归用例以带执行记录的子日志驱动人工 → A → B → 回报 A，检查两个成员标签、A 的重复执行、嵌套决策、请求/token 去重及人工轮次不变。第二个用例固定暂存回报释放、循环终止和无关 help 标记的排除。原始房间日志以只读方式回放，核对第 114 轮及其后的人工轮次。
