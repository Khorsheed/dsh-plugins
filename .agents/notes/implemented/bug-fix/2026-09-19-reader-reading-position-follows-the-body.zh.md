# Agent Note：阅读位置跟着正文走

Status: implemented

## Problem

读者反馈：切到另一个 dsh 会话或另一个标签页再回来，不会回到之前读到的地方——文章在，但在最上面。

两个原因，都在「位置」而不是「文章」上：

- **位置只在恢复路径里应用了一次，就在第一版正文渲染之后。** 而正文可能分两步到达——先 feed 的摘要、后抓到的那一页——那一次赋值会被**短的**那一版钳掉，然后读者就留在了长版的最上面。没有任何东西再贴一次，于是文章在屏幕上、译文在（上一个修复之后）、位置是零。
- **只记住了正文的滚动位置。** 墙有自己的滚动容器和自己的位置，而它从来没被保存过，所以正在翻墙的读者回来时看到的是墙的顶部。

## Decision

- **保存下来的位置就是目标，正文每次（重新）建立时都重新应用一次**——恢复的面板、重新打开的条目、摘要之后落地的重抓、React 重建的元素。这个 effect 以 `[openEntryId, articleHtml]` 为键，和翻译记录完全一样，因为两者描述的是同一件事：这一条，以及它此刻在屏幕上的样子。
- **当正文短到够不着那个偏移时，赋值会在一个很短的窗口内重试**（`SCROLL_SETTLE_ATTEMPTS`，约 30 帧）。这覆盖了图片解码、字体落定、抓取仍在飞行这三种「scrollHeight 比它该容纳的位置小」的原因。它不是轮询循环：一旦滚动容器能够到达该偏移、或读者自己滚动了，就停下。
- **只记录读者自己的滚动。** 设置 `scrollTop` 同样会触发 `scroll` 事件，而保存这个回声正是位置被毁掉的方式：正文短时浏览器会**钳住**赋值，回声携带的就是被钳后的值，会把真正的目标覆盖成它。处理器把事件里的偏移与「上一次程序化赋值实际落到的值」比较，相等就丢弃。
- **墙得到同样的待遇**：位置在读者滚动时保存，在每次进入列表视图时恢复一次（不是在每次行变化时——那会和读者自己的筛选打架）。

## Alternatives considered

**给保存加节流/防抖。** 丢掉最后一个事件恰好就是让阅读位置差一次滚动——详情页位置的写法已经避免了这一点（每个事件都写）。
**基于锚点恢复**（对记住的元素 id 调 `scrollIntoView`）。原理上更正确，但它需要在第三方标记里有稳定的锚点，而本包会把这些标记规范化掉；像素偏移加短重试已经能让读者回到原处，不必发明一套锚点词汇。
**只在重新挂载时恢复**（最初的设计）。漏掉了最常见的一种：只发摘要的 feed，其正文是在面板恢复**之后**、读者眼皮底下被替换的。
**墙的位置在行变化时也重新应用。** 筛选/搜索都会改变行；这时候跳到旧偏移是第二个 bug，不是修复。

## Consequences

- 「我刚才在哪」现在对两个滚动容器都是按正文为键、且在这个页面内稳定的：切面板、切会话、重新打开、正文替换都会回到原位置，只有刷新会重置（面板记忆不落盘）。
- 记忆再也不会被钳位破坏：钳位是程序化回声与目标唯一不同的情形，而它被识别为程序化。
- jsdom 在 `innerHTML` 替换后仍保留 `scrollTop`，而浏览器会钳掉，所以详情位置的测试在替换正文时显式把滚动容器归零。没有这一步，断言在完全没有任何恢复逻辑时也会通过。
