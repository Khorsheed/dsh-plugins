# Agent Note：浏览器的滚动钳制不是读者输入——吞掉锚点的那次重挂载

Status: implemented

## Problem

生产实例上的报告：长文读到一半，点另一个侧栏标签页，再点回来——文章回到了顶部。面板的位置机制（块锚点、settle 窗口、回声守卫——见[状态边界 note](../architecture/2026-09-19-reader-state-boundaries.md)，以及[恢复保真 note](2026-09-20-reader-restore-fidelity.md) 里的文本偏移）已经扛过了三轮「读者忘了 X」，面板自己的重挂载 spec 也全绿。

在一次性实例上用真实浏览器驱动复现：dockkit 的 `TabPanel` 只渲染活动标签页的 body，所以切标签页会把阅读器面板整个卸载，回来是一次全新挂载。锚点本身记录得很忠实（`sessionStorage` 里是 `{block: 75, offset: 3, top: 7853, …}`）。重挂载时，译文重建让文档在已滚动的滚动器下面变矮（scrollHeight 13382 → 4557）；浏览器钳制了偏移并派发滚动事件。这些事件按取值与读者的无法区分，而 `onDetailScroll` 把它们当读者的处理：存下的锚点被钳制值覆盖，「读者已接管」标志也被置起，本要重新落锚的 settle 窗口就此结束。回来时读者停在 scrollTop 0，锚点成了 `{block: 0, top: 0}`——真锚点在恢复中途被毁。

这个缺口对测试不可见：jsdom 从不钳制 `scrollTop`（越过上限的赋值直接生效），所以面板的重挂载 spec 从未制造过钳制事件；而第一个真实浏览器的脚手架 harness 恢复得好好的，因为它的假翻译器让文档**变高**——钳制需要变矮。

## Decision

**记录改为按手势设门。** 仅当该滚动器在 `SCROLL_GESTURE_WINDOW_MS`（400 毫秒）内出现过人类滚动手势（`wheel`、`touchmove` 或按键——翻页键），其滚动事件才算读者的。面板自己的写入早就被回声守卫接住；浏览器的写入（钳制）附近没有任何手势，被窗口检查丢弃。两个滚动器都遵守——正文侧的（`onDetailScroll`，由现有的接管监听打时间戳）和墙面侧的（`onWallScroll`，配了自己的手势监听，按 `[view, rows.length]` 键）。

「读者已接管」标志（`readerScrolledRef`，结束恢复 settle 窗口的那个）现在只由手势监听置位——滚动事件永不置它，于是一次钳制既不能覆盖锚点，也不能终结那个会重新应用锚点的窗口。

## Alternatives considered

**比较滚动偏移来区分程序与人。** 状态边界 note 已为回声情形否过这条路，在这里败得更彻底：钳制**就是**一次真实的偏移变化、携着真实的事件——取值里没有可比较的东西。
**只在恢复/settle 窗口内压制记录。** 那个窗口恰恰也是读者可能真的在滚动的时刻（他们看到文章落定然后调整）；而且钳制可能在文档变矮的任何时刻到来——正文替换、过滤器收窄墙面——不限于恢复时。手势窗口覆盖一切变矮，又不同步误伤真实输入。
**把向下的跳变视为可疑（永不记录更小的值）。** 往上滚是正常的阅读动作；这条规则会拒录读者一半的行为。
**让标签页保持挂载（改宿主/dockkit）。** 切换即卸载是上游行为，不是这个包该改的；而且重挂载只是 bug 被**报告**的地方——钳制隐患存在于每一次变矮，所以无论宿主的挂载策略如何，修复都属于面板的记录规则。

## Consequences

- 浏览器的钳制再也不能覆盖位置或终结恢复窗口，两个滚动器都是——被报告的流程（切走、切回、译文重应用）恢复到记录的块。
- **只靠拖滚动条滚动的读者不再被记录**——拖动派发 `scroll`，附近没有 `wheel`/`touchmove`/`keydown`。他们已记录的锚点照常恢复，任何滚轮、触摸或按键滚动都会恢复记录。知情接受：备选（把滚动器上的 `mousedown` 算手势）也会给文本选择的点击打时间戳，等于为「跟在点击后面的钳制」重开了洞。
- 六个滚动 spec 现在在想被记录的滚动前先桩一个 `wheel`：裸 `scroll` 事件按定义是程序的，spec 也这么写明了。
- jsdom 不会钳制，所以两个新 spec 手工摆出钳制的形状（把时钟老化过手势窗口，再来一次无手势的、偏移更小的 `scroll` 事件）。两者对设门前的代码红、之后绿；重挂载 spec 两侧都绿。
