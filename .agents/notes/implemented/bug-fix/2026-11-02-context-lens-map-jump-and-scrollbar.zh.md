# Agent Note: Context Lens——走势图点击可靠落地，滚动条始终可拖动

Status: implemented

## Problem

一个有 94 轮的房间会话暴露了走势图的两个导航故障和一个呈现故障。点击当前轮次里的另一根请求柱会打开对应请求，但不会重新同步左侧对话，因为轮次号没变时轮次选择直接返回了。点击更早的房间轮次也可能让对话停在原处：宿主的首次加载或普通 `loadOlder` 占用繁忙标记时，`loadThrough` 不翻页就直接完成，而面板只发一次请求、只等 60 帧。最后，走势图使用 macOS 的 overlay 滚动条，滚动后横向拖动柄会淡出，即使屏幕外还有轮次。

## Decision

- 每次点击走势图都同步左侧对话，包括当前轮次里的请求；原有提前返回仍负责避免重复重置面板的轮次状态。
- 宿主轮、房间消息锚点和工具调用共享 `pageForAnchor`：先等会话首批行，再允许三次翻页请求，每次之后给锚点 90 帧的等待。新跳转仍然取代旧跳转。宿主轮保留“落到不早于目标的最近行”兜底，房间消息缺失则保持不动。
- 走势图隐藏原生 overlay 滚动条，仅在内容溢出时显示一个与 `scrollLeft` 双向同步的原生 range 滑块。滑块宽度反映可见比例；拖动和键盘操作直接使用原生行为，不需要自己处理指针事件。

## Alternatives considered

**只修当前轮次点击。** 能修必现路径，但更早房间轮次能否到达仍取决于宿主当时是否空闲。

**无限等待一次翻页请求。** 宿主当前契约里的空返回不代表仍在等待的操作，必须在锚点等待后重试；如果行始终无法挂载，无限等待会让跳转永远悬住。

**给原生 overlay 滚动条加样式。** 滚轮和触控板仍能滚动，但浏览器预览证明，在 macOS 的 overlay 策略下，WebKit 滑块规则和稳定占位仍不能保住拖动目标。手写指针拖动轨道被否决，因为原生 range 已经提供拖动、焦点和键盘行为。

## Consequences

无论是否改变面板轮次，点击走势图现在都有相同的对话同步行为。历史跳转能容忍宿主繁忙，同时不削弱取消和兜底语义。滑块仅在走势图溢出时占 16px 高度；内容装得下时不留空白滚动条槽。

Context Lens 测试覆盖当前轮次柱点击、第一次翻页空返回后重试成功，以及滑块与走势图的双向同步。浏览器预览确认滑块等待后仍可见，`End` 精确到达最大滚动位置，指针拖动会同时更新滑块和 `scrollLeft`。
