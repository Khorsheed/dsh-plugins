# Agent Note: Context Lens 跨采集车道使用同一份完整消息视图比较

Status: implemented

## Problem

一个恢复后的写作会话在比较日志重建的 #122 与实时捕获的 #123 时，报告了三处从未发生的变化：消息 084 的历史空系统提示消失、系统提示在第 49 字断开、一条用户消息发生 `-40 +202` 替换。实际日志只有正常的 model/user 末尾追加。共享 diff 算法本身没有算错，而是两侧输入并不描述同一份消息视图：日志车道保留了宿主会投影为“无消息”的空系统节点、丢失附件名，并把系统提示保留为一整块；实时车道省略空节点、保留附件名，并把同一提示拆成多个 assemble 分段。前缀比较又直接比较展示行，而不是完整的线上消息。

## Decision

- 日志车道在 surface 上保留空的 system、developer、assistant 节点，让后续 replacement 仍能按 seq 寻址；构造模型输入时则省略它们，与宿主的 derived-history 契约一致。物化与无正文请求共用这份过滤基线。
- 日志读取的 file、image block 将非空附件名保留为展示 ref，与实时请求读取规则一致。这里修的是附件标签对齐，不是引入通用消息 projection 重放。
- 前缀比较与变化列表共用同一份重建后的完整消息视图。先按线上消息合并系统分段，再定位第一个内容差异；assemble 归属只用于展示。
- 一对一替换前后位置不同时同时显示两个编号，避免把旧、新坐标误认成一个稳定消息身份。

## Alternatives considered

**屏蔽三个显示症状。** 特判 084、48 字断点或精确字符数只能掩盖这个例子，其他混合车道比较仍会出错。

**仍比较展示行，只对系统分段特判。** 这只能修假系统断点，空节点和附件名仍会产生假编辑，而且第二份消息重建逻辑日后仍可能漂移。

**在日志车道重放全部宿主消息 projection。** 本次图片差异只需要日志已有的附件名，不需要 projection 引擎。更大的重放属于另一项契约，不在本次引入。

## Consequences

#122 → #123 现在只报告真实的 model/user 末尾追加。真实提示词编辑、替换、裁剪和缓存用量仍然可见；本次不解释、也不改写服务商报告的缓存未命中。完全由日志重建的请求仍保持无系统分段的展示方式，跨车道比较则改为比较等价内容。

## Testing

回归覆盖空节点过滤及 replacement 寻址、日志/实时附件序列化一致、整块与分段系统提示相等，以及只有真实尾追加的日志/实时混合请求。原始会话日志以只读方式回放，确认报告中的坐标与字符差异消失。
