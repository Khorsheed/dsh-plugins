# Agent Note：抓取状态镜像跟着写入路径走

Status: implemented

## Problem

读者带着截图报：墙上的卡片显示「抓取」；点开文章，详情页抓到并显示了正文；回到墙上，卡片还是「抓取」而不是「已抓取」——直到下一次挂载。

宿主的按条目标注是「插件持有什么」的唯一权威（缓存正文、在飞/已落盘的抓取记录、带着 message 和 code 的分类失败原因），面板在自己的引擎 store 里镜像它（`fetchStates`）。但镜像只有三个写入者——挂载/rev 时的整墙轮询、只在有东西在飞时才跑的 2 秒轮询、以及 `startFetch` 的收尾——而最常改变宿主状态的两条路径什么都没写回来：`open()` 触发的欠账抓取（经 `fetchBody`）和自动补齐。卡片药丸读的是镜像，所以它回答的是上一次轮询恰好知道的东西。

顺带的两个相邻缺陷：`noteBackfilled` 从不清 `staleBodies`，于是「已过期」标记会比替换掉它的新正文活得还久；而 `staleBodies` 根本没有一条会把它置真的路径（`open()` 从 `getEntryBody` 的回答里看得到 `cached && !fresh`，但把它丢了），所以过期状态不是「没清」，是从来没到过。`fetchBody` 的失败分支还会把标记**清掉**——尽管失败的抓取让宿主那份过期副本原样躺着。

## Decision

这是传播修复，不是新的状态模型——五态药丸（未抓取 / 抓取中 / 待解析 / 已抓取 / 失败）与宿主的推导都原样不动：

- **进镜像只有一条读取路径**：`client/selectors.ts` 的 `fetchStateOf(states, entryId)` 拥有这次查找，含 `none` 默认。卡片药丸与 `sweepRaw` 都走它；failed 变体把 `message` 与 `code` 原样带过——正是摄入提案 M0 的原因分类要消费的东西。
- **写入路径重读它碰过的那一条。** `syncFetchState(entryId)` 是一次定向的 `entryFetchStates([id])` 写回镜像。`fetchBody` 在 `finally` 里调它——一次覆盖它的全部三个调用方（open 的欠账抓取、卡片药丸、详情页的「重新抓取」）——`startFetch` 则去掉现已冗余的整墙轮询。镜像里绝不放客户端自己算的状态：失败的分类在宿主侧，客户端再来一份推导，就是同一个 bug 换一层重演。
- **`open()` 从 `getEntryBody` 的回答里学会两样它以前丢掉的东西**：宿主的缓存副本是否过了期限（`cached && !fresh` → `staleBodies`，写在屏守卫之前——这是按条目的宿主事实，无论此刻屏上是哪个条目都为真），以及镜像是否与回答不一致（宿主已有正文而镜像说 `none`，或宿主已记失败而镜像没见过）——不一致就重读这一条。镜像本来就一致时，零额外请求。
- **补齐每次运行重读一次**（worker 排空后 `refreshFetchStates`），不是每条一次——一次运行封顶八条。
- **`noteBackfilled` 在正文落地时清掉该条目的过期标记**，抓取失败则保留；`fetchBody` 的失败分支也不再清它。标记的规则现在对称了：它描述的是宿主的副本，只有新正文落地才结束它。

## Alternatives considered

**每个可能改变状态的手势之后都来一次整墙轮询。** 同样的答案、N 倍的代价，每次抓取都付一遍；定向重读才是这个手势真正需要的那次轮询。
**成功/失败时在客户端算好状态写进镜像。** 成功那半容易（`ready`），失败那半就得复制宿主的分类（`recordFetchFailure` 存的是 message 加 code）；一个状态两份推导，正是这个 bug 的来路。
**宿主往面板的推送通道。** Remote 契约没有事件；在飞轮询已覆盖要数秒的情况，而一次落定的抓取恰恰是定向读取又便宜又终局的地方。
**顺手扫掉孤儿 raw payload。** 推迟：`fetch:{state:'raw'}` 的记录若其条目滚出了 feed 窗口，就永远没人消费（`sweepRaw` 只走墙上的条目），也永远不被淘汰（`pruneBodies` 对被引用的 raw 文件永远保留）。客户端侧的清扫得为墙上已不显示的条目轮询状态，而按龄淘汰 raw 文件需要一个政策决定——raw payload 本身就是这次抓取的可续性。正确的归属是摄入提案的可续抓取设计，raw 的生命周期正在那里被重新切。

## Consequences

- 卡片在改变宿主状态的那个手势上当即翻面：open 触发的抓取、卡片药丸、详情页重抓、自动补齐，都立刻落到镜像里。
- 镜像处处带着失败的 `message` 与 `code`，M0 的原因 UI 读的就是药丸已经在显示的那份记录。
- `staleBodies` 现在是一张真表：宿主报过期副本时写入，新正文落地时清除（open 的抓取，或补齐落地）。仍然没有任何 UI 读它——「已过期」的呈现是 M0 的事，本次修复刻意一行不建。
- `open()` 的 useCallback 现在依赖 `fetchStates`：一次轮询会重建它，恢复效果随之重跑并在自己的守卫后空转。没有新增任何按滚动/按渲染的工作；新调用都是按手势、按运行发生的。

## Testing

`packages/dsh-reader` 共 290 个测试（+8；其中六个先对着修复前的代码红过，两个是两侧都绿的守卫）：

- `tests/ReaderPane.client.spec.tsx`（+3）：从卡片打开并抓到正文→药丸翻成「已抓取」；自动补齐落地→翻面；open 触发的抓取失败→翻成「抓取失败」且悬停带宿主的分类原因。三个用例都把 mock 驱成一份模型宿主文档（`entryFetchStates` 回答的是写入造成的现状），不做真传播就过不了。
- `tests/store.spec.ts`（新增，3 个）：过期标记的设置/清除、被落地的补齐清除、在失败的补齐后保留。
- `tests/selectors.spec.ts`（+2）：`fetchStateOf` 默认 `none`，以及把 failed 记录连同原因与 code 原样交出。
