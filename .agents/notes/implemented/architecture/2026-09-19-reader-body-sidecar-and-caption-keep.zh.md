# Agent Note: 大正文搬到自己的文件里 —— 而图注就是内容

Status: implemented

## Problem

三件事落在同一批，其中一件是对我自己上一批决定的纠正。

**一条写死的天花版悄悄压过了缓存策略。** 上一批为了让 `state.json` 保持小，规定超过 4 MiB 的正文**完全不缓存**（`tooLarge`）。但这个包本来就有读者可配的缓存策略——`ttlHours`（12 / 24 / 168 / 0，默认 24）与 `maxEntries`（500）——而那条天花版既没在界面上出现，也不受它管：一篇 41 MB 的文章只会被提供一次，之后无论读者选了什么都会被忘掉。读者的反馈是对的：这推翻了一个已经谈定并实现的设置。

**41.8 MB 的下载超时了。** 在字节与字符上限都抬到 64 MB 之后，同一篇文章以 `web fetch timed out` 失败——出网缝的 `timeoutMs` 默认 30,000 ms，而实测直连下载要 19.5 秒，所以任何并发负载都会踩过期限。出网缝的上限一共三个，之前只抬了两个。

**丢掉只有图注的 figure 是错的。** 上一批把所有"抓不到画面"的 `<figure>` 都删掉了，理由是没有画面的图注看起来像丢数据。读者的反驳更有力：图注是页面发布的文字，它带着图号和"这张图画的是什么"，把它藏起来等于把"这张图抓不到"变成"这段文字丢了数据"。已恢复：figure 与图注都留下，由正文上方那行说明为什么它们下面没有画面。

## Decision

- **超过 256 KiB 的正文写进 `bodies/<sha1(entryId)>.html`**，文档只保留 `{ file, chars }`。`INLINE_BODY_MAX_CHARS`（256 KiB）是唯一的阈值；**不再有任何会丢弃正文的上限**。读者的 `ttlHours` / `maxEntries` 对侧车正文与内联正文一视同仁，而每次提交后运行的清扫会删掉文档不再引用的正文文件——所以淘汰、手改文档、以及只剩标签的 annotation 都会释放各自的文件。
- **`getEntryBody` 会把文件读回来**；文件缺失或读不出来就等同于"没有缓存"：视图不返回 html、也不返回错误，于是打开该条目会重新抓取，而不是给一页空白。
- **目录由 state store 独占。** 文档里存的是裸文件名、绝不含路径，而文件名是条目 id 的摘要——条目 id 是 URL，而从远端文本推导出的路径就是一次目录穿越事故的伏笔。
- **清扫是 best-effort**：清扫失败绝不拖垮触发它的那次提交——留下一个不可达的文件只花磁盘，而拒绝一次提交花掉的是读者的标签。
- **部署把 `timeoutMs` 抬到 180,000 ms**，与两个体积上限写在同一行。
- **脚本绘制的 figure 保留图注**；抽取器统计它们的数量（`scriptFigures`），详情页在正文上方说明一次：这 N 张插图抓不到画面、图注保留。

## Alternatives considered

**保留 4 MiB 天花版并把它做成设置。** 侧车存在之后不采纳：在保留策略旁边再放一个体积旋钮，等于要读者为"这篇文章能不能读第二遍"去推理存储内部，而目录既让文档保持小、又不需要新增控件，读者已经配好的策略管住一切。

**改成限制 `state.json` 的总体积，而不是把正文搬出去。** 不采纳：那是同一个问题上升一层——文档是整体重写的，所以对大批文本的正确回答就是根本不放进文档。

**侧车正文按条目 id 建目录。** 不采纳：条目 id 是 URL 和标题；摘要是稳定的、路径安全的、不需要转义规则。

**只在进程退出时删除被淘汰的文件。** 不采纳：看护进程随时重启实例，一次崩溃就会让目录悄悄长大。每次成功提交后清扫是幂等的，在这个规模上也很便宜。

**保持删掉 figure，只靠正文上方那句话。** 按读者的论据不采纳：数量说明的是缺几张图，而不是它们各属于哪段讨论，而图注正是把图和正文绑在一起的东西。

**在每个图注里插一个随图标记（"[插图未抓到]"）。** 暂不采纳：标记文字会被烤进抽取内容，而抽取内容是刻意语言中立的，正文上方那句说明则和面板里其它文案一样有本地化。如果只给数量不够用，再回来考虑。

## Consequences

- 保留策略重新变成它字面上的意思。大文章在 TTL 内从文件读、过期后重抓；条目数超过 `maxEntries` 时，最旧的正文——连文件一起——被释放。
- 磁盘占用不再由文档预算决定：`bodies/` 会长到 `maxEntries` × 正文大小。这是刻意的取舍（读者要求长文章可读），而清扫保证它不会超过文档引用的范围。
- `state.json` 仍然小到可以在每次变更时整体读写——这正是当初那条天花版想保护的性质。
- 卸载说明变了：状态现在是一个目录（`state.json` + `bodies/`），README 说要删掉整个 `dsh-reader/` 才算干净。
- `tooLarge` 字段与它的提示都删掉了——不再有"提供了但不留存"的东西。
- 顺带修掉上一批的两个 bug：`normalizeBody` 从来没有带上 `scriptFigures`（于是脚本插图那句提示只活过一次读取），以及 locale 的 key 联合类型漏了新键（构建在提交之后抓到；两个提交已重做并转绿）。
- 抽取结果保住了上一批丢掉的 84 条图注。

## Testing

`packages/dsh-reader` 现在跑 216 个测试：

- `boot.spec.ts`：300 KB 的正文被写进 `bodies/`，文档里只有 `{ file, chars }`、没有 html；之后一次读取交回**逐字节相同**的标记；`maxEntries: 1` 下淘汰会清扫文档放手的那些文件；阈值以下的正文仍然内联。
- `extract-article.spec.ts`：只有图注的 figure 会被计数**并且图注保留**；带真图的 figure 不计数。
- 客户端那条"太大不缓存"的提示与它的测试随机制一起删除。
