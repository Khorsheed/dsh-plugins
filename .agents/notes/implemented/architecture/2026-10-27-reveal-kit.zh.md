# Agent Note: a shared reveal kit, and the agent's request to show the user something

Status: implemented

## Problem

游戏面板已经学会自己跳到改动的地方（见[游戏面板跳到改动处](../feature/2026-10-27-game-autonav.zh.md)）：它轮询新版本、遵守「用户正忙就不打扰」的规矩，并显示提示。图书馆插件为了把会话里写入的内容展示出来，也自己做了一套轮询，剪辑工作台以后同样需要。每个面板都在重复实现同一个行为。

而且两边都是在猜。面板只能从版本和轮次报告里推断用户该看什么；真正知道该看什么的是 agent（「看看神庙的门」「对比 v5 和 v6」），它却没有办法说出来。宿主既没有给 agent 用的界面工具，也没有从服务端推到页面的通道，所以没有一个约定好的形态，插件单靠自己做不到。

## Decision

- **`@khorsheed/dsh-client-ui-reveal-kit`** 是一个源码级共享库，形态和面板组件库一样（内联进每个使用方的客户端打包，不在任何地方注册）。它提供：
  - `RevealController<T>`：「用户正忙」的规矩（有东西在占用，比如游戏或视频正在播放；20 秒内有操作；会离开当前正在看的条目；面板关着而窗口窄于 820px），每个浏览器一个开关，提示条，agent 请求按序号只处理一次（页面上第一次看到的请求只在刚发生时才处理），并且每次决定都在控制台留一行记录（`[reveal:<name>] …`）。
  - `visiblePoll`：只在页面可见时运行，会话事件可以提前叫醒它。
  - `RevealNoticeBar`：面板顶部的提示条。

  检查脚本把它和面板组件库一起列为允许的源码级依赖。
- **服务端那一半是约定，不是共享代码。** 插件的服务端编译只认自己的 `src/`，所以每个插件各自注册带前缀的工具（`game_show`，以后还有 `library_show` 之类），在内存里按项目保存最新一条 `{ seq, target, note, at }`，并通过页面本来就在轮询的那个 Remote 返回。共享包的 README 写明了这套做法。
- **游戏插件第一个接入。** `AutoNav` 保留游戏自己的判断（一轮结果在哪里、小圆点、新版本与项目绑定的提示），把规矩、开关、提示条和控制台记录交给共享包。`game_show({ view, element?, chapter?, note })` 会先检查位置是否存在，再记下请求。`liveVersion` 把请求带给页面，页面先处理它，再提示新版本，所以 agent 指定的位置优先于自动跳转。技能、模式说明和人设都写明了顺序：改完 → `game_publish` → `game_show` → 汇报或提问。
- **上游。** 在 S17（插件事件到不了客户端）下面登记这个新的使用方。有了插件事件通道之后，`visiblePoll` 换成推送，各插件的工具保持不变。

## Alternatives considered

**由一个中心插件提供一个通用工具（`sidebar_show(panel, target)`）。** 每个面板的位置都不一样（元素和章节、书和站点、工程和片段），而且有了中心插件，每个插件在运行时都要依赖另一个插件。各插件自己的工具随插件一起装、一起卸。

**把服务端那一半也做成共享代码。** 插件的服务端编译不接受自己 `src/` 以外的源码，而这部分只有十几行。

**让工具强制跳转。** 正在玩游戏或正在填字段的用户会被打断，找不到刚才的位置。请求是一个分量很重的建议，但仍然遵守「用户正忙就不打扰」的规矩。

## Consequences

- 图书馆和剪辑工作台可以迁到共享包，什么时候迁由各自的负责人决定。
- 请求存在服务端内存里：重启后会丢失，对于「现在看看这个」这类请求，这正是合适的。
- 现在每个查看者的控制台都能解释每一次跳转和不跳转。
