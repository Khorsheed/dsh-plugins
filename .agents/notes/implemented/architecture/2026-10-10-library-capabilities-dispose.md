# Agent Note: library capabilities verb and dispose guard

Status: implemented

## Problem

A consumer mounting the library per-instance on an isolated Context with its own `stateRoot` (the supported server-side consumption form documented in the README's「工作区接入接缝」) hit two gaps. (1) Writability was knowable only host-side: the store's `available`/`unavailableReason` probe had no wire verb, so a client (or a mounting side's UI) learned a deployment was read-only only by attempting a write — the reader had already solved the same problem with `ReaderService.capabilities`. (2) There was no dispose guard: the service holds nothing but an in-memory listener set, and once instances are mounted and unmounted dynamically, a call after the mounting Context's teardown would silently operate on a dead scope — use-after-dispose had to become a coded refusal, not silent operation.

## Decision

All evolution is additive and generically named (no consumer vocabulary in code, types, or comments); the version stays 0.1.0; the client UI, the `./tool` entry and the ImageRefCache are untouched.

- **Wire capabilities verb** (`src/types.ts`, `src/service.ts`, `src/remote.ts`): `LibraryCapabilities` — `{ protocolVersion: 1, hasStorage, storageUnavailableReason?, hasAttachments }`, the reader's `ReaderCapabilities` evolution rule (only optional fields are ever added, so a consumer written against protocolVersion 1 keeps working; the reason key is absent, never null). `service.capabilities()` reads `store.available`/`store.unavailableReason` and re-runs the per-call attachment probe (`ctx.get('attachments')`) at call time; `@Remote('capabilities')` exposes it as `remote.library.capabilities()`. It is a read-only DISPLAY contract — enforcement stays at the write gates (`storage-unavailable` / `unavailable` refusals), byte-identical to before.
- **Dispose guard** (`src/service.ts`): `LibraryDisposedError` (coded `'disposed'`, package-named through `PACKAGE_NAME`, now exported from `invariant.ts`; the error class is exported from the package root). `dispose()` is idempotent and terminal, drops the listener set, and is wired to the borrowed Context's teardown via `ctx.effect` in the constructor (the canvas-novel precedent — a directly constructed instance gets the wiring too, not only the `apply` path). `assertAlive` sits on EVERY public verb, reads included, so a mounting side never keeps consuming a stale instance. The write boundary — `assertAlive` immediately before the lock in `mutate`, deliberately OUTSIDE the try that maps store errors onto refusals — pins the placement rule: the guard runs before lock acquisition, so a write reaching the boundary after disposal refuses coded and never queues onto a lock a rebuilt instance owns; a write already past the boundary may complete (the store's lock/temp-write/atomic-rename already keeps the disk side safe). Validation from verb entry to the boundary is synchronous in this service, so the entry guard and the boundary guard collapse onto the same tick today; both are written because the contract names the boundary and future evolution may make validation async. A same-root rebuild stays legal: the disposed instance alone stays dead, and the released lock files gate the new instance in.
- **Tests** (`tests/capabilities-dispose.spec.ts`, 9 new): the handshake pins writable-storage + no-attachments shape with the reason key absent, the unwritable root (a state root nested under a regular file) with its reason and the write gate still refusing `storage-unavailable`, and the attachment probe's verdict at call time; the dispose suite pins every public verb refusing the coded package-named error (the synchronous ones throwing), idempotence, Context-teardown disposal, the racing write refusing coded with all three store lock spies silent, the same-root rebuild (the first instance's data all readable, new writes landing), and two live instances on one root genuinely serializing through the lock file. The two hand-built ctx mocks in `service.spec.ts` / `tool.spec.ts` gained a no-op `effect` (the constructor wires `ctx.effect` now) — a mechanical harness accommodation, no expectation changed.

## Alternatives considered

- **A `'disposed'` `LibraryErrorCode` refusal value instead of a thrown error**: reads answer shapes without an error channel (`listProjects`, `listCards`, `dueCards`, `stats`, …), so a return-shaped code would be invisible there or force every signature wider; a thrown coded package error is the canvas-novel/sidechat precedent and covers reads and writes uniformly.
- **Guarding only the writes post-dispose**: reads answering stale state after unload would let a mounting side keep consuming a dead instance indefinitely; the delivery condition is that EVERY public verb refuses, reads included.
- **Wiring disposal in `apply` (the sidechat shape) instead of the constructor**: the documented consumption form includes direct `new LibraryService(ctx, config)` on a mounting side's own Context; constructor wiring (the canvas-novel shape) covers both paths, and a real cordis Context always has `effect`.
- **Re-checking liveness inside the locked body (after lock acquisition)**: rejected — the delivery's placement rule is that the guard runs BEFORE lock acquisition, and the parenthetical covers the rest: a write already waiting on a contended lock when disposal lands is disk-safe by construction (lock/temp-write/atomic-rename), so refusing it too would buy nothing.
- **Splitting `hasAttachments` into can-read/can-save**: the per-call probe the rest of the service uses is `ctx.get('attachments')` itself (only `savePhoto` additionally needs the optional `saveImage`); the handshake mirrors exactly that probe, and a finer split can still arrive as optional fields under the evolution rule.

## Consequences

- `LibraryCapabilities`, `LibraryService.capabilities`, `LibraryService.dispose`, `LibraryDisposedError` and the `remote.library.capabilities` wire verb are new public surface; `PACKAGE_NAME` is exported from `invariant.ts`. All 68 pre-existing tests pass unmodified (77 total, 9 new); the only edits to existing test files are the two no-op `effect` mock additions.
- A client can learn writability (with the reason) and attachment availability up front instead of by attempting a write; enforcement semantics are unchanged.
- The mounting side owns the instance lifecycle: disposal follows the borrowed Context (or an explicit `dispose()`), post-dispose verbs refuse coded, a racing write refuses before the lock, and a rebuild over the same state root is a new instance's business.
- The native UI does not consume the verb yet (display contract landed first, by design); when it does, the additive shape and the protocolVersion rule are already pinned by tests.
