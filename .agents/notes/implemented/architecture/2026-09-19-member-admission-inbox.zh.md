# Agent Note: 串行化成员准入并持久保存人工输入

Status: implemented

## 问题

Room 投递、成员输入框及直接委派工具可能同时争用同一原生成员。有些入口排队，core 却拒绝运行中的 resume。成员输入框无法持久确认已排队输入，也无法说明重启后保留了什么。

## 决策

MemberControls 在 provider 边界持有 FIFO。四家 provider 将新建和续接轮次连同请求的 abort signal 交给它。队列等待整轮结果结算后，用已收敛的 model/effort 配置准入下一轮，不同成员可以并行。取消等待请求不执行它，原生启动阶段取消也不把模型选择标为失败。不支持配置准入的旧 provider 保留忙时拒绝。

成员输入框先将人工输入写入按成员划分的原子收件箱，再返回接受结果。Request ID 对相同重试去重，对改变文本的重用请求拒绝。宿主专用准入回调在 provider 启动前记录 running。回调可以异步执行：core 等待持久化结束，并在启动原生执行前重新检查取消。Room 使用同一边界写 running 和开始耗时计时，排队时间不计入执行。Journal flush 失败会阻止原生执行，不把模型配置标为失败。Stop 可以取消成员的独立工作，但只有 Room 确有 running 轮次时才关闭其任务。完成、失败和取消更新同一输入记录。原生 run handle 尚未发布时，Stop 也能取消已准入的收件箱输入。冻结评测委派拒绝额外人工输入。

收件箱文件使用私有权限、文件及目录 fsync 和原子 rename。损坏状态或持久化失败阻止准入。恢复时保留未执行输入并暂停，之前 running 的输入标为 uncertain，绝不重放结果未知的执行。人工填写结果和证据后，再显式继续剩余输入。只读检查不启动工作，继续队列要求父 agent 存活。

成员运行中输入框仍可编辑，发送和停止按钮独立。收件箱显示排队输入、单条取消、暂停/继续及对账。Room 中选中的外部协调者显示同一收件箱。Room 不再把原生旧协调者的投影统计展示为外部协调者统计，成员独立会话统计仍可查看。Request ID 也支持缺少 crypto.randomUUID 的局域网 HTTP 页面。

## 考虑过的替代方案

**Core 保留忙时拒绝，各 UI 自行排队。** 直接委派工具和 Room 投递仍会有不同执行语义。Provider 边界为所有入口共用。

**确认仅放在内存中的输入已接收。** 重启可能静默丢失已接受工作。确认必须晚于持久输入写入。

**重启后重放全部未完成输入。** 缺少结算的原生执行也可能已经产生副作用。未知结果必须对账，未执行输入暂停到显式继续。

## 影响

成员人工消息可跨浏览器重连和宿主重启保留。原生执行、model/effort 准入和取消共用 FIFO，已发布 run 继续携带精确准入配置，供冻结评测证据使用。

Room 持有自己的持久投递 journal 和短提交链：新成员等待稳定原生句柄落盘，已有且支持配置准入的成员直接进入 core 共用队列，不等待上一轮 Room 结果完成落盘。旧 provider 和房间原生 agent 保留 Room 串行。每次执行都有稳定 run ID，投递结果来自该执行，迟到终态不会覆盖更新轮次的投影。聊天自动任务行记录 delivery ID，完成和 Stop 只结算匹配的行。句柄发布持久化失败时，先等待原生执行结束，再报告终态失败。

统一全部队列展示及最初持久接受时的排序、准入时刷新排队提示上下文，以及用正式目标 attempt 替换聊天自动任务行仍未完成。本次不代表 M3 或完整提案完成。收件箱文本和结果只保存在本地，终态历史压缩尚未实现。真实 CLI/浏览器、流式时延和隔离部署验收仍待完成。
