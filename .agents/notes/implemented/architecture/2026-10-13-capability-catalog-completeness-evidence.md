# Agent Note: capability-catalog completeness evidence and the pure-data production face

Status: implemented

## Problem

A collaboration layer runs experiments whose members execute in OTHER containers, so the target side must produce capability-composition EVIDENCE — data another process can verify — and eval consumes it. The catalog's only fingerprint path was the Remote verb pair `snapshotAt`/`snapshotFor`, which by design MOUNT a preset standing scope as a side effect (the roster's single-flight standing mount) — a price a target-side producer must not pay just to measure, and an impossible one anyway in a bare process with no cordis composition behind it. Worse, the snapshot had no completeness contract: discovery keeps partial results on failure (a scope whose read throws is skipped, the registry's own `complete: false` signal was ignored, an unreadable skill body silently digests as `null`), so a consumer could not distinguish "confirmed empty" (scanned, zero found) from "not installed / read failed" — an empty digest was indistinguishable from a complete one.

## Decision

All evolution is additive and generically named (no collaboration vocabulary in code, types, comments, or docs); the version stays 0.1.98; the Remote verbs' wire form is byte-identical.

- **Per-section completeness on the snapshot** (`src/types.ts`): the additive optional `completeness` field carries one `{ state: 'complete' | 'partial' | 'unavailable', reason? }` descriptor per section the snapshot covers (skills / tools / mcpServers / channels). `complete` = scanned and everything found included (zero found is complete-with-zero, distinguishable from failure); `partial` = some sources failed and the rows are a subset, with `reason` naming the failed source CLASS (never secret content, never raw error text, which may carry paths); `unavailable` = the section could not be measured at all (not installed / read failed / no permission). Like `sha` and `preset`, the field never enters the canonical form `hashOf` digests (pinned by test).
- **The health the rows were gathered with** (`src/skills.ts`, `src/remote.ts`): `collectSkills` fills an optional `SkillsCollectionReport` out-bag — attempted/failed scope reads, registry-flagged incomplete discovery (the harness's `complete: false` signal, previously ignored), unreadable bodies in fingerprint mode — and `catalogSnapshot` takes the matching optional `report` bag. The Remote verbs never pass one, so their rows and digests are unchanged.
- **One tools-side reading implementation** (`src/tool-face.ts`): the service's three private reads (visible schemas, origin tags, prefix-derived MCP server names) are extracted into shared helpers the service now delegates to, with behavior preserved exactly (a `schemas()` throw still propagates from the verbs; the same warnings fire). The evidence producer reads through the same module, so verb/evidence parity is by construction, not by two copies agreeing today.
- **The production face** (`src/evidence.ts`): package-root `produceCapabilityEvidence(options)` — every input explicit (caller-verified `presetId`; absolute `workdir`, relative refused; optional caller-declared `revision`; an optional already-resolved opaque `scope` passed THROUGH to the reads, never resolved or released here; the `skills` / `tools` registry slices; the baseline-diff set; a REQUIRED `coverage` declaration; an optional warning sink). It returns plain JSON-safe data: `measurement` (`kind: 'preset-composition'` + presetId/workdir/revision), `sha` (stamped by the same `catalogSnapshot` fingerprint call the verb makes), all four section descriptors, and the echoed `coverage`. The API has no roster parameter and takes no cordis Context, so it CANNOT mount a standing scope or register a service; a throwing `tools.get` degrades to an unreadable origin tag (a partial section) instead of failing the measurement; the mcpServers descriptor inherits the tools section's state (it is derived from it) and channels inherits skills+tools (it summarizes them). Dependency discipline: node builtins plus this package's existing dependencies only — the published tarball is the target-side runtime (verified: pack-dist → unpack → plain-node import → run against a fixture).
- **The consumer contract** (both READMEs, new seam section): the digest algorithm is owned by THIS package — consumers never recompute it, and any `partial` / `unavailable` section is "not verified", never complete and never "the section is empty". The section also restates the Remote verbs' standing-scope mount caveat as local-only and unchanged.
- **Tests** (`tests/evidence.spec.ts`, 19 new): the completeness matrix (clean scan → complete including zero-found; registry-flagged incomplete discovery / unreadable bodies / unreadable origin tags / a guarded `get` throw → partial with class-naming reasons; absent services / failed sole-scope reads → unavailable); confirmed-empty vs read-failure distinction (absent skills and empty skills hash ALIKE — only the descriptor tells them apart, which is the point); digest parity with the `snapshotFor` path over one fixture; measurement metadata excluded from the digest; a probe pinning that production touches only the handed slices (the opaque scope passes through; no mount, no registration); JSON round-trip; input refusals; the report plumbing itself; `completeness` riding the snapshot without entering the digest.

## Alternatives considered

- **A Remote verb variant returning evidence**: rejected — any verb on the service rides a Context that already paid the composition cost, and the target side is a bare process; the verb would either mount (the side effect being avoided) or duplicate the degrade policy. A pure function with no roster parameter cannot mount by construction, which is stronger than a documented "does not mount".
- **Including the snapshot rows in the evidence bundle**: the four listed items (digest, completeness, measurement, coverage) are the contract; rows would invite consumers to recompute the digest from them — the one thing the contract forbids, because a re-implemented algorithm drifts — and would bloat the JSON boundary with tool parameter schemas.
- **Completeness entering the digest**: rejected on the parity requirement — the evidence digest must equal `snapshotFor`'s over the same registries so two processes can compare; completeness is metadata ABOUT the measurement, recorded alongside the digest, not a capability.
- **Leaving origin-tag degradation out of the completeness model**: the channel enters the digest, and an unreadable tag falls back to heuristic attribution, so a partially heuristic tools section is honestly `partial`. The pre-existing absent-`get` degrade stays `complete`, because it IS the local verbs' own answer on such a registry — evidence must not contradict the verb it claims parity with.
- **Multi-scope evidence reads**: the verbs read exactly one scope (`[scope]`); the face mirrors that. The report plumbing and the partial wording stay general (a failed subset of several scope reads) because `collectSkills` / `catalogSnapshot` are shared, but the production face passes one scope exactly like the service.

## Consequences

- New public surface: `produceCapabilityEvidence` plus `ProduceCapabilityEvidenceOptions` / `ProducedCapabilityEvidence` / `CapabilityEvidenceMeasurement` / `CapabilityEvidenceCoverage` / `CapabilityEvidenceCompleteness`; `CatalogSectionCompleteness` / `CatalogSnapshotCompleteness`; the `RegistrySlice` / `SkillsCollectionReport` / `CatalogToolsSlice` / `ToolSchemaLike` types re-exported from the root; the optional `CapabilityCatalogSnapshot.completeness` field. Version stays 0.1.98.
- The service's tools-side reads now live in `src/tool-face.ts` with the service delegating; observable verb behavior is unchanged (warnings and throw behavior preserved).
- All 284 pre-existing tests pass unchanged (303 total, 19 new); no pre-existing expectation was edited.
- Tarball-verified: pack-dist 0.1.98 → unpack → plain-node import of the package root resolves the face and runs it against a fixture (digest well-formed, completeness correct, JSON round-trip intact).
- This shape is the contract eval consumes: compare `sha`, require every section `complete`, and check `measurement` / `coverage` against the expected composition.
