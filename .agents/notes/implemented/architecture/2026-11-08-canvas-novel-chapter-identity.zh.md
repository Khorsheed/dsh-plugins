# Agent Note: 章节内部身份与展示章号分离

Status: implemented

## Problem

小说的章号 `n` 同时充当图节点身份、日志引用、对齐键和浏览器草稿键。删除尾部章节后复用章号，会把旧记忆和旧草稿挂到另一份正文上。基于这个模型实现章节删除，要么妨碍重写，要么破坏新内容。

## Decision

- `ChapterRecord` 增加可选的持久化 `id`：旧记录读取为原有的 `ch:<n>` 身份，新章节使用新的 `ch_<uuid>`。字段仅对迁移前数据和手工测试夹具可选。
- `n` 继续作为展示章号和文件编号，`seq` 继续作为排序键，现有 Agent 与 Remote 的章节请求不变。以后可以复用章号而不复用身份。
- 图节点把章号作为元数据保存，不再从节点 id 反解。连线、删除影响、对齐基线和确认都使用章节版本 id；展示和影响报告继续使用 `n`。
- 摘要事件和对账确认使用同一身份，确认一个章节版本不会误确认同章号的另一个版本。
- 浏览器草稿键包含章节版本 id，旧草稿不会在复用章号和文件名的新章节中打开。

## Alternatives considered

- **永久保持章号单调递增。** 否决：删除尾部章节准备重写时，下一章会意外跳号，也不能单独解决旧草稿和旧引用。
- **删除后重排所有保留章节。** 否决：会重写章节引用，使现有导航和日志产生歧义。
- **继续从节点 id 解析章号。** 否决：章号是面向用户的位置，不是持久身份。

## Consequences

- 旧章节数据不需要提前迁移，现有读写调用保持原有形状。
- 新章节 id 在标题、计划和正文修改中保持稳定。不同章节版本可以同章号，但不会共享对齐或草稿状态。
- 包构建和全部 310 个测试通过，包括验证新版章节 id 保留连线与影响报告的图测试。
