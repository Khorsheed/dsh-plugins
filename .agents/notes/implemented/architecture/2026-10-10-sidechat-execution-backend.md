# Agent Note: sidechat execution backend port — open/send/read/cancel/release behind one owned seam

Status: implemented

## Problem

The [execution-route seam](2026-10-10-sidechat-execution-route-seam.md) let a mounting side pin the route/cwd of side agents, but execution still happened through the mounted Context's `agents` service — and in the consumer's topology that service IS the management host's registry, so every side agent still landed on the management host. Reimplementing a whole host `agents` service per target is not a viable seam (that interface is the host's entire agent world: create/resume, scope setup, lifecycle). The provider contract needed a narrow port owned by sidechat itself, covering exactly what the service touches for execution. Two adjacent gaps closed with it: a running side turn had NO stop gesture (the only stop was unload-time `disposeAgents`), and the cold-read path (`inspectCold`) and the dispose race were wired to `ctx.agents`/persistence directly, outside any injectable boundary.

## Decision

Additive; generic names; version stays 0.2.3; the wire is untouched (the generated typert faces are byte-identical, verified by diffing the rebuilt `lib/typert.host.d.ts` / `lib/typert.remote-client.d.ts` against the main checkout's).

- **The port** (`src/execution.ts`, exported from the package root): `SideChatExecutionBackend` = `capabilities` + `open(init)` (one verb for lazy create and cold resume, told apart by `init.resume`; a resume failure throws and the service falls back to a fresh open itself) + `readCold?(sessionId)`. `SideChatExecutionSession` = `sessionId` / `resolvedPresetId?` / `status` / `events()` / `send({ text, source })` / `syncTools?()` / `cancel?()` / `release()`. The service consumes the port EVERYWHERE it previously touched `ctx.agents`, handles, or `inspectCold` for execution: `ensureSession`/`openSession` (was ensureAgent/spawnAgent), the live status overlay, `stateOf`/`activityOf`, the openWith tool re-sync, send's followup, and `disposeAgents` (now releases sessions).
- **The open payload carries the resolved values**: `{ contextKey, sessionId, resume, route?, presetId?, cwd?, segmentText(), tools() }` — route/preset/cwd arrive resolved by the service's chains (explicit config > calling session > record > plugin config; cwd is a first-open fact, a resume replays what created the session). `segmentText`/`tools` are LIVE READERS (in-process thunks): the backend re-reads them at every assembly, so per-turn freshness holds for any backend by construction. Refs (the attachment semantics) never reach the backend — the service folds them into `<quoted_context>` text blocks before `send` and parses them back on projection, exactly as before.
- **The default backend** (`SideChatDefaultExecutionBackend`) is the previous `ctx.agents` behavior extracted as-is: the full route chain INCLUDING the `agentDefaultModel` probe, the preset chain through `composeSideAgent`, the cwd chain, the scope setup (prompt section + caller tools with by-name replacement), cold reads via `inspectCold`, and cancel via the agent's own `cancel({ kind: 'user' })` (probed per session — an old host line whose agent lacks the capability simply has no `cancel` on its session). The `agentRoute`/`cwd` config keys stay, consumed through the payload.
- **Injection**: `SideChatConfig.executionBackend`, construction-time (the factory-config precedent). Absent = default backend = byte-identical local behavior. With an injected backend the service NEVER falls back to deployment defaults: the `agentDefaultModel` probe and the calling-less-no-route `agent-unavailable` refusal are default-backend-only rules — an injected backend owns routing (the payload's `route` is advisory and may be absent).
- **Capabilities degrade, never crash**: `{ presets, promptContext, callerTools, cancel, coldRead }`. Service-side gates: `callerTools: false` skips the openWith tool sync silently; `cancel: false` makes the stop gesture refuse coded; `coldRead: false` makes cold reads answer the honest unknown (empty transcript, null error/times, status still `cold`). `presets`/`promptContext` are honored backend-side — the service passes `presetId` and the readers regardless; the flags never rewrite the payload.
- **The stop gesture is newly exposed, host-side only**: `ctx.sideChat.stop(contextKey)` with `SideChatStopOutcome` — coded refusals `not-found` / `not-running` / `cancel-unsupported`. Investigation finding: sidechat had no stop path at all before (no client button, no service verb; only unload-time disposal); the port's `cancel` is what the gesture rides. No Remote change — the wire stays as it is.
- **Dispose interplay**: the open/dispose race guard is generalized to the port (`refuseLateSession` releases a late-opened session on arrival and refuses the caller with the coded disposed error), and a same-root rebuild works with an injected backend too — the resume rides `open({ resume: true })` onto the backend's own persisted log.

## Alternatives considered

- **Reimplementing a per-target `agents` service** (the consumer's first shape): the registry interface is the host's whole agent world; a fake that wide is a fork, not a seam. The port is exactly the operations sidechat performs — narrow enough for a provider to implement honestly.
- **The backend returning projected transcript rows** instead of raw session events: the projection vocabulary (`projectTranscript`, the `<quoted_context>` unfold, the turn-end error scan) would have to be reimplemented by every backend; raw `SessionEvent[]` keeps one projector in the service, and the default backend's events ARE the session journal, so projection fidelity is preserved by construction.
- **Snapshots pushed per change** (segment/tools passed as values in the payload, re-pushed from openWith): loses per-turn freshness unless every mutation pushes, and adds a sync verb per contribution kind; live readers keep the freshness invariant for any backend with zero extra surface (the prompt-section text-provider pattern, generalized).
- **Widening the Remote face** (a wire stop verb, or the calling-less send): rejected — the seam is host-side consumption only, the browser always has a session, and the typert boundary already ruled an optional agent lookup out (see the [route-seam note](2026-10-10-sidechat-execution-route-seam.md)).
- **Making the `agents`/`sessions` injects conditional on a backend being injected**: cordis injects are static; with an injected backend the Context's `agents` is simply never touched (a stub suffices, documented in the README), and `sessions` still feeds cwd inheritance. A boot-semantics change was not worth it.
- **`cancel` on the backend rather than the session**: cancel targets one live session; a per-session optional method also models old host lines whose `Agent` lacks the capability, degrading to the coded refusal instead of a crash.

## Consequences

- New module `src/execution.ts` (port + default backend); the package root exports the port types and `SideChatDefaultExecutionBackend`; `SideChatConfig` gained `executionBackend`; the service gained `stop`; `tsconfig.host.json` lists the new file. The Remote face, the client, and the wire are untouched.
- Fourteen new contract tests: the port drives open/send/read/release with `ctx.agents` and `sessionPersistence` as throwing stubs; the payload carries resolved route/preset/cwd; the deployment default is never probed with an injected backend; calling-less send without a route resolves through an injected backend; cold reads come from the backend (never a resume); same-root rebuild resumes through the port; the open/dispose race releases the late session exactly once; each capability-degrade path; the payload is never rewritten by capability flags; stop cancels through the port and (default backend) through the agent's own `cancel({ kind: 'user' })`; stop's coded refusals and its post-dispose refusal. All 96 pre-existing tests pass UNMODIFIED — the default-backend extraction is byte-identical in behavior (110 total).
- The [route-seam note](2026-10-10-sidechat-execution-route-seam.md)'s implicit assumption that `agentRoute`/`cwd` suffice for non-local targets is superseded for that case (facts updated there): those keys parametrize creation through the Context's `agents` service only; an injected backend is the seam for executing elsewhere.
- An injected backend must still tolerate the package's static injects (`agents`, `sessions` — the README documents the stub); and a backend that persists nothing between `release` and the next `open({ resume: true })` degrades that context to a fresh session on next send (the resume failure falls back, the mapping corrects itself).
