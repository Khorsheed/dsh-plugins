# Agent Note: 后面有消息在等时，回复写明它回的是哪一条

Status: implemented

## Problem

房间按发生先后排（待定 1，选 A）：成员的回复落在它说完的位置，这个位置可能在人于这一轮进行中又发给它的那条消息下面。从上往下读，这条回复像是在回答后一条消息，而成员其实还没收到那一条。房间时间线设计 B 线第 B4 步。

## Decision

- `replyTarget(runId, speechTime, state)`（`src/client/reply-target.ts`）只读投递：这条回复自己的投递（一条人类消息），以及同一成员的第一条更晚的、有气泡的人类投递——在这一轮开始之后、回复落地之前发出，没有被这一轮当作回答吸收，也没被撤回或暂存。
- 找到时，回复卡片顶部加一行安静的小字「↑ 回复的是 21:56 那条 · 你 22:05 那条刚开始处理」，位置和样式同现有的起因行。点击滚到后一条消息的回执（前一条马上被收到，没有回执可滚；官方气泡不带 id）。
- 纯显示，不加数据：旧日志里投递呈现这种形状的地方同样会有这一行。

## Alternatives considered

- **等待中的消息一直压在正在跑的这一轮下面，直到被收到**（待定 1 的 B）：新回复会落在人刚发的消息上面，人得往上找。
- **在等待消息处把这一轮切开**（待定 1 的 C）：把成员根本没看到的消息当作交互点，会误导。
- **滚到被回复的那条消息本身**：官方气泡没有 DOM 句柄做不到；在每个人类气泡下加一个零高度标记行会让每条消息多一道间距。

## Consequences

- 「刚开始处理」在回复落地那一刻是字面事实；之后再读，下一轮的卡片或回复就在它下面，这行字指向仍然正确。
- 这一行只写时钟时间；同一分钟内的两条消息会显示同一个时间。

## Testing

`tests/reply-target.client.spec.tsx`：事故形状下回复带这一行（目标是第二条消息的回执），第二条的回复不带；没有后续消息、回复之后才发的消息、被当作回答吸收的消息都不带；回复卡片渲染出这一行。
