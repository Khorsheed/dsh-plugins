# Agent Note: 标题编辑输入框自适应宽度与客户端长度把关

Status: implemented

[English](2026-08-17-session-title-edit-input-fit-and-length-gate.md) | 中文

## 问题

标题编辑条目的编辑体验有两个缺口。(1) 原地输入框的宽度被钉死在官方标题 crumb 的测量矩形上(`width: placement.width`),输入更长的标题时文字会被挤在原标题的窄框里——输入框只在窗口缩放时重测,从不随输入变化。(2) 宿主 `session-title` 服务把所有被接受的标题限制在 `maxTitleBytes`(base bundle 默认 80 UTF-8 字节),并在 `normalizeSessionTitle` 里静默截断超限输入——用户输入 30 个汉字时,编辑器像保存成功一样关闭,标题却少了约 26 个字符,且没有任何报错。README 把这两点都记在 Known Limitations 里。

## 决策

- **自适应宽度。** 原地输入框现在通过隐藏的镜像 span 测量草稿——该 span 以输入框同字体(同字号/字重,`white-space: pre`)渲染草稿原文,由以 draft 与 placement 为依赖的 `useLayoutEffect` 驱动——并把输入框外宽设为 `clamp(文本宽 + padding + 边框 + 光标余量, crumb 宽, 220px)`:下限是 crumb 的原始测量宽度(删除文字时框不会塌缩),上限对齐官方 crumb 的 `max-width: 220px`(长草稿恰好裁切在 crumb 省略号会出现的同一位置)。输入框自身的 `scrollWidth` 在内容放得下时等于 `clientWidth`,无法缩回,因此镜像 span 才是测量手段。降级的行内编辑器保持固定 220px(等于上限)。
- **客户端长度把关。** 新增 `src/client/title-length.ts`,镜像宿主契约:`MAX_TITLE_BYTES = 80` 与 `normalizedTitleByteLength()`,后者应用宿主截断前相同的清洗(剥离 ESC/CSI/控制/方向控制序列、空白折叠为单个空格、trim)后统计 UTF-8 字节。编辑器以*清洗后*的长度把关,因此触发时机与宿主要截断的时机完全一致:空白密集或夹带控制字符的草稿不会被误报,恰好处于边界的草稿原样通过。超限草稿显示本地化提示(`hint.tooLong`,插值 `{max}`/`{chars}`/`{bytes}`)并阻止提交——行内编辑器禁用保存,原地编辑器忽略 Enter。宿主拒绝路径(`title-invalid`,只可能表示标题为空)保持原样。

## 备选方案

**测量输入框自身的 `scrollWidth`。** 已否决:文本放得下时它等于 `clientWidth`,用户删除文字后永远无法把框缩回去。

**`field-sizing: content` CSS。** 已否决:浏览器支持仍不均衡,而且拟合结果脱离组件掌控(jsdom 里也无法测试)。

**让宿主截断、把缩短后的标题当反馈展示。** 已否决:此时标题已经提交,用户得自己发现再改。提交前拦截并提示才是唯一诚实的做法。

**用近似字符数(比如 80 个"字符")代替 UTF-8 字节。** 已否决:中文标题会被砍得远早于宿主允许,ASCII 又远晚于宿主——两个方向都是假闸门。与宿主逐字节对齐才是关键。

**只为原地编辑器做长度把关。** 已否决(不算问题):行内编辑器共用同一草稿与提交路径,同一把关与提示顺带覆盖,增量面可忽略。

## 后果

长草稿现在会把原地输入框加宽到官方 220px 上限(超出后按 crumb 省略号的同一位置裁切/滚动),超限标题不再可能被静默提交:编辑器会拦截,并用用户的语言解释原因。`MAX_TITLE_BYTES` 是对宿主生产默认值的硬编码镜像——宿主提高 `maxTitleBytes` 后常量必须跟随,否则编辑器会比宿主更严格;README 已标注此点。官方侧边栏重命名对话框仍会静默截断(不在范围内——那是宿主 UI,不是本插件的)。覆盖:字节助手有单测;行内编辑器把关(提示、禁用保存、拦截 Enter、恰好 80 字节的边界)与原地自适应(增长、220px 上限、crumb 宽度下限、原地提示 + 拦截 Enter)有组件测试。
