# Agent Note: each canvas owns its card categories

Status: implemented

## Problem

`proposals/active/2026-09-16-canvas-space.md` §11.4's stage ⑤ and the approved panel prototype both ask for the same thing: the five card kinds stop being a closed set the operator has to accept, and become a list each canvas can rename, extend and retire from. Before this change the five lived in three places at once — the `BoardCardKind` union in `src/types.ts`, the compile-time `kind` enum in `src/tools.ts`, and the hard-coded chip strip in `BoardView.tsx` — so "add a category" meant touching the wire format, the model contract and the UI in the same move, and any of the three could be left behind.

The governance question the proposal settled in the round before this one is why the catalog is per-canvas rather than one global list: **each canvas stores its own copy** (rule ① of §11.8). The user's board is a topic, and the categories that fit 为什么人们不愿表达异议 do not fit a product-evaluation canvas; a global catalog would make every board's chip strip a compromise, and would turn a rename into an edit of every canvas at once.

Three constraints made this more than a settings screen:

- A card must survive its category. Retiring a category is a reversible act; the alternative — dropping each card's row — is data loss hiding behind a UI gesture.
- The model must still be able to say which category it means. Every `canvas_propose_card` call carries a `kind` that the board has to accept, so the enum and the catalog cannot be allowed to drift.
- The 40-odd canvases already on disk have no `categories` field at all. Whatever this change is, it may not need a migration.

## Decision

- **A category id is a string with a grammar, not a union.** `CardCategoryId = string`, and `isCardCategoryId` admits exactly the five built-ins plus `cat_[a-z0-9]{9,32}` — the shape `makeBoardId('cat', …)` mints. The `cat_` prefix is what keeps a custom row from ever shadowing a built-in, which matters because an id is used to build a lookup, not a path. Behavior that only built-ins get (the question lifecycle, the document heading) keeps switching on `BoardCardKind` through `isBoardCardKind`, never on the type.
- **The catalog is a board field: `{ id, label, order, enabled }[]`.** An empty `label` means *show the built-in's localized name* — which is only legal for a built-in — so switching the host language still renames 「灵感」→"Fragment" until the user overwrites it with a label of their own. A custom row can never be nameless: the read substitutes its id.
- **Cards store the id, so a rename touches zero cards.** That single choice is what makes the panel's most common gesture free. It also means the label is a *display* concern and lives in exactly one client module (`src/client/category-label.ts`, which owns both the words and the built-in icons), so the chip strip, the new-card menu and the detail page cannot drift apart.
- **Categories are retired, never deleted.** `enabled: false` removes the chip and refuses new cards; the cards already filed under it stay on the board, and the row keeps its name. The panel lists them in a separate 已停用 section with a 重新启用 button.
- **Zero migration, by the tolerant read.** `normalizeCategories` guarantees three things whatever the file held: the five built-ins are always present, every row is unique by id, and the list is sorted by `order`. `reconcileCategories` then files back any row a card still points at — a hand-edited file that deletes a custom row gets the row back (named after its own id, last in the strip) rather than losing the card, because `normalizeCard` refuses a card whose kind fails `isCardCategoryId`, so an orphan row can only ever be a *legal* one.
- **One verb for the whole panel.** `setCategories` takes the entire desired catalog: rename, add and retire are all "here is the new list", which keeps the write as version-guarded as every other board mutation. `archiveCardIds` rides along on the same request so retiring a category that holds cards and filing those cards away is **one rewrite** — as two calls, the second could lose the version race and leave a retired chip with live cards under it.
- **Every card write asks THIS board.** `putCard`, `patchCard` and `proposeCard` each look the kind up in the board's own catalog and refuse (`invalid-name`) when the row is missing or retired. `isCardCategoryId` alone is no longer enough, and this is the check that makes the agent's entrance honor the same rule as the user's.
- **The model face has one floor.** `menuCategoriesOf` is the single source for both the `kind` enum and the `id（名称）` menu spelled in the tool description, so they cannot disagree. The side-chat entrance gets the asked-about canvas's catalog; the **main-session** entrance keeps the compile-time five, because its definition is registered at boot before any canvas exists — the execution still accepts a custom id (the store checks it against the focused board), the enum just cannot advertise one the model was never shown.
- **The tag the model reads is the id it must send back.** `categoryTagOf` renders an untouched built-in as the **bare id** (`fragment`) and anything the user named as `id（名称）`. This is the round-trip contract: the prompt's card lines, the count line and the `kind` enum all speak ids, and the user's words ride along as a gloss.

## Alternatives considered

- **One global catalog for all canvases.** Rejected in §11.8 and re-confirmed here: the strip is a per-topic instrument, and a global rename would fan out over every canvas's board file.
- **`categories` as a global field with per-canvas overrides.** Rejected: an override layer needs a "what did I change" UI to be usable, and the diff semantics (a row deleted globally but present locally) land exactly where this feature's simplicity lives.
- **Store the label on the card and let cards keep their old name after a rename.** Rejected: it makes a rename a bulk rewrite of every card (the write the user must not pay for), and it can leave two cards with the same category spelled differently forever.
- **Delete a category, re-filing its cards into a chosen destination.** Rejected with the strongest reason attached: a destination picker asks the user to reason about N cards at the exact moment they wanted to hide a chip. Retire-and-ask-once costs nothing and is reversible; the 「改分类」 batch gesture already on the selection bar is where "keep these on the board" belongs, and the panel deliberately says so in its tip line.
- **Keep `BoardCardKind` as the stored type and put custom categories in a separate field.** Rejected: every read path would carry two vocabularies, and the model's `kind` argument would need a union of the two anyway.
- **Give the restored built-ins `order: 0` in `normalizeCategories`.** What I first wrote, and a real defect the suite caught: a legacy file (no `categories` at all) then sorted the five **alphabetically** — document, fragment, grounding, question, reference — silently reordering every existing canvas's chip strip. A restored built-in now carries its own default slot, so an empty field reads as exactly `defaultCategories()`.
- **Spell the model-facing tag with the user's name only (`[灵感]`).** A regression I introduced mid-round and the tests named immediately: `ask.spec` expected the `[fragment]` line because the model has to pass the enum value back. A name that the wire cannot carry is not a tag.
- **Put the rename inside the card editor** (rename here, and every card showing it) — rejected: a rename is a catalog edit, and the board is where the catalog is visible.

## Consequences

- **`card.kind` is now `string` at the type level.** TypeScript no longer forbids comparing it to a non-kind string; `isBoardCardKind` is the only narrowing. Anything new that behaves differently per kind must narrow first — that is the price of an open set, and it is paid once per call site rather than once per user.
- **The state file grew a field, and the two directions are not symmetric.** A 0.4.4 host reading a 0.4.5 `canvas.json` ignores `categories`, and `normalizeCard` refuses any card whose kind is not one of the five — so **downgrading a canvas that has cards under a custom id hides those cards** (they stay in the file; upgrading brings them back). Nothing here pretends otherwise, and the release order is: never ship a canvas with custom categories to an instance that can be rolled back to 0.4.4.
- **The retire confirmation is the only `Modal` in `BoardView`.** It is deliberately a host modal rather than an inline row: the act moves content out of sight, and §10.7's exact words (正文保留、随时恢复) belong where the user's attention is.
- **Retiring a category that holds cards archives them — and the batch selection is dropped for those ids.** `CanvasTab`'s `setCategories` filters the outgoing archive ids out of the selection, otherwise the selection bar would keep offering lens actions on cards that just left the board.
- **The refile fan-out is sequential on purpose.** `refileSelected` awaits one `patchCard` per card because each write presents the token the previous one returned; a parallel fan-out fails its own version guard on every call after the first.
- **`categoryLabelMap` seeds `defaultCategories()` before the board's rows**, so a board object that never passed through `normalizeBoard` (a client fixture, a hand-built Remote payload) still shows 灵感 for `fragment` rather than the bare id. The catalog is authoritative; the defaults are the floor.
- **22 new zh/en locale pairs** (`cat.*`, `board.refile*`, `board.manageCats`, `confirm.retire*`, `toast.catsSaved`, `toast.cardsMoved`), and the `kind` labels stay exactly where the rename note put them.
- **Both READMEs state the new rule twice on purpose** — once at the kind list (a starting point, not a ceiling) and once as the catalog bullet — because the sentence a reader needs is "cards store the id, so a rename touches no card".
- **Still open from §11.8**: whether the tool enum should ever be a union across canvases (it is not — this note's `menuCategoriesOf` is per canvas), and the 顺线扩一圈 / link-view questions that belong to stage ⑥. Stage ⑥ landed the same day ([the link view is a second face of one board](2026-09-23-canvas-link-view.md)); what is still undecided there now sits in §11.8 ⑦–⑨.
