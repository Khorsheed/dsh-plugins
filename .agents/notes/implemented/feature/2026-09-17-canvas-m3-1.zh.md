# Agent Note: 画布 M3.1 —— 选区归引用插件，fullscreen 从不可用作默认建议

Status: implemented

[English](2026-09-17-canvas-m3-1.md) | 中文

## Problem

M3 落地一天之内，3080 反馈了两条。

**详情页的选区「问 Agent」浮层是重复建设。** M2 在卡片详情阅读器里给文本选区做了浮动按钮（选中一段 → 问 Agent）。引用插件（`@khorsheed/dsh-quote`，M1 已上 main）此后在应用级统一接管了选区交互——它的浮层在任何选区上提供 引用到当前会话 / 引用到侧边对话 / 复制。同一个手势在同一个位置有两个浮层应答，不是冗余，是互相干扰：画布那个应用级交互的 bespoke 副本必须退场。

**M3 的宽模式建议适得其反。** M3 在 tab 打开时建议 fullscreen（`openRightbar(track, fullscreen)`）。宿主的 fullscreen 模式**隐藏右栏拖拽把手**（用户实测：宽度变成不可调），而「保留会话列宽」保的是大宽度。一个移除用户自调能力的建议不是建议，是剥夺——它的兜底（点一下退出 fullscreen）还要求用户知道它刚藏起来的那个把手在哪。

## Decision

**选区浮层删除，不做改造。** 从 `CanvasDetailView` 移除：`mouseup` 选区监听、浮动按钮与定位计算、`.askFloat` 样式、`chat.ask` / `chat.selectionRef` 词典键，以及对应的详情 spec 用例。刻意保留的：透镜条的「就此提问」与评论线程的「追问」——那是卡片级与评论级动作，不是选区行为，引用插件对它们没有任何主张。`askAgent` 动词与整条 `openWith` 接线原样不动（透镜与追问还在用）。此后的契约句子：**画布不拥有任何选区交互**；引用插件的浮层是任何文本选区上的唯一答案，画布详情也不例外。

**fullscreen 建议撤回为普通 track 面板。** `suggestWideMode` 不再调用 `openRightbar(track, fullscreen)`——右栏保持普通 track 模式：把手在、宽度用户自调、布局有记忆。保留的是每会话一次性的 `toggleSidebar()` 收**左侧会话列表**建议（以框架 `data-sidebar-collapsed` 标记为门，绝不盲 toggle、绝不重复强制）——收起列表不拿走任何用户一键可恢复的东西，这正是默认建议必须具备的性质。upstream 候选补一句附记：per-tab presentation seam 仍是「这个 tab 想更宽」的诚实形态，但 **fullscreen 本身被取消作默认建议的资格**——它藏把手。

## Alternatives considered

### 为什么不只在引用插件够不到的地方保留浮层？

引用浮层按设计就是应用级的——它覆盖一切可选中的表面，包括我们的详情正文。划出「无引用区」意味着每次选择都要判断哪个浮层赢了手势竞赛——这正是用户报告的干扰本身。一个手势一个主人：为应用级而建的插件拥有它。

### 为什么不保留 fullscreen 建议、改成每次打开画布只发一次（而非每会话一次）？

频率从来不是问题，模式本身才是。每次打开都发，仍是每次打开都藏一次把手；而用户的解法（退出 fullscreen、调宽、再不理这个 tab）等于教他们别碰这个 tab。一个每次实例都需要撤销的建议，是带日程表的 bug，不是特性。

### 为什么不建议一个自定义的更宽 track 宽度？

没有「设置面板宽度」的公开面——track 宽度是 ui-sidebar-right 的 store 事实，与 fullscreen 同宗的归属问题，且同一条 upstream seam 覆盖两者。诚实的默认是普通面板加用户本来就在的把手。

## Consequences

- `packages/canvas/src/client/detail/CanvasDetailView.tsx`：选区监听、浮层、`textPick`/`bodyRef` 状态全删；提问流只剩两个卡片级入口。
- `packages/canvas/src/client/detail/CanvasDetailView.module.css`：`.askFloat` 块删除。
- `packages/canvas/src/client/locales.ts`：`chat.ask`、`chat.selectionRef` 删除（两本词典）。
- `packages/canvas/src/client/index.ts`：`suggestWideMode` 删除 `openRightbar(track, fullscreen)` 调用与 `fullscreen` 参数；每会话 `toggleSidebar()` 建议不变。
- `packages/canvas/src/client/contract.ts`：face 的 `suggestWideMode` 签名相应收窄；`packages/canvas/src/client/tab/CanvasTab.tsx` 不再为此读 `useTabInfo`。
- `tests/detail.client.spec.tsx`：删选区浮层用例（168 → 167 全绿）；`tests/tab.client.spec.tsx`：宽模式断言随新签名。
- `package.json` 0.4.0 → 0.4.1。
- M3 note 的宽模式段是被本篇修正的事实；两篇交叉链接。Remote 面、工具、side-chat 接缝与 M3 的其余全部决策未动。

## Testing

- `packages/canvas`：**167 个测试全绿**（168 − 删掉的 1 个浮层用例）。`rm -rf lib` 后 `pnpm --filter @khorsheed/dsh-canvas build`、`pnpm check:hygiene -- packages/canvas`、`pnpm check:plugins`、`pnpm test:scripts` 全绿。
- 存活的两个提问入口（透镜「就此提问」、评论「追问」）的 spec 覆盖未动，保留的接线是被证明的保留，不只是没删。

## Deferred

- per-tab presentation seam（「这个 tab 想更宽」，定义级或导航级）仍是 upstream 候选——附记更新：fullscreen（藏把手）被取消作其默认的资格。
- 引用插件的浮层覆盖到画布**卡板**（不止详情正文）是它自己包内的表面决策，不由画布接线。
