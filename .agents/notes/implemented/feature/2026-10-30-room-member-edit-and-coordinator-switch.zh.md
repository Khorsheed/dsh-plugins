# Agent Note：邀请和编辑共用一套模型表单，原生 dsh 可编辑，输入框里可切换协调者

Status: implemented

## 问题

- **同一个弹窗里有两套模型控件。** 邀请时用的是 local-agent 的双下拉选择器（模型 + 强度）；编辑一个已经启动的成员时，换成了即选即生效的成员配置浮层（「模型 › / 推理强度 / 暂未取得此模型的强度选项…」）。同一个弹窗两种交互，编辑那一套更难用。
- **房间自己的 agent（dsh）不能编辑。** 不能改名，不能设职责、指令，也不能改模型。它的模型就是会话的模型，只能从输入框的模型选择里切。
- **交接协调者只能在成员页做**（「设为协调者」），离用户决定「这条消息发给谁」的地方很远。

2026-10-30 与用户确认（交互稿 `proposals/prototypes/room-member-dialog-coordinator.html`，仅本地）。

## 决定

- **local-agent** 在 `LocalAgentUi` 上新增一组可选的表单接口：
  - `renderMemberModelPicker(childSessionId, props)`：同一个 `HarnessModelPicker` 双下拉，读取的是这个成员自己的模型目录；
  - `readMemberSelection(childSessionId)`：把成员最新的设定读成草稿。「跟随默认」的选项草稿取它实际解析到的值，因为下拉遇到空值会自动填第一项，而用户没动过的表单不能保存任何东西；
  - `saveMemberSelection(childSessionId, draft)`：和实时控件的选择一样，经成员控制的 `select` 排队应用；有一轮在跑时返回 `deferred`。
  
  转换函数在 `client/member-selection.ts`。
- **房间的编辑弹窗**：当 core 提供这组接口时，已启动的 CLI 成员显示这两个下拉，点「保存」才生效。成员正在运行时提示「本轮结束后生效」；保存被推迟时，成员页再弹一次这条提示。旧版 core 仍用实时控件。
- **dsh 可以编辑。** 编辑弹窗提供称呼、职责、指令，以及会话模型的两个下拉（由 `ctx.modelDirectories` 生成：按 provider 分组的模型，加上所选模型的强度）；保存时调用 `directory.select`。不提供 Provider、模式和工作目录。`updateMember` 现在允许给主 agent 改名：它的身份是加入时的 seq（`legacy:<seq>`），入座以 `isRoomLog` 判断，各处检查也都用 `kind === 'main-agent'`。移除仍然不允许。
- **输入框。** 协调者那一行改为宿主 `Menu`（`@deepseek-ai/dsh-client-ui-primitives`，宿主模型选择用的同一个菜单）的触发按钮，不再由房间自己绘制列表。菜单列出所有成员和「职责 · provider」，当前协调者打勾。选中即调用 `setCoordinator`，不再确认；交接照常在时间线上留一行。只要有成员在运行，或有投递处于排队、运行中、结果未知，触发按钮就置灰并说明原因。这和服务端的 `coordinator-busy` 是同一条件，只是在选之前就告诉用户，而不是选了再报错。

## 考虑过的其他方案

- **交接前弹确认。** 用户选择直接交接，由时间线上的那一行留痕。
- **协调者运行中也允许交接，让它做完这一轮。** 用户选择不允许：有工作在进行时，「下一条由谁回答」会变得含糊。
- **编辑时保留实时控件，只改样式。** 那样同一个弹窗里还是两种交互方式。

## 影响

邀请和编辑用同一套模型表单，点「保存」才生效。房间自己的 agent 和其他成员一样可以查看和编辑。协调者在写消息的地方就能切换。

## 测试

- `local-agent`：`member-selection.spec` 覆盖草稿和选择之间的互相转换，包括「跟随默认」的选项取解析后的值作为草稿。
- `room`：
  - 成员页测试：已启动成员的下拉草稿，经 `saveMemberSelection` 保存且不写名册，以及推迟生效的提示；编辑 dsh 时显示固定说明行，不显示工作目录，预填会话模型，改名会保存，模型不受影响；dsh 的卡片有「编辑」，没有「移除」。
  - 输入框测试：菜单列出成员，选中即交接；有投递在运行时触发按钮置灰。
  - 服务测试：给 dsh 改名后仍然只有一个主 agent，并且仍是协调者。
