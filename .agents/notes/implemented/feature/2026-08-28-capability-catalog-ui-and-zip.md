# Agent Note: capability-catalog UI is a preview grid + modal detail, and add-skill uses a dependency-free zip reader

Status: implemented

English | [中文](2026-08-28-capability-catalog-ui-and-zip.zh.md)

This note goes with the [`capability-catalog` proposal](../../../../proposals/active/2026-08-26-capability-catalog.md) and records two decisions that shipped in its v1 (package `@khorsheed/dsh-capability-catalog`).

## Problem

The catalog proposal's v1 GUI was originally described as an official-style fold card plus a separate MarkdownText reader (a distinct "view full content" surface). The user instead wants a three-column preview grid and a centered detail modal whose source is a **file browser** — a left file tree + right content pane, like worktrees' repo-file view — so a separate "package files" section and a raw "view source" block would be redundant. Separately, the add-skill zip path planned on a third-party zip library, but the typert generator's scratch overlay resolves only `@deepseek-ai/*` source-plane packages and the harness's own node_modules (a third-party host dep is unresolvable there), so the host build broke. And the catalog snapshotted the skill registry at host-global scope, which sees only runtime skills — the model sees user/official skills via the agent-preset scope but the settings GUI did not, and a runtime plugin skill's bundle files (scripts/assets) were invisible unless the plugin exposed them.

## Decision

**1. The GUI is a 3-column preview grid + a centered detail modal, not a fold-card expand or a separate reader.** The proposal originally described an official-style fold card (collapse to expand); the user instead chose: a three-column grid of preview cards (name + one-line description + source/provider pill), where clicking a card opens a centered modal. The modal loads one skill on demand via `ctx.skills.get()` and shows the full description, source/provider/invocation meta, and — when the metadata declares credentials — a per-credential config block (`credentials.set`, value never on the wire; `describeRecord` read-only for the configured state). The **source is a split browser** (the user wanted the source to be a file tree like worktrees' repo-file view): for a directory-bundle skill the "View source" section is a left file tree + right content pane — the tree lists the bundle's SKILL.md + references/scripts/assets (paths the host walks from `resourceBase.kind === 'directory'`); clicking a file loads its text via a `readSkillFile` Remote (SKILL.md reuses the already-loaded detail body), and a single-file skill falls back to a raw `content` block. There is no separate "package files" section — the tree *is* the source. The standalone tab is registered as `settings.section` (id `capabilities`, order 20, after Plugins=15), matching the local-agent registration posture.

**2. Add-skill unpacking is a dependency-free zip reader over `node:zlib`, not a third-party zip library.** The plan was to use adm-zip in the host half, but the host-face files are analyzed by the typert generator against a scratch overlay that only resolves `@deepseek-ai/*` source-plane packages and the harness's own node_modules — a third-party zip lib is not in that tree, so gen-typert fails with `TS2307: Cannot find module 'adm-zip'`. (It works for `zod` / `@deepseek-ai/schemastery` only because those happen to be harness deps.) Since no host edit is allowed and the overlay is per-process, the fix is `src/zip.ts`: a minimal reader handling stored (0) and raw-deflated (8) entries via `zlib.inflateRawSync`, skipping directories and rejecting path-traversal names. This keeps the published package free of a zip runtime dependency and keeps the host face to node built-ins + `@deepseek-ai/*`, which the overlay resolves natively. The add-skill modal offers "upload zip" and "paste SKILL.md" tabs; both install into `$DSH_HOME/skills/<name>/` (user) or `.agents/skills/<name>/` (project), which the existing skill-filesystem watcher discovers — no new registration mechanism. GitHub clone is v1-deferred (`channel === 'github'` returns "not wired in v1").

## Alternatives considered

- **adm-zip / jszip in the host half.** Rejected: the gen-typert overlay can't resolve a third-party host dep, so generation breaks. Client-side decompression (jszip) would move the work but adds a client bundle dependency and larger requests, against the user's chosen host-side UX.
- **Staying with the fold-card + separate MarkdownText reader from the proposal.** Superseded by the user's grid + modal choice; the modal reuses the same detail-loading so no extra surface is lost.

## Consequences

- No new runtime dependency; the host face stays on node built-ins and `@deepseek-ai/*`, so `pnpm check:plugins` and the release build both stay green.
- Skill cards are now preview-only by design; detail requires a click (matches the proposal's progressive-loading rule that the list never batch-fetches bodies).
- **Skill scope is the standing agent-preset key, not host-global.** The catalog snapshots with `agentPresets.standingKeyFor(defaultId)` — the documented host-reader seam — so a host-global settings reader sees the same official/plugin/user skills the model does (the web bundle mounts skill-filesystem under the preset's standing scope, not global). The `detail`/`get` path threads the same scope key, so a user skill's full body, metadata and declared credentials load. When the presets service is absent the catalog degrades to the global layer alone (no presets in a minimal profile ⇒ runtime-only, which is correct there).
- **Bundle visibility is the plugin's choice.** A skill's file tree (the source browser) is rendered only when the registry exposes `resourceBase.kind === 'directory'`. Filesystem/provider-discovered skills always do; a runtime plugin skill only does if the plugin registers with a `resourceBase` (or a `registerProvider`). `inline-html-card` registers content-only, so it falls back to a plain content block — not a catalog defect. This contract is written up as the "Plugin skill registration protocol" in the package README (and is an upstream-candidate ask for dsh-skill to state explicitly).
