# Agent Note：内容数据放在 design JSON 里，以及预览状态

Status: implemented

## Problem

用插件做的那个 3D 游戏，内容已经多到不适合继续写在代码里。场景、任务、元素交互和世界状态都搬进了 JSON（`design/scenes/*.json`、`design/quests/*.json`、元素文件里的 `interactions` 字段），由 `src/` 里的解释器执行这些数据。由此撞上两堵插件的墙。第一，版本里不包含整个 `design/` 目录，游戏 fetch 不到自己的数据，只好在 `src/` 里手抄一份模块，再写测试检查两份是否一致。第二，每轮检查只跑浏览器里的 `tests/*.test.js`，游戏针对这些数据写的 node `.mjs` 测试从来没进过门禁。游戏还实现了 `dshGame.preview({ scene, state })`，可以直接进入某个世界状态，但面板没有入口能用到它。

游戏 agent 最初提议由插件内置一套固定的条件和效果词汇（`setFlag`、`giveItem`、`grantSketch`、好奇度阈值……）。这套词汇属于某一个游戏的题材，而[边界说明](../architecture/2026-10-25-game-plugin-boundary.zh.md)要求插件保持通用。

## Decision

- **词汇归项目。** 条件、效果及其参数由游戏自己定义，由游戏自己的解释器执行；插件不带任何题材词汇。数据里不写 JavaScript。
- **design 下的 JSON 进版本。** `isBuildFile` 现在接受 `design/` 下任意位置的 `.json` 文件；策划正文（`.md`、概念图 `.html`）仍然不进版本。改动这类文件按代码改动处理：要过检查，并成为候选版本。沙箱的 `fetch` 垫片本来就能提供任何进了版本的文件，所以试玩和检查里都能 `fetch('design/…json')`。数据检查会让解析不了的 design JSON 失败；数据的含义仍由游戏自己测试。
- **预览状态。** 游戏可以提供 `dshGame.previews`（一个 `{ scene, state, label }` 数组，或返回这样一个数组的函数），以及 `dshGame.preview({ scene, state })`（拒绝时返回 `false`）。每次运行时，面板都会通过桥接（`previews` 消息）要这份列表。列表不为空时，试玩页舞台栏显示「预览状态」菜单。选中一项会重开一局，等 `dshGame.ready` 为 true 后发送 `enter-preview`；桥接回报 `previewed`，带上 `ok` 和 `supported`，面板据此弹出提示。点重开或停止都回到普通的一局。
- **技能。** `gamedev` 新增「内容数据」一节：场景、任务、交互写成数据，`src/` 里写解释器，加载时就校验，用 fetch 读而不是抄一份，可达性写成测试。它还写明 `dshGame` 的这两个可选成员，并直接说明检查只跑浏览器里的 `tests/*.test.js`，数据测试应该写在那里。

## Alternatives considered

**由插件定义一套条件/效果语言。** 已否决，因为这会把插件绑在一种题材上：下一个游戏要么用不上，要么每多一个动词都得改插件。计划中的下一步是改由项目声明 schema，插件据此校验引用。

**在 `design/` 之外另设 `content/` 目录。** 游戏已经把数据放在 `design/` 下，和描述它们的策划章节放在一起；而且只有 JSON 文件进版本，策划正文不会混进版本。

**在检查里跑项目的 node 测试。** 那样宿主就要在沙箱外运行项目代码。浏览器测试已经可以通过 `fetch` 读到数据。

**不重开，直接在正在运行的这局里进入预览。** 从一局新开的游戏进入的预览可以复现；叠在玩家之前随便做过什么之上的预览则不能。

## Consequences

- 游戏可以删掉抄来的数据模块和那份一致性测试，并把数据测试改写成 `tests/*.test.js`。
- 下一步是由项目声明 schema（ID 命名空间、条件和效果的参数、它们出现在哪些字段）。有了它，检查就能校验引用，元素页能展示和编辑嵌套的交互，glTF 动画名也能核对。格式会从游戏的真实数据中提炼。
- 只有正在运行的游戏提供了非空列表时才会出现预览菜单；旧版本和没有这个接口的游戏看不到任何新东西。
