# Agent Note: 侧边对话 M3——openWith 自我浮出水面：RightbarRoot 根因与修订号差分信号

Status: implemented

[English](2026-09-16-side-chat-m3.md) | 中文

## Problem

3080 实证加宿主源码铁证：消费方（画布）在自定义 main 面板（画布空间）里调 `ctx.sideChat.openWith(...)` 再 best-effort `ctx.sidebarRight.openTab('sidechat', …)` 时，**用户看不到任何反应**。消费方把 M1/M2 契约要求的全做了，换来的却是沉默。

根因是上游的 RightbarRoot 契约：`packages/client/ui-sidebar-right/src/client/shell/RightbarRoot.tsx` 只在 `usePanelInfo(info => info.activePanelId === null)`——即会话面板激活——时渲染右栏。在任何自定义 main 面板上右栏按构造为 null，`openTab` 记录的导航没人看得见。因此"在哪里呈现"这个决策不可能属于消费方：它必须内化到 side-chat 客户端——只有它自己知道兜底层（M2 的浮动 dock）。而要做到这一点，客户端得先**感知** openWith 发生过，且 host→client 方向必须走 Remote 线，不能共享内存。

## Decision

**信号是每个上下文一个 openWith 修订号，经轻量 Remote 轮询差分。** contexts 记录携带 `rev`（持久化、可选，M3 前记录经宽容读取默认 0）；`openWith`——只有它，`send`、`quoteMessage` 都不算——在**每次**调用时递增，因为浮出语义是"消费方刚打开了这个上下文"，一次调用一次浮出。新动词 `@Remote('surfaceHints')` 返回 `{ items: [{ contextKey, rev }] }`——服务能提供的最轻读取（纯内存：无 journal 投影、无持久化检视），2.5s 轮询一次只是一次 map 迭代。客户端的 `useOpenWithSurfacer` hook 轮询它，首个结果只做基线（重载绝不把基线之前的东西重新浮出来），修订号变大即触发现身决策。

**呈现决策放在始终挂载的 root 表面上。** M2 的 dock 条目（`shell.overlay`）在 shell 启动时挂载，无论 side-chat 的哪个面开着，所以它的 surfacer 是主：会话面板激活（`activePanelId === null`，RightbarRoot 的可见条件）→ `openTab`（tab 在那里可见）；自定义 main 面板 → dock store 的 `actions.open(contextKey)`（dock 按构造浮在所有面板之上，`open` 同时切到对应 contextKey）。两层兜底：dock 座位缺席或视口窄于 720px → 仍 `openTab`——此刻不可见，但导航已被**记录**，回到会话面板时 tab 已在正确的上下文上。tab body 只在 overlay 座位缺席时跑同一个 hook（`enabled: !dockAvailable()`），主与兜底绝不双发；没有 overlay 座位的宿主在 tab 自身未开时什么也浮不出——记录在案的降级，与那里本来可能的完全一致。

**消费方契约不动。** `openWith` 签名不变；消费方的 best-effort `openTab` 变成多余但无害（它不再是机制，side-chat 也从未依赖它）。

## Alternatives considered

### 为什么不用 `ctx.remote.$on`（转发宿主事件通道）？

`$on` 机制存在且形状正确——但运行期转发白名单（`@deepseek-ai/dsh-api-remotes` 的 `API_REMOTE_FORWARDED_EVENTS`）是上游拥有的硬编码数组；社区插件不改 harness 就加不进 `sidechat/opened`。类型层的 `TypertRemoteEventSelection` 可 merge 扩展，并不改变转发循环实际转发什么。插件自定义转发事件已记为 upstream 候选；在它落地之前，Remote 轮询是今天能上线的、符合架构的通道。

### 为什么不用自定义 session journal 事件（room 的 `room/*` 实时喂）？

session 事件确实会流到客户端——但 `openWith` 时刻的 side-chat 上下文通常还没有 session（M1 的懒创建），而且把浮出簿记写进模型可见的会话日志，会污染 transcript 的唯一事实源。journal 是 transcript，不是消息总线。

### 为什么不用 M2 的 controller 闭包（纯客户端）？

controller 活在客户端 bundle 的 apply 闭包里——它永远观测不到宿主侧的 `openWith`。任务自己的约束就了断了它：host→client 必须跨 Remote/事件边界，不能共享内存。controller 继续干它本来的活（客户端内部 tab↔dock 交接）。

### 为什么不在 `send`/`quoteMessage` 上也递增修订号？

那些手势是客户端发起的（用户正盯着引起它们的表面），在它们之上浮出是噪音——而且 `quoteMessage` 已经走自己的 `openSideChat` 路径浮出。`rev` 只随 openWith 递增，让"一次变大"恰好只意味着一件事。

## Consequences

- 宿主（`types.ts`、`service.ts`、`remote.ts`）：`SideChatContextRecord.rev?`（宽容读取默认）、`openWith` 每次调用递增、`surfaceHints()` 服务方法、`@Remote('surfaceHints')` 动词（读取，无 agent）。全部线上增量；`openWith` 签名与 M1/M2 全部契约不变。
- 客户端：`use-open-with-surfacer.ts`（轮询 + 基线 + 决策，`SURFACE_POLL_MS` 2.5s、`SURFACE_NARROW_WIDTH` 720），接入 `SideChatDock`（主）与 `SideChatView`（座位缺席时的兜底）；两个 inject 面各增 `surfaceHints` + `openTab`；`openTabWith` 是所有面共享的唯一探测导航助手。
- `package.json` 0.2.0 → 0.2.1；双语 README 记录自我浮出行为、`surfaceHints` 动词与 RightbarRoot 根因。`docs/packages.md` 已再生成。无新增依赖。
- 给下一个人写假定时器套件留的排错注：**surfacer 的挂载轮询消费的是 bench 的默认 mock 实现**（effect 在 `render()` 内就冲刷了），在 bench 调用之后写的 `mockResolvedValue` 永远塑造不了基线——两个 bench 现在把初始 hints 作为选项（`hints`）传入，基线断言因此是诚实的，而不是碰巧通过。

## Deferred

- **upstream 候选**：**插件自定义的转发 Remote 事件**（让包能扩展 `$on` 白名单的机制——如 `TypertRemoteEventSelection` 驱动运行期转发，或在 `dsh.*` manifest 数据里按包声明转发）——落地后可退役 2.5s 的 surfacer 轮询；此前记录的用户消息动作座位、transcript 选区引用 seam、隐藏/折叠会话展示仍然开放。
- transcript 的实时推送（getState 轮询）——与 surfacer 事件同一个 upstream 形状。
