# Agent Note: reader 在浏览器里翻译 —— 端上模型、按句配对、三种视图

Status: implemented

## Problem

墙上收的是英文研究源（验收实例实测：OpenAI alignment 48 条、Anthropic research 43 条，正文合计 886,000 字符，全文长文在 22,000–105,000 字符之间）。详情页把这些正文渲染成 DOM 文本，而读者想用中文读就只能离开这个 pane —— 复制到翻译器或对话里，而那正是这个包存在的意义所在。

两条看起来顺手的路对第一版都不合适：

- **宿主模型调用。** 唯一的一次性缝是 `ctx.llm.stream({ provider, model, messages, system })`（`local-agent-dsh` 用它枚举模型词表），实例默认模型从 `ctx.get('agentDefaultModel').currentSelection()` 读。它能用，而且将来就是「更高质量」那一档 —— 但一篇 22,000–105,000 字符的正文要花几万 token、十几秒，还要把文章再发给模型服务一次。对一个默认动作是「扫墙 → 打开有意思的那篇」的读者来说，第一眼就读的代价和延迟都太重。
- **段落级或文本节点级的浏览器翻译。** 浏览器从 Chrome 138 起就有端上 Translator API（expert 模型、下完语言包不联网、没有按次成本），但最顺手的两种实现答不了读者真正的问题：「这**一句**原文是什么？」段落级单元事后答不了 —— 模型会合句拆句，再去对齐就是猜，猜错就会显示错的原文。文本节点级也答不了 —— 没有行内标记的段落本身就是一个节点。

## Decision

这个功能**整个在浏览器半**。详情条上的地球是开关（点亮 = 这个正文正在显示译文），它右边的箭头打开视图菜单（只看译文 / 双语对照 / 只看原文），文章由页面自己的 `Translator` API 翻译。没有新 Remote verb、不动宿主、不写 `state.json`、不加新依赖；`detectTranslator()` 就是全部降级故事。

- **单元是句子。** 发请求**之前**先切分已渲染的正文：每个散文文本节点按句切开，每一句变成一个 span。于是「译文句 ↔ 原句」的配对是**构造出来的真**，不是事后恢复的。读者要的那个手势 —— 点一句、在段落下看这一句的原文、再点收起 —— 是数据模型的自然结果，不是特例分支。
- **只碰文本节点。** 不做标记往返，所以句子里的链接仍是链接、href 不动，`<pre>`/`<code>` 直接跳过。跨行内元素的句子会变成两个单元（各自那一侧的文本）—— Chrome 自带整页翻译也是这么做的 —— 每一侧仍然只显示它自己的原文。原文留在内存里，所以「只看原文」和取消都能把宿主发来的字节原样还原。
- **批次要校验，兜底让出粒度而不是正确性。** 整句拼成一个字符串、句子之间插哨兵；只有返回的段数与发出的句数相同时才接受。哨兵被改（或调用失败）就把那一批退回「一句一请求」，那种方式不可能错位。仍然失败的单元保留原文 —— 正文里永远没有洞。
- **三种视图，地球是开关。** 默认*只看译文*（点句子是发现路径，用一条可关闭的提示教一次）；*双语对照*把每段的原文常驻在它下面、并可整段折起；*只看原文*显示源文但保留译文随时零成本切回。地球只在显示译文视图时点亮，所以菜单里的勾和地球状态永远不会互相矛盾。配对的两侧会一起点亮，但**只在 hover 时**：鼠标移到某句译文上，这一句（含被行内标记切开的每一段）和它唯一的那行原文一起亮；移到原文行上反向同理，移开就都清掉。**默认不画任何常驻底色或竖条** —— 第一版会把每个展开的原文都标上，读者扫几句就说整篇变花了。原文行**刻意不是控件**：它是读者要选中去引用的文本（单引原文，或连同译文一起引），在它上面挂点击处理会在**拖选结束的那次 mouseup** 上触发，把句子收起来、连带选区与引用浮层一起消失。同理，译文侧的开关在**存在选区时也忽略点击**。一个手势，只在一个地方。
- **不能用就不出现。** 只有页面有该 API、浏览器报告这个语言对可用、且正文本来不是目标语言（由 `isCjk` 按正文脚本判定）时，地球才渲染。仅 Chrome/Edge 桌面版 —— Safari、Firefox、移动端就是没有地球，其余功能不变。
- **`availability()` 只是提示，不是承诺，而失败要说出来。** 验收实例上确实出现过「语言对回报 `available`，`create()` 却抛 `NotSupportedError` —— Unable to create translator for the given source and target language」这种组合，而那条报错**两个语言都不提**（Chromium 在 macOS 构建上有同类记录）。于是三件事一起发了出去：源语言先问浏览器的 `LanguageDetector`（猜错源语言正是建不起来的一条路，而 `isCjk` 分不出德语和英语）；目标语言按 `zh` → `zh-Hans` 两种写法真各建一次；全部以「不支持」被拒时**地球自己藏起来**，状态条写明试过哪些语言对并指向 `chrome://on-device-internals` 的 Broker State。下载/配额这类**非永久**失败则保留地球，消息里带尝试过的语言对和浏览器自己的原因。
- **处理过程诚实。** 首次使用要下语言包：读者看得到下载进度、可以取消。`create()` 失败就给出原因、正文原封不动（不切分、不出现半截译文）。整批全失败就明说，并在菜单里给重试。
- **目前只有中文。** 目标语言在每一处都是参数（session 请求、availability 探测、文案），菜单是一个常量；加语言是改菜单，不是重写。

## How a translation is applied

1. `buildArticle(root, classes)` 遍历正文的文本节点，跳过 code/pre 与非散文，把每段文本按句切开并把该节点换成 span（首尾空白原样保留，所以拼回去是精确的）。它是幂等的，并记录撤销所需的一切。
2. `runTranslation(...)` 先把记忆里已有的句子直接画出来，其余按整句打包发送（句子之间用 `⟦|⟧`，每批约 1,200 字符或 12 句）。被接受的每一段写回它的 span；被拒绝的批次退化成一句一请求。
3. `setView(...)` 按所选视图画 span 与原文块，并在容器上标 `data-reader-translated` —— 这个标记也负责把排版切成中文度量，但只在**至少有一句译文落地之后**（在那之前标记是 `pending`，所以英文文本绝不会被当作中文排版）。
4. 点击一个 span 会翻转该段的 `open` 并重画它所属块的原文容器。容器里显示的是这个块的**原句**，不是它的单元：被行内链接切成三个单元的句子仍然是一行 —— 一单元一行的版本被读者报成稀稀落落的碎片（「Frontier Red Team」/「has developed some…」）。为此块里留了一份扁平化的原文，包含**单元之间那些属于文本节点、不属于任何 span 的空白**；少了它，测试抓出来的是「See thebest-studied domains」。某一行所属句子被展开时它会被高亮，点它则收起整句。容器的位置：段落和小标题放在块**之后**，列表项与引用放在**之内**，而正文是裸文本时放在最后一句之后（`extract-article` 真的会产出这种形状 —— 这是渲染测试发现的，不是读代码读出来的）。
5. `restoreArticle(root)` 把每个原文本节点逐字节放回、移除 span 与原文容器。取消、换正文、卸载三处都会调用它。

## Verification

`packages/dsh-reader/tests/translate.client.spec.ts` 钉住模块：切句（缩写、缩写名、小数、"U.S."、中文句末标点、完全没有句末标点）、切分与逐字节还原、裸文本正文形状、幂等、链接与代码不被碰、视图切换、点击折叠、单请求批量、哨兵不符的兜底（一次批量再逐句）、单个单元失败被计数而不是丢掉整篇、记忆命中不发请求、批间取消。

`ReaderPane.client.spec.tsx` 用脚本化的 `globalThis.Translator` 钉住流程：地球就地翻译、点一句只展开这一句的原文、再点收起、菜单切到只看原文再切回、没有 API / 语言对不可用 / 中文正文时地球不存在、`create()` 失败会给出原因且正文保持原字节、哨兵被改时仍然逐句得到各自译文。

原文排版与它的边距关系也钉住了（13.5px，即正文自身字号；secondary 墨色；行间 3px；边距按容器位置分：段落旁 `-8px 0 14px`、列表项/引用里 `5px 0 4px`、裸文本 `5px 0 10px`）。之所以要分位置：负上边距只有和**段落**自身的底边距才能合成，放在列表项里没有可合成的东西，同一个值就会把原文往上拽、贴住译文 —— 这是从项目符号那一段报回来的。hover 配对同样被钉住，并且断言常驻标记不许回来（`[data-open]` 的视觉规则必须不存在）；界面测试还端到端地跑了「选区保护」：有选区的点击不动原文，没有选区的同一个点击照常开合。一共改了三版：11.5px 的 tertiary 小字加 5px 间距被报「英文又小又稀」；12.5px 仍偏小；而**上边距大于下边距**会把每段原文粘到**下一段**而不是它所属的那一段。配对也做了端到端断言：点击之后，原文那一行与中文那个 span 同时带 `data-open` —— 正是读者要的那个标记。

同一批文件还钉住「建翻译器」这条链：被拒就试下一个目标写法、探测到的源语言先于兜底源、每一对都 `NotSupportedError` 才算永久并带上试过的语言对、网络失败不算永久、已经 `unavailable` 的对直接跳过、语言探测宁可回退也不阻塞、以及界面在「不支持」后藏起地球而「语言包失败」保留地球。

`pnpm --filter @khorsheed/dsh-reader test`：9 个文件、164 个用例全绿。产物已重建（tsc + tsdown），新模块与 CSS 已在 `lib/client.js` 中核对存在。

## Alternatives considered

**第一版就走宿主模型缝（`ctx.llm.stream`）。** 本里程碑否决，但不是永远否决：它任何浏览器都能用、翻译质量更好，代价是每篇长文几万 token、十几秒延迟、以及把文章再发给模型服务一次 —— 对「第一眼扫读」都太重。端上路是零成本、本地、秒级。模型档仍然是「没有该 API 的浏览器」以及将来「翻得更好」菜单项的计划；菜单的形状已经留好了位置。

**把文章送去侧边对话（`quoteToSideChat`，canvas 的先例）。** 否决：译文会落在对话里而不是文章里，无法按文章缓存，还把阅读和聊天混在一起。这个 pane 的承诺就是就地阅读。

**按段落翻译。** 否决：读者的诉求是**一句**的原文，而段落级结果无法可靠地切回去（模型会合句拆句）。猜对齐就会偶尔显示错的原文 —— 一种沉默的错误答案，正是这个包最不能有的失败。

**按文本节点翻译。** 否决：没有行内标记的段落就是一个文本节点，普通散文的「一句原文」根本不存在。先在节点内切句，粒度才是真的。

**底部常驻「原文」条 + 「钉住」（第一版 mockup）。** 被用户在评审环里否决：它在文章下面加了常驻的家具，而且「钉住」描述的是机制而不是读者的意图。段落下就地展开能做同样的事、不多一件家具，句子本身就是可见的入口（hover 底纹 + 一条可关闭的提示）。

**被点的句子就地替换成原文（第二版 mockup 的变体）。** 被用户否决：它一次只显示一种语言，对照只能靠记忆而不是靠看。中文留在原位、原文放在下面是真正的对照阅读。

**两档视图而不是三档（译文 / 原文）。** 否决：双语对照本来就在商定的设计里，点句子替代不了它 —— 想整节核对的读者用的是段落级视图。

**逐单元用 `translateStreaming`。** 否决：批量本来就在句子粒度上渐进落地，在一句短句内部再流式没有可见收益，却多一条要维护正确的路径。

**把译文缓存进 `localStorage`。** 暂时否决：内存记忆有上限、只在页面内（4,000 句），标签页关闭后不残留读者读过什么的任何痕迹。持久缓存等于把文章文本在磁盘上再存一份，而这个包（宿主自己的抓取缓存 `$DSH_HOME/state/dsh-reader`）不需要为一个免费、本地的操作付这个代价。

## Consequences

- 翻译没有增加任何宿主面、线上契约、落盘状态或依赖；它与宿主的兼容故事不变。它的可用性是一个浏览器事实，`dsh.compat.notes` 就这么记的。
- 免费与本地的代价是平台覆盖：仅 Chrome 138+ / Edge 148+ 桌面版。Safari、Firefox、移动端完全看不到地球 —— 是「不提供」，不是「坏了」。
- 切句刻意保守：规则不确定时**不切**，所以没切开的段落让出的是粒度（一个更大的单元），永远不是正确性。含行内元素的句子会拆成两侧；每一侧显示的是那一侧的原文，诚实但未必是完整句子。
- 正文 DOM 由一个 React 不拥有的模块改写。生命周期由三个 effect（换正文、卸载、取消）负责，`restoreArticle` 是逐字节精确的；渲染套件覆盖这个往返，而不是信任它。
- 本里程碑只翻中文，且源语言假定是拉丁/西里尔散文（不含这些字母的文本会被跳过，CJK 正文直接隐藏地球），所以日文→中文暂未覆盖。
- 点击手势本身没有可视线索，靠每个会话一条可关闭的提示教学；如果读者找不到它，正确的修法是加强句子上的可见提示，而不是把菜单做大。
- 读者自己的模型配额永远不会被动用，这也意味着宿主没配模型或额度用尽时翻译照常可用 —— 语言包下过一次之后，离线也能用。
