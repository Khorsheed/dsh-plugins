# Agent Note: Context Lens change list

Status: implemented

## Problem

缓存区原来只比较相邻两次请求，找到第一处不同就停下。它显示「消息 000 的前缀有变化」和一段字符差异，变化是什么、为什么发生、别处还有没有变化，都要读者自己去猜。一个真实案例让这个缺口很具体：某会话里用户用 message-tools 编辑了一条消息，下一次请求的缓存命中只有 0.9%，面板只显示消息 000 里插入了 139 个字。实际过程是：两轮之前，一次系统提示更新被追加在历史中间，当时缓存没有受影响；编辑产生的替换让宿主开启新的请求序列，借机把这条更新合并回开头。另外，工具说明改了时，面板只写一句「工具定义已变化」，也没有对应的筛选项。原因是 `tool-change` 类别只对应宿主在增删工具时插入的 `developer` 消息。

## Decision

请求视图的 `prefix` 在原有的首处差异字段之外，增加完整的变化清单：

- **`changes`**：所有消息级别的变化。消息按固定 id 配对，没有 id 的按内容哈希配对。每条的 `kind` 写的是它背后的宿主事件，不做解读：
  - `replace`：一次 `surfaceOp: replace` 事件，带被换掉的行、换上的行、写入方原样的 `kind · op`，以及日志 seq。
  - `compaction` / `prune`：紧跟在 `compaction/summary` / `compaction/prune` 之后的替换。宿主的影子计价约定保证这两个事件一定相邻，所以这种判断是可靠的。裁剪不改消息 id，只是内容变短。
  - `remove` / `add`：按 id 比出的差异，但没有替换记录可以把两边配对。出现在替换记录开始之前的捕获里，或者对应的记录已经被淘汰。
- **系统提示归组**：所有只涉及系统消息的变化合成一条。差异用新旧两版开头比较；`parts` 列出这条由哪几次事件组成；实时捕获时附上差异起点所在的 assemble 分段名；如果新开头和某条被移除的历史中间系统消息全文相同，就记一个 `sameAs`。这只是一个可以核对的等式，不声称这段内容「移动」了。
- **`toolChanges`**：工具定义按名字配对，分为新增、移除、修改。修改时说明和参数分开比较。`owner` 取自实时注册表上 capability-catalog 的来源标签（`Symbol.for('dsh.tool.origin')`），工具打了标签才有。
- **`tail`**：最后一条保留或被替换的消息之后，没有替换记录解释的新增内容，属于正常追加，只汇总条数和来源。系统消息不并入 tail。
- **`configChanged`**：服务商或模型与上一请求不同。
- **断点**：包含首个不同消息位置的那条变化带 `isBreak`。消息前缀没变时，第一个变化的工具带 `isBreak`。

替换记录存在每个会话一张的有界表里（`InspectorStore.noteReplacement`，最多 2048 条）。实时的 `session/event` 路径通过 `session.eventAt` 把被替换的 seq 解析成消息 id；主会话回放时扫描整份日志（`replacementFactsOf`）。两条路径读同一种行结构：步骤事件把消息放在 `data.message` 下面，用户消息的 `data` 本身就是消息。

面板（`ChangeList.tsx`）先显示一行断点，再列卡片。断点所在的卡片描红框并默认展开。跳转去的是负责显示详情的模块：系统提示和工具去构成筛选，压缩去压缩请求，裁剪去裁剪前的那次请求。没有 `changes` 字段的旧捕获保留原来的首处差异视图。

## Alternatives considered

**画两次请求的对照条，让断点线穿过两行。** 做过三轮原型（`proposals/prototypes/context-lens-cache-explain.html`），想在一张图里同时说明断在哪、变了什么。块的宽度需要每段的 token 数，服务商从不报告；工具和消息的先后顺序在服务商内部，插件看不到。用户反馈不配说明文字就看不懂。最后改用一行断点加一份清单。

**用带解读的类型，比如「移动」「修改」「编辑触发」。** 早一轮原型用过。宿主合并系统提示时发的是两次互不相关的替换，每次替换都会生成新的 id，所以「移动」「修改」是结论，不是数据。现在清单只用事件种类命名，写入方字段原样显示，需要结论的地方改写成可以核对的等式。

**按文本对齐（LCS）来比较。** 固定 id 已经能准确对应消息。按文本对齐会造出宿主从未做过的配对。

**用命中数推断工具和消息在请求里的先后顺序。** 数据能佐证某种顺序，但不能证明。断点行直接写明顺序由服务商决定。

## Consequences

- 宿主记了事件的地方，清单是精确的；没有事件时退化为按 id 的移除和新增，仍然不会声称配对。
- 替换表有内存上限。如果某次请求涉及的替换已经超出 2048 条的窗口，就显示移除和新增。
- `segmenter` 现在给没有分段归属的系统消息行也带上 `messageId`，系统提示归组需要这个字段。
- 前缀没变但服务商那边丢了缓存（过期，或者聚合类服务商把请求路由到了不同后端），显示为「没有断点」，旁边是红色的实测条。面板不猜原因。

## Testing

`tests/changes.spec.ts` 覆盖以下情况：
- 照真实日志构造的「编辑后合并系统提示」，分有替换记录、没有替换记录两种；
- 正常追加、裁剪和压缩的类型判断、真实的事件结构；
- 工具差异、分段归属、与 store 的集成、模型切换。

`tests/client-config.spec.tsx` 渲染清单，检查断点卡片默认展开，以及系统提示的跳转。用同一套逻辑对 3080 的会话日志跑过一次，复现了引发这次改动的会话：请求 #12 显示历史中间追加了系统提示、没有断点；#16 显示系统提示一组是断点，并带 `sameAs`；#20 显示断点在工具定义。
