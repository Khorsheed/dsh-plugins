# Agent Note: capture — pixel snapshots for JS-driven widget figures

Status: implemented

## Problem

The [capture rendered-fetch service](2026-09-21-capture-rendered-fetch.md) serializes the post-render DOM, and one whole class of figure cannot survive that honestly: the JS-driven WIDGET. Measured on the same acceptance target (transformer-circuits.pub/2026/workspace): of 102 figures, 23 are widgets — 6 carrying `<canvas>`, 19 with event listeners inside the subtree (the union is 23). Canvas pixels never reach `outerHTML` at all, and a listener-built overlay's JS-computed absolute positions assume the 1280px capture viewport, so in the reader's narrow column the labels pile onto the caption and the following paragraphs (user-acceptance screenshots, 2026-09-21: the Figure 3 lens readouts and the Figure 5 token-pinning cluster, both among the 23). The inlining pipeline is the right answer for the other 79 — static SVG/composite figures arrive quotable and crisp — but for widgets it can only ever ship a broken flattening.

The script-figure counting rule surfaced a second defect at the same acceptance: a successful 渲染抓取 stores a body whose extraction counts ZERO script figures, and the store dropped zero counts exactly like absent ones — so on the next open the view fell back to the ENTRY's load-time count (84) and the "figures your page draws itself" notice (plus the 「渲染抓取」 action) rose from the dead.

## Decision

The render pipeline gains a **widget snapshot phase** between the scroll sweep and the inline-and-serialize pass (`packages/capture/src/service.ts` `snapshotWidgets`):

- **Detection is behavioral, not visual.** An init script (`evaluateOnNewDocument(installListenerProbe)`, before any page script) wraps `addEventListener` to tag every Element that receives a listener into a window-held WeakSet. The classifier (`markInteractiveWidgets`, self-contained like the other page tasks) then qualifies an OUTERMOST `figure`/`d-figure` as a widget when its subtree holds a `<canvas>` OR a probe-tagged element. Only the figure's own subtree is inspected — a framework's root-delegated listener sits on an ancestor OUTSIDE the figure, which is exactly what keeps a React root from condemning the whole page. `onclick`-property handlers and delegated-only widgets are documented misses; canvas covers the script-rendered case they leave behind.
- **The clip is the content, not the figure.** Each marked widget's box is re-read fresh (late reflow shifts figures) as the union of its NON-`figcaption` children's boxes, plus 8px of slack (axis labels overflow their boxes by a hair), clamped to the document. The caption is excluded from the pixels because it stays in the DOM as text — it would otherwise render twice, and captions are what translation and quoting ride. Chrome screenshots it at 2× raster as WebP q80 (`captureBeyondViewport`, so the sweep's end-of-page scroll position is fine).
- **The swap keeps the figure's identity.** `replaceWidgetsWithSnapshots` removes the widget's non-caption children (and stray text) and inserts one `<img>`: the data URI, `width`/`height` for aspect, the widget's trimmed non-caption text (≤400 chars) as `alt` — the searchable residue of what became pixels — and a `data-capture-snapshot="widget"` marker. The inline-and-serialize pass then runs unchanged. A widget whose own screenshot fails keeps its DOM (the pre-snapshot behavior); the whole phase degrades to nothing on failure and `snapshotWidgets: false` config removes it entirely. Caps: 40 snapshots per render, 4096px max box dimension.
- **"Counted, none" is not "not counted".** On the reader side, `captureBody` now ALWAYS stores the extraction's script-figure count (zero included) and `storeEntryBody` omits the field only when it is absent (reader `service.ts`). The remount chain `view.value.scriptFigures ?? entry.scriptFigures` therefore sees the stored 0 instead of falling through to the entry's stale load-time count; the notice and the action stay gone after a successful render. Bodies stored before this fix carry no count and still fall back — one re-render heals them, permanently.

Fidelity honesty: the snapshot is the widget's DEFAULT state (no pinning/scrubbing), and a panel with internal scrollbars shows its initial viewport. The 「阅读原文」 link beside the notice remains the path to the live widget.

## Alternatives considered

**Ship the page's scripts in a sandboxed iframe (`sandbox="allow-scripts"` srcdoc).** Real interactivity, but arbitrary-site JS then executes inside our webview's frame tree — the sanitize-everything security model the reader is built on exists precisely to never do that — and the figure's text becomes unreachable to translation/quoting just the same (iframe documents are separate). It also multiplies capture size (scripts must ship) for the one thing the reader cannot use: a live demo.
**Serialize computed styles onto every element instead of inlining matched rules.** Preserves more layout, but emits hundreds of declarations per element (multi-MB noise), still cannot move canvas pixels or hover state, and breaks the reader's style whitelist assumptions. Measured unnecessary for the 79 static figures — inlining already passes them.
**Screenshot EVERY figure, not just widgets.** Uniform, but throws away the static SVG figures' quotability and zoom-crispness — quoting is the reader's whole point, and the inline route is the fidelity WIN there (this is the same verdict the [capture note](2026-09-21-capture-rendered-fetch.md) recorded, now scoped to its correct domain).
**Detect widgets by absolute-positioned-descendant ratio.** The probe data shows abs-heavy static composites (Figure 13/14/18: 30–80 absolute descendants, zero listeners) that render FINE through inlining; a position-based rule would rasterize figures that were never broken. Behavior (canvas/listener) names the actual failure — content the DOM cannot carry — layout it cannot.
**Heal the zombie notice by clearing the ENTRY's count instead of storing the body's zero.** The entry count is the load-time fact about the feed payload; the body record is the authoritative "what we have on disk". Storing the body's explicit zero fixes the read at the layer that actually answers opens, without rewriting what the feed said at add time.

## Consequences

- All 23 widgets on the acceptance target arrive as crisp 2× images (verified: Figure 3's six lens-readout panels, Figure 5's whole token/table/heatmap/chart cluster), zero canvas remnants, 5.7M chars under the 8M cap; the other 79 figures keep the quotable DOM route. The widget's text becomes non-selectable pixels — accepted, because the alternative was overlapping garbage text, and the alt keeps a searchable residue.
- One render grows by the screenshot loop (23 widgets ≈ tens of seconds inside a ~2-minute render); per-widget failures are contained to that widget staying DOM.
- The stored-body zero is a durable-record semantic: old records without a count fall back to the entry count (and show the stale notice) until re-rendered once. No migration — the heal is the gesture the feature already provides.
- Deferred: image zoom in the reader (2× rasters stay crisp if the pane grows a lightbox); listener-delegation-only widgets (needs framework-level signal); widgets outside `figure`/`d-figure` containers.
