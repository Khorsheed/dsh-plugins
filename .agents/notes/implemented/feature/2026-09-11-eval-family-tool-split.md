# Agent Note: The mission / datasets / eval tool-row split (M4'③)

Status: implemented

English | [中文](2026-09-11-eval-family-tool-split.zh.md)

## Problem

The [mode-switcher proposal](../../../proposals/active/2026-08-26-mode-switcher.md) requires community model tool rows to live in agent presets, never at the profile root: a session gets a tool exactly when its preset grants it. The worktrees and room pairs ([the split note](2026-09-11-worktrees-tool-split.md)) established the shape, and three plugins were still fused. `@khorsheed/dsh-mission`, `@khorsheed/dsh-datasets` and `@khorsheed/dsh-eval` each provided their service **and** registered their model tools **and** contributed a guidance prompt section from the profile root, so every preset's sessions received the twelve mission tools, the eight dataset tools, the three eval read tools, and four guidance paragraphs in the assembled system prompt.

That was observable, not theoretical: the trajectory of session `session-aabca0ed` on 2026-09-11 (recorded `agentPreset: "standard"`) shows an assembled prompt whose paragraphs 2–9 are the mission, eval, datasets and Agent Teams sections — a standard-preset prompt that reads like an evaluation instance's. The community packages had also already split the *tool-row* half for worktrees and room; mission/datasets/eval had not. A fused package cannot enter a preset at all: the official preset mount rejects any row that `ctx.provide`d a service outside an isolate realm.

## Decision

**Three companion packages, the same core/companion template as the worktrees and room pairs — zero shape deviations.**

- `@khorsheed/dsh-mission-tool`, `@khorsheed/dsh-datasets-tool`, `@khorsheed/dsh-eval-tool` (0.1.0) are tool-only rows: they provide NO service and declare NO `dsh.bundle` patch, so installing one as a dependency only makes its module resolvable — granting is an agent preset's `agent.cordis.yml` naming the row. Each probes its core's global service at apply time (`ctx.mission` / `ctx.datasets` / `ctx.dshEval`) and degrades to a logged no-op when the core is absent, so a preset naming the row still mounts cleanly everywhere. Tools register through deferred `ctx.inject(['tools'])`, the guidance section through deferred `ctx.inject(['systemPrompt'])`; each companion applies its own origin tag, so the capability catalog attributes the tools to the mounted row.
- **The tool definitions were not copied.** Each core exports its factory through a new `./tool` subpath — `missionToolDefinitions(service, tier)`, `datasetToolDefinitions(service, { defaultRepo, group })`, `evalToolDefinitions(service)` — returning untagged, unregistered definitions. The cores' `src/tools.ts` modules were renamed to `src/tool.ts` because the typert generator resolves an export subpath (`./tool` → `lib/tool.js`) back to its source path.
- **The cores stop registering anything model-facing (BREAKING).** `mission`, `datasets` and `eval` keep their service, CLI, slash command, Typert Remote face and web tab; they register no tool and contribute no prompt section, and their `tools` config key is gone. The group tiers moved to the companion rows: mission `all` (default) / `read` / `none`; datasets `all` (default) / `read` / `authoring` / `none`; eval `all` (default) / `none`. Migration is the established two lines — install the companion, name its row in the preset (with `config: { tools: … }` when the group is not the default).
- **The 任务 tab and the 数据集 tab self-hide** (M3'③/M3'④): each registers exactly while the current session's preset composition names the matching companion row, read from the official `pluginInventory` Remote, at the registration level (the tab strip's buttons enumerate registrations, so a hidden tab must be an absent registration). Every unreadable path fails open. eval has no browser half.
- **Granting today**: the eval pack names all three rows in its own `eval` preset with the domain tiers that previously sat on the profile root (`mission-tool: read`, `datasets-tool: authoring`, `eval-tool: all`); `profiles/web-eval/cordis.patch.yml` no longer writes a `tools` key at the three core rows, and that pack installs the three companions as plain members (three `dependencies` entries plus source mode's `UNPUBLISHED_DIRS`, because a profile sets `autoInstallPeers: false` and a peer is therefore never installed on its own). The web-dev dev preset deliberately does NOT reference the rows: the three cores are not members of that pack (unpublished incubation) and a companion imports its core's `./tool` factory at runtime, so a missing row would mark the WHOLE dev preset `broken` — those three rows join it once the packages are published and listed in `profiles/web-dev/package.json`. Applied to the running 3080 instance, the migration is three steps: deploy the companion packages (`deploy:3080`'s family packing carries a core's peer companions), add the three rows to `$DSH_HOME/.agent-presets/dev`, and only then does a dev session keep its mission/datasets/eval tools.
- `check-plugin-independence` gained the three forward edges (`<name>-tool` → core) and the three reverse core edges (the tab gate constants name the companion modules), plus `NO_OWN_PATCH` entries for the three companion directories — a `dsh.bundle` declaration there would re-mount the tools at the profile root, exactly what the split removes.

## Alternatives considered

**Keeping the guidance section in the core and gating its text per scope.** Rejected: the section describes the tools, and ownership follows registration. A core that emits "the mission tools are …" while the tools live in another row would either depend on that row or describe absent tools; the section moved with the tools. The same rule decided it for datasets' conditional text (it names only the verbs the granted group admits).

**Gating the tabs at the component level (`return null`).** Rejected for the reason room already recorded: `conversation.view` buttons are enumerated from slot registrations, so a component-level hide leaves a live button with an empty body. The toggle re-registers/disposes instead.

**Extracting a shared preset-visibility helper package.** Deferred again, now with four inline copies (worktrees badge, room chrome, mission tab, datasets tab). The copies are ~100 lines each and identical in shape; extraction is worth doing when a fifth consumer appears, and the deferral is recorded here rather than silently repeated.

**An escape hatch for sessions that already held mission/dataset state.** Rejected: unlike room's actual-room rule (which protects historical rooms created before the split), hiding a read-only viewer breaks nothing durable — the store, bindings, CLI and slash faces are untouched, and the tab returns the moment the session's preset grants the row.

**Listing the companions as direct dependencies of the packs.** Rejected to match the worktrees/room precedent (and because a published pack depending on an unpublished companion would fail the install): the core's optional peer plus the deploy flow's family packing keep the modules resolvable, and the release-order constraint is recorded instead.

## Consequences

- **Breaking, announced**: sessions on presets that do not name the three companion rows lose the mission / datasets / eval tool sets and the four prompt paragraphs; the cores' service, CLI, slash and tab faces are unchanged. In the eval pack this is visible: a session on the `standard` preset there no longer carries the domain tools, because the tiers moved into the `eval` preset — which is the point of the split.
- **The standard preset's prompt is clean again**: the assembled prompt no longer carries mission/datasets/eval/Agent Teams sections unless that session's preset names the rows. This closes the observation that started the work.
- **The 任务 and 数据集 tabs disappear from standard sessions.** That is a deliberate capability reduction for humans: the tabs are viewer UI, so a preset that grants no tools now shows no tab. Fail-open keeps older hosts (no `pluginInventory` namespace), unreadable composition data, preset-less sessions and `broken` preset groups showing the tabs.
- **Deploying a companion row is two deliberate steps**: `deploy:3080` refreshes packages the profile already declares and refuses to introduce one ("is not a profile dependency — add it deliberately"), and a core's family packing only keeps the *packed tarballs*' family edges resolvable — it does not write the companion into the profile manifest. The live profile therefore needs `dsh plugin --profile web add <companion tarball>` once per companion (installed as a plain dependency, with the documented bundle-less warning), then `pnpm deploy:3080 --package packages/<companion>` for the gated refresh + restart. Verified live on 3080 on 2026-09-12: the three cores deployed at +2609111630 and the three companions at +2609111700, canary PASS, a standard-preset session's assembled prompt dropped from 29 to 26 paragraphs (no mission / eval / datasets sections) and its request header carries none of their tools.
- **The packs carry the wiring, not the preset**: web-eval installs the three companions and names them in the `eval` preset; web-dev names none of them because the cores are not its members (see Decision). **Adjacent pre-existing gap, observed and not fixed here**: the web-dev dev preset already names `@khorsheed/dsh-worktrees-tool` and `@khorsheed/dsh-room-tool`, and that pack's manifest installs neither — with the pack's `autoInstallPeers: false` those two rows have the same unresolved-row failure mode until the sibling packages are published and listed.
- **No inter-plugin dependency was introduced**: each companion degrades silently without its core, and each core works without its companion (it simply registers no tools). The sanctioned-pair surface grew by three entries in the checker.
- **Verification**: the six packages build and their tests pass (mission 130, mission-tool 4, datasets 117, datasets-tool 5, eval 393, eval-tool 3); the companion specs pin registration, origin tagging, group tiers and the absent-core degrade, the core specs pin the no-registration invariant and the untagged factory, the client specs pin the three gate states (granted / not granted / fail-open). `pnpm check:plugins` reports 0 findings across 31 packages and the checker's spec is green; the worktree's `pnpm gate` is the merge gate.
