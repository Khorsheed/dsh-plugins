# Agent Note: side-chat M3 — self-surfacing on openWith: the RightbarRoot root cause, and the revision-diff signal

Status: implemented

English | [中文](2026-09-16-side-chat-m3.zh.md)

## Problem

3080 evidence plus a host-source proof: when a consumer (canvas) calls `ctx.sideChat.openWith(...)` from a custom main panel (the canvas space) and then best-effort `ctx.sidebarRight.openTab('sidechat', …)`, **nothing visible happens**. The consumer did everything the M1/M2 contract asked, and the user saw silence.

The root cause is upstream's `RightbarRoot` contract: `packages/client/ui-sidebar-right/src/client/shell/RightbarRoot.tsx` renders the right Sidebar only while `usePanelInfo(info => info.activePanelId === null)` — i.e. only while the CONVERSATION panel is active. On any custom main panel the rightbar is null by construction, so `openTab` records a navigation nobody can see. The presentation decision — tab vs. anything else — therefore cannot be the consumer's; it must be internalized by the side-chat client, which alone knows its own fallback tier (the M2 floating dock). To do that the client must first LEARN that an `openWith` happened at all, and the host→client direction must ride the Remote wire, never shared memory.

## Decision

**The signal is a per-context openWith revision, diffed over a lightweight Remote poll.** The contexts record carries `rev` (persisted, optional, defaulting to 0 for pre-M3 records via the tolerant reader); `openWith` — and nothing else, not `send`, not `quoteMessage` — bumps it on EVERY call, because the surfacing semantic is "a consumer just opened this context", once per call. The new `@Remote('surfaceHints')` verb answers `{ items: [{ contextKey, rev }] }` — the lightest read the service offers (memory only: no journal projection, no persistence inspection), so a 2.5s poll costs one map iteration. The client's `useOpenWithSurfacer` hook polls it, seeds a baseline on the first result (a reload never re-surfaces what predates it), and a revision bump fires the presentation decision.

**The presentation decision lives in the always-mounted root surface.** The M2 dock entry (`shell.overlay`) mounts at shell boot whether or not any side-chat surface is open, so its surfacer is the primary one: conversation panel active (`activePanelId === null`, the RightbarRoot visibility condition) → `openTab` (the tab is visible there); a custom main panel active → `actions.open(contextKey)` on the dock store (the dock renders above every panel by construction, and `open` also re-aims the context). Two fallback tiers: dock seat absent OR viewport narrower than 720px → still `openTab` — invisible now, but the navigation is RECORDED, so returning to the conversation panel finds the tab already on the right context. The tab body runs the same hook only when the overlay seat is absent (`enabled: !dockAvailable()`), so primary and fallback never double-fire; a host with no overlay seat surfaces nothing while the tab itself is closed — the documented degrade, matching what was ever possible there.

**The consumer contract is untouched.** `openWith`'s signature does not change; the consumer's best-effort `openTab` becomes redundant but harmless (it is no longer the mechanism, and side-chat never relied on it).

## Alternatives considered

### Why not `ctx.remote.$on` (the forwarded Host-event channel)?

The `$on` mechanism exists and is the right shape — but the runtime forwarding allowlist (`API_REMOTE_FORWARDED_EVENTS` in `@deepseek-ai/dsh-api-remotes`) is upstream-owned and hard-coded; a community plugin cannot add `sidechat/opened` to it without a harness change. The type-level `TypertRemoteEventSelection` merge being extensible does not change what the forwarding loop forwards. A plugin-authored forwarded event is recorded as an upstream candidate; until it exists, the Remote poll is the architecture-honest channel that ships today.

### Why not a custom session-journal event (the room `room/*` live feed)?

Session events do flow to the client — but a side-chat context at `openWith` time usually has NO session yet (M1's lazy creation), and appending surfacing bookkeeping into a model-visible session log pollutes the transcript's single source of truth. The journal is the transcript, not a message bus.

### Why not the M2 controller closure (client-side only)?

The controller lives in the client bundle's apply closure — it can never observe a HOST-side `openWith`. The task's own constraint settles it: host→client must cross the Remote/事件 boundary, not shared memory. The controller keeps doing what it was for (tab↔dock hand-offs inside the client).

### Why not bump the revision on `send`/`quoteMessage` too?

Those gestures are client-initiated (the user is already looking at the surface that caused them), so surfacing on them is noise — and `quoteMessage` already surfaces through its own `openSideChat` path. Keeping `rev` openWith-only makes "a bump" mean exactly one thing.

## Consequences

- Host (`types.ts`, `service.ts`, `remote.ts`): `SideChatContextRecord.rev?` (tolerant-reader defaulted), `openWith` bumps it per call, `surfaceHints()` service method, `@Remote('surfaceHints')` verb (read, no agent). All wire-additive; `openWith`'s signature and every M1/M2 contract unchanged.
- Client: `use-open-with-surfacer.ts` (poll + baseline + decision, `SURFACE_POLL_MS` 2.5s, `SURFACE_NARROW_WIDTH` 720), wired into `SideChatDock` (primary) and `SideChatView` (fallback when the seat is absent); both inject faces gained `surfaceHints` + `openTab`; `openTabWith` is the one probed navigation helper every surface shares.
- `package.json` 0.2.0 → 0.2.1; READMEs (zh/en) document the self-surfacing behavior, the `surfaceHints` verb, and the RightbarRoot root cause. `docs/packages.md` regenerated. No new dependencies.
- The M3 test-debugging note, for the next fake-timer suite: **the surfacer's mount poll consumes the bench's DEFAULT mock implementation** (effects flush inside `render()`), so a per-test `mockResolvedValue` written after the bench call never shapes the baseline — the benches now take the initial hints as an option (`hints`), which is what made the baseline assertions honest rather than accidentally passing.

- NOT done: a live 3080 walk of the canvas-space integration (canvas M2's openWith landing in the dock — the wiring is jsdom-covered; the feel is not).

## Deferred

- **Upstream candidates**: a **plugin-authored forwarded Remote event** (a mechanism for packages to extend the `$on` allowlist — e.g. `TypertRemoteEventSelection` driving runtime forwarding, or a per-package forwarding declaration in `dsh.*` manifest data), which would retire the 2.5s surfacer poll; the previously recorded user-message action seat, transcript-selection quote seam, and hidden/folded session presentation remain open.
- Live-feed push for transcripts (the getState poll) — same upstream shape as the surfacer event.
