# Agent Note: one verb for drafting an experiment — the form, the tool and the skill (I5 · T34)

Status: implemented

English | [中文](2026-09-16-eval-plan-draft.zh.md)

## Problem

Step 2 of the eight-step flow — *the agent drafts the experiment, the draft lands in the Experiments list* — worked, in the sense that a determined agent could get there. It took three separate acts: `write` a `dataseek.plan/1` document with the contract spelled from memory, `write` each new condition the same way, then `eval_plan_validate` to find out what was wrong with them. A person had no path at all: 新建实验 was a button that printed a sentence telling you to go write the file yourself (T36 left it pointing here).

Three things were wrong with that, and only the first is about convenience.

**The contract was being spelled twice, by whoever happened to be drafting.** `dataseek.plan/1` has eight required keys and five optional blocks, and its cross-field rules are not guessable — the one that bit this slice is that declaring `expectedNs: ["llm-draft"]` without a judge is an *error*, not a warning, while an *empty* `judge` block silently switches that check off. Every hand-written plan in the dataset repository carries `"judge": {"conditions": [], "samples": 0}` for exactly that reason. A drafting verb that copied the convention would have inherited a plan that claims a verdict source nothing can produce.

**A new condition written from scratch is a broken experiment that looks fine.** A comparison answers a question when its conditions differ in ONE field. A declaration typed fresh differs in however many fields its author did not think about — `instructions`, `skills.pack`, `env.keys`, `reasoning.effort` — and none of them shows up as an error anywhere, because each value is individually legal. It shows up months later as a paired difference nobody can attribute.

**And a person's draft and an agent's draft were not the same kind of thing.** The list says they are (ui-spec §五 puts drafts and runs in one table because to the person planning the next comparison they are the same kind of thing). If the form had grown its own writer, the two would have been two implementations of "what a draft is", and the first divergence would have been invisible — both produce a file, both validate, and only one of them has the empty judge block.

## Decision

- **One service verb, three faces.** `draftExperiment(request, {session})` writes the plan and any new condition, then validates. The 新建实验 form reaches it through `newExperiment`; the agent reaches it through `eval_plan_draft`; the `eval-planning` skill tells the agent to. There is no second writer, and a test spies on the service to pin that both faces land on it — the lab list genuinely cannot tell a person's draft from an agent's, because they are the same bytes from the same code.
- **The tool is this row's only write, and drafting is why that is safe.** Every other write-class verb stays shut for the reason stated since T14: an agent that could start a run could start one nobody approved. Drafting starts nothing — it produces a file and a `草稿` row — so the argument that closes the others does not reach it. The tool's description leads with `DRAFTING IS NOT STARTING`, the prompt section repeats it, and a test asserts both strings, because the sentence is load-bearing rather than decorative.
- **A new condition is a COPY, and the shape has no way to express anything else.** `newConditions` takes `{id, from, …}` and `from` is required: there is no field for "write me one". Only the six fields ui-spec §五 lists can change. A copy that changes nothing is **refused** — that is one subject under two names, and it would double every count keyed by condition id.
- **Three fields move without being named, and each is a correction rather than an extra edit.** `home.sha` is always nulled (it hashes the *original's* scoped home; carrying it would claim a provision that never happened). `harness.version` is nulled when the harness name changes (that version was the other CLI's). `notes` is replaced by a provenance line — the original's commentary is about the original, and `notes` is excluded from the condition hash, so rewriting it changes no subject's identity.
- **`expectedNs` defaults by whether the plan has a judge**: `script + human-final` without one, all three with one. The repository's own convention — all three plus an empty judge block — is the same claim with the check switched off, and a default that lies and then suppresses the complaint is worse than one that is briefly surprising. Drafts write no `judge` key at all when no judge is named, so the `JUDGE_REQUIRED_FOR_LLM_DRAFT` error stays armed for anyone who passes `expectedNs` by hand.
- **Nothing is ever overwritten.** Both writes use `wx`, so the check and the write are one operation: a draft cannot lose a race, and it cannot replace a plan somebody approved or a condition somebody locked. A taken name is a refusal that says so.
- **A plan validate REJECTS is still written.** It lands as a `草稿` with its errors named — in the list, on the review page, and in the tool's answer. Refusing to save would leave a person with nothing to look at and nothing to fix. The refusals are only the cases where there would be no draft at all: an unresolvable repository, a name that is not a file name, an item the set does not declare, a source condition that does not exist, a target that does.
- **The verdict comes back as the plan-review page's own payload, not a summary.** `draftExperiment` calls `planReview` on what it just wrote, so the sentence an agent reports to a person and the list that person then reads on the page are one call to one `validatePlan`. A test asserts equality with `service.planReview(planPath)` rather than spot-checking fields.
- **The form's pickers are reads, not text fields.** `draftOptions` answers the dataset sets with their items and their stage schemas in one call, and the condition registry comes from the page the conditions tab already reads. A person cannot invent an item id here; `eval_plan_draft` refuses one and lists what the set holds, which is the same guarantee for the agent.
- **The skill ships with the pack, replaced whole, like the preset.** `skills/eval-planning/` goes to `$DSH_HOME/skills` — `dsh-skill-filesystem`'s `user-dsh` root, which the eval preset's own `skill-filesystem` row surfaces. It is apparatus, not preference: it teaches the one drafting verb and names what is *not* the agent's (approving, logging in, provisioning, the final verdict). Let that drift and a draft becomes a run nobody approved.

## Alternatives considered

### Why not let the tool return the raw `PlanValidation`, the way `eval_plan_validate` does?

One shape for "what validate said" is easier to hold than two, and an agent that drafts then edits will call `eval_plan_validate` next and get the other one. But the review projection is strictly more useful at this moment — it carries the plan's own digest (what was actually written, including the conditions that were appended) and tags each line `ok / warn / error`, which is the reviewer's whole decision procedure. More importantly it is the payload the *person* will see one page later, and the point of this slice is that the two sides are looking at the same thing. The tool's description says which it is.

### Why not refuse a plan validate rejects, instead of writing it?

A refusal is the tidier contract: nothing lands unless it is runnable. It is also the less useful one. The errors validate reports are about files on disk — a condition that violates the contract, a stage schema that left the supported subset — and fixing them means looking at them. A refusal hands back a message and no artifact; a draft hands back a row in the list, a review page that lists every problem, and a file to edit. The lab already has a word for a plan that has not passed validate, and it is `草稿` — the first of the seven statuses. Writing it is what makes that word mean something.

### Why not auto-fix the `expectedNs` / judge interaction by writing the empty judge block, like every hand-written plan does?

It is the convention in the repository, it is legal, and it would have made every draft pass validate on the first try. It is also how the check gets switched off: with `judge` present, `JUDGE_REQUIRED_FOR_LLM_DRAFT` never fires, so a plan that expects `llm-draft` and has nobody to produce it reads as clean. The default now states what the run can actually do, and anyone who wants the old shape can pass `expectedNs` explicitly and see the error. (The validator's own asymmetry — an empty judge block suppressing the check — is left alone: it is not this slice's to change, and plans in the field depend on it.)

### Why not refuse a minted condition the caller forgot to name in `conditions`, instead of appending it?

Refusing is more explicit and teaches the shape. But minting a subject for an experiment and then leaving it out of the experiment is not a thing anyone means, and the refusal costs a round trip to fix a typo. The append is visible rather than silent: `result.conditions` and the plan's digest both show what the plan ended up naming, and the tool's description says it happens.

### Why not add 新建条件 as its own form on the conditions page, where the button is?

The button is there and it points at the list's form instead, which is one more click. A form there would be a second way to write `conditions/<id>.json`, and the two would drift — and it would let a person mint a condition with no experiment to use it in, which is how a registry fills with subjects nobody ran. ui-spec §五 already says 选模型即新建条件 and sends the reader back to 新建实验; the button now says where to go rather than that the feature is missing.

### Why not put the skill inside the profile directory?

It would be removed by the profile's own `rm -rf`, which is tidier. `dsh-skill-filesystem` does not scan there: its roots are the project's `.dsh/skills` / `.agents/skills` and the user's `$DSH_HOME/skills` (plus whatever `customSkillDirs` names). A skill under `profiles/web-eval/` would be on disk and in nobody's catalog. The preset roster has the same shape and the same consequence, and the README says so beside both `rm -rf` lines.

## Consequences

- `packages/eval/src/draft.ts` (new): `draftExperiment` (mint, write, refuse) and `draftOptions` (the form's pickers). `EvalDraftRefused` is the refusal class — deliberately not the class a contract violation gets, because a plan with errors still lands.
- `packages/eval/src/service.ts`: `draftExperiment` / `draftOptions`, both resolving the repository through the same `resolveRepoScope` every read verb uses, so the session binding's dataset whitelist is honoured.
- `packages/eval/src/remote.ts`: `newExperiment` / `draftOptions`, both session-carrying.
- `packages/eval/src/tool.ts`: `eval_plan_draft`, the fifth definition. `mintArgument` checks `id` / `from` by hand — the parameter subset carries `required` at the argument root only, so a nested record's keys are all optional to the schema however the description reads.
- `packages/eval/src/client/NewExperimentDialog.tsx` (new), plus its wiring in `LabView.tsx` / `contract.ts` / `client/index.ts` and ~50 dictionary keys. The form's CSS carries a comment about why it declares no `min-width`: a dialog's content that insists on being wider than its modal is clipped, not scrolled, and jsdom cannot see that — only a real browser can. `placeholder.new` is gone; `conditions.newPlaceholder` now points at the form instead of at this task.
- `profiles/web-eval/skills/eval-planning/SKILL.md` (new), and `SKILL_IDS` in both profile scripts.
- Both profile scripts: a pre-existing bug fixed while adding the skill backup. `[ -d "$X" ] && rm -rf "$X"` under `set -e` **ends the script** when `$X` does not exist — the AND-list is the last command of its list and its status is 1 — so a fresh install never reached its own success line. Now an `if` block.
