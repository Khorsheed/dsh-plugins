# Agent Note：实验室四阶段的旅程与结论先行（T72）

状态：已实现

## 问题

T67 之后，每个详情页都有了一个状态和一个主动作，但旅程的其余部分仍然要人自己琢磨下一步做什么：
- 列表是一张平铺的表，等人的 run 和正在推进的 run 看起来一样；
- 驱动已经死掉的 run 永远显示运行中；
- 就绪是一列原始 code，没有修法；
- 全格 `released` 之后，run 会自己变成已完成，不管有没有人看过；
- 结果页先摆审计，不先给答案；
- `eval_run_status` 给了 agent 格子的桶，却没有一个能和人共用的词。

## 决定

- **状态只在一处推出，收尾是走到终点的唯一办法。** `deriveExperimentStatus` 现在也读收尾标记（ns `eval-closure`）：①②③ 进 `done`，④ 进 `void`，别的路都到不了这两个状态。
- **`stalled` 是算出来的，从不写账。** 它要求同时满足：
  - 非终态；
  - 本实例没有活 job；
  - 并非全格已判；
  - 账本（格子进入当前阶段的时刻，加上注解）超过 `STALL_THRESHOLD_MS` 没动（10 分钟，定义在 `src/experiments.ts`）。
- **标记写成 run 第一格上的注解，读时扫全部格子取最新。** 这是导出注解的写法，因为 `run.meta` 在 `runCreate` 时就冻结了。规则由 `recordClosure` 在写时把关，读的一方不用裁决：
  - `flagged` 与 `void` 要理由；
  - 最新的生效；
  - 作废之后一律拒写。
  
  归档（ns `eval-archive`）走同一套写法，只影响分组。
- **列表按该谁动分组：**
  - 需要你处理（草稿 / 待批准 / 停滞 / 被拒 / 评估中）
  - 运行中
  - 已完成（已完成 / 评估不成立 / 已取消）
  - 已归档
  
  默认只看本会话的 run 加全部草稿，组头给「另有 n 个」。
- **就绪分阻塞项与提醒。** 阻塞项是 error，加上「条件状态不是 `ready`」的 warning。每行映射到一句人话和一个修法：provision / 改端点 / 登记仓库 / 让 agent 处理。阶段 bar 的动作就是第一条阻塞项的修法。
- **「让 agent 处理」经宿主的会话输入面把文字填进输入框草稿，不发送。** 输入面拿不到时退到剪贴板。
- **结果页先给结论卡。** 结论卡两行：第一行是来源句，第二行是有效性计数，点开进折叠的审计。作废的 run 整页只剩理由。
- **`eval_run_status` 加回 `status` / `stalledMinutes` / `closure` / `archived`。** 这几个字段和列表那一行取自同一个 `experimentDetail`。eval-tool 的提示词教这套词。

## 考虑过的其他做法

- **用看门狗把 `stalled` 写进账本。** 否。文案不许；而且这会把「读钟」变成一条日后要撤回的事实——run 再动起来时，得有人写「不停滞了」。每次读的时候现算，永远是新的。
- **沿用「全格 `released` 即已完成」。** 否。「判官做完了」与「人说了结果是什么」是两件事。把两件事合成一件，正是 pilot-d 里判官缺席的一格还能给出笃定 Δ 的来路。现在只有一个明确的出口才能收尾。
- **照交互稿 v5 把停滞放进运行中。** 否。停滞的 run 没有任何东西在推，人不动它就一直停着，而需要你处理正是放这类 run 的组。这处偏离记在场景表里。
- **原地续跑停滞的 run。** 没做。续跑要知道每格停在哪一步、单元还在不在，这是编排器的事。重跑是把同一份 plan 再批准一次，也就是起一个新 run，旧行可以归档。
- **给补判一个新的 Remote 动词。** 没做。补判是一次委派，委派的父该是一个会话，所以补判走「让 agent 处理」。
- **「让 agent 处理」直接发送。** 否。填进草稿，人可以先改，也可以不发；替人发出去，就是一轮人没要的模型对话。

## 后果

**得到的：**
- 列表行、阶段 bar、工具回答说的是同一套词；
- 死掉的 run 十分钟内会浮上来；
- 一份结果只有真有人确认过，才会显示成已确认。

**付出的：**
- 原来读作已完成的 run，没人收尾就读作评估中；
- 另一个进程里健康的 CLI run 在单个阶段待满十分钟会读成停滞，因为账本没有心跳；
- 重跑会留下旧 run，作为单独的一行。
