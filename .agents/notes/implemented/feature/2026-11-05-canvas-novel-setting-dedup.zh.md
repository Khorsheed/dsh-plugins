# Agent Note: 设定对账先搜索再建卡，疑似重复由用户裁决

Status: implemented

## Problem

对账没有给提取子 agent 已有设定名册，公司的正式名称和描述性称呼可能因此变成两张卡，“A 与 B”这类合并名也可能与 A、B 各自重复。完全同名匹配无法修复这些问题，但无上限名册会让每章 prepare 都随作品膨胀，模糊的自动合并又会危及正典。

## Decision

- 对账素材包最多携带 100 条相关设定，依次按本章命中、近期使用和画板顺序排列。每条包含 ref、名称和类型；省略数量会提示改用搜索，而不是打印完整目录。
- `novel_read(what=settings)` 支持按 `query`、`kind` 搜索名称与正文，并按 `refs` 读取完整详情。归档卡不参与匹配。
- `memories` 可用 `ref` 指定已有设定。ref 优先于本章描述性称呼；新的差异内容带章节和证据追加，不覆盖旧文本。无效 ref 会丢弃该条。
- 名称互相包含或合并名会生成 `duplicate` 待办，不进入对账的自动落实路径。用户选择“合并到已有卡”时追加差异，选择“确认另建”时才创建独立卡。没有候选卡的合并名同样需要确认。
- 搜索、匹配和待办持久化都是确定性规则。不发明别名，也不把模糊的公司名匹配当作同一实体的证据。

## Alternatives considered

- **每次 prepare 都放入全部设定。** 否决：成本会随作品增长并在每章重复。有界名册处理常见情况，搜索处理长尾，导入端仍检查全量卡片。
- **相似名称自动合并。** 否决：名称包含和合并名只是线索，不等于同一实体。合并与另建都需要明确决定。
- **显式 ref 命中后覆盖旧卡。** 否决：章节提供的是补充事实，不是抹除既有正典的授权。追加能同时保留旧文本和证据轨迹。

## Consequences

- 即使相关名册漏掉了正式设定，对账也能通过描述性称呼补充它，而不产生第二张卡。
- 疑似重复可以留待裁决，不阻塞其他导入。该章重新对账会替换未决的疑似重复项，已决定的卡片保留。
- 确认另建时会再次检查完全同名，避免重复创建审核期间已经出现的卡。
- 测试覆盖关键字、类型、ref 搜索，描述性称呼更新，合并名合并，确认另建，以及浏览器中的两种操作。小说插件完整测试通过 36 个文件、282 条测试。
