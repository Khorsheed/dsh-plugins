# Agent Note: 长篇小说可以删任何东西，改动经图找影响、按清单对齐

Status: implemented

## Problem

用户希望自己和 Agent 都能随时改、随时删，又不想每改一次就让模型把整本书重读一遍。

当时的情况是：

- 设定、人物、关系、伏笔只能从画布卡片页删。删了之后，引用它的地方（事件的地点、人物的势力、子设定的上级、灵感的绑定）都悬空，没人知道。
- 改了一条设定或一段正文，没有办法知道影响到哪几章、哪几段。唯一的办法是让 Agent 把全书重新看一遍。

## Decision

### 书是一张图（`graph.ts`）

章节、设定、人物、关系、伏笔、事件、灵感都是点。现有数据里的引用就是连线，类型如下：

| 连线 | 含义 |
|---|---|
| `told-in` | 事件写在哪章 |
| `at` | 事件发生在哪个设定 |
| `with` | 事件牵涉哪个人物 |
| `cause` | 事件由哪件事引出 |
| `reveals` | 派生的揭晓事件指向它的伏笔 |
| `parent` | 设定属于哪个上级 |
| `base` | 势力的据点 |
| `faction` / `home` | 人物的所属势力、常在地点 |
| `pair` | 关系连着的两个人物 |
| `uses` | 章节用到的设定：计划里的「用到的设定」，或对账时找到的设定 |
| `advances` | 计划推进的事件 |
| `cast` | 计划里的出场人物 / 视角人物 |
| `moves` | 伏笔在哪些章被推进过 |
| `bound` | 灵感绑定的事件 |

这张图不存盘，每次从数据现算，并带一份反向索引：从任何一点都能直接查到谁指向它。

### 删除（`deletePreview` / `deleteNode`，以及 `novel_write(what=delete)`）

删除之前先沿指向它的连线走一步，把影响列出来。能按规则处理的当场处理，不调模型：

- 下属设定移到被删设定的上级下面；
- 人物的所属势力 / 常在地点、势力的据点里去掉它；
- 事件的地点、人物、起因里去掉它；
- 删人物时，他的关系卡一起删；
- 删事件时，绑在上面的灵感解绑；删伏笔时，绑在它揭晓事件上的灵感也解绑。

已写章节的正文从不改动，只在确认框和工具回复里写明「第 N 章正文写到过它」。

界面上，世界观、人物、关系、伏笔、时间轴的详情里都有「删除…」。点了先在原地展开确认，列出上面这些影响。章节不能这样删。删卡片需要画布服务提供 `deleteCard`，没有时返回 `unsupported`。

### 待对齐（`align.ts`，`align.json`）

**基线。** 对齐时给每个点记一份指纹，连同它的类别、名字，以及当时有哪些已写章节带着它。已写章节另存一份当时的正文。一本书第一次读待对齐时，把当前状态记为基线。

**一处改动。** 指纹和基线不一样、或已经不在了的点，就是一处改动。所以不管改动来自设定页、画布卡片页、手改文件还是工具，都能发现。同一个点改多次只算一处，改回原样就自动消失。新加的点不算改动，因为还没有已写章节指向它。

**影响范围。** 每处改动沿图走一步，找到它碰到的已写章节，只从这些章节里摘出点名它的段落；正文改动则只摘出改了的段落。Agent 拿到的只有这份清单和这些片段（`novel_read(what=changes)`），处理完一项就用 `novel_write(what=aligned, id)` 勾掉一项。

**不需要模型的改动。** 没有已写章节带着的改动，列在「已自动处理」里。

**不进清单的改动。** Agent 自己的写入在可见的一轮里，所以下面这几种都会当场把基线更新到最新：

- 写卡（genre agent 的 `writeCard`）、写事件、工具删除；
- 对账：把这一章动到的点和这一章都记为已对齐；
- 用户删除时规则做的那些修正。被删的点本身仍按规则进清单或进「已自动处理」。

**界面。**

- 章节页的「接下来」：有待对齐时，第一件就是「待对齐 N 处 · 查看」。
- 设定页和时间轴的工具栏：显示「待对齐 N」徽章。
- 待对齐页（`novel:align`）：
  - 顶部写明「只会读：第几章几段，约多少字」，并有「让 Agent 对齐 N 处」按钮，点了往对话发一条消息；
  - 每处画一张一步的小图，附上要读的原文片段，可以单独「忽略」；
  - 底部折叠「已自动处理」。

### 对账不再单独写人物经历

对账的输出格式里去掉了 `experiences`。写稿材料包里人物「近来」的经历，改从有他参与、且写在已写章节里的事件取。事件还没覆盖到的章节，继续用旧的经历记录。

## Alternatives considered

- **每个操作记一条日志，把操作序列交给模型。** 否决：同一个点反复改会变成很多条，改回原样也消不掉；而且直接改文件、经画布卡片页修改的改动都记不到。
- **改动后全量刷新。** 否决：token 成本随书的长度增长。
- **把图存成一份索引文件。** 否决：会和数据不同步。现算的成本是读一遍各个记录文件，已写章节的正文只在读待对齐时才读。
- **删除时连正文一起改。** 否决：正文是用户的，要不要改由用户在对话里决定。

## Consequences

- **换来的。** 用户和 Agent 都可以随便改、随便删。机械性的后果立刻处理，要模型判断的部分只按点处理，成本和影响到的段落数成正比，和书有多长无关。
- **代价。** 待对齐每次读都要读已写章节的正文来比对，长书会慢一些。基线里存了一份正文副本，书越长，`align.json` 越大。
- **漏判。** 设定的影响靠名字在正文里找段落：名字换了说法（简称、代称）的段落会漏。正文改动按段落比较，段落顺序变了会被当成改动。
- **不处理的情况。** 画布卡片页直接删卡时，规则修正不会自动跑，悬空的引用由读取端忽略；被删的点照样进待对齐。章节删除没有做。
