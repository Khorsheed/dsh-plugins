# Agent Note: side-chat M1 — the side-chat session lifecycle, per-turn prompt freshness, and the assistant-actions quote seam

Status: implemented

English | [中文](2026-09-16-side-chat-m1.zh.md)

## Problem

The [side-chat proposal](../../../proposals/active/2026-09-16-side-chat.md) builds a **right-sidebar "side Agent" resident in every preset**: each `contextKey` binds one persistent agent session; refs are opaque `{ label, text }` chunks; the plugin must not know any consumer's types. M1 delivers the conversation-scenario core: the package scaffold, `ctx.sideChat.openWith` (with per-turn systemPrompt updates and caller tools), the Remote face, the right-Sidebar tab UI, and the「引用到侧边对话」message action.

Three hard questions shaped the milestone, and the code alone cannot carry their answers:

**How do caller-supplied tools and a per-turn-fresh systemPrompt reach one context's agent?** `openWith` must UPDATE, never recreate — so what is the update mechanism on an already-live agent, and what is the creation-time mechanism that stays consistent with it?

**Where does the contextKey → session mapping live, and what fences its writes?** The mapping is deployment-level state (`$DSH_HOME/state/sidechat/`) that no session workspace can hold — and `openWith` arrives from other plugins in-process, carrying no wire session to stamp a policy with.

**What is the message-action seat for「引用到侧边对话」?** The proposal named the message-tools precedent (`conversation.chat.node` shadowing) but left the exact seat to implementation-time verification.

## Decision

**Each contextKey binds ONE ordinary agent session, created lazily on the first send.** `ctx.agents.create({ sessionId: randomUUID(), meta: { cwd, agentPreset }, setup })` (the eval/room precedent) — the cwd inherits from the live session the contextKey names (the conversation scenario: the source conversation), else from the session the send gesture runs in; the preset defaults to the deployment default through a probed `agentPresets` roster (room's `composeRoomAgent` shape). After a restart the first gesture cold-resumes with `ctx.agents.resume`; a resume failure (torn log) falls back to a fresh session and corrects the mapping. Reads never resume: a cold context answers from a `sessionPersistence` inspection (room's `inspectCold`). Lazy creation means `openWith` costs no agent composition for a context the user never engages — the agent spins up when the user actually asks.

**Tools injection: the `setup` callback at create/resume, plus live re-attach by name.** The finding: `agents.create`/`agents.resume` accept an `AgentSetup(agentCtx, agent)` that runs BEFORE publication, and everything registered through `agentCtx` — scoped tools, prompt sections — files into that agent's layer and unwinds with it (the preset-mount contract). Cordis's property proxy (`getTraceable`) rebinds a service's `this.ctx` to the accessing context, so `agentCtx.tools.register(def)` and `agentCtx.systemPrompt.section(...)` land agent-scoped (verified against `ScopedLayers.effect`, which derives the scope from the passed ctx via `scopeOf`). For an already-LIVE agent the same two calls work on `agent.ctx` (registrations are rejected only after disposal). `openWith` therefore keeps caller tools name-keyed per context, registers them in setup, and on repeat calls disposes-and-re-registers changed names on the live agent. Origin tagging is the CALLER's responsibility — side-chat never tags on its behalf (the repo convention).

**Per-turn freshness: a prompt section whose text provider re-reads the record at every assembly.** `PromptSection.text` may be `(context) => string`, evaluated at each prompt assembly. At create/resume the agent's scope registers `sidechat:context` (order 10300, after the deployment persona suffix at 10200) whose provider returns the built-in orientation segment plus the record's LATEST consumer segment. `openWith` merely updates the record — the next assembly reads it fresh. No `agent.inject` journal spam, no accumulation, no create-time snapshot.

**The mapping is one version-guarded JSON document under the re-rooted fence — canvas `store.ts`, not datasets.** `$DSH_HOME/state/sidechat/contexts.json` (`{ version: 1, contexts: [...] }` with a tolerant reader; corrupt = refused, never clobbered). Writes keep the mounted `ctx.fs` and re-root the writable boundary at the plugin state dir, exactly canvas's precedent: Remote mutations (`send`/`quoteMessage`) stamp the CALLING session's resolved mode and id; host-side `openWith` carries no session, so it resolves the DEPLOYMENT DEFAULT mode (`sandboxPolicy.resolve()`) with the same re-rooted boundary and no sessionId stamp — a read-only deployment still denies, and `resolve()`'s rejected-by-canvas fallback-root problem does not apply because the boundary is overridden, not inherited. A composition without `ctx.fs` degrades to memory-only state (logged once, never blocking a gesture).

**The quote action rides `conversation.chat.assistant-actions` — an official list slot; the user-message gap stays open.** The probe found ui-chat's `TurnTailNodeView` declares `'conversation.chat.assistant-actions': { kind: 'list', scope: 'session' }` with owner `{ messageId }`, rendered inside the finalized assistant message's `MessageIconActions` row (`extraActions`), with ui-message-feedback as the shipped precedent. The action calls `quoteMessage(agent, { messageId })`: the HOST folds the message text from the calling session's journal (contextKey = the calling session's id — no body crosses the wire), appends the ref, and the client surfaces the tab via the official `ctx.sidebarRight.openTab('sidechat', { params: { contextKey } })` navigation face (canvas M1.5's conclusion, probe-degraded). The USER-message row's `MessageIconActions` takes no `extraActions` — there is no user-message action seat; the only alternative (message-tools' whole-node shadow at priority -1) would collide with message-tools' own shadow and fork the official bubble's visuals. The honest M1 version is assistant-only, and the gap is an upstream candidate below.

## Alternatives considered

### Why not `agent.inject()` for the systemPrompt segment?

`inject` queues a durable user-role context message per `openWith` call: the journal accumulates one injection per refresh, the model sees N stale copies until compaction, and "update" semantics become "append and hope the newest wins". The section text provider has exactly the update semantics the proposal demands (per-turn freshness, zero journal noise) and is the mechanism prompt sections exist for.

### Why not create the agent eagerly in `openWith`?

An eager agent costs a full composition (preset mount, scoped world) for every context a consumer merely mentions — including contexts whose user never opens the tab. Lazy creation keeps `openWith` cheap (a state write), and the proposal's own lifecycle clause ("create on first use") reads the first SEND as the first use. Acceptance #4 (a consumer's openWith + tools drives the agent's behaviour) is exercised through a send either way.

### Why not shadow the user-message node for quote-on-user-messages (the message-tools precedent)?

message-tools registers `conversation.chat.node` key `user` at priority -1 with a full visual clone. A second shadow from side-chat would fight it for the key (whichever priority wins, the other's features disappear — edit/withdraw or quote), and every clone drifts from the official bubble as ui-chat evolves. One honest action on assistant messages beats two broken seams; the user-message seat is recorded as an upstream candidate.

### Why not bare `node:fs` for `contexts.json` (the datasets binding precedent)?

The canvas M1 note settled this for deployment-level CONTENT state: `ctx.fs` buys version guards (two browser tabs never silently lose the mapping), atomic publication, the observation trail, and the read-only deployment's denial. The mapping is small, but it is session-stamped content that races; bare fs forfeits all four for nothing.

### Why not persist the transcript beside the mapping?

The session journal IS the transcript's durable store; a shadow copy would drift on the first restart. `projectTranscript` folds `user/message` + `assistant/message` text and pairs `tool/call`/`tool/result` into one-line statuses — the same fold over a live snapshot and a cold inspection, which is what makes "重启后历史完整" a replay, not a cache.

## Consequences

- New package `packages/sidechat` (`@khorsheed/dsh-sidechat`, 0.1.0): identity triangle (cordis row `sidechat` / `clientBundle('@khorsheed/dsh-sidechat')` / invariant `PACKAGE_NAME`), self-mounting `dsh.bundle.patch`, typert Remote pair, zh+en READMEs with Compatibility, invariant companion.
- Host: `src/service.ts` (`ctx.sideChat`: `openWith`, `getState`, `listContexts`, `send`, `quoteMessage`, `disposeAgents`), `src/store.ts` (state root + re-rooted fence), `src/agent-setup.ts` (probes: agentPresets/sessionPersistence, `composeSideAgent`, `inspectCold`), `src/journal.ts` (transcript projection), `src/remote.ts` (namespace `sidechat`: `getState`/`listContexts` reads, `send`/`quoteMessage` agent-first mutations).
- Client: right-Sidebar tab (kind `sidechat`, key = package name, navigation params `SideChatTabParams { contextKey? }` merged into `SidebarRightTabParamsMap`), transcript with official `MarkdownText`, ref chips, composer under the canvas invariants (uncontrolled textarea, IME hard stop, ⌘⏎/button send), zh+en locales, `--dsw-*` tokens only, official icons; the「引用到侧边对话」entry at `conversation.chat.assistant-actions` (id `sidechat-quote`, order 20).
- `scripts/gen-typert.mts`: `packages/sidechat` joined `TYPERT_PACKAGES` (the hard-coded registry every typert package lands in). `docs/packages.md` regenerated (34 packages).
- One convention confirmation other packages may cite: **agent-scoped contributions from OUTSIDE the setup callback work on the live `agent.ctx`** (tools hot-swap by name; prompt section text providers read mutable state per assembly). The setup callback remains the only publication-guaranteed point; live re-attach is an update path, not a creation path.
- `zod ^4.4.3` is a runtime dependency for the same reason as every typert package: the generated `lib/typert.remote-client.js` imports it. No other runtime dependencies.
- Side-chat sessions are ordinary sessions and appear in the session list (auto-titled from the first message). `agents.create` has no hidden-session flag; whether side sessions deserve presentation-level folding (subagent-style lineage) is an open question, noted rather than solved.

- NOT done: a live-browser walk of the real 3080 instance (deploy is a separate flow; the jsdom specs cover the wiring), and acceptance #4's live-model check (the service spec drives the mechanism through the fake factory; the model's behaviour on a real route is the 3080 walk's business).

## Deferred

- M2: multi-context switcher list, unread badges, live-feed push (replacing the 1.2s poll), tool-row styling polish.
- M3: the canvas M2 integration (the consumer side of `openWith`), carried by the canvas proposal.
- Upstream candidates: a **user-message action seat** (e.g. `conversation.chat.user-actions`, or `extraActions` on the user row's `MessageIconActions`) so quote/forward extensions stop needing node shadows; a **hidden/folded session presentation** for plugin-owned agent sessions (side-chat sessions currently list beside ordinary conversations); **programmatic right-Sidebar activation from the HOST side** (today only the client can `openTab`, so a host-side consumer's `openWith` cannot surface the tab without the consumer's own client half).
