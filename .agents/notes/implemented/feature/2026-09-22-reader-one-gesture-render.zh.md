# Agent Note: reader——一个手势跑完整条抓取管线

Status: implemented

## Problem

条目正文流上有两道缝，都是验收实测出来的（2026-09-22，部件快照版）：

1. **一个意图要点两次。** 需要渲染的链接让用户先点「抓取」（普通抓取落到 JS 前的壳，带脚本图提示），再点「渲染抓取」——壳从来不是那一下点击想要的东西，第二下纯属仪式。
2. **「重新抓取」会毁掉渲染产物。** 它永远走普通抓取，把渲染抓来的正文覆盖回页面的原始壳——部件快照改动让它更糟：渲染成功后提示（连同渲染按钮）消失，连回头路都没有。

两件事底下是同一个问题：哪些动作授权一次渲染？[capture 笔记](2026-09-21-capture-rendered-fetch.md)把渲染门在"一次显式用户点击"上；要点两次，是因为把这条读成了"点渲染按钮本身"——那是仪式，不是安全。

## Decision

**一条规则：指向单条文章的显式用户手势跑完整个管线——先普通抓，落到脚本图壳就自动接续渲染抓取。** 手势清单：新增链接、卡片「抓取」、卡片菜单的抓取、打开条目、详情页「重新抓取」。后台路径（feed 定时刷新、回填扫描）永不升级——这正是防止阅读器变成"拖着浏览器的爬虫"的那条界。手势门的安全内容不变：渲染仍只跟随指向该条目的用户动作，站点允许记录照常累积。

- **升级**在 `maybeAutoRender`（`packages/dsh-reader/src/client/ReaderPane.tsx`）：capture Remote 探测在场 + 有链接 + `scriptFigures > 0` → `captureBody`。每条目每窗格会话只自动触发一次（`autoRenderTriedRef`）；渲染失败留下提示条和手动「渲染抓取」重试，重开不会复燃。渲染在飞时提示条变为进度文案（`detail.rendering`）。
- **正文记录的 `rendered` 标记**（types/store/service/contract：随正文入库、`getEntryBody` 返回）是「重新抓取」的路由依据：渲染过的条目重新渲染。普通抓取永不置位，其正文保持普通路线。标记出现之前入库的旧正文与普通正文不可区分——它们先普通抓一次、落到壳、被自动升级愈合成带标记的渲染正文（不做迁移；管线即迁移）。
- 重新抓取按钮也读 `captureBusy`：重渲染要数分钟，看起来死掉的按钮就是坏按钮。

## Alternatives considered

**保留两次点击（渲染动作独立）。** 拆分的唯一内容是手势记账，而"抓取点击 + 渲染点击"并不比抓取点击多授权任何东西——反正阅读器都会抓这个 URL。代价是每个脚本重的页面都要点两下，以及上面的毁尸体 bug。
**后台路径也自动渲染（feed 刷新、回填）。** 那是宿主抓取注释早已拒绝的爬虫（"一条目一抓取，按读者请求"）再拖一个百 MB 浏览器。永不。
**给升级加设置开关。** 为一个没有实测反对方的行为加表面；capture 包不在场就是总开关（探测不到就不升级）。有部署真提需求时再加。
**启发式识别旧渲染正文（快照标记、内联样式密度）。** 嗅探标记只对快照之后的构建有效，还会误读手写页面；显式标记加管线自愈是精确的，不需要考古。

## Consequences

- 脚本图流程现在是：打开/抓取 → 提示条变进度文案 → 渲染正文换入。失败保留重试。队列忙和拒绝与普通抓取失败走同一条错误行。
- 每个落到壳页的显式手势现在都会付出一次渲染（数分钟、一个 Chrome）——有意为之，因为壳从来不是意图；每条目每会话一次的去重和正文缓存给它封顶。
- capture 笔记的许可条目今天读作"指向条目的显式手势"，本轮把它从"渲染按钮自己的点击"拓宽；渲染产物一侧由[部件快照笔记](2026-09-22-capture-widget-snapshots.md)负责。

## Testing

`packages/dsh-reader`——422 测试本地全绿：原 capture 通路客户端测试改写为自动渲染用例（打开 → 壳抓取 → 无第二次点击 captureRender 即触发；入库携带 `rendered: true` + `scriptFigures: 0`），失败用例钉住循环守卫与手动重试，路由用例钉住「重新抓取」→ 渲染（含在飞按钮态、普通抓取零调用）。boot 套件往返验证 `rendered` 标记与显式零计数。3199 端到端：从壳到 23 张快照正文只需一次点击；再次「重新抓取」走服务端渲染（站点渲染计数 7→8）且不丢弃屏上正文。
