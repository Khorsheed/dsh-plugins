# Agent Note: 游戏工作台的 3D 套件

Status: implemented

## Problem

游戏工作台原来只能做 2D 画布游戏。用户想做一个山海经题材的 3D 游戏，里面会有很多精怪、元素和环境，风格是用户试过交互稿（`proposals/prototypes/game-3d-qingqiu.html`）后选定的水墨风。模型只能写代码和数据，没有文生 3D，所以 3D 必须是模型能稳定写出来的形式，而且要接进现有闭环：沙箱试玩区、无头 Chrome 里的轮末检查、候选版本、面板的点选。

## Decision

在 [游戏运行时套件](../architecture/2026-10-22-game-runtime-kits.zh.md) 的接缝上加第二个套件 `3d-three`（`src/kits/three3d.ts`）。

- **运行时。** 3D 项目的每个 bundle 都带 `_dsh/three.module.js`（固定依赖 `three@0.170.0` 的压缩 module 构建，从磁盘读一次）和 `_dsh/dsh3d.js`（`packages/game/runtime/dsh3d.js`，纯 ES 模块，随 `files` 发布），外加 `_dsh/imports.json` 映射裸模块名 `three` 和 `dsh3d`。游戏按裸模块名 import，不往项目或快照里复制任何东西。
- **dsh3d** 给游戏提供四样东西。一是 `build(look)`：把 `parts3d` 配方拼成带程序动效的模型。二是风格即数据：卡通明暗层数、反向外壳描边、背景、地面和雾的颜色；`ink`、`qinglv` 只是起点，`game.json` 的 `style3d` 按键覆盖，由模型根据用户自己的描述写出，`createWorld` 经加载器暴露的 `window.dshManifest` 读取。另有开放词表：`defineBase` / `definePart` 注册内置没有的身体和部件。三是 `createWorld()`：45° 正交镜头、`step(dt)` / `start()`、`terrain`、`place`、登记可点选实体的 `add`、`follow`、`focus`。此外还有给工作台用的 `pick(x, y)`、`pause(on)`、`highlight(list)`。
- **外观。** `src/look3d.ts` 校验两种外观。`parts3d` 配方：内置 base 为 `quadruped` / `bird` / `fish` / `serpent` / `humanoid`，内置 parts 为 `ear` / `horn` / `tail` / `wing` / `fin` / `eye` / `face`，另外接受项目注册的任何标识符名字；没注册的名字在拼装时报错并指明用 `defineBase` / `definePart`，由冒烟检查报出；项目自定义部件的其余参数保留在 `extra` 里；`legs`、`heads`、`segments` 这类数量是各自范围内的整数。`gltf` 外观：路径必须在项目内。glTF 加载器还没发，dsh3d 对 gltf 外观显示占位方块，带 `recipe` 时则按配方拼。`ElementView` 在像素 `look` 旁边新增 `look3d`，面板的像素编辑器不受影响。
- **建项目。** `game_open` 接受 `runtime: 3d`；这时轻量门提供 3D 风格（`ART_STYLES_3D`），并写入 `runtime: { kit: '3d-three', version: 1 }`。建 2D 项目写的内容和以前完全一样。
- **桥接。** 游戏的 `pick` 可以返回结构化引用（`id`、`inst`、`name`、`state`、`point`、`region`），`picked` 消息把它放在 `ref` 里带出来。新增的 `pause`、`highlight` 消息在游戏提供了对应钩子时调用它。面板的「点中即插芯片」和候选版本的差异圈（M1c）都建在这上面。
- **检查。** dsh3d 的渲染器保留绘图缓冲，所以原来的 2D 黑屏回读在 WebGL 画布上照样能用；这台机器上无头 Chrome 不加额外参数就能渲染 WebGL。

## Alternatives considered

**固定的风格列表和固定的身体/部件列表。** 第一版正是这样，用户指出了问题：工作台是给任何游戏用的，预设没想到的题材（霓虹、糖果色、机器人、小车）要么悄悄退回水墨，要么根本写不出来。现在风格是模型按用户描述写出的数据，身体和部件是带内置起点的注册表。

**Babylon.js。** 它自带物理、GUI 和检查器，但体积大好几倍，模型也没有对 three.js 那么熟。工作台要的是模型能写对的渲染器，游戏专用的那一层保持薄、由我们自己掌握。

**把 three.js 抄进仓库。** 那样 git 里会冻结一个约 700 KB 的文件，版本也看不出来。精确版本的依赖把来源记在锁文件里，随插件像其他依赖一样安装。由于套件是从磁盘读这个文件、而不是打进 bundle，`three` 列在 `dsh.runtimeDependencies` 里，`pack-dist` 才会把它留在发布清单中；第一次部署到生产时漏了这一条，那里的 3D 项目只会报缺文件。

**让模型直接写 three.js 网格。** 能用，但每只精怪都会变成面板读不懂、改不了的定制代码；而山海经「其状如 X 而 Y」天然就是「身体 + 部件」。配方是数据：面板能给它出滑块，模型能一次提三个方案，精修路径也能用同一份配方在 Blender 里烘焙。

**现在就发 glTF 加载器。** 目前还没有任何东西产出 glTF（那是精修里程碑的事），没有产出方的加载器等于没测过的接口。在那之前，gltf 外观按内嵌配方拼，或显示占位，绝不报错。

## Consequences

- 3D bundle 在试玩、检查和导出时比 2D 大约 0.75 MB，导出的单文件 HTML 也大这么多。
- 沙箱加载器是按文本改写 import 模块名的，所以内置模块注释里写出的 import 语句也会被改写。`dsh3d.js` 开头写明了这一点；第一版就踩了这个坑（自己 import 自己，报「循环」）。
- 快路径的精细度上限就是拼装器本身：程序化造型有意保持简单，在墨线描边下读起来清楚；更精细的模型走精修路径，而不是不断扩充 `build`。

## Testing

`tests/look3d.spec.ts` 固定了这些行为：配方归一化（数值夹紧、丢弃无效部件、数量范围，比如六足）；gltf 路径不能出项目；按套件校验外观；轻量门（3D 写入套件并提供 3D 风格，2D 不出现 `runtime` 键）。`tests/three3d.chrome.spec.ts` 用 3D 套件经 `ChromeChecker` 跑一个真实 3D 游戏，验证：地形上用配方拼出的九尾狐画面不是空白；在九尾狐投影位置调用 `pick` 返回 `jiuweihu` 及其实例、状态和区域；点地面识别为地面；场景面数在预算内；`pause` / `highlight` 可用。另验证一个从不绘制的 3D 世界会被判为空白。五种身体原型在两种风格下的截图都人工看过。
