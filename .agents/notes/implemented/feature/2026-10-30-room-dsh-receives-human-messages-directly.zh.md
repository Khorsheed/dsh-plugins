# Agent Note：房间自己的 agent 直接收到用户的原消息

Status: implemented

## 问题

用户发给 dsh（房间自己的 agent）的消息会送达两次。`postMessage` 先把用户的 `user/message` 写进房间会话，而房间会话就是 dsh 自己的会话，所以这些话已经在它的上下文里了。接着 `runMainAgent` 又把同样的话和简报、房间变动、暂存回报一起包成一条 `source: room` 消息，通过 `agent.followup` 发出去。宿主把 room 来源的开轮消息渲染成「收到执行请求」卡片（ui-chat 的 `turn-trigger`），于是对话里先是用户气泡，紧接着一张重复它的卡片，模型也为同样的话付了两次 token。成员（CLI agent）没有这个问题：给它们的副本只在它们自己的子会话里。

## 决定

- 当用户消息发给主 agent、不带附件、且房间的 agent 在线时，`postMessage` 不再自己写 `user/message`。它照常把消息归入任务、追加 `room/dispatch`、上浮运行中的卡片。引擎拿到 `direct: human`，`runMainAgent` 用用户的原消息调用 `agent.followup(human)`：只写一次，是宿主自己的一轮，没有触发卡片。agent 正忙时，消息像普通会话一样排进它的收件箱，所以房间的排队条会显示它，宿主的排队操作也适用。
- 房间要补充的内容——首轮简报、房间变动、通知、暂存回报、点名外部会话的提示——照旧计算，只是不再包含用户的话。这些内容按消息 id 存进 `engine.directExtras`。新增的 `agent/pre-step` 钩子在这一轮第一步，把它们作为一条 room 来源的消息插到用户消息之前，只在有内容时才插。所以大多数轮次开始时根本没有卡片。
- `engine.directMessages` 标记这类消息，让这一轮的其他 pre-step 不再处理它：
  - 任务归属已经在 `postMessage` 里做过；
  - 暂存回报已经放进补充内容；
  - 外部协调者守卫把它视为房间自己的派发，不再转发。
  
  这一轮结束时清除这些标记。

## 考虑过的其他方案

- **保留副本，只去掉里面用户的原话。** 能去掉重复上下文，但宿主仍会给每条 room 来源的开轮消息画触发卡片，而房间没办法隐藏宿主的节点。
- **这次就让带附件的消息也走直达路径。** 附件的上传凭据是在房间把消息写进日志的那一刻绑定的。走直达时由宿主稍后写入；如果排队的消息被撤回，则根本不会写入，凭据可能被回收或泄漏。带附件的消息暂时仍走旧路径。

## 影响

发给 dsh 的消息只显示一次，就是一个普通气泡，dsh 的上下文里也只有一份。dsh 正在一轮中间时，消息先在排队条里等待，等它下一轮开始才进入对话记录——和宿主自己的行为一样。dsh 的队列也获得了宿主的排队操作（编辑、删除、插话），插话设计可以直接依赖这一点。

## 测试

`room`：
- dispatch 测试：followup 收到的是用户的原消息（来源为 user，文本完全一致），房间没有另写副本；补充内容带有简报和 `room_message`，但不重复用户的话；这一轮结束后标记已清除。
- help 测试：点名外部会话的提示放在补充内容里。
