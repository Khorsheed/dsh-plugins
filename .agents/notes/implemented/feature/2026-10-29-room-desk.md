# Agent Note: a room member's mode tools act on the room's desk

Status: implemented

## Problem

In a room, the coordinator and the members each run their own mode, which may differ from the room's own (a 开发 room coordinated by a 写作 Codex member). An external member's mode tools run as a stand-in over the member's OWN child session (local-agent's preset tool host). So when the coordinator called `canvas_open`, the canvas opened in the CLI's own session, and the room never showed it. The focus was recorded there too. When the human switched canvases in the room's sidebar, the coordinator's `canvas_write` still wrote to the old one. And a 开发 room hid the canvas sidebar entry altogether, because its own preset does not grant the canvas row.

## Decision

The user settled the rules in conversation on 2026-10-29:

- **Tools, prompts and skills stay with each member's own preset.** Nothing from the room's mode or another member's mode is mixed in. This was already true and is unchanged.
- **The desk mark.** room's `memberMode` now also returns `desk: { sessionId, role, member }`, where the role is `coordinator` when the member is the room's coordinator right now. local-agent's `PresetToolHost` puts `Symbol.for('dsh.agent.desk')` = `{ session, role, member }` on the stand-in on every list and call, so a handoff moves the role. The mark is dropped when the room is not live there or the room names no desk. Execution, approvals, the recorded mode and plugin state stay on the member's session.
- **Canvas (the pilot).** `src/desk.ts` reads the mark:
  - The coordinator's target is the room session's canvas. A member's is its own choice, else the room's.
  - `canvas_open` from the coordinator focuses and binds the ROOM session. A member's open stays on its own session.
  - Both append a log-only `room/desk-opened` event to the room: `{ owner: '@khorsheed/dsh-canvas', member, role, runId?, data: { canvasId, title, created } }`. The type is ROOM's vocabulary (registered in `ROOM_EVENT_TYPES`), because the host refuses to read a log carrying an event type nobody registered. A desk exists only in a room, so room is always there to vouch for it. The first build wrote `canvas/desk-opened`, which nobody registered, so a room carrying it failed to load its history ("unknown to this harness and not marked ignorable"). room registers that old spelling too, and canvas still renders it.
  - Writes and new canvases stay fenced by the member's own session and workspace.
  - The canvas client claims the event (`client/open/desk-row.ts`) and renders「bill 切到了画布《雨夜》 打开 →」in the room. A row seen arriving (within 20 s of its event, once per page) follows: the coordinator's opens the canvas tab, a member's adds the canvas to the strip WITHOUT showing it, marked fresh (`CanvasSelectionStore.addCanvas`, a dot on the strip row until the row is shown). This is choice A.
  - **In the member's card.** room's `memberMode` names the member's run in progress (`desk.runId`), and the event carries it. room's replay attaches a `room/desk-opened` that names a run to that run's execution record (`attachments`). The running card and the reply render each one at the end of the card through a keyed seat keyed by `owner`: `room.run.attachment` on the running card and `room.member.attachment` on the reply (a child slot is declared by exactly one registration, so each card declares its own). canvas registers its row there: inside the card it names only the canvas (「新建了《潜梦者》 打开 →」), and only the live running card follows. Once the seat is registered, an event that names a run gets no conversation row of its own; one that names no run, or a room without the seat, keeps the standalone row. The user asked for this on 2026-10-29: one entry per member turn, not a reply plus a separate row.
- **Writes, too.** The user asked for this on 2026-10-29: in a room, a member's new card left no trace, because its tool rows live in its own session. `canvas_write` now reads the board before and after a write it makes as a room member and appends room's `room/desk-wrote` (same envelope; `data: { canvasId, title, items }`). Each item is `added`, `changed`, `commented`, `archived` or `manuscript`, with the card's name and category. A failed write throws first, so nothing is told. The card seat now hands the owner ALL of its events in the turn (`attachments`). canvas folds the writes into one line per canvas: a card added and then edited counts once, as added. The line reads 「《潜梦者》 新增人物卡「数据标注员」 · 批注「全书命题」 查看 →」, and its door opens the card when the turn touched exactly one. A member's write seen live also puts that canvas on the strip.
- **The novel's own writes.** `novel_write` (chapters, plans, outline, review) and `novel_extract` (the reconciliation that adds and updates cards) are told too. canvas-novel reads the work's cards and chapters around the call (`NovelService.deskSnapshot`) and appends the same canvas-owned `room/desk-wrote`, so the canvas renders the line. Its items add `chapter` (「写了第 1 章《别替我起名》」). A card is named by its category's title field, then a name field, then its text's first line, then any filled field. A card nothing names is counted (「新增 1 张原则卡」) rather than shown with empty quotes; the first build showed 「」. The user found the gap on 2026-10-29: a turn that wrote a chapter and reconciled nine cards left no line.
- **Escaped line breaks.** The K3 / Kimi route sometimes delivers string arguments with their newlines still escaped, so a card showed a literal `\n`. `canvas_write` now unescapes a string that holds no real line break but does contain `\n`. This covers the text, comment, title and every field value (`src/text-escapes.ts`). A string that already holds a real break keeps its backslashes. Cards written before this fix keep their literal `\n`.
- **Novel (canvas-novel).**
  - The novel tools read the same mark (`src/desk.ts`): `novel_bind` from the coordinator binds the ROOM session and announces it with the canvas-owned `room/desk-opened` event (a novel is a canvas, so the canvas row renders it). A member binds itself. Every novel tool resolves the work the canvas way: the coordinator uses the room's, a member its own, else the room's.
  - The novel tools are granted per agent on `agent/created`, which never names a stand-in. So before this change a 写作 CLI member got only `novel_bind`; 3080's `mode-tools.jsonl` showed this. local-agent now announces each stand-in with scoped `local-agent/stand-in-created` / `-disposed` events. The novel grant tracks stand-ins and gives them the three tools whether or not anything is bound: the CLI lists its tools once at start, and an unbound call answers how to bind.
- **Video editing, game, library (the second batch).** Each package inlines the canvas pattern (`src/desk.ts`; its own `room/desk-opened` row and both card seats, keyed by its package name; the roomModes path in `preset-visibility.ts`).
  - **video-studio.** `video_project create/open` binds the acting session. `resolveProject` reads the desk. `data` is `{ projectId, title, created }`. A coordinator's open, seen live, opens the 剪辑 tab and switches its panel through a small per-session hand-off (`requestPanelProject`), because the panel read its binding only at mount. Its door only shows a project and never rebinds.
  - **game.** `game_open` (create, adopt by path, switch) binds the acting session through `settle()`. `game_read/propose/publish` read the desk through `placeOf()`. Workspace and fence stay the member's own (`store.checkProject`). The game panel can only show a session's binding, so a member row's door rebinds the room to that project. A room session bound as the desk carries a `desk` mark in the registry: the turn-end check and the turn card skip it, because a room turn is not a game build turn, and members publish through `game_publish`.
  - **library.** `bindingOf`, `bindingSummaryOf` and the textbook list read the desk. `library_binding` and the write-time auto-bind bind the acting session. Auto-bind decides by the acting session's OWN binding, so a member writing elsewhere still binds itself. A knowledge card's `source.ref` stays the member's own session. Photo attachments resolve in the member's session, then the room's. `data` is `{ projectId, projectName, resourceId?, resourceTitle? }`. A coordinator's bind seen live opens the library on that book (`RevealedProject.reveal(projectId, resourceId?)`). The binding chip's grant check takes the same room union.
- **Sidebar union.** room's client provides `ctx.roomModes` (`presetsOf`, `subscribe`) from its store's roster. The canvas visibility criterion gains a third path: in a room, any member preset that grants the canvas row shows the tab. It is probed through `ctx.get`, with a deferred `ctx.inject(['roomModes'])` subscription, so without room the criterion is unchanged. `docs/plugin-visibility.md`「房间桌面」states the rule for every plugin.

## Alternatives considered

- **A plugin-named event type (`canvas/desk-opened`).** This shipped first and broke loading: the host refuses logs with unregistered types. The ignorable plugin-record API is marked experimental and has no production caller.
- **Copy the event range into the card on the client.** The client's event window is paged, so the reply card cannot reliably see the events of its run.

- **Make the stand-in's `session` the room session.** That would append `agent-preset/selected` to the room and switch the room's own mode. It would also make every plugin's private state shared across members.
- **One generic room renderer plus the right Sidebar's `navigation.params`.** Opening "that one canvas" lives in each plugin's own client state. Navigation params exist only on the 0.2.1 host line, and room would have to know every plugin's strip. Each plugin claims its own event instead.
- **No mode distinction for any sidebar entry.** This would undo the 2026-09-17 visibility rollout across about 8 packages and crowd every session's guide. The union shows exactly what a room's members can reach.
- **Fire `agent/created` for stand-ins.** Every plugin listening to it would take the model-less stand-in for a real agent. The stand-in event reaches only the entries that ask for it.
- **Every member's open moves the front tab.** Parallel members would yank the sidebar back and forth while the human reads. The user chose A.

## Consequences

A writing coordinator in a 开发 room now works on the canvas the room shows, and the human sees each switch. Members add canvases beside it without stealing the view. Sessions outside rooms behave exactly as before.

Gaps:

- library's photo cache listens to `session/event` from its preset-mounted tool row. Whether a photo the human sends in a room reaches a member's plane has not been confirmed against the host; check it on 3080.
- Writes (`room/desk-wrote`) exist for canvas only. Candidates per package: video imports, edit proposals and renders; game publishes and proposals; library pages, quizzes, assessments, notes and roadmaps.

- The fresh dot does not survive a reload. The room row still records who opened what.

## Testing

- `room`: `memberMode` names the desk role, before and after a coordinator handoff.
- `local-agent`: the stand-in carries the mark and the role refresh; there is no mark without a desk or a live room; execution still runs on the member's own session.
- `canvas`, tools: the coordinator's create focuses the room and announces it; the coordinator writes on the canvas the room shows; a member's switch stays its own while it falls back to the room's canvas.
- `canvas-novel`: a stand-in holds the tools unbound and drops them on dispose; the coordinator works on the room's novel. `novel_bind` from the coordinator binds and announces to the room, while a member binds itself and reads the room's novel until it does.
- `local-agent`: each stand-in is announced once and its disposal announced.
- `canvas`, client: the Definition and row (follow once, a member's goes beside, a history row only offers the door); the strip's `addCanvas` and fresh mark; the visibility union following the roster.
