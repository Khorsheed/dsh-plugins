# Agent Note: a room member's mode tools act on the room's desk

Status: implemented

## Problem

In a room, the coordinator and the members each run their own mode, which may differ from the room's own (a 开发 room coordinated by a 写作 Codex member). An external member's mode tools run as a stand-in over the member's OWN child session (local-agent's preset tool host). So when the coordinator called `canvas_open`, the canvas opened in the CLI's own session, and the room never showed it. The focus was recorded there too. When the human switched canvases in the room's sidebar, the coordinator's `canvas_write` still wrote to the old one. And a 开发 room hid the canvas sidebar entry altogether, because its own preset does not grant the canvas row.

## Decision

The user settled the rules in conversation on 2026-10-29:

- **Tools, prompts and skills stay with each member's own preset.** Nothing from the room's mode or another member's mode is mixed in. This was already true and is unchanged.
- **The desk mark.** room's `memberMode` now also returns `desk: { sessionId, role, member }`, where the role is `coordinator` when the member is the room's coordinator right now. local-agent's `PresetToolHost` puts `Symbol.for('dsh.agent.desk')` = `{ session, role, member }` on the stand-in on every list and call, so a handoff moves the role. The mark is dropped when the room is not live there or the room names no desk. Execution, approvals, the recorded mode and plugin state stay on the member's session.
- **Canvas (the pilot).** `src/desk.ts` reads the mark:
  - The coordinator's target is the room session's canvas. A member's is its own choice, else the room's.
  - `canvas_open` from the coordinator focuses and binds the ROOM session. A member's open stays on its own session.
  - Both append a log-only `canvas/desk-opened` event to the room.
  - Writes and new canvases stay fenced by the member's own session and workspace.
  - The canvas client claims the event (`client/open/desk-row.ts`) and renders「bill 切到了画布《雨夜》 打开 →」in the room. A row seen arriving (within 20 s of its event, once per page) follows: the coordinator's opens the canvas tab, a member's adds the canvas to the strip WITHOUT showing it, marked fresh (`CanvasSelectionStore.addCanvas`, a dot on the strip row until the row is shown). This is choice A.
- **Novel (canvas-novel).**
  - The novel tools read the same mark (`src/desk.ts`): `novel_bind` from the coordinator binds the ROOM session and announces it with the canvas's `canvas/desk-opened` event (a novel is a canvas, so the canvas row renders it). A member binds itself. Every novel tool resolves the work the canvas way: the coordinator uses the room's, a member its own, else the room's.
  - The novel tools are granted per agent on `agent/created`, which never names a stand-in. So before this change a 写作 CLI member got only `novel_bind`; 3080's `mode-tools.jsonl` showed this. local-agent now announces each stand-in with scoped `local-agent/stand-in-created` / `-disposed` events. The novel grant tracks stand-ins and gives them the three tools whether or not anything is bound: the CLI lists its tools once at start, and an unbound call answers how to bind.
- **Sidebar union.** room's client provides `ctx.roomModes` (`presetsOf`, `subscribe`) from its store's roster. The canvas visibility criterion gains a third path: in a room, any member preset that grants the canvas row shows the tab. It is probed through `ctx.get`, with a deferred `ctx.inject(['roomModes'])` subscription, so without room the criterion is unchanged. `docs/plugin-visibility.md`「房间桌面」states the rule for every plugin.

## Alternatives considered

- **Make the stand-in's `session` the room session.** That would append `agent-preset/selected` to the room and switch the room's own mode. It would also make every plugin's private state shared across members.
- **One generic room renderer plus the right Sidebar's `navigation.params`.** Opening "that one canvas" lives in each plugin's own client state. Navigation params exist only on the 0.2.1 host line, and room would have to know every plugin's strip. Each plugin claims its own event instead.
- **No mode distinction for any sidebar entry.** This would undo the 2026-09-17 visibility rollout across about 8 packages and crowd every session's guide. The union shows exactly what a room's members can reach.
- **Fire `agent/created` for stand-ins.** Every plugin listening to it would take the model-less stand-in for a real agent. The stand-in event reaches only the entries that ask for it.
- **Every member's open moves the front tab.** Parallel members would yank the sidebar back and forth while the human reads. The user chose A.

## Consequences

A writing coordinator in a 开发 room now works on the canvas the room shows, and the human sees each switch. Members add canvases beside it without stealing the view. Sessions outside rooms behave exactly as before.

Gaps:

- The fresh dot does not survive a reload. The room row still records who opened what.
- video-studio, game and library still read only their own session. They are the next batch, per `docs/plugin-visibility.md`. library's attachments go through the desk too, so a photo sent in the room reaches the member.

## Testing

- `room`: `memberMode` names the desk role, before and after a coordinator handoff.
- `local-agent`: the stand-in carries the mark and the role refresh; there is no mark without a desk or a live room; execution still runs on the member's own session.
- `canvas`, tools: the coordinator's create focuses the room and announces it; the coordinator writes on the canvas the room shows; a member's switch stays its own while it falls back to the room's canvas.
- `canvas-novel`: a stand-in holds the tools unbound and drops them on dispose; the coordinator works on the room's novel. `novel_bind` from the coordinator binds and announces to the room, while a member binds itself and reads the room's novel until it does.
- `local-agent`: each stand-in is announced once and its disposal announced.
- `canvas`, client: the Definition and row (follow once, a member's goes beside, a history row only offers the door); the strip's `addCanvas` and fresh mark; the visibility union following the roster.
