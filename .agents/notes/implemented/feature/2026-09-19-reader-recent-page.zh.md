# Agent Note：一份属于读者自己的「最近阅读」

Status: implemented

## Problem

读者要一个**最近阅读**页，设计在动手前就定好了：表头一个时钟入口、独立页面、落盘、上限 100 条、可清空。

它与紧挨着落地的另一件事之间的张力，正是这份记录的重点。面板现在把「读者刚才在哪」放在**会话内存**里（打开的正文、阅读位置、译文），并且刻意什么都不落盘。「最近阅读」是**相反**的一类状态：「我刚才在读什么」是关于读者自己行为的事实，一份刷新或重启后就清空的列表不算任何记录。它也适合落盘，而译文不适合——一条标题和一个读者自己索要过的 URL，没有第三方正文。

做它的时候暴露了第二个问题：详情页**只**从墙上的解析结果里找条目（`allEntries.find`）。feed 的窗口会滚动，所以一条指向「feed 已不再发布」的条目的最近记录，点开将**什么都打不开**——而那恰恰是这份列表存在的意义。

## Decision

- **`state.json` 增加 `recent`**：`{ entryId, sourceId, title, url?, readAt }[]`，新到旧、每条目一行、上限 `MAX_RECENT_ENTRIES`（100）。规范化器丢掉打不开的（缺任一 id）与无法排序的（没有时间戳），合并重复，再截断——这个文件是用户可编辑的状态，和里面其他表一样。
- **宿主半三个 verb**：`recordRead`（重开同一条是**挪到最前**而不是新增一行，随后截断）、`listRecent`、`clearRecent`。`recordRead` 刻意**不做批量攒写**：打开是人手节奏的动作，一个还没 flush 的队列会在重启时丢掉它。
- **就在打开文章的那个手势里写**——卡片、恢复路径、这一页自己，走的都是同一个 `open()`，于是「打开即已读」只有一条规则，而从这一页重开也顺带把它挪到最前。写是 fire-and-forget；同时镜像进面板自己的 store，让这一页在本次会话里第一次打开就是对的；页面在挂载时、以及每次显示时都重新读宿主的副本。
- **一行里不存正文、也不存摘要。** 正文缓存与 TTL 已经归 `annotations` 管，再存一份文本就是第二个缓存加第二套过期策略。
- **`entryById`：先在墙上的解析里找，再退到存储的记录。** 这就是这一页能重新打开一篇**已滚出 feed 窗口**的文章的原因——恢复打开的那条路径用的是同一个 helper，所以这种条目也能扛过一次面板切换。**源**已经被删掉的那一行渲染成不可点，并说明原因（已经没有东西可以用来打开它了）。
- **这一页是列表，不是网格**：标题（一行、省略号）、来源、「多久以前」，整行就是按钮。它沿用订阅页行的度量，让两个页面读起来像同一个插件。
- **清空是一次点击，不弹确认。** 列表里没有任何东西是读者唯一的副本，为这个页面唯一的动作套一个模态框，只会让这个页面显得危险。

## Alternatives considered

**像阅读位置那样放进面板的会话内存。** 否决：那是「我上一秒在哪」，而读者的诉求就是一个能活下来的页面；它还会和会话快照的前提（刷新 = 一次新的到访）自相矛盾。
**顺带把抽出的正文或摘要也存进去。** 否决：`annotations` 已经在缓存策略下持有正文，一份悄悄变成第二个缓存的最近列表，会为同一批文章把存储翻倍。
**按源各一行，而不是按条目。** 否决：RSS 条目没有源级别的页面可以重开，而读者记得的单位是「我读过的那篇文章」。
**按时间上限（30 天）而不是按条数。** 否决：条数才是文件大小的边界（`state.json` 保持小），而 100 条早已远超「我刚才在读什么」的需要。
**在时钟上挂一个带条数的角标。** 否决：它会和表头已有的未读数打架，而且一条被打开就会失准（面板不会在每次写入后重读列表）。

## Consequences

- `state.json` 最多增长 100 行小记录（几 KB），每次打开写一次。不存正文，所以增长由「读了几篇」而不是文章大小决定。
- 详情页的条目查找不再是「只认墙上的解析」。这是一次真实的放宽：一个条目现在可以只靠四个字段渲染，所以详情页自己的那些提示（`summaryOnly`、脚本插图说明、截断说明）对这类行天然不适用——在抓取答复之前，根本没有正文可提示。
- 这一页让每次面板挂载多一次本地 RPC，因为那个 fallback 必须在详情页需要它之前就绪。
- 删掉一个源不会删掉它的最近记录（那是读者的记录），它们仍然列出但不可打开。跟着源一起删等于悄悄改写历史；改成这一行自己说明原因。
- 上限住在宿主 store（`MAX_RECENT_ENTRIES`），读取时再应用一次，所以手改过的文件也无法让页面无界增长。面板的乐观镜像是**不**截断的（它绝不 import 宿主 store——那个模块会拖进 `node:fs`），这无害：这一页每次打开都会重读宿主那份已截断的副本。

## Testing

`packages/dsh-reader` 共 254 个测试（新增 14 个）：

- `tests/annotations.spec.ts`（+4）：丢掉打不开或无法排序的记录、缺 URL 合法、重复项合并并保留文件顺序、100 行上限从最旧一端截断、列表可穿过磁盘文档往返。
- `tests/boot.spec.ts`（+4）：最新打开的排最前、重开把条目连标题一起挪到最前、打不开的记录被拒、上限丢掉最旧一条、列表在同一个 state root 的第二个宿主里依然存在，`clearRecent` 同样持久。
- `tests/ReaderPane.client.spec.tsx`（+6）：每次打开都记下条目及其来源与 URL；页面列出宿主持有的内容、点击可重开；feed 已不再发布的条目从记录重建后可打开；源被删掉的行不可点并说明原因；清空后列表为空且保留空态；什么都没读过时没有可清空的东西。
