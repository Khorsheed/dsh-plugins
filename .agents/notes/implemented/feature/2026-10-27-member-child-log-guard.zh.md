# Agent Note: member child-log write guard and repair command

Status: implemented

## Problem

10-24 到 10-27 之间，成员子会话日志以七种不同的方式变得无法读取：重启后有一轮没有收尾；Claude 被取消后仍在写入；Kimi 写出的步骤乱序且有缺口；Kimi 写出的步骤编号比已写的更高的步骤还小；重新挂载后 Kimi 把积压内容折叠进已结束的轮次；Kimi 把 Skill 注入当成新的一轮；Kimi 在回复之后补写重复的孤立工具。每个提供方都各自维护轮次和步骤编号，而宿主的日志读取器要么全读、要么全拒：只要有一个事件不符合发布版 V4 的关系规则，整个成员就会从历史视图和 Context Lens 中消失。每一种情况都只能靠手工发现、手工修复。

## Decision

- **写入关卡（`packages/local-agent/src/child-log-guard.ts`）。** registry 会在每个成员子会话准备时、重新挂载时和第一次同步时安装它（重复安装无副作用），四个提供方包都不用改。它包装会话的 `append`，在每个关系事件拿到序号之前做出处理：
  - **纠正**只有一种正确答案的情况。步骤取本轮的下一个编号，提供方原来的编号记为别名，后续事件按别名跟随。指向从未开始的轮次的内容并入当前轮次。开始新的轮次或步骤前，先用宿主自己的 `interruptedTurnClosers` 关上仍然打开的那一个。不在任何步骤里、但必须属于步骤的事件，会先为它开一个步骤。已声明但从未开始的工具调用，先补写它的 tool/call，再写结果。
  - **转走**放在哪里都不合规的事件：已结束轮次的事件、没有打开轮次时的事件、找不到对应声明调用的工具事件。转走的事件写入 `<local-agent homes>/quarantine/<childSessionId>.jsonl`，每条注明原因；每个会话的每种原因第一次出现时记一条警告。
  - **校验**每个纠正后的事件：用宿主的发布日志检查函数（`assertReleasedV4Relationships`，加载时探测，没有就降级）判断，保证关卡的规则不会和读取器的规则走偏。只有在现有日志已经通过检查时才用它判断新事件；装关卡之前就已不合规的日志，不会导致整轮内容被转走。
  - 不涉及轮次和步骤关系的事件原样通过。
- **修复命令（`pnpm repair:member-logs`，`scripts/repair-member-logs.mts`）。** 默认只报告严格读取器拒绝的每份成员日志，以及打算怎样修复。`--apply` 修复其中没有进程持有的日志：先把原文件备份到会话目录之外，按宿主的分帧方式写回（先头部一帧，再事件一帧），并在替换前用严格读取再读一遍。`--quarantine` 汇总关卡转走的事件。修复规则就是每次事故时用过的那些。
- 不在插件里做「重新挂载时自动重写」。宿主的持久化接口没有重写功能；由插件直接改写存储文件，等于重新实现宿主的存储层，还会和它的写入所有权冲突。长期方案是向上游申请宿主的修复接口。

## Alternatives considered

- **再逐个修一遍提供方。** 这七种情况来自四个驱动各自的编号逻辑。在 core 放一道关卡，连没见过的新情况也能覆盖。
- **直接丢弃不合规的事件。** 转走可以保留这些事件，记下的原因也能指向提供方的 bug。
- **现在就整合整个提供方家族。** 几个实时驱动正在其他分支上修改。这道关卡是第一层共享代码；家族整合另行设计。

## Consequences

- 提供方的任何疏漏都不会再让成员的存储日志变得不可读。最坏的情况是某个迟到的事件进了隔离文件，而不是日志。
- 如果隔离记录里出现真正的回复内容，而不是噪音或重复，就说明某个提供方有 bug。
- 修复命令需要 `DSH_HARNESS`（它使用 harness 的 zstd 和格式目录）。

## Testing

- `local-agent`（418）：关卡的测试用例把每一种事故形态写进一个装了关卡的会话（步骤缺口与重复、从未开始的轮次、上一轮未结束就开始下一轮、取消后的迟到写入、写进已结束轮次的积压、没有声明或从未开始的工具结果、装关卡前就已不合规的历史），断言宿主检查通过且没有内容被悄悄丢掉。它还断言格式正确的一轮会原样通过。
- 修复脚本的测试覆盖了这些规则。用 10-25 到 10-27 修复前留下的 9 份备份做测试目录：其中 6 份不可读，`--apply` 之后 6 份全部可读。生产环境的 51 份成员日志全部可读，隔离记录为空。
