# Agent Note: 房间成员的模式工具落在房间桌面上

Status: implemented

## Problem

房间里，协调者和成员各跑自己的模式，可以和房间本身不同（开发模式的房间，由写作模式的 Codex 成员协调）。外部成员的模式工具以替身身份在成员**自己的**子会话上执行（local-agent 的 preset tool host）。于是协调者调 `canvas_open` 时，画布开在 CLI 自己的会话里，房间里看不到；focus 也记在那里。用户在房间侧栏切了画布，协调者的 `canvas_write` 仍写旧的那块。而开发模式的房间干脆把画布侧栏入口藏了，因为房间自己的 preset 没有授予画布那一行。

## Decision

规则由用户在 2026-10-29 的对话中逐条确定：

- **工具、提示词、skills 仍只按成员自己的 preset。** 不混入房间或其他成员的模式。这一条本来就成立，没有改动。
- **桌面标记。** room 的 `memberMode` 额外返回 `desk: { sessionId, role, member }`，成员此刻是房间协调者时 role 为 `coordinator`。local-agent 的 `PresetToolHost` 每次 list/call 都在替身上挂 `Symbol.for('dsh.agent.desk')` = `{ session, role, member }`，交接后角色随之变化。房间不在本进程活着、或房间没给桌面时撤掉标记。执行、审批、记录的模式、插件状态都留在成员自己的会话上。
- **画布（试点）。** `src/desk.ts` 读这个标记：
  - 协调者的写入目标是房间会话的画布；成员先用自己选过的，没有再用房间的。
  - 协调者的 `canvas_open` 对**房间**会话做 focus 和绑定；成员的打开留在自己会话。
  - 两者都往房间追加一条只进日志的 `room/desk-opened` 事件：`{ owner: '@khorsheed/dsh-canvas', member, role, runId?, data: { canvasId, title, created } }`。这个类型属于 **room** 的词表（登记在 `ROOM_EVENT_TYPES`），因为宿主拒绝读带有未登记事件类型的日志；桌面只存在于房间里，所以总有 room 在场为它担保。第一版写的是 `canvas/desk-opened`，没人登记，带这条事件的房间历史加载失败（「unknown to this harness and not marked ignorable」）。room 把这个旧写法也登记了，canvas 也仍然渲染它。
  - 写入和新建画布的围栏仍是成员自己的会话和工作区。
  - 画布客户端认领这条事件（`client/open/desk-row.ts`），在房间里渲染「bill 切到了画布《雨夜》 打开 →」。看着它到达的行（事件 20 秒内、每页一次）会跟随：协调者的打开画布标签页；成员的把画布加进标签栏但**不切过去**，标记为新（`CanvasSelectionStore.addCanvas`，标签上亮一个小点，直到被看过）。这就是方案 A。
  - **放进成员的消息卡里。** room 的 `memberMode` 带上成员正在进行的那一轮（`desk.runId`），事件也带着它。room 回放时，把指明某一轮的 `room/desk-opened` 挂到那一轮的执行记录上（`attachments`）。运行中的卡片和回复卡片在卡片末尾，通过按 `owner` 分发的挂载位渲染每一条：运行中的卡片用 `room.run.attachment`，回复卡用 `room.member.attachment`（一个子挂载位只能由一个条目声明，所以两张卡各声明一个）。画布在那里登记自己的一行：在卡片里只写画布（「新建了《潜梦者》 打开 →」），也只有运行中的卡片会跟随。挂载位登记之后，指明某一轮的事件不再单独占一行；没指明轮次的事件，或者房间没有这个挂载位时，仍然单独显示。这是用户 2026-10-29 提的：成员一轮只占一条，而不是一条回复再加一条单独的行。
- **写入也要报。** 用户 2026-10-29 提出：房间里成员新增卡片没有任何痕迹，因为它的工具调用行都在它自己的会话里。现在，房间成员调 `canvas_write` 时，写入前后各读一次画布，向房间追加 room 的 `room/desk-wrote`（同样的外层结构，`data: { canvasId, title, items }`）。每一项是 `added`、`changed`、`commented`、`archived` 或 `manuscript`，带卡片名和分类。写入失败会先抛错，所以什么都不报。卡片挂载位现在一次把这一轮该插件的全部事件交给它（`attachments`）。画布把写入按画布合成一行：同一张卡先新增后修改只算新增。这一行写作「《潜梦者》 新增人物卡「数据标注员」 · 批注「全书命题」 查看 →」，这一轮只动了一张卡时，「查看」直接打开那张卡。成员的写入如果是实时看到的，也会把那块画布加进标签栏。
- **转义的换行。** K3 / Kimi 这条路有时把字符串参数里的换行仍以转义形式传来，卡片上就出现字面的 `\n`。现在 `canvas_write` 遇到没有真换行、却含 `\n` 的字符串会还原它，正文、批注、标题和所有字段值都覆盖（`src/text-escapes.ts`）。已有真换行的字符串保留其中的反斜杠。修复之前写入的卡片仍然带着字面 `\n`。
- **长篇小说（canvas-novel）。**
  - 小说工具读同一个标记（`src/desk.ts`）：协调者的 `novel_bind` 绑定**房间**会话，并用归画布所有的 `room/desk-opened` 事件通知房间（小说就是一块画布，由画布那一行渲染）；成员绑定自己。所有小说工具按画布的方式找作品：协调者用房间的，成员先用自己的，没有再用房间的。
  - 小说工具按 `agent/created` 逐个 agent 授予，而替身从不触发这个事件。所以改之前，写作模式的 CLI 成员只拿到 `novel_bind`，3080 的 `mode-tools.jsonl` 里能看到。现在 local-agent 用带作用域的 `local-agent/stand-in-created` / `-disposed` 事件通知每个替身。小说的授予逻辑跟踪替身，不管有没有绑定都给它三个工具：CLI 启动时只列一次工具，没绑定时调用会说明怎么绑定。
- **剪辑、游戏、图书馆（第二批）。** 每个包都内联了画布的做法（`src/desk.ts`；自己的 `room/desk-opened` 行和两个卡片挂载位，按包名登记；`preset-visibility.ts` 里的 roomModes 路径）。
  - **剪辑（video-studio）。** `video_project create/open` 绑定行动会话；`resolveProject` 读桌面；`data` 为 `{ projectId, title, created }`。协调者的打开如果是实时看到的，会打开剪辑标签页，并通过一个按会话区分的小交接（`requestPanelProject`）把面板切过去，因为面板原本只在挂载时读一次绑定。它的「打开」按钮只负责显示，从不改绑定。
  - **游戏（game）。** `game_open`（新建、按路径收编、切换）通过 `settle()` 绑定行动会话；`game_read/propose/publish` 通过 `placeOf()` 读桌面。工作区和围栏仍是成员自己的（`store.checkProject`）。游戏面板只能显示某个会话的绑定，所以成员那一行的「打开」会把房间改绑到那个项目。作为桌面被绑定的房间会话，在登记表里带一个 `desk` 标记：回合结束检查和回合卡都跳过它，因为房间的回合不是游戏构建的回合，成员通过 `game_publish` 发版。
  - **图书馆（library）。** `bindingOf`、`bindingSummaryOf` 和教材列表都读桌面；`library_binding` 和写入时的自动绑定都绑到行动会话。自动绑定只看行动会话**自己的**绑定，这样成员写别的项目时仍会绑定自己。知识卡的 `source.ref` 仍是成员自己的会话。照片附件先在成员会话里找，再到房间会话里找。`data` 为 `{ projectId, projectName, resourceId?, resourceTitle? }`。协调者的绑书如果是实时看到的，会把图书馆打开到那本书（`RevealedProject.reveal(projectId, resourceId?)`）。绑定 chip 的授予判断也用同一个房间并集。
- **侧栏并集。** room 客户端从 store 的成员名单提供 `ctx.roomModes`（`presetsOf`、`subscribe`）。画布的可见性判据加第三条路径：在房间里，任一成员的 preset 授予了画布那一行就显示。用 `ctx.get` 探测，再用延迟的 `ctx.inject(['roomModes'])` 订阅，没有 room 时判据不变。`docs/plugin-visibility.md`「房间桌面」一节把这套规则写给所有插件。

## Alternatives considered

- **用插件自己命名的事件类型（`canvas/desk-opened`）。** 第一版就是这么上线的，结果日志加载失败：宿主拒绝带有未登记类型的日志。宿主那套「可忽略插件记录」接口标着实验性，也没有生产调用方。
- **在客户端把这一轮的事件范围拷进卡片。** 客户端的事件窗口是分页的，回复卡片没法可靠地拿到它那一轮的事件。

- **把替身的 `session` 直接换成房间会话。** 会往房间追加 `agent-preset/selected`，把房间本身切成成员的模式；各插件的私有状态也会被成员们共用。
- **通用 room 渲染器 + 右栏 `navigation.params`。** "打开指定的那一块"靠各插件自己的客户端状态；导航参数只在 0.2.1 宿主线上有；room 还得认识每个插件的标签栏。所以改成各插件认领自己的事件。
- **侧栏入口一律不按模式区分。** 要撤回 09-17 在约 8 个包上做的可见性改动，每个会话的入口列表都会变长。并集只显示房间成员真能用到的。
- **给替身触发 `agent/created`。** 所有监听这个事件的插件都会把没有模型的替身当成真 agent。替身事件只送到主动监听它的组合入口。
- **每个成员的打开都切前台。** 多个成员并行时，用户正在看的侧栏会被来回抢。用户选了方案 A。

## Consequences

开发模式房间里的写作协调者，现在操作的就是房间正在显示的画布，用户能看到每次切换。成员把画布加在旁边，不抢视图。房间外的会话行为与原来完全一样。

缺口：

- 图书馆的照片缓存是在它按模式挂载的工具行上监听 `session/event` 收集的。用户在房间里发的照片能不能传到成员那一层，还没有对照宿主确认，需要在 3080 上实测。
- 写入事件（`room/desk-wrote`）目前只有画布做了。各包的候选：剪辑的导入、剪辑提议、导出；游戏的发版、外观方案；图书馆的拍照页、出题、判卷、讲义、路线。

- 新标签的小点刷新后会消失；房间时间线那一行仍记录着谁打开了什么。

## Testing

- `room`：`memberMode` 给出桌面角色，协调者交接前后都覆盖。
- `local-agent`：替身带上标记、角色会刷新；没有桌面或房间不在时没有标记；执行仍在成员自己的会话上。
- `canvas` 工具：协调者新建画布会 focus 房间并通知房间；协调者写到房间正在显示的画布；成员切换留在自己会话，没选过时回落到房间的画布。
- `canvas-novel`：替身没绑定时也有工具，销毁时撤掉；协调者使用房间的小说。协调者的 `novel_bind` 绑定房间并通知房间；成员绑定自己，绑定之前读房间的小说。
- `local-agent`：每个替身创建时通知一次，销毁时也通知。
- `canvas` 客户端：Definition 和那一行（只跟随一次、成员的放旁边、历史行只给门）；标签栏的 `addCanvas` 和新标记；可见性并集随成员名单变化。
