# Agent Note: 侧边对话 M1——会话生命周期、回合级提示词新鲜度与 assistant-actions 引用座位

Status: implemented

[English](2026-09-16-side-chat-m1.md) | 中文

## Problem

[side-chat 提案](../../../proposals/active/2026-09-16-side-chat.md)要建一个**全 preset 常驻的右栏"随身 Agent"**：每个 `contextKey` 绑定一个持久 agent 会话；引用是不透明 `{ label, text }` 文本块；插件不得认识任何消费方的类型。M1 交付会话场景核心：包脚手架、`ctx.sideChat.openWith`（含 systemPrompt 回合级更新与调用方工具）、Remote 面、右栏 tab UI、消息动作「引用到侧边对话」。

三个硬问题塑造了本里程碑，而代码本身承载不了它们的答案：

**调用方供给的工具与每轮新鲜的 systemPrompt 如何到达某个 context 的 agent？** `openWith` 必须更新、绝不重建——那么 live agent 上的更新机制是什么，与之一致的创建时机制又是什么？

**contextKey → 会话的映射存哪，写入拿什么围栏？** 映射是部署级状态（`$DSH_HOME/state/sidechat/`），任何会话工作区都装不下——而 `openWith` 来自同进程的其他插件，不携带可以盖章策略的线上会话。

**「引用到侧边对话」的消息动作座位是什么？** 提案点了 message-tools 先例（`conversation.chat.node` shadow），但准确座位留给实施时核实。

## Decision

**每个 contextKey 绑定一个普通 agent 会话，首次发送时懒创建。** `ctx.agents.create({ sessionId: randomUUID(), meta: { cwd, agentPreset }, setup })`（eval/room 先例）——cwd 继承自 contextKey 指向的 live 会话（会话场景即来源会话），否则继承发送手势所在会话；preset 缺省经探测的 agentPresets 花名册解析部署默认（room `composeRoomAgent` 的形状）。重启后首个手势经 `ctx.agents.resume` 冷恢复；恢复失败（日志残破）退回新建并更正映射。读取永不唤醒：冷上下文从 sessionPersistence 检视回答（room 的 `inspectCold`）。懒创建意味着 `openWith` 不为用户从未打开的上下文付出 agent 组合——用户真正提问时 agent 才启动。

**工具注入：创建/恢复时的 `setup` 回调 + live 上按名热替换。** 核实结论：`agents.create`/`agents.resume` 接受发布前执行的 `AgentSetup(agentCtx, agent)`，经 `agentCtx` 注册的一切——作用域工具、prompt section——都落入该 agent 的层并随其卸载（preset 挂载契约）。cordis 属性代理（`getTraceable`）把服务的 `this.ctx` 重绑到访问方上下文，所以 `agentCtx.tools.register(def)` 与 `agentCtx.systemPrompt.section(...)` 是 agent 作用域的（对照 `ScopedLayers.effect` 核实：它经 `scopeOf` 从传入 ctx 推导作用域）。对已 LIVE 的 agent，同样两个调用在 `agent.ctx` 上成立（仅在销毁后才拒绝注册）。因此 `openWith` 把调用方工具按名键控在每个 context 上，setup 里注册，重复调用时在 live agent 上销毁旧注册、注册新定义。origin tag 由**调用方**负责——side-chat 绝不代标（仓库惯例）。

**回合级新鲜度：文本提供器每次组装重读记录的 prompt section。** `PromptSection.text` 可以是 `(context) => string`，每次提示词组装求值。创建/恢复时在 agent 作用域注册 `sidechat:context`（order 10300，跟在部署人格后缀 10200 之后），提供器返回内置定向段 + 记录里最新的消费方段。`openWith` 只是更新记录——下一次组装自然读到新值。没有 `agent.inject` 的日志噪音，没有堆积，没有创建时快照。

**映射是重定界围栏下的一份版本守卫 JSON——照 canvas `store.ts`，不照 datasets。** `$DSH_HOME/state/sidechat/contexts.json`（`{ version: 1, contexts: [...] }`，宽容读取；损坏=拒绝，绝不重写）。写入沿用挂载的 `ctx.fs`，可写边界重定界到插件 state 目录，完全是 canvas 先例：Remote 变更（`send`/`quoteMessage`）盖**调用会话**解析出的模式与 id；宿主侧 `openWith` 没有会话，按**部署默认模式**（`sandboxPolicy.resolve()`）写入，边界同样重定界、无 sessionId 章——只读部署照样拒绝；canvas 否决 `resolve()` 的理由（退回根不确定）在这里不成立，因为边界是被覆盖而不是被继承。未挂载 `ctx.fs` 的组合降级为纯内存状态（记一次日志，不阻塞任何手势）。

**引用动作落在 `conversation.chat.assistant-actions`——官方列表槽；用户消息侧差距保留。** 核实发现 ui-chat 的 `TurnTailNodeView` 声明了 `'conversation.chat.assistant-actions': { kind: 'list', scope: 'session' }`（owner 为 `{ messageId }`），渲染在定稿助手消息的 `MessageIconActions` 行内（`extraActions`），ui-message-feedback 是在库先例。动作调 `quoteMessage(agent, { messageId })`：**宿主**从调用会话的日志按 messageId 折出文本（contextKey = 调用会话 id——正文不过线），追加引用，客户端经官方 `ctx.sidebarRight.openTab('sidechat', { params: { contextKey } })` 导航面切到对应上下文（canvas M1.5 的结论，探测降级）。用户消息行的 `MessageIconActions` 不接受 `extraActions`——没有用户消息动作座位；唯一替代（message-tools 的 priority -1 整节点 shadow）会与 message-tools 自己的 shadow 打架，并分叉官方气泡的视觉。诚实的 M1 版本只做助手消息，差距记为下面的 upstream 候选。

## Alternatives considered

### 为什么不用 `agent.inject()` 注入 systemPrompt 段？

`inject` 每次 `openWith` 排一条持久的 user 角色上下文消息：日志按刷新次数堆积注入，模型在压缩前看到 N 份过期副本，"更新"语义退化成"追加且祈祷最新的赢"。section 文本提供器恰好是提案要的语义（每轮新鲜、零日志噪音），也是 prompt section 存在的意义。

### 为什么不在 `openWith` 里立即创建 agent？

立即创建要为每个消费方只是提及的上下文付出完整组合（preset 挂载、作用域世界）——包括用户从未打开 tab 的上下文。懒创建让 `openWith` 保持廉价（一次状态写入），且提案自己的生命周期条款（"首次使用时 create"）读作首次**发送**才是首次使用。验收 #4（消费方 openWith + 工具驱动 agent 行为）无论哪条路都经发送验证。

### 为什么不为用户消息的引用做节点 shadow（message-tools 先例）？

message-tools 以 priority -1 在 `conversation.chat.node` 的 `user` 键上注册了完整视觉克隆。side-chat 再来一个 shadow 就会与它抢键（谁的优先级赢，另一方的功能就消失——编辑/撤回或引用），而且每个克隆都会随 ui-chat 演进偏离官方气泡。助手消息上一个诚实的动作，胜过两个互相破坏的 seam；用户消息座位记为 upstream 候选。

### 为什么不用裸 `node:fs` 写 `contexts.json`（datasets binding 先例）？

canvas M1 note 已为部署级**内容**状态了断此事：`ctx.fs` 带来版本守卫（两个浏览器标签页不丢映射）、原子发布、观测轨迹、只读部署的拒绝。映射虽小，但它是会话盖章、会竞争的内容；裸 fs 白白放弃这四样。

### 为什么不把 transcript 存在映射旁边？

session journal 就是 transcript 的持久存储；影子副本在第一次重启后就会漂移。`projectTranscript` 折叠 `user/message` + `assistant/message` 文本、把 `tool/call`/`tool/result` 配成一行状态——同一份折叠跑在 live 快照与冷检视上，这正是"重启后历史完整"是重放而非缓存的原因。

## Consequences

- 新包 `packages/sidechat`（`@khorsheed/dsh-sidechat`，0.1.0）：identity triangle（cordis 行 `sidechat` / `clientBundle('@khorsheed/dsh-sidechat')` / invariant `PACKAGE_NAME`）、自挂载 `dsh.bundle.patch`、typert Remote 对、双语 README（含 Compatibility）、invariant 伴侣。
- 宿主：`src/service.ts`（`ctx.sideChat`：`openWith`、`getState`、`listContexts`、`send`、`quoteMessage`、`disposeAgents`）、`src/store.ts`（state 根 + 重定界围栏）、`src/agent-setup.ts`（探测：agentPresets/sessionPersistence、`composeSideAgent`、`inspectCold`）、`src/journal.ts`（transcript 投影）、`src/remote.ts`（命名空间 `sidechat`：读取 `getState`/`listContexts`，agent 优先变更 `send`/`quoteMessage`）。
- 客户端：右栏页型 tab（kind `sidechat`，key = 包名，导航参数 `SideChatTabParams { contextKey? }` 并入 `SidebarRightTabParamsMap`）、官方 `MarkdownText` 渲染的 transcript、引用 chips、画布三件套的 composer（非受控 textarea、IME 硬停、⌘⏎/按钮发送）、zh+en 词典、只用 `--dsw-*` token 与官方图标；`conversation.chat.assistant-actions` 的「引用到侧边对话」条目（id `sidechat-quote`，order 20）。
- `scripts/gen-typert.mts`：`packages/sidechat` 加入 `TYPERT_PACKAGES`（每个 typert 包都要落的硬编码注册表）。`docs/packages.md` 已重新生成（34 个包）。
- 一条其他包可引用的惯例确认：**在 setup 回调之外对 live `agent.ctx` 做 agent 作用域贡献是成立的**（工具按名热替换；prompt section 文本提供器每次组装读可变状态）。setup 回调仍是唯一有发布保证的时点；live 热挂是更新路径，不是创建路径。
- `zod ^4.4.3` 是运行时依赖，理由与每个 typert 包相同：生成的 `lib/typert.remote-client.js` 引用它。没有其他运行时依赖。
- 侧边会话是普通会话，会出现在会话列表里（首个消息自动得题）。`agents.create` 没有隐藏会话开关；侧边会话是否该有展示层面的折叠（subagent 式谱系）是开放问题，记录而未解。

## Testing

- `packages/sidechat`：**45 个测试全绿**——`tests/service.spec.ts`（18：懒创建 + cwd/preset 继承、live 复用、"重启"后冷恢复、恢复失败回退、引用折叠与清空、按 messageId 引用、openWith 更新语义（含回合级段新鲜度与 live 工具热替换）、跨实例文档往返、线上与宿主侧写入的围栏、无 fs 纯内存降级）、`tests/journal.spec.ts`（6：投影，含工具配对与孤儿结果）、`tests/vocabulary.spec.ts`（9：引用标签、引用折叠、宽容读取）、`tests/remote.spec.ts`（2：agent 优先约定、无 agent 读取）、`tests/client.spec.tsx`（10：空态、transcript 与 chips、⌘⏎/按钮发送与清空、IME 硬停、运行轮询、导航参数切换上下文、宿主缺席提示、引用成功/失败）。
- `pnpm --filter @khorsheed/dsh-sidechat build`（gen-typert → tsc → tsdown）、`pnpm check:hygiene -- packages/sidechat`、`pnpm check:plugins`、`pnpm test:scripts` 全绿。
- 未做：3080 真机的浏览器实走（部署是独立流程；jsdom spec 覆盖了接线），以及验收 #4 的真模型检查（service spec 用假工厂驱动了机制；真实路由下的模型行为属于 3080 实走）。

## Deferred

- M2：多上下文切换列表、未读标、实时推送（替换 1.2s 轮询）、tool 行样式打磨。
- M3：画布 M2 集成（`openWith` 的消费方一侧），由画布提案承载。
- upstream 候选：**用户消息动作座位**（如 `conversation.chat.user-actions`，或用户行 `MessageIconActions` 的 `extraActions`），让引用/转发类扩展不再依赖节点 shadow；**插件自有 agent 会话的隐藏/折叠展示**（侧边会话目前与普通会话混排）；**宿主侧的程序化右栏激活**（今天只有客户端能 `openTab`，宿主侧消费方的 `openWith` 没有自己的客户端半边就无法切出 tab）。
