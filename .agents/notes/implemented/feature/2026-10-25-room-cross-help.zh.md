# Agent Note：房间成员向别的会话求助

状态：已实现

[English](2026-10-25-room-cross-help.md) | 中文

## 问题

房间经常卡在一个问题上，而别的会话手里正好有相关上下文。典型场景：会话 A 开发了一个插件，房间用这个插件时导出报错。新邀请一个成员，A 的上下文就丢了；把 A 搬进房间，又会把它从自己的工作里拉走。负责人的设计见交互稿 `proposals/prototypes/room-cross-help.html`（v3，2026-10-25 定稿）。这次实现第一批：从房间向普通会话求助，整条链路跑通。

## 决定

- **外援留在原地。** 房间工具行新增 `room_help`。目标会话可以用标题、id 或宿主的 `@[…](dsh-session:…)` 引用来指定，通过宿主的 `sessionReferenceResolver.listCandidates` 解析。会话没在运行时，用 `sessionController.resolveAgent` 唤醒，官方定时任务插件也走这条路。求助用 `agent.followup` 排进对方的队列，对方正忙就先做完当前这一轮，用的就是宿主原生排队。
- **求助在对方会话里是一张卡片。** 排进去的 `user/message` 带 `room-help` 来源，内容有：求助 id、发起房间及标题、发起成员、op、发起者的原话。客户端把它认领成 `room-help-request` 节点，画成写明来源房间、可以跳回去的卡片，做法跟 dsh-game 一样。消息正文另外加了给模型看的说明。
- **外援工具只挂在外援自己身上。** `room_help_reply`（最终答复加简短交接）和 `room_help_ask`（反过来追问）注册在外援 agent 自己的 `agent.ctx.tools` 上，既不进预设，也不挂在 profile 根上。一个 pre-step 钩子负责挂工具：求助消息进入某个 agent 的这一轮时给它挂上；另外，日志里已有求助的 agent 在第一步也会挂上，因为重启后 agent 局部的工具会丢。
- **答复按汇报的方式送达。** 外援的追问和回信，作为 report 来源的 `room/dispatch`（`reportFor: help:<id>`）送到发起成员手里，计划核对用的也是这条路。发起者正在跑就并进当前这一轮，空闲就唤醒它，和宿主把后台子 agent 的结果交给父 agent 的方式一致。发起者回答追问或者再追问，都是带着求助 id 再调一次 `room_help`。
- **忘了调回信工具也有答复。** 外援空闲后检查：这一轮认领了求助，却既没回信也没追问，就把它最后一条回复当作回信，标 `fallback`。求助没被认领就离开了队列（比如队列被清空），这次求助记为失败。
- **确认。** 人在房间里 @ 过这个会话，或者房间以前问过它，求助直接发出。否则第一次求助会借用现有的问题卡片，出一张「允许 / 不允许」，最多等 10 分钟。
- **向别的房间求助。** 目标是房间时，求助经那个房间自己的成员名单转交，不直接进它的会话：
  - 有点名成员（`member` 参数，或 @ 菜单写的「成员（房间）」标签）就交给那个成员，没有就交给协调者。
  - 求助作为 `help` 来源的 `room/dispatch` 发出，带 `help: {id, room, roomTitle, from}`。信封会告诉成员：这一轮的最终回复会自动送回去。
  - 那个房间的时间轴上会出现 `room/help-in` 卡片，写明交给了谁。
  - 那个房间暂停时，求助像其他 agent 消息一样被扣住：发起方这边显示排队中，对方驳回则这次求助失败。
  - 派活结束时，引擎的 `settled` 钩子把成员的最终回复送回发起房间；没完成就把这次求助标为失败。
- **提醒。** 求助还在排队或处理中，超过房间的 `helpReminderMinutes`（协作分组的「求助提醒」，10–120 分钟、每档 10 分钟，默认 30）时，那一行标黄，写明已等多久，从进入当前状态时算起。不会自动取消。
- **团队与成员列表。**
  - 团队树把每个被求助的对象挂在最近一次发起求助的成员下面，画成虚线「外援」节点，所有求助都结束后变灰。节点的派活记录就是这几次求助。外援不计入成员数，也不计入用量。
  - 「加入房间成员」可以从团队节点上点，也可以从提示点：同一个普通会话第 3 次回信那行会出一次提示，可以永久关掉。加入后这个会话就留在成员名单上，记为 `room/help-link` / `room/help-unlink` / `room/help-nudge-dismissed`。这样做不复制会话、不改成员名单本身，只是一条 @ 的快捷路径。成员页把这些会话列在「外部会话」区，@ 菜单把它们归到「本房间成员」组。找它帮忙仍然走 `room_help`，用量算在它自己的会话里。
- **@ 菜单。** 房间输入框的 @ 菜单分两组：本房间成员，和其他会话（来自宿主自己的会话引用候选）。没打字时列最近 5 个；打字后两组一起模糊匹配，输入的字按顺序出现即可，排序是完全匹配 > 开头匹配 > 连续子串 > 按字序，同一档里按最近排。协作间默认收起，点箭头（或按 →）展开成员；打字时协作间成员按名字直接参与匹配。成员自己的会话不列。选中的会话通过作用域内的 `slash/input-insert-reference` 事件，插成宿主原生的会话 chip；宿主没有这个入口时，退回插入引用文字。发出去的文字带着 `dsh-session:` 引用，它既是「你 @ 过」的确认依据，也是 `room_help` 用来找会话的线索。
- **日志。** 三种事件：
  - `room/help`：发起者、目标、正文；
  - `room/help-message`：`question` / `reply` / `message`，带交接和 fallback 标记；
  - `room/help-state`：`queued` / `running` / `asking` / `replied` / `failed`。

  房间时间轴上每次求助是一行 `room-help`，状态和消息原地更新，带「看求助内容」和「打开对方会话」。

## 考虑过的方案

**通过预设或 profile 根给外援工具。** 否决。那样每个会话都会带上这两个工具，可它们只在求助进行中才有用；而且普通会话的预设不归我们改。

**在外援的队列栏里显示求助。** 做不到：宿主的队列栏只列人发的消息。负责人定先在房间那一行显示排队状态，用起来再看。

**插进忙碌外援当前这一轮。** 否决。外援在做的是别人的事，求助应该等它这一轮结束。

## 后果

- 还没做：CLI 成员发起求助（成员桥还没有 `room_help`）。
- 重启：外援的工具能恢复，但房间盯外援这一轮的观察在内存里。跨重启还没结束的求助，不会再有兜底回信；外援仍然可以用工具回信。
- 测试覆盖：
  - 求助带房间来源排进队列；
  - 工具只挂在外援身上；
  - 回信送到发起者；
  - 确认卡片；
  - 追问和补充；
  - 兜底回信；
  - 各种拒绝；
  - 两种客户端节点；
  - 新事件的持久化。
