# Agent Note: Room team collaboration — lean member prompts and honest removal

Status: implemented

## Problem

room 给成员的提示词是一条用户消息，什么都往里堆：角色指令、每次派发都带的房间目标，以及只要有人加入、改名或改角色就整段重发的成员名册。名册把其他成员角色指令的第一行当成「职责」；协调者写的指令通常只有一段，于是成员会读到别人的整段简报（「被要求打招呼时……」），像是在给自己下指令。名册还在教「回复末尾独占一行 `@名字 <内容>`、需房间主人确认」的协议，而每个 provider 其实都已经挂了 `member_message` 桥工具。另外，移除成员用的是浏览器原生 `confirm`，文案说「其运行将被中断」，但 `removeMember` 只记一条 `room/member-removed`：运行中的成员继续跑，排队的活还在排队，等它回报的协调者会一直等下去。

## Decision

按负责人 2026-10-22 批准的计划分步交付（外部 CLI 成员的按成员权限尚未完成，见 Consequences）。

**提示词瘦身。** 成员的「第一次」派发以一段【房间简报】开头：它的名字和公开职责、它自己的私有指令、房间目标、其他成员（名字 + 公开职责 + provider，绝不带他们的指令），以及工具约定（CLI 成员用 `member_message`，房间自己的 agent 用 `room_message`，看实时名册用 `room_read`；回复里写 `@名字` 不会转交给任何人）。协调者职责随简报或交接说明一次，不再每次派发都带。交接说明（只在新协调者的第一轮带一次）按对话原样呈现：人说的话、房间自己 agent 的回复、成员的回复、派出的活（发送者 → 接收者），加上房间目标和进行中的任务；回报不放进去，因为它重复了成员的回复。之后每次派发只带它上次以来的变化：指令改动、协调者交接，以及 `roomChangesSince` 产出的一行行【房间变动】（加入及其职责/provider、离开、改名、职责变化、目标变化）。目标不再每次都带。行尾 `@名字` 的兜底解析整个删除：已经没有地方教它，回复末尾的普通提及也不该变成转交。

**公开职责。** `role`（≤ 30 字，`ROOM_ROLE_MAX`，超长返回 `role-too-long`）加入邀请请求、`room/member-added`、`room/member-updated`（null 为清除）、`room_invite` 工具以及 local-agent 桥的 `room_invite` schema。卡片以标签显示它；对话框把指令标为「只给它自己」。

**移除。** `removeMember` 现在真的按确认层说的做，顺序是：用现有 `cancel` 停掉运行中的一轮；取消排队中的投递（`room/delivery-state` cancelled）；未完成的看板任务关闭为已取消，或经新增的 `room/task-edited.member` 把待开始的任务转给 `transferPendingTo`；离开名册；再把每条被取消的投递报告给等它的人（`DispatchEngine.reportOutcome` 改为公开；已移除的发送方从它最后一条 `room/member-added` 取名字）。返回 `RoomRemoval` 摘要。`restoreMember` 以原 id、职责、指令和子会话重新加入，记忆延续；被取消的活保持取消，引擎会跳过排队期间已结算的投递，撤销不会让它复活。客户端用卡片内的确认层（`RemoveMemberConfirm`）取代 `window.confirm`：按 room 状态列出实际后果（`removalImpact`），可选待开始任务的接手人，默认焦点在「取消」，Esc 和点外部关闭，当前协调者给出说明而不是失败，移除后显示 5 秒撤销条并写明做了什么。`RoomDelivery` 增加 `replyTo`，客户端据此说出谁在等。

**成员自由通信与回报。** 所有由 agent 发出的消息——协调者派活、任何成员的 `room_message` / 桥上的 `member_message`、投递回报——都走同一条路径（`messaging.ts` 的 `sendOrHold`）。任何成员都可以给其他成员发消息；`room_message` 只限协调者的限制去掉了（邀请成员和看板编辑仍只限协调者）。消息默认 `kind: 'task'`——对方这一轮的最终回复会回报给发送人（`replyTo`），也就是把协调者的回报推广到所有发送人——或者 `notify`，只是知会，不回报。每条派发记录 `from`、`kind`、`hop` 和可选的 `inReplyTo`，送达时带一行信封：`【来自 claude · #m12 · 派活】（你这一轮的最终回复会自动回报给对方…）`、`【来自 kimi · #m13 · 知会】`、`【#m12 的回报 · 来自 codex · 完成】` 后接成员自己的结论。发送方读回 `sent #m12（… 做完后结果会自动回报给你，不用轮询）`。房间自己的 agent 的回报引用它这一轮最后一条助手文字。CLI 成员的发言行记录 `reportedTo`，显示为「→ 已汇报给 X」。

**扣留与设置。** 新增 `room/settings` 事件（成员页「协作设置」），包含 `memberMessages`（默认 `free` / `confirm`）、`hopLimit`（默认 10，范围 2–50）和 `paused`。人的消息（或不在任何房间轮次里发出的消息）`hop` 为 1，否则为发送方当前投递的 hop + 1；回报也算一跳。以下情况消息会作为待处理的转交被扣留，并带上它本该成为的派发（`reason` + `intent`）：房间暂停、hop 超过上限，或者——仅对非协调者的成员消息——房间要求确认。确认后原样放出那条派发（跳数上限的放行会重新计数：「继续这条链」）；房间取消暂停时按顺序放出被暂停扣下的消息，并重新检查其他规则。旧的转交仍走原来的确认路径。

**团队视图。** 成员页新增「团队」按钮（每张卡片上也有「在团队中定位」），打开右侧栏页面（`room-team`，与计划页同样注册，受同一个 room 界面显隐开关控制）。`teamOf` 把回放出的状态投影成一棵树：每个成员挂在给它派活最多的人下面（从「你」开始逐层展开，所以一定是树；还没被派过活的成员挂在协调者下面）；边统计派活、回报和知会次数；每个节点汇总轮数、耗时和观测到的 token，并列出它收到的每次投递。一套界面按自身宽度自适应：600px 以下是缩进树，节点展开后显示投递列表和会话入口；更宽时同一棵树自上而下画出不带文字的主干分支连线（每个父节点一根主干、子节点上方一条横线、再分到每个子节点），选中成员的详情显示在下方，一层放不下时折叠成「+N」。次数——来自父节点的派活、回报、知会，其他来源放在悬停说明里——显示在每个节点的胶囊上（窄树里内联显示）。第一版的曲线连线、绿色回报回流线和线上标签在 2026-10-23 被替换：成员和轮次一多，线和标签就互相压住。带 `member` 导航参数打开时，每次导航都会选中并滚动到该成员。context-lens 的上下文构成色条尚未接入；金额不显示（没有计价数据）。

**带宿主 preset 的原生 DSH 成员。** 负责人明确：成员的「模式」就是宿主的 agent preset。外部 CLI 成员（claude / codex / kimi）不加载任何 dsh 插件，preset 对它们没有意义；房间自己的 dsh 与房间会话共用 preset。新增成员类型 `native`：在本宿主进程里的 DSH 子 agent。邀请带 `kind: 'native'` 和可选的 `preset`，用 `agentPresets.resolve` 校验（`unknown-preset` 附带已声明的 id）；`listProviders` 为对话框返回宿主 preset 列表，对话框提供「原生 dsh 子成员」和 preset 选项（邀请后锁定）。引擎在它第一轮时经 `agents.create` 创建子 agent：`parentAgent` 为房间的 agent，`meta` 带 `parentSession/origin/agentPreset`，在 setup 里 mount 所选 preset（`composeRoomAgent`，与房间自己的 agent 同一条路），记下 `childSessionId`，之后像驱动房间自己的 agent 一样驱动它（room 来源的 followup，以最后一条助手文字作为结果），并把回复作为发言镜像进房间。重启后按同一 preset 恢复子 agent。它的 room 工具看到的是子会话，所以 `nativeRoute` 把原生成员自己的会话映射到所属房间，并认定它为调用者（发消息、读取、计划命令），而不是把子会话升级成新房间。原生成员暂时不能当协调者。

## Alternatives considered

**名册变化时照旧重发，只是精简一下。** 不采用：成员自己的会话已经保存了它看过的名册；增量更省，读起来也像新消息，要看全貌的调 `room_read`。

**为没有桥的 provider 保留行尾 `@名字` 兜底。** 不采用：四个 provider 都有桥，而这个解析会把回复末尾的普通提及变成转交。

**按 provider 把简报放进会话级系统提示词。** 暂缓而非否决：首次派发的简报已经消除重复，不用动四个 provider；改用 `--append-system-prompt` 等通道是之后可单独做的改进。

**确认层承诺「回收常驻进程」。** 删掉：门面没有回收入口，常驻运行时本来就按空闲超时回收，所以确认层不写这一条。

**只按同一对成员之间的来回计跳。** 考虑过，可以拦乒乓又不限制长接力；负责人选择整链计数、默认 10 跳（一次正常的实现 → 审查 → 补测 → 回报大约 7 跳）。

**像参考截图那样每次投递一个节点。** 不采用：room 成员是常驻的，几轮下来就会铺出几十个节点；改为成员是节点，投递挂在它下面。

**团队单开一个对话页签。** 负责人选择在成员页放入口、打开侧栏页面，主区域留给对话。

**原生成员走 dsh-cli 子进程、按 scope 预置 preset**（local-agent-dsh 的预置方式，也是暂停中的云端线固定 preset 绑定的方向）。负责人决定本地房间不采用：每个 preset 都要一套 scope 目录、复制 preset 包、多一个进程；宿主内的子 agent 可以直接组合任何已声明的 preset，房间和上下文工具也都看得到它。云端线之后基于这一方案适配。

**默认每条成员消息都要确认。** 这是原来一阶段的行为；负责人决定成员之间自由通信，确认改为设置项。

## Consequences

- 暂停中的云端协作线（`codex/room-*` 分支）也改了 `assemblePrompt`（每轮加【本轮来源】）和邀请对话框；负责人决定本地这条线先合入，那条线之后基于它适配。它的来源标签可以自然地映射到下一步的消息信封。
- 尚未完成：外部 CLI 成员的按成员权限（claude 计划 / 逐项确认，codex 只读）。需要在 local-agent 核心加一个委派级参数，记在委派记录里，并由各 provider 的 exec 与 live 启动遵守；claude provider 正有人在改，所以单独交付。CLI 子会话创建时仍不带 preset 标记，读取会话 preset 的宿主界面会把它们显示为无 preset。
- 旧日志照常回放：没有 `role` 即视为无职责；旧房间只是不再重发名册；没有 `hop` 的派发视为链的起点；没有 `intent` 的转交仍走原来的确认路径。
- 桥的回执从 `sent | pending-confirm | busy` 放宽为这些词后接说明（`sent #m12 …`）；local-agent 原样转交，类型同时允许两种形式。
- 测试覆盖：简报内容（不含他人指令）、之后的提示只带增量、职责校验、以 `@名字` 结尾的回复仍是普通发言、`roomChangesSince`、移除忙碌成员（停止、取消排队、报告协调者、转交任务）及撤销，确认层的后果、协调者和键盘路径，成员之间派活后带消息编号回报，知会不回报，跳数上限扣留与放行，暂停/恢复的顺序，确认模式扣留成员消息但不扣协调者派活，团队投影与树，以及原生成员（preset 列表与校验、按所选 preset 创建、复用、发言镜像、工具路由）。
