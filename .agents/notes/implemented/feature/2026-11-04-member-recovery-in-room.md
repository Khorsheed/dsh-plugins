# Agent Note: recover a stuck member from the room, and retry safe start failures on their own

Status: implemented

## Problem

On 2026-11-04 (prod) the host restarted while a Kimi member was mid-round. Its `kimi acp` left a stale session lock, so the next native start (`session/load`) failed with "This session is in use by another Kimi Code CLI instance". `member-control.ts` recorded the member's configuration as `failed`. A failed native start waits for the user; only `admissionFailed` (a refusal by the admission's own configuration check) was rechecked on its own. Every later round, and the room's 立即载入, then failed in 0 ms with the stored error. The only way out was 对账并重试. That button lives only in the member's own session composer, inside the model chip dropdown (`MemberConfiguration.tsx`), and the user could not find it from the room. A round a restart left `uncertain` (batch 5 S4) had the same problem: its 待对账 controls were on the members page only.

## Decision

1. **The core classifies retryable start failures.** `types.ts` exports `LocalAgentRetryableStartError`, the brand constant `RETRYABLE_START_FAILURE` (`'localAgentRetryableStart'`), `BEFORE_PROMPT_FAILURE` (`'beforePrompt'`) and `isRetryableStartFailure(error)`. They are also re-exported from the package root. The predicate checks either mark (`=== true`) as a plain property, on the error and up to four `cause` levels. `beforePrompt: true` is what Kimi's `KimiSessionOccupiedError` (main a9369a97a) already carries, so Kimi's occupied-session failure is retried with no Kimi change, as long as the error reaches the core unwrapped or as a `cause`. So a provider bundled against another core copy, or one that does not import the core, can still mark a failure. `MemberConfigurationController.rejectAdmission(error, recheck)` now defaults `recheck` to `isRetryableStartFailure(error)`. A marked failure is stored as `admissionFailed` and survives a restart. The member's next admission (its next message, a room dispatch, 立即载入) reconciles and retries the start once, as the 5d4f refusal path already did. Nothing retries without an admission. The failed round itself never re-runs. A failure from `run.result` (after the run was returned) never reaches `rejectAdmission`. A cancelled start is not a failure. Unmarked failures still wait for the user.
2. **Contract for providers.** Throw `LocalAgentRetryableStartError` (or set either mark) only from the round start (before the run is returned) or `prepareMember`, and only when no prompt can have left for the model. Its `message` is shown after 「上次启动没有成功：」, so write it as plain language. Kimi's stale-lock fix already throws an error with `beforePrompt: true` when its in-path cleanup could not clear the lock. Switching it to `LocalAgentRetryableStartError` would only make the intent explicit.
3. **立即载入 / 重新载入 recover first.** `MemberConfigurationController.startFailed()` reports `failed` with no selection waiting. That is a native start or refused admission, as opposed to a model/effort choice that did not apply (the choice stays `pending`). It also covers records written before this change, like the prod member's. `reloadMemberTools` calls the new `recoverFailedStart(binding)`, which runs `retry` before either path. When the retry fails again, it answers `{ ok: false, reason: 'start-failed', error }` and starts nothing. When 立即载入's own start fails, `lastReload.error` now carries the reason (`MemberToolsFace.reloadDone`'s new optional `error`, `MemberToolsTracker`).
4. **The room edit dialog shows the recovery.** It has a new `MemberRecoveryLine` (pure state in `member-recovery-view.ts`) under the 模式工具 line, in the same 12px register and reusing its classes. It reads the gateway's `memberConfiguration` and `memberInbox` and polls every 3 s. When the start failed, it shows 「状态 ⚠ 上次启动没有成功」, the provider's reason, 对账并重试 (`retryMemberConfiguration` at the read revision), and one sentence saying later messages go through and the failed one is not resent. A selection that did not apply reads 「上次的模型设置没有生效」. An `uncertain` ledger row reads 「待对账」, with the caller or typed text, an evidence field and 确认已完成 / 确认已取消 (`controlMemberInbox` `reconcile`, the members page's semantics). All four gateway calls are duck-typed in `membersFace`, so without local-agent the block never renders. 立即载入 / 重新载入 in the dialog also run 对账并重试 first when the block reads a failed start (`MemberToolsLine.recover`). That covers an older core too. A second retry is a no-op on a recovered control. When it fails again, the line shows 「上次启动没有成功：<reason>」 and does not ask for the load.

## Alternatives considered

- **Auto-retry every failed native start at the next admission.** Rejected. Core cannot tell whether a provider sent the prompt before failing, and a re-sent prompt is paid work done twice. Only the provider knows, so the provider marks it.
- **A new record field for the failure kind.** Rejected for item 3. "failed with nothing pending" already separates a start from a selection, and it also classifies the records already on disk.
- **Render local-agent's own `MemberConfiguration` / `MemberInboxView` inside the dialog.** Rejected. They are composer-shaped (dropdown chip, inbox list) and would not match the dialog. The room also keeps its edge to local-agent as optional reads it renders itself, like the 模式工具 line.

## Consequences

- `LocalAgentMemberToolsReload` gains the `start-failed` variant, and `lastReload` gains `error`. An older room ignores both.
- The provider side (`packages/local-agent-kimi`) is untouched here. Until it throws the retryable kind, a stale lock still waits for the user. The user can now recover it from the room, and 立即载入 recovers it in one click.

## Testing

- `packages/local-agent/tests/member-controls.spec.ts`: 7 new tests. A retryable start failure is retried by the next admission, including after a restart. A still-retryable failure tries once per admission. A plain failure waits for the user and fails without starting. A retryable error after the run was returned changes nothing. A cancelled start is neither failed nor retried. A failed selection is not a failed start. The brand is read through `cause` and without the class.
- `packages/local-agent/tests/member-tools-status.spec.ts`: 4 new tests. 立即载入 retries the failed start and then starts. A retry that fails again answers `start-failed` with the new reason and starts nothing. A start failing after the recovery carries `lastReload.error`. 重新载入 also recovers first, and a selection that did not apply is left alone.
- `packages/room/tests/member-recovery.client.spec.tsx`: 12 new tests. They cover the state fold, the failed-start block (retry at the revision, recovered note, failed again), the selection wording, 待对账 (evidence required, reconcile arguments) and nothing to recover. In the dialog: the block beside 立即载入, 立即载入 running retry before reload, a failing retry showing the reason without loading, and no family meaning no block. They also cover the `startError` fold and English copy.
- Screenshots of the dialog at 1280 and 390, failed and uncertain, from `packages/room/tests/preview/member-tools.html?state=recoveryFailed|recoveryUncertain`.
- Not verified: a real Kimi stale lock, a live 3080 instance, and the dialog against a live gateway.
