# Agent Note: 还没有气泡的房间消息在输入框上方等待

Status: implemented

## Problem

房间的原生 dsh 协调者忙时，人发的消息要等轮到它才被收下：在那之前这条消息不在房间日志里（写进去就等于插进正在跑的这一轮——宿主每一步都从日志现算历史），所以没有气泡可以挂回执（[回执 note](2026-11-08-room-message-receipt.zh.md)）。输入框上方的队列行只显示正文，既不说还没送到，也没法收回。房间时间线设计 B 线第 C1 步（待定 5，选 A）。

## Decision

- **一条规则**：有气泡的消息，状态在气泡上；还没有气泡的消息，在输入框上方占一行。
- **「还没有气泡」看数据，不加字段**：投递回放记下 dispatch 的 `messageId` 是否已在日志的人类消息里（回执那一步的 `RoomDelivery.bubble`）；缺省就是还不在日志里。旧日志里这些消息早已写入，不会出现这种行。
- **这一行**：所有带消息 id、没有气泡、仍在排队或运行中的人类投递，在输入框上方的队列条里写「待送达 · <正文>」，排队期间带撤回（和回执同一个 `withdrawDelivery` Remote）。消息落进日志（`bubble: 'after'`）时这一行消失，而不是投递转为运行时——宿主写气泡比房间写运行边晚一点，这一行不能在气泡出现前就没了。
- 宿主自己的 `next-turn` 队列行不变。

## Alternatives considered

- **在时间线底部画一个虚线的「待送达」气泡**（待定 5 的 B）：房间节点只能锚在日志位置上，原生协调者运行时这个位置在它那一轮中间——气泡会被画进轮次过程、轮次结束时跟着折叠（10-29 卡片挪出折叠轮次那次修复的同一机制），还像是插进了这一轮。
- **立刻把消息写进日志**：那是往正在跑的一轮里插话（T0 ③），不是排队。

## Consequences

- 协调者被阻塞的行保留「等上一轮核对」的措辞。
- 原生协调者带附件的消息仍走房间先写日志的路径（T0 ③）：它有气泡和回执，而正在跑的那一轮下一步就已经看到它——设计里保留的已知偏差。

## Testing

`room-composer.client.spec.tsx`：还不在日志里的原生协调者消息显示「待送达 · …」并带撤回（以 dispatch seq 和成员调用 Remote）；有气泡的 CLI 成员排队消息不列出；气泡进日志后即使投递还在运行，这一行也消失。`receipt.client.spec.tsx` 钉住这种消息在时间线上没有回执。
