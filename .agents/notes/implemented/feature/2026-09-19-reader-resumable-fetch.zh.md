# Agent Note: 离开页面也不会停的抓取

Status: implemented

## Problem

抓取以前只在读者停留在那一篇的时候有效。HTTP 请求确实由宿主发出，但**原始网页是交回浏览器**的，由浏览器抽取、再请宿主落盘——所以切到别的面板、关掉标签、刷新页面，这次下载就白费了。右栏让这件事更糟：`RightbarRoot` 只在 `activePanelId === null` 时渲染侧栏，所以一旦打开任何主面板（侧边对话、某个会话），灵感空间面板是**被卸载**而不是被隐藏，连同它所有的客户端状态。

读者的诉求：在卡片上按一下、走人、回来时文章已经就绪；同时墙上要能看出哪几篇已就绪、哪几篇在抓、哪几篇坏了，让"打算读什么"这件事在墙上就能决定。

## Decision

- **宿主在 `fetchEntryBody` 作答之前，先把原始 payload 写盘。** 存在 `bodies/<digest>#raw`（就是放超大正文的那个侧车目录），并在条目 annotation 上记 `fetch: { state: 'raw', at, rawFile, chars, url, truncated }`，然后才把 payload 交回去。中途离开的浏览器因此不花任何代价：payload 在盘上，记录也写着。
- **请求开始前先写 `fetching` 记录**，这样重新打开墙时能说"正在抓"。超过十分钟的记录视为已废弃（拥有它的进程可能已经重启）。
- **浏览器半负责把存下的 payload 消化掉。** 加载时、以及只要有 `fetching`/`raw` 就每两秒，面板向 `entryFetchStates` 询问当前展示的条目，并把 `raw` 的抽出来——同时两条，走 `getRawBody` → `extractArticle` → `storeEntryBody`，而后者正是清记录、清扫 raw 文件的那一步。
- **状态是"按条目"而不是"按源"。** 条目来自浏览器对 feed 的解析，所以搭不上源摘要：`entryFetchStates` 接收墙上正在展示的 entry id，回答 `none | fetching | raw | ready | failed`（失败带上分类代码，于是卡片悬停显示与详情页同一句话）。
- **卡片标签行里有一个「抓取」药丸**：灰＝什么都没抓（点即抓）/ 蓝＝抓取中或已抓待解析 / 绿＝已有新正文 / 红＝上次失败，悬停给原因，再点即重试（手动点击不受退避限制）。颜色就是状态，一面墙可以一眼扫出"哪些能读"。
- **失败在发生处就分类。** `fetchEntryBody` 现在把错误也过一遍新增流程用的 `classifyFetchFailure` 并落 `failureCode`，卡片红态因此用读者看得懂的话解释，而不是复读宿主缝原话。
- **打开条目依旧自动抓取**（用户的决定）：药丸与详情页调的是同一段代码，所以在墙上预抓和在详情页等待是同一个机制，不是两套。

## Alternatives considered

**继续把抓取留在浏览器，用模块级 Promise 保活。** 不采纳：只能扛过面板切换；刷新、关标签或宿主重启依然丢，而且请求会留在一个没人看的 JS 上下文里跑。
**做成宿主侧任务队列 + 进度事件。** 暂不采纳：本包除了轮询没有到浏览器的推送通道，而"状态记录 + 两秒轮询"给出的信息量相同、机器少得多。真要有带取消的队列，这张记录就是它天然的挂载点。
**让宿主来抽取。** 不可能：宿主运行时没有 DOM 解析器（feed 解析放在浏览器半也是同一个原因）。存原始、稍后抽取是同一个想法的诚实版本。
**把抓取状态显示在来源行上。** 不采纳：读者做决定的最小单位是"一篇文章"，而一行源覆盖几十条状态各异的条目。
**墙一加载就把所有条目都抓了。** 不采纳（与补齐的既有设计一致）：那是对每个订阅当爬虫。药丸让读者自己选，自动补齐仍然每次切一片。

## Consequences

- 抓取现在是**可续的**：raw 在盘上，下一次有浏览器时抽取。代价是每次抓取多一次文件写入，以及一个可能很大的暂存 payload（41 MB 的页面就是 41 MB 的 raw 文件，直到被抽取）。
- state 文档的 keep 条件必须认识 `fetch`：只有一份"已存 payload"的 annotation 以前会在下一次读取时被丢掉，于是每一份 raw 都**悄悄消失**。这是新测试抓到的，不是靠看代码看出来的。
- 轮询 effect 只依赖"是否有东西在飞"这个**布尔值**，回调通过 ref 取。原来依赖回调本身会成环——轮询改状态、状态重建回调、回调重跑 effect——测试套件甚至跑不完。
- `state.json` 依旧很小：正文与 raw payload 都在 `bodies/`，而清扫既不会删被引用的正文，也不会删被引用的 raw。
- 手动重试是刻意的：保护自动补齐的六小时退避**不适用于点击**，因为点击就是一个人决定花这次请求。
- 墙上每次加载多一次往返，有东西在飞时每两秒一次。都是本地 RPC，而且状态没变时 store 写入是 no-op。

## Testing

`packages/dsh-reader` 现在跑 222 个测试（新增 6 个）：

- `boot.spec.ts`：`fetchEntryBody` 作答前已把 raw 写盘（返回 `rawFile`、`bodies/` 里有一个文件）；`entryFetchStates` 报 `raw`；`getRawBody` 交回 payload 与它的 URL；`storeEntryBody` 把状态翻成 `ready` 并清掉 raw 文件；403 报 `failed` 且 code 为 `blocked`。
- `ReaderPane.client.spec.tsx`：卡片按宿主状态显示「抓取 / 已抓取 / 抓取失败」；点灰药丸（与红药丸）会调用 `fetchEntryBody`；红药丸悬停带分类原因；`raw` 条目经 `getRawBody` → `storeEntryBody` 被抽取，全程不发网络请求。
