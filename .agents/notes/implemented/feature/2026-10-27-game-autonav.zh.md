# Agent Note: publishing takes the user to the result

Status: implemented

## Problem

agent 改完元素或发完版本后，用户得自己去右栏里找结果：打开页签，再挑元素或切到「试玩」。2026-10-27 用户提出希望面板自己跳过去。

那一天先后试了三种做法，最后保留的是第四种：

- **由页面推断去哪。** 页面读轮次报告、轮询新版本、留意项目绑定变化，并给改过的元素打上小圆点。这种做法不需要 agent 配合，但它是在猜，而且动得太早：2026-10-27 v13 刚上线它就跳到了「试玩」，而 agent 那时还在收尾。
- **在此之上再加一个 `game_show` 工具。** 它补上了 agent 的意图。两分钟后 agent 调用它打开元素列表，于是有两个来源在移动面板。同一个 agent 在更早的一次发版时也没有调用这个工具。
- **共享的跳转工具包**（`client-ui-reveal-kit`）。它是为图书馆和剪辑也写的，但实际只有游戏在用。

用户选择了单一来源，也就是 agent 的发版，而且代码要尽量少。

## Decision

- **只有 `game_publish` 会移动面板。** 发版通过（或者生成候选版本）时，会在服务端内存里留下一条「请用户看这里」的请求：每个项目只保留最新一条 `{ seq, target, note, at }`，通过页面轮询的 `liveVersion` 返回。
- **agent 可以指定位置；不指定就由这个版本决定。** `show` 取 `play`、`versions`、`elements`、`elements:<id 或名字>` 或 `design:<章节>`；`note` 是一句话，说明看什么。找不到的位置会退回默认位置，工具的返回会写明这一点。默认位置通过和上一个版本对比得出：改了代码、素材，或者是第一个版本，就打开「试玩」；只改了一个元素，就打开它的页面；改了好几个，就打开元素列表，并附上一句「v13：改了阿努比斯、托特」这样的说明。候选版本一律打开「试玩」，在那里等用户确认。
- **页面只负责执行请求**（`src/client/reveal.ts`）。每条请求只处理一次。刷新页面时看到的请求（早于 90 秒）算作历史，不处理。游戏正在运行、或者 20 秒内在面板里操作过时，请求会以提示的形式等着（去看看 / 不用了）。面板关着、窗口又窄于 820px 时，保持关闭。每个决定都会在控制台留一行 `[game:reveal]`。同一个轮询还会在会话绑定的项目变化时刷新页签，比如协作间成员调用了 `game_open` 之后，但它从不自己跳转。
- **元素列表按最近修改排在前面**，依据是每个元素文件最后一次修改的时间。
- 删除的内容：页面自己的推断、「改完自动跳转」开关、改过的元素上的小圆点、`game_show`，以及共享工具包。

## Alternatives considered

**由页面决定（只保留浏览器逻辑）。** 不需要模型配合，结果确定。但它不知道 agent 的意图，而且在发版那一刻就动，哪怕 agent 还有事要做。agent 是在它认为结果已经就绪时才发版的，所以把跳转绑在发版上，时机更合适。

**单独的 `game_show` 工具。** 它给 agent 的能力和现在一样，但这是一个可能被忘掉的额外步骤，而且协作间成员看不到要求它这样做的 dsh 人设。把选择并进 `game_publish` 之后，每次发版都会移动面板，agent 只需决定去哪里。

**现在就做共享工具包。** 只有一个使用方时，这样做为时过早。等图书馆或剪辑真的采用同一套流程时，再把它们实际共用的部分抽出来。

**保留小圆点。** 小圆点依赖轮次报告，而协作间成员的工作不会产生轮次报告，所以它们只能标出一部分改动。元素列表按最近修改排序，不用记录「看没看过」也能看出哪些是新的。

## Consequences

- 回合结束时的自动发版（dsh 的一轮结束了，但没有调用 `game_publish`）不会移动面板，用户在面板里提交的版本也不会。
- 页面可见时仍然每 6 秒轮询一次，因为宿主无法主动推送（缺口 S17）。轮询读的是两个小文件和内存里的那条请求。
- 请求保存在服务端内存里，重启后就会丢失。对于「现在看看这个」这类请求，这正是合适的。
