# Agent Note: 点开一条就把正文抓下来

Status: implemented

## Problem

打开一条本地没有正文的条目，渲染出来是**一页空白**：标题、来源行，然后什么都没有——没有正文、没有原因、也没有可点的动作。实测案例是 `https://transformer-circuits.pub/2026/workspace/index.html`，从该站自己的 Atom feed 点进去：

- 那个 feed 每条只给 **167 字符的摘要**、不给全文，所以卡片有标题和摘要，而条目的 `contentHtml` 是空的。
- 宿主既没有缓存正文、也没有任何失败记录（state 文档的 `annotations` 一共 4 条，没有一条是这篇）。自动补齐还没轮到它——每轮墙只补 8 条、同时 2 个请求——而**打开一条从来不触发抓取**：`getEntryBody` 只读缓存、feed 自己的 payload 和已记录的失败。
- 于是 `open()` 落进最后一个分支：`error === undefined`，而对 feed 条目它刻意什么都不设。代码里写的理由是"补齐正在抓它，在这里报错是撒谎"——关于"错误行"这点是对的，但读者看到的是空白页，分不出"还没抓"和"读不了"。

抓取和抽取本身没有任何问题：这一页 200、418 KB HTML，用本仓库自己的提取器（在 jsdom 里跑）能提出 **321,868 字符**正文。插件只是从来没去要过。

## Decision

**打开一条既没有正文、也没有已记录原因的条目，就地抓一次——而且只抓一次。**

- 详情页的 `open()` 调用的是卡片上「抓取正文」用的同一个 `fetchBody(entryId, url)`：宿主抓取 → 浏览器抽取 → `storeEntryBody`；抽不出东西时 `fetchEntryBody` 会把失败记在条目上。一条代码路径、一份契约：成功就把正文缓存下来，失败就留下下次打开会读到的那句原因。
- **已经知道原因的不自动抓。** 如果 `getEntryBody` 回了 error（已记录的反爬、登录墙、非网页类型、跨站跳转，或上一次抽取失败），详情页只显示那句原因 + 「阅读原文」，不发请求。对一个已经拒绝过我们的页面每次打开都发一次请求不是修复；要重试就用卡片自己的「抓取正文」，那是刻意的动作。
- **保存链接的规则不变。** 抓回来了但没能变成正文的保存链接，已经有「这一页抽不出正文…」（上一次"仅链接"那批交付的），只有 **feed 条目**缺正文时才自动抓。两种状态不同，代码里也分开写。
- **页面上明说在抓。** 请求在飞的时候渲染一行新的 `detail.fetchingBody`（「正在抓取正文…」/ "Fetching the full text…"），由 store 里条目的 `fetching` 标志驱动。一次请求那么久的空白正文区，正是这次改动要消灭的那种观感。
- **`fetchBody` 在组件里上移到 `open` 之前**，两个 `useCallback` 才不会形成循环；`open` 现在把它列进依赖。

## Alternatives considered

**继续等自动补齐（维持现状）。** 不采纳：读者看不出正文只是"还没轮到"，墙每轮只切 8 条，而实测那条什么都没有。"点开就能读"就是这个面的全部承诺。

**每次缺正文都自动抓，包括已有失败记录的。** 不采纳：那会让每一次打开被反爬/登录墙挡住的文章都变成对该站点的新请求，而失败是已知的、也已经解释过了。重试保持手动、明确。

**保存链接抽取失败的也自动抓。** 同样不采纳，而且那种情况本来就有句子和手动重试。

**hover 预取，或墙一加载就把所有缺正文的都抓了。** 不采纳，那是爬虫行为：宿主那条候选切片（每轮 8 条、失败 6 小时退避）正是这个预算被刻意设计成的形状，而 hover 会把请求花在读者根本不会打开的条目上。

**改成一个"还没抓，点击抓取"的按钮。** 诚实但对这次的需求更差：读者要的是"点开就能读"，不是再多一个要找的控件。在"抓取本身是一个决定"的场合（已有失败记录），那个按钮还在。

## Consequences

- 正文缺失时，**打开一条就付一次请求**——README 本来就写着"想看某条正文时点开它，付一次抓取"，现在实现与它对上了。
- **过期的缓存会在打开时自愈。** 以前缓存超过期限会产生同样的静默空白页（宿主对过期正文不回 html）；现在详情页会重新抓。
- **一次失败只花一次请求，不是每次打开一次。** `fetchEntryBody` 会把原因记在条目上，下次打开时 `getEntryBody` 会把原因交回来、页面把它渲染出来，不会再抓。
- **墙上的补齐与"打开"可能对同一条并发发两个请求**，本可以只发一个。两者都是同一时刻的用户可见动作，重叠有限（补齐并发 2），要串行就得在墙和详情之间共享一份在飞注册表——这次刻意不做。
- feed 条目的空白态没有了；没有任何 link、也没有正文的条目仍然什么都不渲染，因为既无从抓取也无话可说。

## Testing

`packages/dsh-reader` 现在跑 198 个测试（`ReaderPane.client.spec.tsx` 新增 3 个）：

- 打开一条只有 link、没有 description 的 feed 条目时，`fetchEntryBody` 恰好被调用一次且参数就是这个 link，并把返回的内容渲染出来（原先的空白页）。
- 请求在飞的时候，「正在抓取正文…」那一行在屏幕上；正文到达后它消失。
- 页面什么都没抽出来的保存链接仍然显示它的句子，并且 `fetchEntryBody` 被调用 **0** 次——这条刻意的限制被钉住。
