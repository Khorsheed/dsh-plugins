# Agent Note: panel edits commit as versions; element lore

Status: implemented

## Problem

2026-10-22 用户走查 3D 项目的元素页，觉得面板里「改动」的模型让人困惑。元素编辑写进工作文件，还就地改了线上版本的快照，所以试玩区变了却没有新版本。之后输入框上方的改动条和每次改完的提醒都在问「要不要告诉 agent」，读起来像是不发就不算数。参数定稿写进了 `game.json`，却没写进线上版本，还清掉了试玩值，于是试玩区退回旧值，要等 agent 下一轮出版本才生效。元素页上，「让 agent 改外观」压在一长列配方滑块下面。另外，元素有外观、有数值，却没地方写它是谁——而它的行为（异兽会受惊、会好奇、会靠近）恰恰来自这个。

## Decision

- **编辑只改工作文件，版本来自提交。** `editElement` 只写元素文件。每次编辑记进用户层的 `edits`（按元素和种类各一条，文字如「毕方的外观」）。页签上方出现「N 项修改还没进游戏 · 提交为新版本」。`commit` Remote 跑与回合结束相同的 `checkRow` 流程（不设修复上限，不往对话里送）。通过就生成版本，说明写「面板修改：…」（自动上线关着时成为候选）。没通过的结果留在提示条里，附「交给 agent 修」，把问题写进对话框。上次检查已通过的同一份构建回答 `unchanged`。不管下一个版本由谁生成（面板提交、`game_publish` 或回合结束），都会把未提交的修改写进说明并清空。
- **定稿即提交。** 定稿把默认值写进 `game.json` 并记一条修改，面板随即提交。试玩区换到带新值的版本。
- **不再追问「告诉 agent」。** 输入框上方的改动条（`conversation.input.dock`）、改完的提醒及标题栏开关、「未发送改动」标签都删掉了。面向 agent 的 `pending` 清单保留：`game_read` 总览列出一次后清空。技能告诉 agent，面板修改是用户的决定，改元素文件或 `game.json` 之前先 `game_read`。参数抽屉上的「告诉 agent」保留，因为那是用户主动给的反馈。
- **设定（lore）。** 每个元素都可以有 `lore` 字符串。它在元素页的「设定」卡片里显示和编辑，不进数值和字段编辑器，面板保存时最多 2000 字，并自动汇总成生成章节「元素设定」。`game_read element` 会显示它；技能要求 agent 给每个元素写设定，行为和文案照它来。
- **元素页顺序。** 预览 → 让 agent 改外观及方案 → 设定 → 折叠在「细调外观」里的 3D 配方 → 字段。试玩画面不再接收元素热替换；转盘预览仍实时跟随编辑。

## Alternatives considered

**保留实时生效，只改改动条的文案。** 这是最先提的方案。用户更想要显式提交：试玩区里看到的改变就该是一个版本，这样时间线、轮末卡片和回滚都能看到它。

**每次编辑自动提交。** 每拖一下滑块、画一笔都要跑浏览器检查并多出一个版本，时间线会被淹没，画到一半的外观也能玩。提示条把修改攒起来，由用户决定何时成为版本。

**设定只写在一个策划章节里。** 所有元素写在一个文件里好写，但离用户看模型的元素页太远。逐元素的设定放在外观旁边，章节由它生成。

## Consequences

- 在面板里改过的元素，提交之前玩不到。提示条负责提醒，agent 的版本也会顺带带上它们。
- 提交检查的是整个工作目录，所以 agent 写到一半的文件可能让它失败。失败留在提示条里，可以交给 agent。
- agent 只通过 `game_read` 得知面板修改，不会被强塞消息。其余靠技能里的规矩和版本说明（「面板修改：…」）。
- 取代了 [游戏开发模式](2026-10-09-game-dev-mode.zh.md) 里「显式发送」的用户层；2026-10-10「不自动附带」的决定仍然成立，因为不会往用户的消息里塞东西。
