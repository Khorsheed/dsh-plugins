# Agent Note: capture——JS 驱动部件图的像素快照

Status: implemented

## Problem

[capture 渲染抓取服务](2026-09-21-capture-rendered-fetch.md)序列化渲染后的 DOM，而有一整类图不可能体面地活过序列化：JS 驱动的部件图。在同一个验收目标上实测（transformer-circuits.pub/2026/workspace）：102 张图里 23 张是部件——6 张带 `<canvas>`，19 张子树内有事件监听器（并集 23 张）。canvas 像素根本不进 `outerHTML`；监听器建的浮层按抓取时 1280px 视口算绝对坐标，到了 reader 窄栏里标签全叠在图注和后文段落上（2026-09-21 用户验收截图：Figure 3 透镜读出和 Figure 5 token 钉选集群，都在这 23 张里）。内联管线对另外 79 张是正确答案——静态 SVG/复合图既可选可引又清晰——但对部件图它只能产出残破的拍平。

同一轮验收还暴露了脚本图计数规则的第二个缺陷：渲染抓取成功后存下的正文，提取计数为零张脚本图，而入库把"零"和"没有"同等丢弃——于是下次打开时视图回退到条目添加时的加载期计数（84），「页面自己绘制的插图」提示（连同「渲染抓取」按钮）死灰复燃。

## Decision

渲染管线在滚动扫描和序列化之间插入**部件快照相**（`packages/capture/src/service.ts` 的 `snapshotWidgets`）：

- **检测看行为，不看长相。** init 脚本（`evaluateOnNewDocument(installListenerProbe)`，先于一切页面脚本）包装 `addEventListener`，把收到监听器的 Element 打进驻 window 的 WeakSet。分类器（`markInteractiveWidgets`，与其他 page task 一样自包含）随后把最外层的 `figure`/`d-figure` 判为部件：子树含 `<canvas>` 或有被探针标记的元素。只检查 figure 自己的子树——框架根委托的监听器挂在 figure 之外的祖先上，这恰好保证 React 根不会株连整页。`onclick` 属性式处理器和纯委托部件是记录在案的漏网；canvas 兜住了它们剩下的脚本渲染情形。
- **裁剪框取内容，不取整张 figure。** 每个被标记部件的盒重新现读（晚期重排会挪动图），取其非 `figcaption` 子元素的并集，外加 8px 余量（坐标轴标签常溢出半格），并夹在文档范围内。图注不进像素，因为它以文本留在 DOM——否则渲染两遍，而图注正是翻译和引用的载体。Chrome 以 2x 光栅截 WebP q80（`captureBeyondViewport`，扫描停在页尾也无所谓）。
- **替换保住 figure 的身份。** `replaceWidgetsWithSnapshots` 移除部件的非图注子节点（和散落文本），插入一张 `<img>`：data URI、`width`/`height` 保比例、部件修剪后的非图注文本（≤400 字符）作 `alt`——变成像素的内容留下的可检索残渣——以及 `data-capture-snapshot="widget"` 标记。序列化相随后原样运行。单张截图失败的部件保留 DOM（快照前的行为）；整相失败静默降级；`snapshotWidgets: false` 配置整相关闭。上限：每次渲染 40 张快照，盒边长 4096px。
- **「数过，没有」不等于「没数过」。** reader 侧 `captureBody` 现在永远携带提取的脚本图计数（含 0），`storeEntryBody` 只在字段缺失时缺省（reader `service.ts`）。重挂载链路 `view.value.scriptFigures ?? entry.scriptFigures` 因此读到入库的 0，而不是落空回退到条目陈旧的加载期计数；渲染成功后提示与按钮保持消失。本修复之前入库的正文没有计数，仍会回退——重新渲染一次即永久愈合。

保真的诚实边界：快照是部件的默认状态（没有钉选/拖刷），带内部滚动条的面板呈现初始视口。提示旁的「阅读原文」链接仍是通往活部件的路。

## Alternatives considered

**把页面脚本装进沙箱 iframe（`sandbox="allow-scripts"` srcdoc）。** 能换来真交互，但任意站点的 JS 就此在我们 webview 的框架树里执行——reader 立身的"抓来的内容必须消毒"模型存在就是为了永不如此——而且图内文字同样够不到翻译/引用（iframe 文档互相隔离）。还给抓取体积翻倍（脚本得随行），换来的只是 reader 用不上的东西：一个能玩的 demo。
**给每个元素序列化计算样式，代替内联匹配规则。** 布局保真更多，但每元素数百条声明（数 MB 噪音），canvas 像素和悬停态依旧拿不到，还破坏 reader 样式白名单的假设。实测对 79 张静态图无必要——内联已经通过。
**所有图一刀切截屏，不止部件。** 整齐，但扔掉静态 SVG 图的可引性和缩放清晰度——引用是 reader 存在的意义，内联路线在那里恰是保真的赢面（[capture 笔记](2026-09-21-capture-rendered-fetch.md)记录过同一裁决，现在把它划到正确的适用范围）。
**按绝对定位后代比例判部件。** 探针数据显示 abs 多的静态复合图（Figure 13/14/18：30–80 个绝对定位后代、零监听器）经内联渲染完好；按位置的规则会把从没坏过的图也打成像素。行为（canvas/监听器）才命名真正的失败——DOM 带不动的内容——而不是布局。
**清条目上的计数来治僵尸提示，而不是把正文的零入库。** 条目计数是添加时关于 feed 载荷的事实；正文记录才是"盘上有什么"的权威。把正文的显式零入库，是在真正回答"打开"的这一层修读路径，而不是改写 feed 当时说过的话。

## Consequences

- 验收目标上 23 张部件全部以 2x 清晰图像到达（已验证：Figure 3 六联透镜读出、Figure 5 整个 token/表格/热力图/曲线集群），无 canvas 残留，5.7M 字符在 8M 帽内；其余 79 张图保住可引用的 DOM 路线。部件文字变成不可选像素——接受，因为替代品是叠成团的垃圾文本，且 alt 留有可检索残渣。
- 单次渲染增加截图循环开销（23 个部件 ≈ 数十秒，在约 2 分钟的总渲染内）；单部件失败只影响该部件留 DOM。
- 入库的零是持久记录语义：无计数的旧记录仍回退到条目计数（显示陈旧提示），重新渲染一次才愈。不做迁移——愈合用的就是特性自带的手势。
- 遗留：reader 内图片缩放（2x 光栅若有灯箱依旧清晰）；纯委托监听器部件（需要框架级信号）；`figure`/`d-figure` 容器之外的部件。

## Testing

`packages/capture`——77 测试本地全绿（本轮之前 66；同弧随带 +2 嵌套 CSS 内联用例）：jsdom 分类（canvas、探针标记监听器、嵌套取最外、隐藏/超大跳过、快照上限）、裁剪数学（页面坐标、文档夹取、图注排除、余量）、替换语义（图注保留、残余移除、失效 id 跳过）；假浏览器管线测试（被标部件 → 裁剪截图 → 替换参数；rect 消失 → 不截图仍干净渲染；配置关闭 → 无探针无截图）；真 Chrome 集成夹具新增 canvas+监听器部件，须以一张 WebP img 到达且图注留文本，静态图保持 DOM。集成套件同时带上 `--no-proxy-server`——有系统代理的机器上代理会自己回答夹具域名（HTTP 503，旧代码同样复现）。验收目标实弹（构建产物、真 Chrome）：23/23 部件快照、零 canvas 残留，两张用户报告的图均目视验证。

`packages/dsh-reader`——420 测试本地全绿（此前 419）：新 boot 测试钉住"显式零入库并返回，缺失保持缺失"；capture 通路客户端测试现在断言存库携带 `scriptFigures: 0`。
