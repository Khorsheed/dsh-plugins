# Agent Note: Room report gate — a decision model picks when a report is handed over

Status: implemented

## Problem

在一个真实房间里（邀请 Claude Code、Kimi、Codex 打招呼），每句招呼用户都看到 3 到 4 遍：成员自己的发言卡片；协调者 `sleep 45` 加 `room_read` 之后做的一张汇总表；然后每条回报各唤醒协调者一整轮，每轮再复述一遍表。每条回报都单独唤醒协调者，没有任何地方告诉它用户已经看过这些回复，也没有告诉它回报会自己送到。每个完成的任务还会多出一行「✓ kimi 完成了「…」—— 目标进度 3/3」，重复整段请求（进度数字在渲染时才算，所以每行都是 3/3）。

## Decision

**由一道门控决定回报「什么时候」交出去**（[report-gate.ts](../../../../packages/room/src/report-gate.ts)）；收到之后说什么、做什么仍由接收方自己决定。一个需要回报的投递结束时，先看规则——设置为 `each`、失败或结果不确定、最后一个未完成的结果、计划内的工作、或者没有可用的决策模型，都立刻交。否则询问可选的 `typesafe` 服务（按名字探测，room 不依赖它）一个是非题 `deliver_now`，状态里包含：用户的请求、接收方派活时附的说明（`room_message` / `room_invite` / 桥工具上的 `note`：「三位都打完招呼再一起跟用户说」）、用户上一条消息之后还没得到回应的时长、这一批的进度（完成数 / 总数 / 谁还在跑、跑了多久）以及已到达的结果。概率低于 0.5 则「攒着」。

**攒着的回报不会丢，也不会单独占一轮。** 它记为带 `held: true` 的 `room/dispatch` 和一条 `room/report-gate` 的 hold 结论，随接收方的下一轮一起送达：房间自己发起的提示词会把所有攒着的回报放在本轮正文前面，一次唤醒全部交出。不是房间发起的轮次——用户直接跟房间的 agent 或某个原生成员说话——则通过公开的 `agent/pre-step` 接缝在第一步前面附上攒着的回报。刻意「不」推进 agent 收件箱：宿主对 `next-turn` 收件箱里每条排队消息各开一轮，第一版（推进收件箱但不唤醒）在 3080 上把三条攒着的招呼变成了协调者的三轮。随轮次带上时记 `release`（原因 `carried`）；没有别的可交时——用户点「现在交给 dsh」（`releaseReports`）、3 分钟计时器到点、或重启之后（计时器在进程内；`recover` 在每次活跃访问时都会运行，所以只放出本进程没有计时器的那些）——派一个简短的轮次把它们带上。

**用约定减少重复。** 回报信封写明「这条回复用户已在房间里看到，不要复述」；简报告诉成员派完活就结束这一轮，不要 `sleep` / `room_read` 轮询，可以用 `note`，收到回报不要再做汇总；`room_message` / `room_invite` 的返回也这么说。由消息打开的看板任务不再显示完成行——成员的回复卡片就代表完成。

**呈现。** 成员发言改成会话条目：成员颜色头像加一张浅底卡片（头部：名字、公开职责、provider、时间；markdown 正文，沿用长回复折叠；淡色底栏：复制、会话入口、耗时、「→ 已汇报给 X」）。「协作设置」改用宿主的 `DisclosureRow`（整行可点，折叠时显示当前取值）、`SegmentedControl` 和 `Switch`，并新增「回报什么时候交给对方：决策模型判断 / 每条都交」（`room/settings.reportTiming`，默认 `judge`）。有回报被攒着时，房间里显示一行虚线框「📥 dsh 的收件箱里有 N 条回报…」，附模型给出的概率和「现在交给」按钮。

## Alternatives considered

**等这一轮的结果全部到齐再唤醒一次。** 负责人否决：串行工作（先实现、再交给审查）在第一个结果到达时就必须推进。协调者自己的 `note` 加决策模型替代任何固定规则；成员之间也可以直接接力。

**让决策模型同时决定回复程度（act / brief / silent）。** 负责人否决：下一步做什么是协调者的判断；门控只管交出的时机，信封要求不复述。

**`join` / `each` 派活参数。** 被自由文本 `note` 取代，表达同样的意图且更多。

**发言气泡。** 负责人选择浅底卡片：房间里多个 agent 轮流说话，卡片把每一轮区隔成块；气泡会挤压代码块和表格。

**回报并入正在跑的一轮。** 交给房间自己 agent 的回报不进该成员的派活队列；agent 正在跑一轮时，用 `agent.steer`（`next-step`）插进这一轮的下一步，而不是排成新的一轮。排在后面时，它会在 agent 已经回答之后再叫起第二轮——实测见于模型没守「不轮询」，自己读到回复先答了一次，回报到了又答一次。agent 空闲时仍各开一轮。

## Consequences

- profile 里没有配置 `typesafe` 的房间，在时机上与以前一样（每条回报都交），但仍有「不要复述」的信封和「不要轮询」的说明。
- 房间自己的 agent 的回复保持宿主的助手消息样式，只有成员发言是卡片。
- 测试覆盖：门控规则与模型结论、提前到达的结果被攒进协调者收件箱（判断状态里带派活说明和这一批的进度）并由最后一个结果放出、手动交出、高概率时立刻交出、收件箱行的折叠、隐藏的完成行、卡片化的发言，以及宿主组件的设置。
