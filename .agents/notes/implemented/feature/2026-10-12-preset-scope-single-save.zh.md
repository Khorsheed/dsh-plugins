# Agent Note: preset 范围编辑器只剩一个「保存」，受管根不再可见

Status: implemented

## 问题

[按 preset 限定的 skill](../../proposed/feature/2026-09-13-capability-catalog-preset-scoped-skills.md)的范围编辑器把投递机制漏进了用户流程：未受管的 skill 给的是「移入受管目录并可限定 preset」（收养），受管的给的是「保存」加「释放回用户技能目录」（释放）。三个以机制命名的按钮横在用户和该区唯一的问题之间——这个 skill 在哪些 preset 生效。尤其「释放」，不了解所有权规则就无法理解：受管 skill 的投递随插件消亡，而释放后的 skill 由宿主的文件系统 provider 投递、插件不在也活着。

## 决策

勾选框就是全部界面。空选 = 所有 preset；一个「保存」应用勾选，路由不可见：未受管 skill 勾了子集走收养，受管的改 scope 走重写，受管的被清空勾选走释放回用户技能根（空 scope 不需要代管投递）。收养/释放按钮及其文案删除；提示语写明「空选即处处可见」以及「全部取消并保存即还原为普通用户技能」。勾选未变时保存置灰——但受管的「空对空」状态保持可点，给历史上遗留的受管-未限定 skill 留一条释放路径。

## 考虑过的替代方案

**保留显式的释放动作。** 不采用：释放和「重新对所有 preset 生效」是同一个意图；为一次罕见过渡多一个按钮，等于强迫用户理解受管根的概念。

**加一个「所有 preset」哨兵 chip。** 不采用：空选已经表达了这个意思；哨兵是同一状态的第二种说法。

**未受管 skill 的勾选默认全选。** 不采用：全选读起来像「限定到当前存在的全部」，会把集合冻结在未来新增的 preset 之外；空选才是未限定的诚实状态。

## 影响

受管根不再出现在主流程里（「受管目录/释放」文案消失；投递被拒时冲突行仍会指出默认根）。一个已知边界：从项目根收养、后来又被清空的 skill，释放后落在用户根——释放目标从来只有用户根，单保存流程让这次搬家少了一次可见点击；提示语写明了还原行为。测试钉住 apply 的路由（收养/改 scope/释放/空选不写）以及两条一键保存流程的端到端行为。
