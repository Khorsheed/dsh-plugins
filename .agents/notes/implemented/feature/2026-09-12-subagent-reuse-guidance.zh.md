# Agent Note：模型可见引导——一次性 subagent 与命名 room 成员的分流

状态：已实现

[English](2026-09-12-subagent-reuse-guidance.md) | 中文

## 问题

模型在选择「一次性 `subagent_*` 委派」还是「邀请命名 room 成员」时没有任何信号。两条路径的差别恰好只在延续性：一次性 run 返回结果即消失；room 成员保有自己的 CLI 会话、跨轮累积上下文。需要与同一代理迭代的工作（review → 修复 → re-review）属于后者，但工具描述里只字未提——而成员的名字是它唯一的职能标记，同样没有任何地方鼓励职能式命名。

## 决策

两个工具都加引导，只改描述文本（无行为变化）：

- **`subagent_*`（local-agent-tool-subagent 的 `familyWording`）**：这是一次性路径；当预计要与同一代理多轮协作且 `room_invite` 可用时，改为邀请命名成员，按职能起名（`design-review`、`restart-test`），让后续轮次按职能寻址并复用累积的上下文。
- **`room_invite`（room 的 `tool.ts`）**：反向引导——成员持久存在并累积上下文，凡预计要与同一代理跟进的工作都优先邀请而非一次性 `subagent_*`；一次性委派留给自包含、无后续的任务。外加命名提示：职能式命名让人和其他成员一眼看出这个长期角色的用途。

分流写法遵守家族的独立性规则：subagent 工具只说「`room_invite` 可用时」——room 不在场什么都不变。

## 验证

`pnpm --filter @khorsheed/dsh-local-agent-tool-subagent build+test`（15）与 `--filter @khorsheed/dsh-room build+test`（195）全绿。没有测试快照描述文本。行为验证靠真实会话：给主 agent 一个迭代式任务，观察它是否改为邀请职能命名的成员而不是发一次性委派。

## 备选方案

**改默认——所有委派都走 room。** 否决：一次性任务占多数，邀请 + 每次派发的名册开销对它们是纯成本；且每成员会话单 in-flight 会把一次性调用本可并行的工作串行化（三路并行评审需要三个成员）。引导把选择权留在该在的地方。

**只在 `room_invite` 一侧写。** 否决：决策发生在模型伸手取委派工具的那一刻——也就是 subagent 的描述。只写一侧会让更常用的那条路径没有标记。

## 后果

- room 的 `tool.ts` 是共享地盘（M3'/M4' 拆分 2026-09-11 刚落地）：本次只加描述文本；room 负责人经本 note 知悉。
- 如果真实会话里模型仍然不走这个模式，下一个抓手是家族工具结果文本里附加的自我描述（fresh 委派结果尾部那段），而不是继续堆描述 prose。
