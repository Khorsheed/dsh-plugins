# Agent Note: Room tasks — work grouped by the human request that started it

Status: implemented

## Problem

房间记录了谁派了什么活（`from`、`replyTo`、`hop`），却没记录这些活是为了什么。团队视图只能按成员两两统计派活次数，回答不了「我的请求一共花了多久、时间花在了哪」这种跨多个 agent、多轮的问题。事后推断恰好在关键处失效：房间自己的 agent 直接回应人时，那一轮走的是宿主普通输入通道，不经过 room 的派活记录，它派出的活就追不回那条消息；有两个请求同时进行时，协调者某一轮可能同时带着两边的结果。

## Decision

**任务** = 一条引发了派活（至少有一次投递归属于它）的人类消息，加上这些活引发的一切。没有派活的闲聊不算任务。归属在派活写入时就记下，新日志不做事后推断：

- 每条 `room/dispatch` 记录 `task`（任务起点那条人类消息的 `user/message` id；没有消息的人类派活，例如邀请时的首个任务，用派活自己的 id）和 `parent`（发送者当时正在执行的那次投递，`<seq>:<memberId>`），成员的二次派活据此挂在它自己的活下面。
- 在房间轮次里的成员，派活沿用那一轮的任务。房间自己的 agent 直接回应人时，派活归到触发它这一轮的那条人类消息所属的任务（`trigger`）。
- 新的人类消息按以下顺序归属：输入框的标签（`setTaskHint`，或 `postMessage` 上的 `task`）——`human`；否则在有任务还没完成时，问决策模型（`typesafe`，在进行中的任务和「新任务」之间选择）——`model`，带置信度，协调者这一轮会读到一行【任务归属】说明；都没有则自成一个任务。归到别的任务时写一条 `room/task-link`（以最新一条为准）。
- 协调者可以用 `room_message` / 桥工具上的 `task` 覆盖（`"new"` 或 `room_read` 里的「任务 N」编号）；在人发起的那一轮里，这也会把那条人类消息改归（`by: coordinator`）。
- 回报和放出轮次沿用来源的任务。没有 `task` 的旧派活在回放时按因果推断：回报取来源的任务，其余取它之前最近一条人类消息所属的任务。
- `RoomState.jobs`（`replayJobs`）按新到旧列出任务：编号、标题（去掉开头的 @ 提及）、包含的消息及各自如何归属、状态（进行中 / 有投递结果不确定时为需要处理 / 已完成 / 已停止）、投递和成员。投递现在带上各环节的时间点（派出、开始、结束、攒着、交出）。
- `stopJob` 停止一个任务：运行中的投递经现有 `cancel` 停掉，排队中和攒着的不再执行，并记 `room/job-stopped`。

**任务页，以及它替代了什么。** 这取代了 [room_task 工具](2026-08-20-room-task-tool.zh.md) 和 [quest-bar 胶囊](2026-08-22-room-quest-bar-redesign.zh.md)。任务成为看房间里工作的唯一方式，于是重叠的界面被合并或下掉（负责人已同意）：

- 右侧栏「任务」页（kind `room-tasks`，参数 `task`）：顶部是房间目标（可编辑），按进行中 / 需要处理 / 已完成 / 全部筛选（已完成默认只显示最近 20 个），每个任务的详情包括：人说过的话及每条补充是怎么归进来的、停止整个任务（就地确认，列出会停掉哪些成员的工作）、需要人处理的事（结果不确定的投递就地核对、任务内等放行的消息）、任务的活属于某个正式目标时显示该目标、按每次投递的 `parent` 建出的子任务树（回报往回走，不算节点；运行中的子任务可以单独停）、以及成员泳道时间线（排队 / 等交出 / 执行三段）。
- 任务页不放输入框。「追问」和「＋ 新任务」在主输入框上放一个可删除的「任务 N」/「新任务」标签（任务页和输入框共用的客户端存储）；下一次发送把它作为 `postMessage` 的 `task` 带上。窗口较窄时任务页会关掉，让输入框露出来。
- 输入框上方收拢成一个任务胶囊（「● N 个任务进行中」，有不确定的投递或待放行的消息时多一个琥珀色「⚠ N 件需要处理」），点开就是任务页；全新的房间显示邀请胶囊。没有右侧栏时胶囊退化为原地的核对视图。
- 下掉的：任务板（`room/task-*` 写入、add/close/update 远程方法、看板胶囊、对话流里的「✓ 完成了」行）、`room_task` 工具（派活就是 `room_message`，自动归到某个任务）、单独的计划页和计划 / 后台 Agent 胶囊（`room_plan` 保留；计划显示在它所属的任务里，还没有任务接手时显示在列表下方），以及移除成员时转交待开始任务。旧日志里的 `room/task-*` 仍回放进 `RoomState.tasks`，只是没有界面再读它。

## Alternatives considered

**事后从日志推断任务（时间窗、hop 链）。** 不采用：房间自己的 agent 直接回应的轮次没有可追溯的 room 记录，并发请求又会交错。

**严格按因果（每条人类消息都是一个任务）。** 负责人否决：补充的一句（「顺便让 codex 也测一下」）会把同一件事拆成好几张卡片。由协调者判断，决策模型给建议；输入框的标签可以强制指定。

**用日志 seq 标识任务。** 不采用：房间自己的 agent 直接回应的轮次里，归属在 `agent/pre-step` 中判断，那时宿主还没写入这条人类消息，只知道它的 id。

## Consequences

- 有任务进行中时，每条人类消息多一次决策模型调用（上限 8 秒；没有 `typesafe` 时跳过）。
- 旧房间也能通过因果推断得到任务。
- 协调者在 room 派活之外自己开的原生子 agent 会话不再有房间界面（原来的后台 Agent 胶囊会列出它们）；它们仍在宿主自己的会话列表里。
- 测试覆盖：任务页（筛选、详情、就地停止、追问标签、单独停子任务、子任务树与时间分段）、任务胶囊与输入框标签，以及 @ 消息形成任务并并入 agent 随后的派活、决策模型归属的补充被协调者改为新任务、未知任务引用、输入框标签、成员二次派活挂在自己的投递下、停止任务，以及任务引用解析。
