# Agent Note: datasets — 整理那一轮直达「核对并登记」、评审页先出首屏、「添加题集」对话框改成表单

Status: implemented

## Problem

T90 之后，登记申请递交以后在「题集」tab 的提示条后面等人。整理会话递交完申请，人得自己切 tab、找到提示条、再打开审阅页。164 题的仓库上，审阅页要五六秒才出第一屏。周边还有两处小毛病。一是「返回题集列表」只是一行文字链接。二是「添加题集」对话框里，「新仓库位置」是一句话，后面跟着链接样式的「恢复默认位置」，看着像句子，不像一个字段。这个对话框看起来也比「新建实验」窄，但没人量过。

## Decision

### 入口：整理那一轮轮尾的卡片

一轮里的 `datasets_propose_registration` 调用递交了申请（非 `dryRun`，结果里有 `filed`），这一轮的轮尾就出现一张卡片，位置在收尾那段话下面、工具组外面。卡片写明是哪份申请，只有一个动作「核对并登记」。点一下，提案 id 先放进插件生命周期内的焦点通道（`createReviewFocus`），然后切到同一会话的「题集」tab。题集视图挂载时取走这个请求；已经挂着的话立刻取走。取到就直接打开这份申请的审阅页，中间不经过列表，也不经过提示条。已经处理过的申请，按钮换成描边的「查看」。

- **机制**：`src/client/review-turn.ts` 是一个结构化的 `uiConversation` 定义（`kind: 'datasets-proposed'`）。它把每个 `tool/call` 头和对应的追加型 `tool/result` 配成对，只留 `proposeCardOf` 判为 `filed` 的结果，作为这一轮的 Turn 数据发布出去。`ReviewTurnTail` 是 ui-chat 的 `conversation.chat.turnTail` 列表里的一项：它读这份数据，以这一轮的结束序号为界，每份申请渲染一张 `ReviewCard`。ui-schedule 的「已创建任务」卡走的是同一条路。申请调用自己那一行仍交给 ui-tool 的通用工具视图。
- **注册时机**：定义和列表项都在 `conversation.chat.turnTail` 的 inject 回调里注册。这个槽由 ui-chat 声明，而 ui-chat 组合了 ui-conversation，所以等到 `uiConversation` 一定存在时才去读它（`ctx.get`）。两者都是本包的可选 peer，运行时不 import。缺了它们就什么也不注册，申请照 T90 的样子在提示条后面等。
- **切 tab**：宿主没有切会话 tab 的公开调用，`openView` 只到外框和 tab 头。所以卡片在 `[data-conversation-tabs]` 下找文字等于题集 tab 自身标签的 `role="tab"` 按钮去点。这是带兜底的 DOM 锚点：找不到 tab 条，或者 150 ms 后 tab 仍未选中，卡片就用一句话告诉人去哪儿点。请求已经在通道里，人点过去照样直接打开审阅页。
- **skill 与工具定义**：收尾一句改成「点下面的按钮核对并登记」。

### 审阅页：申请时算好，先出页头

在临时 0.2.0-rc.2 实例上实测，用的是 164 题的 HumanEval 仓库，题集共 658 个文件：

| 各段（改前，每次打开） | 耗时 |
|---|---|
| 协议 validate（约 500 次 git 子进程） | 4.7–5.9 s |
| 快照（树 + 每个文件的分区） | 75–98 ms |
| 分支尖 + 工作区脏检查 | ~50 ms |
| 版本号与日期 | ~30 ms |
| mapping 核对 | ~3 ms |
| 原目录遍历 | 2–4 ms |
| **`proposalReview` 合计** | **4.9–6.1 s** |
| `reviewFiles` | 5.6 s（它也跑了一遍 validate） |

大头是 validate，而它的结果只取决于提交号。所以提案库现在按提交号缓存这些事实：validate 结论、错误数、版本号、日期。缓存放在内存里，同时原子写入 `<提案根>/cache/<commit>.json`。`propose` 本来就跑同一套检查，于是这笔开销挪到了申请时（约 5.3 s，落在 Agent 本来就在等的那次工具调用里），之后每次打开都命中缓存。validate 跑不起来时照常报告，但不写缓存。另外新增 `proposalHead`：只用存下来的申请和缓存回答页头与四张概况卡，不做快照。

| 改后 | 耗时 |
|---|---|
| `proposalHead` | 22 ms |
| `proposalReview`（命中缓存） | 45–54 ms；新进程 115 ms |
| `reviewFiles` | 46 ms |
| `reviewItem` | 80 ms（改前 98） |
| `propose` | 5.3 s（挪过来的开销） |

浏览器里实测，点「核对并登记」打开已缓存的申请：审阅页第一帧 67 ms，页头 124 ms，整页 190 ms。冷启动并删掉缓存文件后，页头 0.9 s，整页 23.7 s。这是兜底路径：新启动进程里的头几次 Remote 调用要重算 validate，所以它测的是缓存丢失的情况，不是常态。

页面分两步渲染。`ReviewSkeleton` 按加载完成后的页面列排版：返回按钮、标题、四张概况卡（`proposalHead` 一回来就填上）。下面是骨架条，分别落在对照的两栏网格、各层列表和登记名字段的位置上。完整审阅到达时页面不跳。

### 返回按钮

「返回题集列表」改成 primitives 的 `Button`（`size="sm"`、`variant="ghost"`），带左箭头图标。用 ghost 是因为它只是页标题旁的次要导航，不该和页面的主操作「确认登记」抢眼。`IconChevronLeftOutlineMedium` 是手工加进 `src/client/icons.tsx` 的，因为图标生成器坏了（见 Consequences）。

### 「添加题集」对话框

- **宽度**：两个对话框一样宽，都是 primitives Modal 的默认 `width: min(380px, 100%)`：1440 下 380 px，390 视口下 342 px，内容列 332 px。没有内容把它们撑开。改前实测「添加题集」380×739，「新建实验」380×482。差别在内部样式：它自带一套标签字重和间距，还有行内链接样式的恢复按钮，所以看上去像另一种、更挤的对话框。修的是内部样式，宽度没动。对话框现在用宿主表单对话框的节奏：行间距 12 px，标签 12/18 次要色，必填标记 11 px。
- **「新仓库位置」是字段**：有标签，有只读的单行路径框（`role="textbox"`、`aria-readonly`），右边是「更改…」。路径由 `splitPathTail` 拆成两段：前段可省略，末两级保持可见，效果就是中间省略。完整路径放在框的 `title` 上；框设了 `user-select: all`，点一下就全选，方便复制。
- **一列按钮**：「选择目录…」（数据在哪）、「更改…」，以及更改后出现的「恢复默认」，都是描边 `sm` 按钮，同在一列 88 px 宽的按钮列里。1440 下三者都在 798–886 px，88×28。「恢复默认」放在路径框下面的说明行，是一眼就能看出可点的次要按钮，和邻居一样大。选过目录后，说明行写「放在你选的目录下。」。git 说明也缩短了。

## Alternatives considered

**卡片留在工具行（`tool.call.toolview`）。** 第一版就是这么做的。真机上，一轮结束后宿主把工具调用折叠成一组「已完成，用时 1 秒」，卡片所在的流项高 0 px。收尾那句话说「点下面的按钮」的时候，按钮恰好被藏起来了。轮尾才是宿主给 Turn 级产物的正规位置。两处都留的话，一轮运行时卡片会出现两次，所以工具行交还给通用视图。

**申请一递交就自动切到审阅页。** 人可能还在读收尾的话，自动切走会把人拽出对话；如果是人没在看的会话，还会打开一个他没要的审阅页。点一下，主动权留在人手里。

**用公开的切 tab API。** 0.2.0 没有。长远的正解是向上游要一个，在那之前按约定用 DOM 锚点兜底。锚点失效时，人只是多点一下，插件不会崩。

**加速 validate 而不是缓存。** validate 的开销大致是每个文件一次 git 子进程。改成 `git cat-file --batch` 对所有调用方都有好处，但那要动协议检查器的内部，不在本任务范围。而且同一提交的结论永远不变，缓存既正确又快得多。

**把添加对话框放宽，去对齐更宽的宿主对话框。** 两个对话框都不比对方宽，都是 Modal 默认值。只放宽这一个，反倒会制造出原本想消除的差异。

**仓库路径用可编辑输入框。** 可编辑就会有人手敲路径，而选目录的流程不校验手敲的路径。只读框加「更改…」，改位置只有一条路。

## Consequences

- 点卡片直达审阅页。已缓存的申请约 0.1–0.2 s 出第一屏，改前是 5–6 s。开销落在 `datasets_propose_registration` 里，Agent 本来就在等那一步。
- 入口依赖三个宿主面：ui-chat 的 `conversation.chat.turnTail`、`uiConversation.events`、tab 条的 DOM。前两个缺了就没有卡片；第三个失效时，卡片用一句话告诉人去哪儿点。
- 卡片上的「1 条提醒」数的是申请的 mapping 提醒；审阅页「校验」卡数的是 validate 提醒，测试仓库上是 2 条。两个数都对，但读起来像一回事。措辞对齐交给审阅页文案的负责人。
- 390 宽下，路径框保留的末段本身也可能被截断。完整路径仍在 `title` 里，也可以复制。
- `scripts/sync-icon-artwork.mts --check` 对每个 harness 检出都在 `IconQueueOutlineArtwork` 处失败，所以左箭头图标是手工加的。下次同步图标之前，生成器要先修好。
- 临时实例验证时用了两个测试替身。一个是监听回环端口的桩模型，由它发出 Agent 的工具调用；执行这些调用的是真的 `datasets_propose_registration`，渲染结果的也是真的轮次、定义、卡片和审阅页。另一个是 `PATH` 上的假 `osascript`，替代 macOS 的选目录框。早期有一次无头点击「更改…」时假程序还没装上，调起了真的选目录框；事后核对，没有残留的 osascript 进程。
