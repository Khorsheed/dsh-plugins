# Agent Note: 保存的链接一个都不丢 —— 仅链接预览、如实的原因分类，以及一个找得到的列表

Status: implemented

## Problem

读者往灵感空间里加了两条链接，得到两种不同的失败，它们一起暴露了一条错规则和五个缺口：

| 读者的动作 | 结果 |
| --- | --- |
| 粘了一条 OpenReview 的 PDF 链接 | 卡片出现了，但点开显示的是反爬页，不是论文 |
| 粘了一条机构代理的论文链接（`…ezproxy.obspm.fr/html/…`） | 「抓取失败」——而且**什么都没存下来** |
| 想删掉第一条 | 详情页没有删除入口，唯一的路是订阅管理页 |

第一条的证据在落盘状态里：那条源的 URL 变成了 `https://openreview.net/challenge?redirect=%2Fpdf%3Fid%3D…`，payload 是一块 4,783 字符的挑战页。OpenReview 对非浏览器请求回的是反爬挑战（`302 → /challenge…`，然后 **200**），而 `classifyPayload` 正确地把它判成「网页」——于是挑战页被当成正文存了下来。直接实测同一条地址是 403。所以**只看状态码判不出来**，这也正是「把 401/403 当拒绝」那版修法从一开始就不够的原因。

第二条下面压着一个代码缺陷。宿主出网缝拒绝跨源跳转时会抛 `WEB_REDIRECT_BLOCKED`，`ReaderService` 本该接住它、为新一跳重新进缝。但它是**在错误消息里**找这个代码（`/WEB_REDIRECT_BLOCKED/i.test(errorMessage(error))`），而宿主把代码放在 `error.code`、消息里从来没有它（`WebError extends HarnessError`，`errorMessage` 只返回 `error.message`）。于是跟随逻辑是**没有测试的死代码**，每一次跨源跳转——这个代理、普通短链、任何换域名的 feed——都直接把宿主缝的原话甩给用户。README 里写的「本插件自己最多跟 3 跳」和实际发布的代码不一致。

同一个「要么成功带正文、要么失败」的规则还带出三个缺口：

- 读不到正文的链接没有办法成为一张卡。`addSource` 返回一个拒绝，URL 就没了——这正是读者特意保存了东西之后最不该得到的结果，而对「移动端投递」这条成长路线是致命的。
- 没有正文，墙根本看不到这条链接：`load()` 只为 `hasBody` 的源取 payload，所以只链接的源不会产生已解析条目、也就没有卡片。
- 时间排序里没有 `publishedAt` 的条目按 `0` 计，于是刚保存的链接排在「最新在前」的**最底部**；与此同时，只链接的源既没有发布日期也没有正文，也没有任何「按类型」的收窄能看到它。

## Decision

**读者粘进来的 URL 一律保存；变化的只是「能不能预览」以及「为什么不能」。**

- **新增的判定携带原因，而不是变成一次拒绝。** `addSource` 现在只拒绝 `invalid-url` 和 `duplicate`，其余情况都写入一条 `link` 源并返回 `{ outcome: 'saved-link', failure: { code, message } }`。弹窗的判定从「抓取失败」（对这条 URL 说不出任何东西）改成「已保存，以及为什么没有预览」。
- **七个失败代码，其中只有一个可重试。** `ReaderPreviewFailureCode` 是 `blocked | login | unsupported-type | redirected | empty | unreachable | http`；`isRetryablePreviewFailure` 只放行 `unreachable`，`listBackfillCandidates` 会跳过记录成不可重试的保存链接——反爬、登录墙、PDF 和 404 永远给同一个答案，按定时器重试它们就是「记仇的爬虫」。订阅管理页那一行的「刷新」仍可手动重试，成功后清掉记录（`withoutFailure`）。
- **宿主在存储之前先给 payload 分类。** `inspectPreview(raw, finalUrl, requestedUrl)` 统计可见文本（剥掉 script/style/标签）——少于 200 字符时再去找反爬或登录页留下的痕迹词、以及主机是否变了。命中任一条就**不把 payload 存成正文**：卡片变成「仅链接」。这条规则让挑战页永远成不了文章，而且它刻意粗糙：宿主没有 DOM，但**一页真有正文时永远不会被二次怀疑**。
- **只有能还原的跨源跳转才会被跟随。** `crossOriginRetarget(error, current)` 读 `error.code`、解析拒绝消息里点名的 origin，**只在主机不变时**返回「新 origin + 原路径与查询」（即 `http://host/feed` → `https://host/feed` 这种升级）。换主机的跳转如实上报。拒绝消息只给目标 ORIGIN，跟着它去抓根路径拿到的是另一个页面，然后还会被当成读者粘的那个地址存下来。
- **原因刻意记两处。** 源上记 `failure`（墙要标记卡片、补齐要判断能不能重试），条目的 annotation 上也记一份，key 是 `linkEntryId(sourceId)`——一个新的共享 helper，因为保存链接的条目 id 以前是浏览器半里手写的魔法字符串。第二份记录正是让 `getEntryBody`（详情页唯一那次调用）能自解释、而不是回一篇空白的原因。
- **墙上看得到链接。** `load()` 现在为每条带正文的源**以及每一个 `link` 源**都取一次 payload，所以只链接的源会产出卡片，卡上有一个「仅链接」徽章，悬停给出分类后的原因。订阅源的条目没有这个徽章：feed 缺正文是补齐的活儿，而且补到了会另有一个标记。
- **详情页说清原因，并给出出路。** 有代码时句子来自代码（`preview.*` 文案），不来自宿主缝的消息；消息留着做诊断。这一行永远带「阅读原文」。
- **保存的链接就在读者所在的地方删。** 详情工具条多了一个垃圾桶按钮，只对 `link` 源出现；卡片右键菜单同款。订阅源的条目刻意两者都没有：下次刷新它还会回来，一个会自我撤销的「删除」是假承诺。
- **保存的链接按「源加入的时间」参与排序。** `ReaderSourceSummary` 增加了一个必填的 `addedAt`；行上带着它，条目的 `publishedAt` 缺席时 `timeOf` 回落到它。刚加的那条在「最新在前」的最上面，而不是最底下。
- **两处都能按类型收窄。** `kindQuery('rss'|'link')` 把 `#rss` / `#link` 写进搜索框——和 `#源id`、`@标签id` 同一套本地谓词（D14），不花请求、看得见也能清掉。订阅管理页有自己的类型筛选（带条数）和排序（按添加时间 / 名称 / 按抓取时间，默认添加时间倒序），因为删除动作在那里，而那个页面混着两种不同的东西。

## Alternatives considered

**保持「失败就拒绝」，URL 不存。** 这是以前发布的版本，也正是读者的报告否掉的那个选项：加不进去、链接没了，既没有卡片可删、可打标签，也不能以后打开。存下来只是 `state.json` 里多一行；丢掉 URL 丢的是读者请插件保管的东西。

**把挑战页（或 PDF 字节）照存，让浏览器提取器去失败。** payload 存在，`hasBody` 就是 true，墙看上去更完整。但代价是卡片的正文就是一块反爬页——正是报告里那个症状（「加进去了，点开没有可读内容」）。不采纳：一个不是文章的正文，比诚实地承认没有正文更坏。

**跨源跳转一律照跟，路径靠猜。** 拒绝消息只带目标 origin，路径不可知。保留当前路径（`origin + pathname + search`）对 scheme/端口升级是对的，对真正换站的跳转是错的——那会抓回一个通常不是文章的页面并当成源存下。不采纳，改为如实上报这次移动；宿主缝自己的消息也正是这么建议的（"retry against that URL directly"）。

**也给订阅源的条目一个删除（或做一个隐藏墓碑）。** feed 里的条目删不掉——feed 会重新发布它——所以诚实的动词是「隐藏」，那需要一个新的持久化 annotation 字段和客户端过滤。推迟：这是另一个功能、另一个词，而这次报告要的是单条 URL。

**类型收窄只加在订阅管理页。** 不采纳：墙才是读者第一眼看的地方，而「我刚加的那条链接在哪」是在那里问的。墙上的收窄复用了已经存在的本地谓词，代价只是弹层里多三行。

**保留 README 的旧说法，只修代码。** 「最多跟 3 跳」描述的是一段从未运行、而且对换主机不可能忠实实现的行为。README 现在写的是代码实际做的事。

## Consequences

- 读者的 URL 在任何失败形态下都活得下来，卡片会说清是哪一种。三种真实原因把读者指向不同动作（自己去浏览器打开 / 去别处登录 / 那根本不是网页），这也是词汇表是七个代码而不是一个「不可用」的原因。
- 永久性拒绝不再产生自动请求。一条躲在反爬后面的链接，在读者手动刷新之前只花掉一次请求。
- **wire 形状有变化**：`ReaderSourceSummary.addedAt` 现在必填。两半在同一个包里发布，没有版本错配要管；但读旧宿主的客户端会拿到 `undefined`——排序和管理页的筛选片都用 `?? ''` 兜住，退化成「时间未知、排最后」，而不是抛错。
- **两个选择词被占用**：`#rss` 与 `#link`。源 id 是 `${kind}-${hash}`，都不可能撞上；一份手写的、id 真的叫 `link` 的文档会被遮蔽，但这不是本包会产出的形状。
- 预览启发式可能把一页真的极短、同主机、也不带任何痕迹词的页面降级成「仅链接」：payload 不存，详情页给原文。这是接受了的代价——这种页面在阅读器里本来没有可读的东西——阈值是一个导出的常量。
- 从永久失败里出来是手工的，这是刻意的：自动重试要么敲站点、要么需要在补齐里再长一套「就是再试一次」的策略，而那个按钮已经归订阅管理页所有。
- 失败词汇表是持久的（`state.json`），而 `normalizeStateDoc` 会丢掉不认识的代码而不是信任它：新宿主加一个代码时，旧客户端退化成「没有分类原因」，而不是渲染出一个缺句子的空档。
- 订阅源的条目仍然不能从墙上删掉，墙上的类型收窄是会话状态（活在搜索框里），不是持久化偏好。

## Testing

`packages/dsh-reader` 现在跑 195 个测试，其中 20 个是这次新增的：

- `host-pure.spec.ts`：`classifyFetchFailure` 覆盖每一种失败，包括那条回归——带 `WEB_REDIRECT_BLOCKED` **代码**、目标是登录主机的算 `login`，目标是普通主机的算 `redirected`；`crossOriginRetarget` 跟随同主机的 scheme 升级、拒绝换主机，并且不对「只有消息里像」的值动作；`inspectPreview` 不碰真有正文的页面，同时认得 200 的反爬页、登录中间页、极短页面和跨主机的空跳。
- `boot.spec.ts`：OpenReview 形状的挑战页既不作为 payload 存储、也不进入补齐候选，而条目级的详情回答带着原因；一次暂时失败之后的手动刷新会清掉记录；没有 `web` 的组合仍然保住 URL 并给它分类；404 保住链接并记成 `http`；普通网页照旧带正文保存。
- `selectors.spec.ts`：`#link` / `#rss` 按类型收窄，而 `#源id` 仍按源收窄；没有日期的保存链接在两个排序方向上都按源的 `addedAt` 定位。
- `ReaderPane.client.spec.tsx`：「仅链接」徽章带分类原因、并且跟随代码（登录墙不会被叫成反爬）；保存的链接有删除、订阅源的条目没有；新增判定汇报「已保存、无预览」并给出原因、同时清空输入框；订阅管理页按到达顺序排序、按类型收窄；以及一条 payload 什么也没提取出来的保存链接，点开时会自解释，而不是只渲染一个标题配空白。
