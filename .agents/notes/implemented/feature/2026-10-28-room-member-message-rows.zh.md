# Agent Note：房间里显示成员之间互发的消息，以及每条回复在回应什么

Status: implemented

## 问题

协调者是外部成员时（例如由 Codex 成员担任的游戏策划大师），聊天流里只看得到各人的回复。协调者派给人物建模师的活、成员之间的告知，都只记在日志和任务页里，聊天记录里没有。所以协调者的回复读起来像自言自语，成员的回复上也看不出它在回应哪条派活或哪份汇报。

## 决定

- **成员消息行（`room-dispatch`）**：来源（origin）为 `coordinator` 或 `member` 的 `room/dispatch`，每条在聊天流里显示为一行：`↪ 游戏策划大师 派活给 人物建模师：…`（告知类显示为「告知」，颜色更淡），点开看全文。收件人还没接手时标「排队中」（暂存、已取消、没送达同理）。状态在渲染时从房间状态读取，所以 Definition 只认领 dispatch 事件本身。以下几类不认领：
  - 用户自己发的消息（走官方的用户消息节点）；
  - 汇报（回复上的「已汇报给」和判断行已经表达了）；
  - 跨会话求助和旧版转发（各有各的行）；
  - 原生主 agent 发的消息。它的工具调用本来就显示在聊天里。主 agent 加入时没有 id，它发的消息带 `legacy:<seq>` 身份，靠这一点区分。
- **回复上的来由行**：回复的 run id 就是这次投递（delivery）的 id，所以 `speechCause`（client/speech-cause.ts）读这条投递来判断来由：
  - 成员发来的 → 「回应 X 的派活：…」或「回应 X 的告知：…」；
  - 汇报 → 「回应 X 的汇报」；
  - 把攒着的汇报一起交过来的那一轮 → 列出这些汇报的发送人。
  
  点击会滚动到来源那一行并闪一下：成员消息行，或汇报人的那条回复（回复现在带 `data-room-run` 属性）。用户发起的轮次和求助轮次不显示来由行。为此 `RoomDelivery` 新增了 `reportFor` 和 `releases` 两个字段。

## 考虑过的其他方案

- **把告知折叠成一个计数。** 同一来回的几行在聊天记录里并不相邻，计数没有合适的位置可放；显示成颜色更淡的一行，占的地方也差不多。
- **在 Definition 里认领 `room/delivery-state` 的更新事件。** Definition 的 match 一次只看到一个事件，分不出来源，结果用户发起的每次投递都会产生一个没有 start 的孤儿 Context。

## 影响

外部成员当协调者的房间现在能顺着读下来：谁让谁做了什么，每条回复在回应什么。原生 dsh 当协调者的房间和以前一样，只是成员的回复上多了来由行。如果来源那一行还没被聊天渲染出来（在很靠上的位置），点击不会有反应。

## 测试

`room` 的节点测试覆盖了：Definition 认领哪些 dispatch；成员消息行（名字、「排队中」、点开看全文）；以及 `speechCause` 在成员派活、汇报、原生 agent 派活（没有滚动目标）、把攒着的汇报交过来的轮次、用户发起的轮次这几种情况下的结果。
