# Agent Note: any working change can be published from the panel; versions say who published

Status: implemented

## Problem

2026-10-24，游戏会话里的一个 Claude Code 成员改了七个文件，跑了自己的预览就停下了。它的交接文档写着「发布归 dsh 那一侧」。成员手里没有 `game_publish`，用户又是直接跟成员说话，没有任何 dsh 回合结束，所以对话里说做完了，试玩区却还停在旧版本。同一天早些时候，dsh agent 自己也在没发版的情况下就追问了用户。面板上的提交条帮不上忙，因为它只列面板里的修改。

## Decision

- **提示条覆盖所有来源。** `changes` Remote 把工作目录里的游戏文件和待确认的候选版本快照比较，没有候选就和线上版本比较。修改时间比那个版本的记录早不到一分钟或更晚的文件，逐字节比对。结果包括：新增、改动、删除的文件，最近一次改动的时间，其中的面板修改，以及「上次检查在最新改动之后跑过并失败」时的问题清单。页面可见时，提示条每 8 秒查一次，成员在回合之外写的文件就是这样被发现的。它显示「有新改动还没进游戏 · N 个文件 · 最近一次 …」（还没有版本时显示「还没有可玩版本」），可以展开文件列表，按钮是「检查并发版」。这个按钮就是原来的提交：同一套检查，不设修复上限，和面板修改合成一条提示。
- **有人还在写时禁用。** 绑定这个项目的会话有回合正在跑时，`busy` 为 `turn`（回合钩子会报告 `turn/start` 和 `turn/end`）；文件在 20 秒内刚变过时为 `recent`，因为 CLI 成员给不出别的信号。此时按钮禁用，提示条写明原因。回合结束时本来就会检查；最近在写的人停下来后，提示条会再查一次。文件静下来后不会自动发版，否则会有大量空跑。
- **版本记录谁发布的。** `VersionRecord.by` 取 `user`（检查并发版、定稿）、`agent`（`game_publish`）或 `turn`（回合结束时的检查）。版本时间线逐行带标签，`game_read` 写成「v3（用户发布，用户认可过的版本）」。旧版本没有标签。标签只说明是谁按下了发布，不代表文件是谁写的；改了什么由说明和文件对比来交代。
- **先发版，再汇报。** 技能、模式引导段和两份人设现在都写明：只要改了能玩的东西，汇报或追问之前就主动 `game_publish`，不用等用户开口。发版没有风险：自动上线关着时只会生成候选，检查没通过就不出版本。CLI 成员汇报改完后，由 dsh agent 替它发版；写给成员的交接里说「告诉我，我来发版」。

## Alternatives considered

**agent 还在写时给一个次要的「仍然现在检查」按钮。** 最初画的是这个。用户更倾向于禁用：写到一半的构建多半过不了检查，而回合结束时本来就会检查。

**文件静下来后自动发版。** 这样不用点就能接住成员做完的工作，但每次写作停顿都会触发一次浏览器检查。等提示条确实不够用了再说。

**两条提示（面板修改一条、文件改动一条）。** 两者最后走的是同一套检查、生成同一个版本；分成两条，用户反而要琢磨该点哪一个。

**识别每个文件的作者。** 插件看不到 agent、CLI 成员和用户自己的编辑器各写了什么。它只记谁发布，改了什么由说明和对比来交代。

## Consequences

- 页面可见时，面板每 8 秒对项目做一次文件状态扫描，再加上对最近改过的文件逐字节比对。
- 试玩区里既有用户发布的版本，也有 agent 发布的版本，时间线上两者交错，靠标签区分。
- CLI 成员该不该拿到模式工具（从而能自己发版），由 room / local-agent 负责人决定；这次改动不依赖它。
- 交互稿：`proposals/prototypes/game-publish-bar.html`。实际上线的「检查中」状态只用文字列出三个阶段，没有实时进度。
