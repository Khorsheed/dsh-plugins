## 目标

让一个人和一个 agent 能顺着一条线把实验做完：**提问 → 起草方案 → 就绪 → 运行 → 看作答 → 人工评估 → 结论**。每一步都在同一个地方看得到状态，都知道下一步该做什么。结论页给出的数字，要和它的证据强度相符。

四条硬口径（讨论中已定）：

1. **会话不绑定题库。** 题库按仓库登记一次，版本由实验钉住（repo@commit）。一个会话可以跑多个实验、用多个题库。
2. **「请人选择」一律用宿主的 `ask_user_question`。** 不另做卡片 UI。
3. **沿用 T67 的四阶段**（实验设计 / 运行记录 / 结果对比 / 人工评估），只在里面做增量，不重做外壳。
4. **只有「启动」有阻塞项。** 启动之后没有任何一步拦路：数据问题由计算口径自动降级，人的判断写成标记跟着结果走。

### 1. D7 结论校准（eval · `report.ts`，最先做）

价值最高、改动最小。两处口径修正都**只降级，不拦路**。

- **判定来源按类别比。** 判定分两类：「判过」（判官初判或人终评，同属一类）和「只有脚本」。每条判据在这一对的各格里要么都判过，要么都只有脚本；不齐就只做描述：不给 Δ 和置信区间，`rankReason` 写明原因。
  - 这样人只改了一条判据的终评不会被误判为不一致。要防的是「一侧有判官、另一侧只剩脚本」。
  - 判官采样全部报错的格标「判官缺席」。它在人工评估里显示为提示，并附一个可选的「补判」，不是阻塞项。
- **置信区间按题数算。** 有差值的题不足 3 道就不算区间，`ci = null`。现在 1 道题也照算，于是出现 `[4, 4]`。
  - 例：1 题 × 1 次不给区间；14 题 × 1 次给区间。这时区间的含义是「换一批同类题，结论稳不稳」。
  - 排名门槛不变（`report.ts:1757` 的 n 是每题最少配对次数，≥ 3 才排名）。给了区间但没达排名条件时，页面标「仅供参考，未达排名条件（每题需跑满 3 次）」。
  - 取这个口径的原因：每题只跑 1 次的实验很常见（用户 2026-09-23 确认），按「每题次数」算的话这类实验永远看不到区间。
- `ReportPage` 在 `ci === null` 时不渲染区间，写「只有 k 道题有差值，给不出区间」。
- 结果对比加第五条有效性校验 **「判定覆盖一致」**：每条判据在比较的各格里要么都被判过（人终评与判官初判同属「已判」），要么都没有；一侧只剩脚本、或判官采样全部报错（判官缺席），即不通过，这一对降级为描述。前四条不过仍是整个比较节不下发。

### 2. D8 实验列表（eval）

- 默认只看「本会话发起」，读 run 的 `originSession`，会话本身不存任何东西。可切到「全部」。
  - 命令行发起的 run 没有 `originSession`，默认视图看不到。所以页首给一句「另有 n 个不属于本会话」。
- 按「需要你处理 / 运行中 / 已完成 / 已归档」分组。归档只是隐藏，不动账本。
- **僵尸行用推导修，不写账本。** 账本归 mission，eval 的状态一直是推导出来的（T35a 定的边界）。
  - 推导条件：本进程没有活 job，**并且**格子一段时间没有任何进展，就推导为「停滞」，给「重跑」。
  - 只看第一条不够：命令行或别的进程发起的 run，在本进程里本来就没有 job。
  - 原来设想的「卡住」和「中断」合成这一个态。

### 3. 结论先行 + 人工评估出口 + 就绪清单（eval client + 服务端收尾动词，都在四阶段里）

- **结果对比**：页面顺序是「结论卡（回答方案里写的问题）→ 判据 → 效率 → 审计（折叠）」。Close out / Export 挪到结论卡下。校验文案改成人话，内部字段名只在审计折叠里出现。
- **人工评估：可做可不做（D9）。** 页首的判官缺席只是提示，附可选的补判。页底四个出口：
  - **提交终评**：结论标「来源：人终评」。
  - **带标记提交**：人觉得评得有问题，但让结果往下走；写一句理由，结论卡顶部原样显示，也写进导出。
  - **不做终评，直接收尾**：结论标「来源：判官初判，未经人工确认」。
  - **放弃终评**：人认为本轮评估不成立。实验收成终态「评估不成立」，只保留原始数据和理由，不给结论。它和归档、删除是两回事，也写进导出。
  - 「已完成」只在人点了前三个出口之一后出现，实验不会自己变成已完成。结果对比在「评估中」也随时能看。
  - 人终评仍然只能由人做（R1）。
  - **实现形状**（T70 定死）：四个出口是 eval 的 run 级注解，做法同 T60 的导出注解；不加 mission 状态，不改账本状态机。ns 与字段在 T72 文案里定。
- **实验设计 · 就绪段**：把现有的 validate / environment 结果重排成两组：「阻塞项」（主按钮就是解决它）和「提醒」（不影响启动，附带「让 agent 处理」）。「让 agent 处理」只是在输入框预填引用，不自动发送。全部就绪后主按钮变成「批准并启动」，只有人能点。已完成的实验这一段只读，读实验钉住的快照。

### 4. D1 + D2 会话去绑定、按仓库登记（datasets · datasets-tool · eval-tool · eval · preset 提示词）

跨四个包，**先出实施计划，评审后再动手**。

- **实施计划第一题：agent 往哪写。** 去绑定之后 `eval_plan_draft` 和 `eval_repo_write` 没有了写入目标。题库仓库是多 agent 共享检出，HEAD 不能动。两条路：
  - **(a)** eval 按实验开分支和 worktree（`exp/<id>`），plan / analysis 写在里面，人合并。改动小，协议不动。
  - **(b)** 实验成为部署级对象：plan / conditions / analysis 存在 eval 自己的状态目录，只引用 repo@commit；题库仓库只读，取题用 `git show` / `git archive`，不开 worktree。
  - 倾向 (b)：它和「会话不绑定、实验是主对象」同一个方向，T68 那类「plan 指向旧检出」的问题也随之消失。代价要写进计划：
    - run 与 plan 今天按「解析路径或 planSha」配对（T35a），要跟着改。
    - 已有 plan 要迁移，或者兼容读取。
    - 分析初稿要不要、怎么回到仓库，需要单独一步显式的「发布」。
    - 这是协议改动，比 rev13 大。
  - 两条路都要重写 G16 白名单，并一起定 `datasets_put_item` 的写目标。ui-spec 在定之前写「待 T73 实施计划定」。

- **登记单位是仓库**，worktree 不单独登记。登记表单复用数据集协议提案的「绑定确认流」，默认只勾 modelFacing 层。
- **去掉输入框上的题库 chip**（datasets 的 composer chip）。会话里也不放实验 chip，见任务 7。
- **plan 记录 repo@commit**，运行时 eval 按 commit 取题。已有实验一律读自己的快照，不读任何「当前绑定」。
- **可见层是题集属性，只管规划 / 分析 agent 能读到哪几层。** 默认只看题面，只有人能改。选手那边的隔离继续由容器挂载与 scope 负责（ui-spec R3），两件事不混。
- **agent 的选择规则**（写进 preset 提示词，工具侧兜底）：
  - 先定仓库：人在话里点名了 / 当前实验已经钉了仓库 / 登记的仓库里只有一个含这些题。
  - 再定版本：缺省是最新。只有和相关实验钉的版本不一致、会影响对比时才追问。
  - 定不下来就用 `ask_user_question` 问人，并停下等待。
  - 工具在候选不唯一时返回错误，未登记的仓库直接拒绝，错误里提示用 `ask_user_question`。
- **待定细节**：datasets 是通用存储，非 eval 场景要不要保留一个可选的「会话收窄」？实施计划里给出结论。
- **验证**：上线前跑一轮 pilot，确认 agent 真的会停下来问人，而不是继续硬绕。

### 5. D5 方案字段 rev13 + 数字就地编辑（eval · eval-tool）

- plan 协议 v1-rev12 → rev13，新增三个字段：「要回答的问题 / 预期 / 怎么算回答了」。旧 plan 缺这三项时，实验设计里不显示这一块。结果对比的结论卡原样回答「问题」。

### 6. D6 作答并排视图 · 一期（eval 服务端 Remote + client）

- 按题并排，两组的同一部分对齐排列。可以从运行记录、人工评估、结果对比任意一处进入，只按「题 × 组 × 次」定位，不向人展示路径。
- **一期两个视角**：
  - 「提交的报告」：stage*.md 按 markdown 渲染，判官引用过的段落就地挂上判定证据。
  - 「判定证据」：逐条判据的判定和理由，以及脚本输出。
  - 「过程」链到 T69 已有的子会话视图。
- **盲评开关**：打开后组名换成 A / B。人工评估复用同一个视图，不另做一套。
- 读取沿用 cell-artifact 的三条规则：只读本格、只读文本、超过 256KB 截断并说明。作答仍存在 attempt 的 `archive/workspace/`，随 bundle 导出，存放位置不变。
- **二期**：「代码改动」diff。需要钉住的 commit 加 `populate-manifest` 算出初始工作区，在 eval 服务端计算后经 Remote 下发。

## 验收标准

每个任务用 `pilot-d-preset` 或同形实验验收，并按 ui-spec §九 的视觉基线自查。合入前由交互稿作者对照三样看：ui-spec 对应那行、交互稿对应场景、下面点名的单测，结论回给协调者；合并归协调者。

**体验参照线**（用户 2026-09-23 定）：不满在内容、旅程和设计感，不在外壳。前端验收以交互稿 v5 为参照：逐场景看结论先行、每页一个主动作、人话文案、状态词一致、层次清楚；只能用宿主 tokens，按「同等层次」判，不要求像素一致；依赖宿主能力的待证项（tab 标签重绘、S18）按退路走，不算不过。截图在收口时统一截一次（明暗两套 + 400px 宽），在交互稿作者自己起的临时实例上截，不用 3171、不经手 token。

- **放弃**：

  - 重做实验详情外壳（T67 四阶段已经够用）。

- **风险**：
  - **D1 的写入模型如果选 (b)，是协议级改动**，工作量明显大于其余任务，可能拖慢 M4。可以先做 (a) 作为过渡，但要在计划里写明 (a) 是否会被 (b) 取代，别留两套。
  - **置信区间按题数算**时，区间反映的是题目之间的波动，不含同一道题多次运行的波动。页面上「仅供参考，未达排名条件」这句话要保留，防止被读成已分出胜负。

  - **rev13 是协议修订**，要按协议流程走，旧 plan 必须能照常读。
  - **事件回流可能长期拿不到宿主 API。** 退路（实验 tab 计数 + 列表 + `eval_run_status`）要做到本身就够用，而不是临时凑合。
