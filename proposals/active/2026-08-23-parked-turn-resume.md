# ankh-guard:等待用户输入的回合不应被重启自动续跑(parked-turn-resume)

- **分类**：plugin
- **状态**：planned
- **最后更新**：2026-08-23
- **查重结果**：已搜 `proposals/active/`、`proposals/closed/`、`.agents/notes/`（含 archived)。命中均为背景而非同一意图：ankh-guard 的 resume 机制历史 notes(`2026-08-20-review-sweep-guard-fixes` 等）确立了"中断会话自动续跑"的现状语义，本提案是它的边界修正而非重复；`2026-08-22-restart-lock-unify` 是并发互斥，无关。无重复，新建。
- **官方依赖**：取决于 M1 可行性核实的结论——同进程能查到提问/审批的 pending 状态则纯插件；查不到则需上游契约扩展（上游候选，届时登记进 `docs/upstream-seam-registry.md`)。

## 问题

重启恢复时，"泊着等用户输入"的会话被当作"被中断的工作"批量自动续跑。3080 实证（2026-08-23)：一次升级日的三次非计划退出中，泊在提问卡片上的会话（如「梦境守护者小说世界观探讨」，泊在一组 ask_user_question 上）每次恢复都被唤醒，重放报告、重复提问、白烧 token；用户视角是"非活跃会话集体被叫醒"。

根因：宿主 `AgentStatus` 是二元的（`'idle' | 'running'`），回合阻塞在等待用户输入（ask_user_question 待答、审批待决）时状态仍是 `running`;guard 的 SIGTERM 快照（`snapshotInterrupted`）以此判定"有活回合"，resume pass 于是对它们恢复 + 注入续跑。

这类回合的正确待遇是**什么都不做**：提问/审批卡片持久于会话日志，重启后 UI 照常渲染，用户随时能答——没有"被中断的工作"需要续。自动续跑反而有害：回合重放可能重复提问、生成重复卡片，且每个泊着会话每次都烧一个回合。

## 目标

1. SIGTERM 快照与 resume pass 两处都把"等待用户输入"的回合排除出"被中断"集合：真正在执行（模型在流式输出、工具在跑）的才救。
2. 泊着会话在重启后完全无感：无唤醒、无注入、无重复卡片。
3. 不改变既有正确语义：发起者收报告、真中断者续跑、崩溃信使（无 initiator 记录由第一个被碰的会话代领）均不动。

非目标：不改宿主的 AgentStatus 模型；不动崩溃报告的认领规则；不处理"浏览器里填到一半的草稿"（那是 UI 侧问题，见「顺带上游缝」)。

## 方案

1. **M1 可行性核实**：确认同进程可查询"该会话的当前回合是否阻塞在用户输入上"——候选信号：`UserQuestionService`（待回答提问）、`user-approval`（待决审批）。两者任一 pending 即视为泊着。查不到则登记上游缝（一个 `agent/status` 细分或 pending 查询口），先以"能查多少查多少"降级。
2. **M2 实现**：`snapshotInterrupted` 的快照过滤 + resume pass 的双重检查（快照时刻在执行、恢复时刻仍非泊着——防止快照后泊下的竞态）。附 Agent Note 与单测。
3. **验收**：四会话验收测试（A 发起/B 中断/C 空闲/D 新建）扩展 E 会话——泊在一组未答提问上，重启后应与 C/D 一样安静；另补"提问在重启后仍可正常回答"的回归。

顺带上游缝（独立上报，不阻塞本提案）：提问卡片的**草稿**（用户填到一半未提交的内容）只活在浏览器临时状态，重启重连即丢。建议上游把草稿持久化（sessionStorage 或落日志）——即使不重启，刷新也丢。与本提案的关系：本提案消灭"重复提问/白跑回合"，草稿持久化消灭"白写"，正交互补。
