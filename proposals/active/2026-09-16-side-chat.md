# 侧边对话：通用上下文聊天（side-chat）

- **分类**：plugin
- **状态**：planned
- **最后更新**：2026-09-16
- **查重结果**：已搜 `proposals/active/` + `proposals/closed/` + `.agents/notes/`（含 archived），关键词「侧边 / sidechat / side chat / 随身 / 上下文聊天」——**无重复提案**。唯一命中 [file-preview-side-drawer](.agents/notes/) 是文件预览的侧抽屉，无关。相关而非重复：[canvas-space](2026-09-16-canvas-space.md)（本提案是它的 M2 聊天供给方，单向被探测）、[room-session-promotion](2026-08-27-room-session-promotion.md)（自有聊天 UI + agent 会话的实现先例，不是上下文聊天）。
- **官方依赖**：纯插件。右栏 tab 座位、`ctx.agents`、session journal、MarkdownText 均为已存在 seam。

## 目标

一个**全 preset 常驻的"随身 Agent"**：右栏里的轻量聊天，围绕"当前上下文"对话——普通会话里引用几条消息问两句；装了画布时，画布的"就此提问"也由它承接。它一次建设、处处受益，且**不知道任何具体插件的存在**。

设计红线（用户定的）：**不相互嵌套**。side-chat 不认识"卡片""消息"等具体类型，引用一律是不透明文本块；不装画布时它在普通会话里完整可用。

## 现状（契约实测要点）

- 自有聊天 UI + agent 会话的在库先例是 room：host 侧 `ctx.agents.create/resume` + `agent.followup`，客户端自绘 transcript/composer；headless 会话先例在 eval（`packages/eval/src/job.ts:494`）。
- 右栏页型 tab 座位（`ctx.sidebarRightTabs.register` + `sidebar.right.pane.tab` keyed）是官方 seam，session 作用域；canvas v1/M1.5 均在用。
- 消息级动作有 message-tools 先例（`conversation.chat.node` 体系）；「引用到侧边对话」动作的准确座位实施时核实。
- `MarkdownText`（GFM/KaTeX）渲染助手消息，零新依赖。
- preset 可见性自隐有 room 的 `preset-visibility.ts` 先例（读 `pluginInventory`，fail OPEN）——本插件**不做自隐**（全 preset 可见），该先例是给画布用的。

## 方案

### 0. 定位与命名

显示名 **侧边对话**；包名 `@khorsheed/dsh-sidechat`，目录 `packages/sidechat`（npm 占用发布前查）。Remote 命名空间 `sidechat`，cordis 行 id `sidechat`。

### 1. 会话模型：contextKey → 一个 agent 会话

- 每个 **contextKey** 绑定一个持久 agent 会话（`ctx.agents.create`，`meta.cwd` 继承来源会话的 cwd，`agentPreset` 可配、缺省沿用 profile 默认）；重启后 `ctx.agents.resume` 冷恢复。
- 普通会话里 contextKey = 来源会话 id；其他插件（画布）供给自己的 contextKey（如 `canvas:<id>`）。side-chat 对 contextKey 无解析、无类型。
- 历史从 session journal 投影（user/assistant 文本，工具调用折叠为一行状态），经 Remote 给客户端。

### 2. 通用引用协议（ref）

```jsonc
{ "label": "沉默并不总是…", "text": "…", "icon": "optional" }
```

- 引用 = 不透明文本块：渲染为 composer 上方的 chip（M2 起可内联展开全文），发送时拼进用户消息（标注来源 label）。
- **流向规则**：内容永远流向**来源处绑定的 context**——会话 A 的引用进 A 的 context（key = 会话 id），画布 X 的提问进 X 的 context（key = `canvas:<id>`）；添加动作无需也不应让用户选目标。多 context 仅是"不同来源各有自己的侧边会话"，tab 顶部切换器只用于翻看。
- 普通会话：消息动作「引用到侧边对话」把消息内容落成 ref（座位实施时核实，message-tools 先例）。
- 其他插件（画布）经宿主服务 API 传 refs——side-chat 全程不知道"卡片"是什么。

### 3. 宿主服务 API（插件间协作 seam，同进程对象）

```ts
interface SideChatService {
  openWith(input: {
    contextKey: string
    label: string                      // tab/标题显示用
    systemPrompt?: string              // 追加段，创建时注入
    tools?: ToolDefinition[]           // 调用方供给的模型工具（宿主侧对象）
    refs?: Ref[]
  }): Promise<void>
}
```

- **单向边**：消费方（如画布）探测 `ctx.get('sideChat')`，在自己的 manifest `dsh.references` 登记服务名（数据级提及的既定位置）；side-chat 永不提及消费方。消费方缺席=它自己降级；side-chat 独立装卸。
- **回合级新鲜度**：`openWith` 重复调用同一 contextKey 时更新 systemPrompt 段（`agent.inject` 或重建注入），不是"创建时快照"——板摘要这类上下文必须每轮新鲜。
- 工具注入走 `agents.create` 的 setup 挂到该 context 的 agent 上；origin tag 由**调用方**负责（side-chat 不代标）。

### 4. 客户端

- 右栏 tab：transcript（助手消息 `MarkdownText`）+ ref chips + composer + 上下文标题（label）。样式只用 `--dsw-*` token + 官方 icon。
- 普通会话里点开即是围绕该会话的随身 Agent；画布等消费方调 `openWith` 时客户端经事件/共享 store 切到对应 context 并激活 tab（程序化激活右栏 tab 的官方 API 由 canvas M1.5 先行探明，沿用其结论；没有则只切内容不强制展开，记 upstream 候选）。
- 编辑器约束照 canvas 先例：composer 非受控、IME composition 期间不打扰。

### 5. 与画布的关系（信息侧，不在本包实现）

canvas-space M2 起不再自建聊天：透镜「就此提问」/评论「追问」→ `openWith({ contextKey: 'canvas:<id>', systemPrompt: 主题+板摘要+工具契约, tools: [canvas_*] })`。画布探测不到 side-chat 时隐藏聊天入口、卡板完整可用。普通会话里想引用画布内容走画布的 `canvas_search` 工具（canvas 全局注册、自带 origin tag），side-chat 不感知。

## 里程碑

- **M1（会话场景核心）**：包脚手架（identity triangle/自挂载/README 双语/compat）、`SideChatService` + contextKey 会话管理 + `openWith`（含 systemPrompt 回合级更新与 tools 注入）、Remote（transcript/send/refs）、右栏 tab UI、消息动作「引用到侧边对话」、测试。**验收：不装任何其他插件，普通会话里完整的侧边聊天。**
- **M2**：客户端体验增量——ref chip **内联展开全文**（引用内容随对话走，缓解详情/聊天两 tab 往返）；**浮动 dock 模式**：panel 组件同时注册 `shell.overlay`（worktrees badge 先例），在自定义 main 面板（如画布空间）上聊天以浮层承接、详情 tab 不让位，位置记忆；**选区引用探针**：会话区任意文本选区 → ref 的官方 seam 核查，无则登记 upstream 候选（不做 DOM anchor hack）；多 context 切换列表、未读标。
- **M3（自我浮出水面）**：`openWith` 被调用时客户端自动选择呈现位——当前在会话面板（`activePanelId === null`）→ 右栏 tab；在自定义 main 面板 → 浮层 dock（3080 实证：宿主 `RightbarRoot` 只在会话面板渲染右栏，自定义面板里 tab 按构造不可见，dock 是 `shell.overlay` root 作用域不受此限）。消费方因此只需 `openWith`（+ 可选 best-effort `openTab`），无需关心呈现。

## 实现记录

- **M1（2026-09-16，worktree `.worktrees/side-chat`，已合并并上 3080）**：包脚手架（identity triangle/自挂载/README 双语/compat minHost 0.1.5-rc.1）、`ctx.sideChat`（`openWith` 更新而非重建语义、contextKey→会话生命周期、journal 投影、画布 store.ts 重扎根围栏先例）、Remote（getState/listContexts/send/quoteMessage）、右栏 tab（MarkdownText/ref chips/composer 守 canvas 不变量）、消息动作「引用到侧边对话」落官方 `conversation.chat.assistant-actions` 座位。45 测试绿。细节见 Agent Note `.agents/notes/implemented/feature/2026-09-16-side-chat-m1.md`（feat/side-chat 分支）。
  - 关键机制：`agents.create/resume` 的 `AgentSetup` 在发布前跑，`agentCtx.tools.register`/`systemPrompt.section` 入 agent 层；回合级新鲜度用 `PromptSection.text` provider（每次装配重读），不用 `agent.inject`。

- **M2（2026-09-16，已合并并上 3080，0.2.0）**：ref chip 内联展开（durable 消息文本回折 round-trip，零影子状态）、浮动 dock（`shell.overlay` + 共享 `SideChatPanel`，位置记忆经 defineStore persist，tab↔dock 交接）、context 切换器 + 未读点、选区引用探针（结论：无官方 seam，`window.getSelection` 是被禁的 DOM anchor——登记 upstream 候选 `conversation.chat.selection-actions`）。57 测试绿。细节见 Agent Note `2026-09-16-side-chat-m2.md`。

- **M3（2026-09-16，0.2.1，已合并并上 3080）**：openWith 自我浮出水面——host 侧每 context 一个 openWith 修订号（仅 openWith 递增），客户端 `surfaceHints` 轻量轮询差分触发；呈现决策：会话面板（`activePanelId === null`）→ 右栏 tab，自定义 main 面板 → 浮层 dock（root 作用域不受 `RightbarRoot` 限制），无 overlay 座位/窄屏回 tab。63 测试绿。Agent Note `2026-09-16-side-chat-m3.md`。消费方契约不变，canvas 的 best-effort `openTab` 冗余无害。
- **消息消失修复（2026-09-17，0.2.2，已合并并上 3080）**：3080 实证「发送后消息消失，不能真实对话」——根因：`spawnAgent` 的 `agents.create/resume` 未传 `agentOptions`（provider/model），宿主 agent-loop 的 `prepareRequest` 在空 seed route 下抛错，而 `step()` 内它**先于** `user/message` 落账执行——turn 在消息落 journal 前死亡，投影永远看不到该消息（durable inbox 仍持有该消息，下一个成功 turn 会自动 claim，无需数据修复）。修复：create/resume 均传 agentOptions——优先继承调用会话 `requestHeader()?.config` 路由，回落探测 `agentDefaultModel.currentSelection()`（probe 非 inject）；投影折 `turn/end` 产出 `lastError`（后续干净收口自动清除）+ 面板可关闭错误条，turn 静默死亡从此可见；发送乐观 user 行消除 1.2s 轮询空窗。74 测试绿（+11）。Agent Note `2026-09-17-side-chat-agent-options.md`。
- **持久化/preset/投影三连修（2026-09-17，0.2.3，已合并并上 3080）**：3080 地面核实（session journal 直读）：①**contexts.json 从未落盘**——store 构造期一次性 `ctx.get('fs')` 输掉挂载顺序（inject 未声明 fs），memory-only 静默降级，每次重启全部映射丢失、journal 成孤儿；改为 `ctx.inject(['fs'])` 延迟捕获（canvas index 注释的 datasets-tool 先例），fs 晚到时重置 loaded 并回冲窗口期记录，无 fs 组合保持 memory-only 而非插件 pending。②**preset 继承**——create 解析 `calling.session.header.agentPreset` 优先（此前用部署默认，3080 恰好是 dsh-writing 才"碰巧一致"），resume 保持 record 所记。③**AGENTS.md 块渲染**——journal 里 `agent-instructions`/system-prompt snapshot/skill-catalog 三类注入被投影当用户气泡渲染；对齐官方 UI 的 context-provenance 分类（`KnownContextForm` 六类）跳过，自家 plugin 消息保留。80 测试绿（+6）。Agent Note `2026-09-17-side-chat-fs-deferred-preset-projection.md`。3080 上两个孤儿 side 会话 journal 不做数据修复（无害）。

1. `@khorsheed/dsh-sidechat` 可 `dsh plugin add` / `remove` 一条命令装卸；identity triangle 三处同名；`dsh.bundle.patch` 自挂载；`files` 含 `lib/client.js` 与 `cordis.patch.yml`。
2. `pnpm run build` + `pnpm run test` 绿；`pnpm check:plugins`、`pnpm check:hygiene` 过。
3. 3080 实测：普通会话里打开右栏侧边对话 → 提问（继承会话 cwd，文件工具可用）→ 消息动作引用两条消息 → 追问 → **重启后历史完整**；卸载画布（如已装）不受影响；深色主题正常。
4. 模拟消费方调 `openWith`（带 systemPrompt + 一个测试工具）：agent 按注入提示行动、能调该工具；重复调用更新上下文而非重建会话。
5. 卸载后 state 与来源会话不受影响。

## 风险 / 放弃的东西

① **composer 不做官方输入机对齐**。撤回回填/斜杠/图片等官方 composer 生态在侧边对话里不可用（与 room-composer-parity 同源的已知取舍）；轻量优先，后续看反馈再评估。

② **tools 注入是宿主侧对象传递**，不过 Remote——只有同进程插件能消费，这是刻意的（跨进程才有类型/安全问题），文档写明。

③ **contextKey 冲突**：格式不约束（`canvas:<id>` 是消费方自选），side-chat 只保证按 key 隔离；文档建议消费方带前缀。

④ **右栏在自定义 main 面板激活时的表现**依赖 canvas M1.5 的探针结论；若右栏在该场景不可用，画布的聊天承接退化为"回到会话面板后可见"，记 upstream 候选，不阻塞本插件（普通会话场景不受影响）。
