# dsh-plugins

English | [中文](README.md)

The community plugin monorepo for the **dsh** (DeepSeek Harness) ecosystem: **thirty-plus purely additive plugin packages, organized into 7 suites**. Every package integrates through official extension points only — slots, commands, Remote services, session projections. No official package is modified, no official UI slot is replaced, no core service is hacked; when an optional capability is absent the plugin degrades silently instead of failing the boot. The whole set is designed for coexistence: install, uninstall, or toggle any combination without interference, and the production instance runs the full stack long-term.

## Suites: seven ready-to-run experiences

The recommended install unit is a **suite** (one npm package), not a single plugin: a suite pulls in its members as npm dependencies and mounts their canonical rows through its own patch; every suite except the basic one also ships an inline agent preset granted per session. Install the suite, and you have installed the mode.

If you would rather pick, any single package or suite installs on its own and coexists with a collection without mounting anything twice.

### Local multi-agent

Delegate subtasks to coding-agent CLIs installed on your machine, each with its own context and accounting, resumable across turns; every harness runs in its own scoped home (`$DSH_HOME/local-agent/<name>`, 0700) and **never touches the private configuration and credentials in your user directory**.

Versus the official offering: you can have the lead agent invite any harness you choose for the task at hand — e.g. invite Kimi for frontend work, Codex / Claude Code for orchestration, DSH for concrete coding.

## Agent preset design

A mode suite installs more than plugins: it also delivers an inline **agent preset granted per session**. Three design rules:

1. **Tools are granted per session.** Model-facing tool rows never mount at the profile root: every tool surface splits into a core (global service/UI) plus an in-package `./tool` / `./agent` companion entry; the preset's composition names the companion rows — a session gets these tools exactly when it runs on that preset, and every other session's tool surface stays clean. With the companion core absent the row stays pending; nothing crashes the host.
2. **UI hides with the grant.** Session-bound surfaces (conversation tabs, header badges) follow the preset grant — a session that was never granted the tools never sees the entry; cross-session deployment surfaces get no runtime switch and are governed by what you install. The full convention lives in [docs/plugin-visibility.md](docs/plugin-visibility.md).
3. **Purely additive declarations.** A preset re-bases verbatim on the official standard composition and only appends community tool rows at the end — no official row is modified.

Six mode presets ship with their suites (dev / writing / learning / video / gamedev / eval — see the table above); the essentials suite carries no preset — everyday use needs no mode switch.

### Install

Prerequisite: a dsh host (per-package version requirements live in the "Host" columns of the capability map and in each package README's Compatibility section). **The recommended path is a suite** (see [Suites](#suites-seven-ready-to-run-experiences)); single-package installs are the advanced path for tailoring or debugging.

```sh
# A suite (recommended): one package installs a whole mode
dsh plugin --profile web add @khorsheed/dsh-basic        # or dsh-dev / dsh-writing / dsh-learning / dsh-video / dsh-gamedev / dsh-bundle-eval

# A single package (self-mounting packages mount their own loader row — no hand-edited cordis.yml)
dsh plugin --profile web add @khorsheed/dsh-whalesong

# The local-agent family piecemeal: the core and the harness must both be installed explicitly
dsh plugin --profile web add @khorsheed/dsh-local-agent
dsh plugin --profile web add @khorsheed/dsh-local-agent-kimi   # or -codex / -claude-code / -dsh
```

On hosts ≥ 0.1.7-rc.2 you can skip the command line: **Settings → Plugins → Add plugin**, paste the npm package name, and follow the prompts. Note that this entry accepts **single plugin packages only** — this repo is a monorepo, and pasting its GitHub URL is refused and rolled back (the official installer only installs the plugin package at a repository root, not subdirectories). On release day, include a version floor (e.g. `@khorsheed/dsh-basic@^0.1.0`): pnpm's default 24-hour minimum-release-age protection hides same-day releases behind bare names.

Restart the web instance to take effect. Composition component packages (`local-agent-dsh-headless`, `ui-content-preview`, etc.) are not mounted by `dsh plugin add` — they land through a suite's patch or a provider patch; the full relationship map lives in [docs/packages.md](docs/packages.md).

### Uninstall

```sh
dsh plugin --profile web remove @khorsheed/dsh-<name>
```

General rules:

- **Uninstalling restores exactly.** No plugin modifies or replaces official files; removal returns the composition to precisely its previous state.
- **User data is deliberately kept.** The local-agent family keeps each harness's scoped home (`$DSH_HOME/local-agent/<name>`), so a reinstall needs no re-login; ankh-guard keeps its state dir (credentials, restart records, interrupted-session snapshots). No uninstall touches session logs — the audit trail of edits and withdrawals belongs in the log on purpose.
- **Family rows stay graceful.** Remove the local-agent core while a harness remains and the harness row stays **pending, never crashing** — reinstalling the core restores it.
- **`enabled: false`** disables a row without uninstalling — a deployment-layer operation, not a code change.

### Develop

A standalone pnpm monorepo; every package publishes as `@khorsheed/dsh-*`.

```
packages/   one directory per publishable plugin or suite
profiles/   sync sources of the suite front-door repos (basic / dev / eval / writing / learning / video / gamedev)
build/      shared build/test presets (tsdown client bundle, vitest source-plane config)
scripts/    repo tooling (pack-dist, gen-typert, mirror sync, gate checkers)
```

```sh
pnpm install
pnpm run build      # pnpm -r --if-present run build
pnpm run test       # pnpm -r --if-present run test
pnpm run typecheck  # pnpm -r --if-present run typecheck
```

Tests must run through the root `pnpm test` or `pnpm --filter <pkg> test` — bare `vitest run packages/xxx` bypasses each package's vitest config (the source-plane alias preset) and fails with misleading resolution errors.

**The dev-time dependency on the harness checkout.** Two mechanisms resolve against a local deepseek-harness clone (env `DSH_HARNESS`, default `~/code/deepseek-harness`); the published npm artifacts alone cannot satisfy them:

- `scripts/gen-typert.mts` regenerates `lib/typert.*` artifacts against the harness checkout (packages with `./typert`/`./remote` exports); full builds are freshness-cached and only regenerate when inputs or outputs change (`GEN_TYPERT_FORCE=1` forces).
- `build/vitest.ts` (the shared vitest preset) maps platform imports through the harness's `tsconfig.base.json` paths — published packages ship no `src/`, and their `/client` entry is a loader-wrapped browser bundle, so bare imports explode.

CI note: clone deepseek-harness next to this repo and set `DSH_HARNESS` before `pnpm test`; a stale harness checkout means the tested API surface may lag the production host. Releases go through `scripts/pack-dist.ts` (`--family` rewrites peer-dependency scopes); verify the tarball before `npm publish`. The full repository discipline lives in [AGENTS.md](AGENTS.md).
