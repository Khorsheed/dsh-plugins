# 插件 README 写法

README 是用户（和 agent）认识一个插件的第一页：读完几十秒，就该知道它替你做什么、怎么装上、装完怎么开始。其余的细节都在代码和 CHANGELOG 里，README 不重复。

样板：[packages/library/README.md](../packages/library/README.md)（中文）与 [README.en.md](../packages/library/README.en.md)（英文）。

## 核心：讲「你做什么 → 它替你做什么 → 最后得到什么」

- 少解释功能，多讲使用者的动作和得到的结果。读者不该一边读一边在脑子里翻译。
- 不出现插件内部的名词和机制：preset、tab、行、服务、Remote、注入、组合入口、状态机、阈值、数据格式……这些都不写。
- 用界面上的叫法：模式、侧栏、会话；按钮名照界面原文写（中文版用中文界面文字，英文版用英文界面文字，两边都去 `src/client/locales.ts` 里核对）。
- 口语化、短句。可以有态度（「最烦的是没人管」「错题不翻篇」），但不夸张、不承诺做不到的事。

## 结构（按顺序）

1. **标题**：`# @khorsheed/dsh-<名字>`，下一行语言切换。
2. **一句话**：它替你做什么。例：「让 agent 当你的读书教练：帮你排进度、记笔记、出题，还盯着你把错题订正对。」
3. **一段场景**（三四句）：以前做这件事有多麻烦 → 装上之后你做什么、它替你做什么 → 你得到什么。
4. **主图**一张。
5. **能做什么**：5–7 条，每条「**加粗的短句**：一句话」。加粗短句本身就是一个结果或动作（「拍一页就能记笔记」「错题不翻篇」），后面一句说清你做什么、它替你做什么。不写数字阈值、算法和内部流程。
6. 最多再放 1–2 张图，跟在最相关的那条后面。
7. **安装**：只讲一条主路径——在 DSH 的「插件 → 添加插件」里输入包名、点安装。
   - 插件随某个套件提供时，写**套件**的包名，并说一句「本插件会跟着某某套件一起装好」，因为单装通常用不起来。
   - 再用一句话说装完怎么开始（开新会话、选哪个模式、对 agent 说什么）。
   - 如果它只在某个模式里出现，提醒一句「在其它模式里看不到是正常的」。
   - 命令行安装、单独安装放到「给开发者」。
8. **已知限制**：2–3 条，用户会实际碰到的。
9. **Compatibility**：一句话，写最低版本和已验证版本（与 package.json 的 `dsh.compat` 一致；细节留在 `dsh.compat.notes`）。
10. **给开发者**：三条以内——入口文件在哪、单独安装要注意什么、仓库与 CHANGELOG 链接。深入的说明放 `docs/`，在这里给一个链接即可。

## 篇幅

- 普通插件 40–60 行。
- 套件（family / mode bundle）50–70 行：开头讲「这个模式适合谁、在里面能做什么」，多一节「可以这样跟 agent 说」（3–5 句示例）；成员只列「名字 + 它替你做什么」一句话，不列行 id。
- 不放折叠的「实现原理」大段。真正需要保留的开发者文档放到包的 `docs/` 下。

## 双语

中英文内容一致，英文是用自然的英文改写，不逐字翻译。改完一边要同步另一边，并用 `pnpm run verify-translation-pairing --write <README.en.md>` 重新记录。
