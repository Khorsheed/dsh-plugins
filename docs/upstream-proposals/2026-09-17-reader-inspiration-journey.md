## 0 先说诊断：你看到的三件事，一件是 bug，一件是我的设计错了

我把 3080 上真实的状态文件读出来了（`$DSH_HOME/state/dsh-reader/state.json`），这是硬证据：

| 事实 | 值 |
| --- | --- |
| 上游 feed 实际大小 | **646,905 字符**（不是我之前估的 45 KB——里面有大段正文） |
| 宿主缝返回给你的 | **100,000 字符整**，`truncated: true` |
| 那 100,000 字符的结尾 | `…except in specific parts of the transcript after the model's orig` ← 句子中间截断 |
| 里面完整的条目 | `<item>` 开 2 个、`</item>` 只闭了 **1** 个 |
| 于是解析结果 | 整个 XML 没闭合 → **解析失败 → 0 条** |

**所以「订阅成功了但没有内容卡片」的根因是：宿主缝把正文按字符数截断，而截断一行 XML 必然让整份 XML 不合法。** 解析器（浏览器 DOMParser）正确地拒绝了它，墙上一片空白。这不是"刷新不拉内容"——拉到了，100 KB，只是**拉到的东西没法当 XML 用**。

顺带确认：那个 100,000 是宿主侧的默认值（`web-fetch-http` 的 `maxBodyChars`），插件改不了；3080 的部署配置里也没有覆盖它。

## 1 用户到底来干什么（按优先级）

| # | 意图 | 频率 |
| --- | --- | --- |
| J1 | **「有什么新东西？」** —— 打开，扫一眼，挑一篇读 | 每天多次，最高频 |
| J2 | **「把这条链接收起来」** —— 粘贴一个 URL，希望立刻看到它进墙 | 随时 |
| J3 | **「把那个源订上」** —— 粘一个 feed 地址，之后不用再管 | 偶尔 |
| J4 | **「读一篇，并把其中一段引用到对话里」** | 经常 |
| J5 | **「调整刷新、暂停/删掉某个源」** | 很少 |
| J6 | **「把这里的东西发到侧边对话」** | 偶尔 |

关键观察：**J1 是最常见的动作，而它现在是最失败的路径**。J5 最少，而我上一版把它的入口做成了表头的一个常驻按钮。

## 2 当前旅程（逐步，标出哪里断了）

### J1 打开看新内容 —— ✗ 断了

```
打开 tab
  → 加载源列表（listSources）
  → 对每个有 payload 的源取 payload（getBodies）
  → 浏览器解析
      · 小 feed（< 100,000 字符）→ 出卡片 ✓
      · 大 feed（你的那条 646 KB）→ XML 被截断 → 解析失败 → 0 条 ✗
  → 墙显示「没有匹配「」的条目。」
```

**三个独立缺陷叠在这一条路径上：**

1. **截断的 feed 一律 0 条**（真实 bug，见 §0）。宿主缝对大 payload 是"截断"，而我们的解析是"全有或全无"。
2. **失败了不说明原因**。解析失败的文案（`result.error`）我存进了 store，**但墙上从来没渲染它**——所以用户看到的是「没有匹配「」的条目」，一句关于搜索的话，而搜索框是空的。
3. **摘要级降级缺失**。宿主缝在截断时其实还知道条目标题之外的元数据吗？不——它只给正文。所以一旦正文截断，标题、链接、日期全部拿不到。**这是最伤的一点**：646 KB 的 feed 里，前 100 KB 至少包含完整的第 1 条，我们却一条都拿不到。

### J2 粘贴一条链接 —— ✓ 基本通

```
点 + → 弹窗 → 粘贴 → 抓取
  → 宿主按内容判定：feed → 订阅；网页 → 存单条
  → 立刻回报判定 + 理由（失败时给宿主缝原话）
  → 墙重新加载，新卡片出现（默认「全部」过滤）
```
断点：粘贴一篇**超大**网页（> 100,000 字符）时，正文必然截断；现在会显示「受限篇幅」+「阅读原文」，这条是**设计如此**，可接受。

### J3 订阅一个源 —— ✓ 通，但 T 恤尺码问题

订上了、能刷新，但**大 feed 落进 J1 的第 1 条缺陷**里：订阅成功、墙上没东西，用户以为没订上。

### J4 读 + 引用 —— ✓ 通

点卡片 → 详情页渲染正文 → 划选 → quote 浮层 → 引用进草稿。截图里的内容卡片没出来，所以这一条你还没走到。

### J5 订阅管理 —— ✓ 通

表头齿轮 → 每源一行（条目数 / 上次抓取 / 更新中 / 失败原因）+ 单源刷新 / 暂停 / 删除 + 每日刷新时间。

### J6 侧边对话 —— ✓ 通（组合里有 sideChat 才显示）

## 3 「为啥首页变成展示订阅源？」

**因为我把两件事混在了一个面上，这是我的设计错误。** 我上一版把来源卡片网格当成"墙的门面"放在最上面，理由是「一眼看到有哪些源」。但那回答的是 **J5（管理）** 的问题，而你打开这个 tab 问的是 **J1（有什么新内容）**。J5 是低频的，它不该占首页的黄金位置——它已经有自己的页面了。

**正确的关系**应该是：

- **首页 = 内容**（J1）——卡片流就是主角，第一屏就应该看到内容。
- **订阅源 = 一种视图/入口**（J5）——齿轮进去看完整管理；首页最多留一行极轻的"来源条"，或者作为筛选器存在，而不是卡在内容前面。

---

## 4 「这个被覆盖的部分是什么？」

**是一个布局 bug。** 工具条是一行 flex：搜索框（`flex: 1`）+ 「全部/今日」分段控件 + 只看未读 + 排序。搜索框的 `flex: 1` 没有配 `min-width: 0`，而它内部的 `<input>` 有浏览器默认的固有宽度，于是搜索框拒绝收缩、把分段控件挤到它下面并压住了「全部」两个字。你截图里露出来的那个「）」就是被盖住的半截按钮。

这类 bug 之所以会出现，是因为我上一版**没有配溢出测试**：测试只断言"元素存在"，从不断言"没有元素重叠"。

## 5 方案（已确认，已实施）

> 用户确认：首页＝① 纯内容卡片流 + 一行来源筛选条；超大 feed＝"所有能完整闭合的正常展示，不完整的展示能展示的，最后告知内容不完整并引导跳原文"。

### 已实施

| # | 内容 |
| --- | --- |
| A1 | **抢救式解析**：完整条目全部保留（用文档根的命名空间声明重包片段——否则带 `content:encoded` 的完整条目自己也解析不了）；截断的那条尽力修复，正文渲染已到达的部分；标 `partial` |
| A2 | **墙上说明原因**：读不完整的源在筛选片上带 `!`，墙上给一行「未完整 · 源名 — 内容超过宿主 100,000 字符上限…」+ 阅读原文 |
| A3 | **布局重叠修复**：`.search` 补 `min-width: 0` / `flex: 1 1 auto`，`.segmented` 补 `flex: 0 0 auto`，并加静态断言锁住这三条约束 |
| A4 | **空态说人话**：查询为空时不再说"没有匹配「」"，改为"还没有条目，新增一个源或按刷新" |
| B1 | **首页改成内容优先**：条目卡片第一屏；订阅源降为一行可滚动筛选片（`全部 · 源A · 源B`），点片=本地筛选，值写在搜索框里可清 |
| B2 | 见 A1（用户口径） |

### 批次 A：立刻修（都是缺陷，不需要产品决策）

| # | 修什么 | 怎么做 |
| --- | --- | --- |
| A1 | 被截断的 feed 一条都拿不到 | **抢救式解析**：`<item>…</item>` 完整闭合的条目全部保留，截断在半路的那个丢掉，并给整个 feed 标上"未完整"。你的那条 feed 因此会出 **1 条**（首条完整），而不是 0 条 |
| A2 | 解析失败/截断在墙上一声不响 | 源卡片显示「未完整 · 已解析 N 条」，并在墙上给一行原因（复用 `state.stale` 那套文案位） |
| A3 | 工具条重叠 | `min-width: 0` + `flex-shrink` 修正，并**加一条溢出断言**（在 3 种宽度下断言工具条子元素两两不重叠），挡住这一整类 bug |
| A4 | 0 条的空态说人话 | 「没有匹配「」的条目」在 `query` 为空时不该出现：改为「这个源还没有内容 / 内容未完整」等具体原因 |

### 批次 B：要你定的信息架构

**B1 首页第一屏是什么？**（我推荐 ①）

1. **纯内容卡片流**（推荐）：打开就是内容；来源降级为一行极轻的"筛选条"（`全部 · 源A · 源B …`，可横向滚动），点它筛内容。管理全部走齿轮。
2. **内容优先 + 折叠的来源网格**：默认折叠成一行统计（`1 个源 · 21 条`），点开展开成卡片网格。
3. **保持现状**（来源网格在上，内容在下）。

**B2 大 feed 的策略**（这决定 A1 的深度）：

- **只抢救完整条目**（成本低，你的那条出 1 条）——推荐先做这个。
- **再加"流式增量抓取"**：宿主缝不支持 Range/分页，所以做不到真正分页；能做的是把 feed URL 当成"每次都重新抓、只保留能拿到的部分"，也就是 A1 的重复。
- **对超大 feed 明确报"太大，建议换一个小一点的 feed 源"**，把预期讲清楚而不是假装能用。

**B3 「来源」还要不要出现在首页？**

- 我倾向：**只在有内容时出现一行筛选条**；一个源都没内容时不出现（避免出现"有源、没内容、还不知道为什么"的第三种空态）。
